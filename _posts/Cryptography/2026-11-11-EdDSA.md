**EdDSA (Edwards-curve Digital Signature Algorithm)**는 Twisted Edwards Curve(뒤틀린 에드워즈 곡선) 위에서 Schnorr Signature(슈노어 서명)의 변형을 사용하는 Digital Signature(디지털 서명) 방식이다. [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032)

EdDSA는 하나의 알고리즘 틀이고, 곡선과 Hash Function(해시 함수)을 정해야 실제로 쓸 수 있다. 이렇게 값을 정한 것을 Instance(인스턴스)라고 부른다. 대표적인 Instance가 Ed25519와 Ed448이다. 이 글은 RFC (Request for Comments) 8032와 원 논문을 기준으로 하며, 동작 원리는 Ed25519를 중심으로 설명한다.

## 배경과 필요성

### Digital Signature와 ECDSA의 약점

Digital Signature는 Private Key(개인키)를 가진 사람만 만들 수 있고, Public Key(공개키)를 가진 누구나 검증할 수 있는 값이다. Message(메시지)가 바뀌지 않았다는 것과 서명자가 누구인지를 함께 확인한다.

Elliptic Curve(타원곡선) 기반 서명으로 먼저 널리 쓰인 것은 ECDSA (Elliptic Curve Digital Signature Algorithm)이다. ECDSA는 서명할 때마다 Nonce(한 번만 쓰는 비밀 값)를 새로 뽑아야 한다. 서명식은 다음과 같다. `G`는 Base Point(기준점), `n`은 Base Point의 Order(위수), `z`는 Message의 Hash 값, `d`는 Private Key이다. Order는 점을 몇 번 더해야 덧셈의 Identity(항등원)가 되는지를 나타내는 수이다.

```
R = [nonce]G
r = R의 x 좌표 mod n
s = nonce^(-1) * (z + r * d) mod n
```

이 구조에는 두 가지 부담이 있다.

첫째, Nonce 관리가 안전성을 좌우한다. 서로 다른 두 Message에 같은 Nonce를 쓰면 `r`이 같아진다. 그러면 두 서명식은 미지수가 `nonce`와 `d` 두 개인 연립방정식이 되고, 누구나 `d`를 계산할 수 있다. EdDSA 원 논문은 Sony PlayStation 3의 ECDSA Code Signing이 Nonce를 재사용해서 장기 Private Key가 노출된 사례를 직접 언급한다. [High-speed high-security signatures](https://ed25519.cr.yp.to/ed25519-20110926.pdf)

둘째, 서명식에 Nonce의 모듈러 역원 `nonce^(-1)`이 들어간다. 역원 계산은 곱셈과 덧셈보다 비용이 크다.

참고로 ECDSA도 Nonce를 Private Key와 Message에서 유도하는 결정적 방식을 쓸 수 있다. [RFC 6979](https://datatracker.ietf.org/doc/html/rfc6979) 다만 이는 선택 사항이고, EdDSA는 결정적 유도가 알고리즘 정의 자체에 들어 있다.

### EdDSA의 설계 목표

RFC 8032는 EdDSA의 장점을 여섯 가지로 정리한다. [RFC 8032 Section 1](https://datatracker.ietf.org/doc/html/rfc8032)

1. 여러 Platform(플랫폼)에서 성능이 높다.
2. 서명마다 고유한 난수를 요구하지 않는다.
3. Side Channel Attack(부채널 공격)에 더 강하다.
4. Public Key와 Signature(서명)가 작다. Ed25519는 Public Key 32 Byte, Signature 64 Byte이다. Ed448은 각각 57 Byte, 114 Byte이다.
5. 덧셈 공식이 Complete(완전)하다. 곡선 위의 모든 점에 예외 없이 같은 공식을 쓴다.
6. Collision Resilience(충돌 내성)가 있다. Hash Function의 충돌이 발견되어도 서명 체계가 바로 깨지지 않는다. 이 성질은 PureEdDSA에만 해당한다.

### 표준화 과정

- 2011년: Daniel J. Bernstein, Niels Duif, Tanja Lange, Peter Schwabe, Bo-Yin Yang이 논문 "High-speed high-security signatures"에서 EdDSA와 Ed25519를 제안했다. 이 논문은 CHES (Cryptographic Hardware and Embedded Systems) 2011에 실렸다. [ePrint 2011/368](https://eprint.iacr.org/2011/368)
- 2015년: 논문 "EdDSA for more curves"가 정의를 일반화했다. 원래 정의는 `q mod 4 = 1`인 Finite Field(유한체)에만 맞았고, 이 논문이 그 제한을 없애고 Prehash(사전 해시) 방식을 추가했다. [ePrint 2015/677](https://eprint.iacr.org/2015/677)
- 2017년 1월: IRTF (Internet Research Task Force)의 CFRG (Crypto Forum Research Group)가 RFC 8032를 발행했다. 분류는 Informational(정보 제공)이며 Internet Standard(인터넷 표준) 문서가 아니다. [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032)
- 2023년 2월 3일: NIST (National Institute of Standards and Technology)가 FIPS (Federal Information Processing Standards) 186-5를 발행하면서 EdDSA를 승인 알고리즘에 추가했다. 같은 문서에서 DSA (Digital Signature Algorithm)는 기존 서명을 검증하는 용도로만 남았다. [Federal Register 2023-02273](https://www.govinfo.gov/content/pkg/FR-2023-02-03/html/2023-02273.htm)

## 핵심 개념

### Twisted Edwards Curve

Twisted Edwards Curve는 다음 식을 만족하는 점 `(x, y)`의 집합이다. 좌표는 Finite Field `GF(p)`의 원소이다. `GF(p)`는 0부터 `p - 1`까지의 정수에 `mod p` 연산을 적용한 체이다.

```
a * x^2 + y^2 = 1 + d * x^2 * y^2
```

`a = 1`인 경우가 Edwards Curve이고, Twisted Edwards Curve는 `a`를 1로 고정하지 않도록 일반화한 형태이다. 이 일반화는 2008년 Bernstein, Birkner, Joye, Lange, Peters가 제안했다. [Twisted Edwards Curves](https://eprint.iacr.org/2008/013)

두 점 `P1 = (x1, y1)`, `P2 = (x2, y2)`의 덧셈은 다음과 같다.

```
x3 = (x1 * y2 + x2 * y1) / (1 + d * x1 * x2 * y1 * y2)
y3 = (y1 * y2 - a * x1 * x2) / (1 - d * x1 * x2 * y1 * y2)
```

Identity는 `(0, 1)`이고, `(x, y)`의 역원은 `(-x, y)`이다. `a`가 `GF(p)`에서 제곱수이고 `d`가 제곱수가 아니면 이 공식은 Complete하다. [MathWorld: Twisted Edwards Curve](https://mathworld.wolfram.com/TwistedEdwardsCurve.html)

Complete하다는 것은 분모가 0이 되는 입력 쌍이 없다는 뜻이다. 서로 다른 두 점의 덧셈, 같은 점의 Doubling(두 배 연산), Identity와의 덧셈을 모두 한 공식으로 처리한다. 경우에 따라 분기하지 않으므로, 연산 흐름이 비밀 값에 따라 달라지지 않는 구현을 만들기 쉽다. RFC 8032도 Complete한 덧셈 공식이 Side Channel 방어에 도움이 된다고 설명한다. [RFC 8032 Section 8.1](https://datatracker.ietf.org/doc/html/rfc8032)

Ed25519가 쓰는 곡선의 이름은 edwards25519이다. `p = 2^255 - 19`, `a = -1`, `d = -121665/121666`이다.

```
-x^2 + y^2 = 1 - (121665/121666) * x^2 * y^2
```

`p mod 4 = 1`이므로 `-1`은 `GF(p)`에서 제곱수이고, `d`는 제곱수가 아니다. 따라서 Complete 조건을 만족한다. 이 곡선은 Montgomery Curve인 Curve25519 (`v^2 = u^3 + 486662 * u^2 + u`)와 Birationally Equivalent(쌍유리 동치)하다. 즉, 같은 곡선을 다른 좌표 형태로 표현한 것이다. [High-speed high-security signatures](https://ed25519.cr.yp.to/ed25519-20110926.pdf)

### Scalar Multiplication, Order, Cofactor

Scalar Multiplication(스칼라 곱) `[s]P`는 점 `P`를 `s`번 더한 결과이다. `P`와 `[s]P`를 알아도 `s`를 구하기 어렵다는 가정이 타원곡선 서명의 안전성 근거이다.

edwards25519 곡선 위의 점은 모두 `8 * L`개이다. `L`은 다음 값을 가진 소수이다.

```
L = 2^252 + 27742317777372353535851937790883648493
```

Base Point `B`는 Order가 `L`인 점이다. 서명은 `B`가 만드는 크기 `L`의 Subgroup(부분군) 안에서 계산한다. 전체 점의 개수를 Subgroup의 크기로 나눈 값 8을 Cofactor(여인수)라고 한다. RFC 8032의 Parameter `c`는 Cofactor의 밑이 2인 로그이며, Ed25519에서는 `c = 3`이다.

Cofactor가 1이 아니면 Order가 작은 점이 존재한다. 예를 들어 `(0, -1)`은 두 번 더하면 Identity `(0, 1)`이 되는 Order 2인 점이다. 이런 Small Order Point(작은 위수 점)는 뒤에서 설명할 검증식 불일치 문제의 원인이 된다.

### Schnorr Signature와 EdDSA의 관계

Schnorr Signature를 타원곡선 위에서 쓰면 구조는 다음과 같다. `x`는 Private Key, `A = [x]B`는 Public Key, `H`는 Hash Function이다. 코드 블록 안의 세로선 두 개는 Byte 열을 이어 붙이는 연산을 뜻하며, 이후에도 같은 뜻으로 쓴다.

```
서명:  r을 무작위로 선택
       R = [r]B
       e = H(R || M)
       S = (r + e * x) mod L
       서명은 (R, S)

검증:  [S]B = R + [e]A
```

EdDSA는 이 구조를 유지하면서 네 가지를 바꾼다.

1. `r`을 무작위로 뽑지 않고 Private Key와 Message의 Hash로 결정한다.
2. Hash 입력에 Public Key `A`를 추가한다. 원 논문은 여러 Public Key를 동시에 공격하는 상황에 대한 우려를 줄이는 저렴한 방법이라고 설명한다. [High-speed high-security signatures](https://ed25519.cr.yp.to/ed25519-20110926.pdf)
3. 곡선, Hash Function, Encoding(인코딩)을 Instance 단위로 고정한다.
4. 검증식의 양변에 Cofactor를 곱한다.

### Parameter와 Instance

RFC 8032는 EdDSA를 11개의 Parameter로 정의한다. [RFC 8032 Section 3](https://datatracker.ietf.org/doc/html/rfc8032)

| Parameter | 의미 |
|---|---|
| `p` | 곡선이 정의되는 Finite Field `GF(p)`의 크기 |
| `b` | Public Key의 Bit 수. Signature는 `2b` Bit |
| Encoding | `GF(p)` 원소를 `b - 1` Bit로 표현하는 방법 |
| `H` | 출력이 `2b` Bit인 Hash Function |
| `c` | Cofactor의 밑이 2인 로그. 2 또는 3 |
| `n` | Secret Scalar(비밀 스칼라)의 최상위 Bit 위치 |
| `a`, `d` | 곡선 식의 계수 |
| `B` | Base Point |
| `L` | `B`의 Order인 홀수 소수 |
| `PH` | Prehash Function. PureEdDSA에서는 입력을 그대로 돌려준다 |

RFC 8032가 권장하는 두 Instance의 값은 다음과 같다. [RFC 8032 Section 5](https://datatracker.ietf.org/doc/html/rfc8032)

| 항목 | Ed25519 | Ed448 |
|---|---|---|
| 곡선 | edwards25519 | edwards448 |
| `p` | `2^255 - 19` | `2^448 - 2^224 - 1` |
| `a`, `d` | `-1`, `-121665/121666` | `1`, `-39081` |
| `b` | 256 | 456 |
| `c` (Cofactor) | 3 (8) | 2 (4) |
| `n` | 254 | 447 |
| `H` | SHA-512 | SHAKE256 (출력 114 Byte) |
| Private Key, Public Key 크기 | 32 Byte | 57 Byte |
| Signature 크기 | 64 Byte | 114 Byte |
| 보안 강도 | 약 128 Bit | 약 224 Bit |

SHA-512는 SHA (Secure Hash Algorithm) 2 계열의 512 Bit 출력 Hash Function이다. SHAKE256은 SHA-3 계열의 출력 길이를 지정할 수 있는 Hash Function이다. RFC 8032는 128 Bit 보안 강도로 충분하면 Ed25519를, 그렇지 않으면 Ed448을 권장한다. [RFC 8032 Section 8.5](https://datatracker.ietf.org/doc/html/rfc8032)

### Encoding

Ed25519는 정수를 32 Byte Little Endian(낮은 자리 Byte가 앞에 오는 방식)으로 표현한다.

곡선 위의 점 `(x, y)`는 32 Byte로 압축한다. `y`는 `p`보다 작으므로 255 Bit면 충분하다. 남는 최상위 1 Bit에는 `x`의 최하위 Bit를 넣는다. 곡선 식에 `y`를 넣으면 `x^2`이 정해지고, 이를 만족하는 `x`는 `x`와 `-x` 두 개이다. 저장해 둔 1 Bit로 둘 중 하나를 고른다.

```
x^2 = (y^2 - 1) / (d * y^2 + 1)
```

Public Key 32 Byte와 Signature의 앞 32 Byte(`R`)가 이 형식을 쓴다.

## 동작 원리: Ed25519

아래 절차는 RFC 8032 Section 5.1의 Ed25519를 따른다. 기호는 RFC 8032 Section 5.1과 같게 썼다. [RFC 8032 Section 5.1](https://datatracker.ietf.org/doc/html/rfc8032)

### 전체 흐름

```
[Key Generation]
Private Key (32 Byte 난수)
        |
     SHA-512
        |
  +-----+--------------------+
  | 앞 32 Byte               | 뒤 32 Byte
  | Pruning                  |
  v                          v
Secret Scalar s            prefix
  |
  v
Public Key A = [s]B

[Sign]
r = SHA-512(prefix || M) mod L
R = [r]B
k = SHA-512(R || A || M) mod L
S = (r + k * s) mod L
Signature = R || S   (32 Byte + 32 Byte)

[Verify]
k = SHA-512(R || A || M) mod L
[8][S]B = [8]R + [8][k]A 이면 유효
```

### Key Generation

1. 32 Byte 난수를 만든다. 이 값이 Private Key이다. 구현에 따라 Seed(시드)라고도 부른다.
2. Private Key를 SHA-512로 Hash해서 64 Byte `h`를 얻는다.
3. `h`의 앞 32 Byte에 Pruning(Bit 고정)을 적용한다. 구현 문서에서는 Clamping이라고도 부른다.
   - 첫 Byte의 하위 3 Bit를 0으로 만든다.
   - 마지막 Byte의 최상위 Bit를 0으로 만든다.
   - 마지막 Byte의 두 번째 상위 Bit를 1로 만든다.
4. 결과를 Little Endian 정수로 읽은 값이 Secret Scalar `s`이다.
5. `A = [s]B`를 계산하고 Encoding한 32 Byte가 Public Key이다.
6. `h`의 뒤 32 Byte는 `prefix`로 두고 서명할 때 쓴다.

Pruning의 결과로 `s`는 항상 8의 배수이고, Bit 254가 항상 1이다. 8은 Cofactor이다. Small Order Point `T`는 `[8]T`가 Identity이므로, 8의 배수인 `s`를 곱하면 Small Order 성분이 사라진다.

Private Key 32 Byte에서 `s`와 `prefix`가 모두 결정된다. 따라서 저장해야 하는 비밀은 Private Key 하나이다.

### Sign

Message를 `M`이라고 한다.

```
r = SHA-512(prefix || M) mod L
R = [r]B
k = SHA-512(ENC(R) || ENC(A) || M) mod L
S = (r + k * s) mod L
Signature = ENC(R) || ENC(S)
```

`ENC`는 위에서 설명한 32 Byte Encoding이다. `r`이 ECDSA의 Nonce에 해당한다. `r`은 `prefix`와 `M`으로 결정되므로, 같은 Private Key로 같은 Message를 서명하면 항상 같은 Signature가 나온다. 서명 과정에는 난수가 필요 없고, 모듈러 역원 계산도 없다.

`M`은 `r`을 계산할 때 한 번, `k`를 계산할 때 한 번, 모두 두 번 Hash에 들어간다.

### Verify

1. Signature를 앞 32 Byte `R`과 뒤 32 Byte `S`로 나눈다.
2. `R`과 Public Key `A`를 곡선 위의 점으로 Decoding(디코딩)한다. `S`는 정수로 읽고 `0 <= S < L`인지 확인한다. 하나라도 실패하면 무효이다.
3. `R`, `A`, `M`을 이어 붙인 값을 SHA-512로 Hash하고 `mod L`을 적용해 `k`를 계산한다.
4. 다음 식을 확인한다.

```
[8][S]B = [8]R + [8][k]A
```

RFC 8032 Section 5.1.7은 8을 곱하지 않은 식 `[S]B = R + [k]A`를 대신 확인해도 충분하지만 필수는 아니라고 적는다. 두 식의 차이는 "Cofactor와 검증식 불일치" 절에서 다룬다.

### 검증식이 성립하는 이유

정상적으로 만든 Signature는 `S = r + k * s (mod L)`이고, `B`의 Order가 `L`이므로 다음이 성립한다.

```
[S]B = [r + k * s]B
     = [r]B + [k]([s]B)
     = R + [k]A
```

양변에 8을 곱하면 검증식이 된다.

위조가 어려운 이유를 식의 구조로 보면 다음과 같다. `s`를 모르면 주어진 `R`과 `k`에 맞는 `S`를 계산할 수 없다. 반대로 `S`와 `k`를 먼저 정하고 `R = [S]B - [k]A`로 역산하면, 그 `R`을 넣어 계산한 Hash 값이 처음 정한 `k`와 같아야 한다. 이는 Hash Function의 출력을 원하는 값으로 맞추는 문제이다. 이 문단은 직관적인 설명이며 엄밀한 안전성 증명은 아니다.

## 예시: RFC 8032 Test Vector 1

RFC 8032 Section 7.1의 첫 번째 Test Vector로 각 단계의 값을 따라가 본다. Message는 길이 0인 빈 Byte 열이다. Private Key, Public Key, Signature는 RFC 8032의 값이다. `h`, `s`, `r`, `k`는 위 절차대로 직접 계산한 중간값이며, 최종 Signature가 RFC 8032의 값과 일치하는 것을 확인했다.

```
Private Key
  9d61b19deffd5a60ba844af492ec2cc44449c5697b326919703bac031cae7f60

h = SHA-512(Private Key)
  앞 32 Byte: 357c83864f2833cb427a2ef1c00a013cfdff2768d980c0a3a520f006904de90f
  뒤 32 Byte: 9b4f0afe280b746a778684e75442502057b7473a03f08f96f5a38e9287e01f8f  (prefix)

Pruning 후 (Secret Scalar s의 Little Endian 표현)
  307c83864f2833cb427a2ef1c00a013cfdff2768d980c0a3a520f006904de94f

Public Key A = ENC([s]B)
  d75a980182b10ab7d54bfed3c964073a0ee172f3daa62325af021a68f707511a

r = SHA-512(prefix || M) mod L
  0x0474a058ac758fc5edc2af18741049226853afb47d7844f2ea3d898c300789f3

R = ENC([r]B)
  e5564300c360ac729086e2cc806e828a84877f1eb8e5d974d873e06522490155

k = SHA-512(R || A || M) mod L
  0x0454522e167e3e8a132cec316125d8f86cdf00c6e70405293d19964c8ebcea86

S = (r + k * s) mod L 의 Little Endian 표현
  5fb8821590a33bacc61e39701cf9b46bd25bf5f0595bbe24655141438e7a100b

Signature = R || S
  e5564300c360ac729086e2cc806e828a84877f1eb8e5d974d873e06522490155
  5fb8821590a33bacc61e39701cf9b46bd25bf5f0595bbe24655141438e7a100b
```

Pruning 전후를 비교하면 두 Byte만 바뀐다.

- 첫 Byte: `0x35`(`0011 0101`)에서 하위 3 Bit를 0으로 만들어 `0x30`(`0011 0000`)이 된다.
- 마지막 Byte: `0x0f`(`0000 1111`)에서 최상위 Bit는 0으로 두고 두 번째 상위 Bit를 1로 만들어 `0x4f`(`0100 1111`)가 된다.

`r`과 `k`는 정수 값을 16진수로 적은 것이고, 나머지는 Byte 열을 순서대로 적은 것이다.

## 변형: PureEdDSA, HashEdDSA, Context

### PureEdDSA와 HashEdDSA

RFC 8032는 Message를 처리하는 방식에 따라 두 가지를 구분한다. [RFC 8032 Section 4](https://datatracker.ietf.org/doc/html/rfc8032)

- PureEdDSA: `PH`가 입력을 그대로 돌려준다. Message 전체가 서명 계산에 직접 들어간다. Collision Resilience를 가지지만, Message를 두 번 읽어야 한다.
- HashEdDSA: `PH`가 Message를 먼저 짧은 값으로 Hash한다. Message를 한 번만 읽고 서명할 수 있지만 Collision Resilience를 잃는다. `PH`에서 충돌하는 두 Message는 같은 Signature를 가지기 때문이다.

### Ed25519, Ed25519ctx, Ed25519ph

RFC 8032는 edwards25519 위에 세 가지 변형을 정의한다. 차이는 Hash 입력 앞에 붙는 `dom2` 값과 `PH`이다. [RFC 8032 Section 5.1](https://datatracker.ietf.org/doc/html/rfc8032)

```
dom2(phflag, context) =
  "SigEd25519 no Ed25519 collisions" || octet(phflag) || octet(len(context)) || context
```

| 변형 | `dom2` | `PH` | Context |
|---|---|---|---|
| Ed25519 | 빈 문자열 | 입력 그대로 | 사용하지 않음 |
| Ed25519ctx | `phflag = 0` | 입력 그대로 | 비어 있지 않아야 함 (SHOULD NOT be empty) |
| Ed25519ph | `phflag = 1` | SHA-512 | 선택 |

Context(컨텍스트)는 최대 255 Byte의 문자열이다. 같은 Key를 여러 Protocol(프로토콜)에서 쓸 때 한 Protocol의 Signature가 다른 Protocol에서 유효하게 쓰이지 않도록 구분하는 용도이다. RFC 8032는 Context를 Protocol이 정한 고정 문자열로 쓰도록 권고한다. [RFC 8032 Section 8.3](https://datatracker.ietf.org/doc/html/rfc8032)

RFC 8032는 Prehash 변형인 Ed25519ph와 Ed448ph를 쓰지 않도록 권고한다(SHOULD NOT). [RFC 8032 Section 8.5](https://datatracker.ietf.org/doc/html/rfc8032)

Ed448은 Ed25519와 달리 `dom4` 값이 항상 Hash 입력에 들어가므로 기본 Instance에서도 Context를 쓸 수 있다. 기본값은 빈 문자열이다.

## 보안 특성과 구현 시 주의점

### Deterministic Nonce

`r`이 Private Key와 Message로 결정되므로 서명 시점의 난수 품질에 의존하지 않는다. 난수가 필요한 곳은 Private Key를 만들 때뿐이다. [RFC 8032 Section 8.2](https://datatracker.ietf.org/doc/html/rfc8032)

만약 서로 다른 두 Message에 같은 `r`이 쓰였다면 어떤 일이 생기는지 식으로 확인할 수 있다. `R`이 같고 `k1`, `k2`는 누구나 계산할 수 있으므로 다음이 성립한다.

```
S1 = r + k1 * s  (mod L)
S2 = r + k2 * s  (mod L)

S1 - S2 = (k1 - k2) * s  (mod L)
s = (S1 - S2) * (k1 - k2)^(-1)  (mod L)
```

`s`를 알면 임의의 Message에 서명할 수 있다. EdDSA는 `r`에 Message를 Hash 입력으로 넣어서, 다른 Message에는 다른 `r`이 나오게 한다.

### Collision Resilience

`r`은 공격자가 모르는 `prefix`가 들어간 Hash이고, `k`는 `R`이 Message보다 앞에 들어간 Hash이다. 원 논문은 Hash Function의 충돌만으로는 이 체계를 깰 수 없다고 설명한다. [High-speed high-security signatures](https://ed25519.cr.yp.to/ed25519-20110926.pdf)

### Side Channel

원 논문의 Ed25519 구현은 비밀 값이 배열 Index(인덱스)나 분기 조건으로 흘러가지 않도록 작성되었다. Cache Timing(캐시 접근 시간)이나 Branch Prediction(분기 예측)을 관찰하는 공격을 막기 위한 것이다. [ePrint 2011/368](https://eprint.iacr.org/2011/368)

이 성질은 알고리즘이 아니라 구현의 성질이다. RFC 8032에 실린 예제 코드는 Side Channel 방어를 하지 않는다고 RFC가 직접 밝힌다. [RFC 8032 Section 8.1](https://datatracker.ietf.org/doc/html/rfc8032)

### Signature Malleability

Signature Malleability(서명 가변성)는 유효한 Signature를 Private Key 없이 다른 유효한 Signature로 바꿀 수 있는 성질이다.

`[L]B`는 Identity이므로 `[S + L]B = [S]B`이다. 검증자가 `S`의 범위를 확인하지 않으면 `(R, S + L)`도 같은 Message에 대해 유효한 Signature가 된다. RFC 8032는 검증 단계에서 `0 <= S < L`을 확인하도록 해서 이를 막는다. [RFC 8032 Section 8.4](https://datatracker.ietf.org/doc/html/rfc8032)

Transaction(트랜잭션) 식별자를 Signature에서 만드는 시스템에서는 이 검사가 빠지면 같은 Transaction에 서로 다른 식별자가 생길 수 있다.

### Cofactor와 검증식 불일치

검증식은 두 가지가 쓰인다.

```
Cofactored:    [8][S]B = [8]R + [8][k]A
Cofactorless:  [S]B = R + [k]A
```

정상적인 절차로 만든 Signature는 두 식을 모두 통과한다. 차이는 `R`이나 `A`에 Small Order 성분이 섞여 있을 때 생긴다. Small Order Point `T`는 `[8]T`가 Identity이므로, `R` 대신 `R + T`를 넣어도 Cofactored 식의 결과는 변하지 않는다. Cofactorless 식에서는 `T`가 남아서 결과가 달라진다. 따라서 한 식은 통과하고 다른 식은 실패하는 Signature를 의도적으로 만들 수 있다.

단일 시스템에서는 큰 문제가 아닐 수 있다. 그러나 Blockchain(블록체인)처럼 모든 Node(노드)가 같은 판정을 내려야 하는 환경에서는 Node마다 다른 Library(라이브러리)를 쓰면 같은 Transaction의 유효성 판정이 갈릴 수 있다. 관련 자료는 다음과 같다.

- 2020년 논문 "Taming the many EdDSAs"는 표준 권고와 실제 Ed25519 구현 사이의 불일치를 분석했고, 대부분의 Library가 최신 표준 권고를 따르지 않는다고 보고했다. [ePrint 2020/1244](https://eprint.iacr.org/2020/1244)
- Zcash는 ZIP (Zcash Improvement Proposal) 215에서 검증 규칙을 명시했다. Cofactored 식만 쓰도록 하고 Cofactorless 식 사용을 금지했다. Batch Verification(일괄 검증, 여러 Signature를 한 번에 검증하는 방법)과 호환되도록 하는 것도 목적이다. [ZIP 215](https://zips.z.cash/zip-0215)
- RFC 8032 Section 8.8은 Cofactor를 곱하는 것이 안전성에 반드시 필요하지는 않지만, 어떤 Signature가 유효한지에 대해 구현들이 일치하도록 한다고 설명한다. [RFC 8032 Section 8.8](https://datatracker.ietf.org/doc/html/rfc8032)
- Oasis의 설계 문서는 FIPS 186-5가 Cofactored 식을 명시적으로 요구한다고 적는다. 이 글에서는 FIPS 186-5 원문을 직접 확인하지 못했으므로 2차 자료 기준의 내용이다. [Oasis ADR 0009](https://docs.oasis.io/adrs/0009-ed25519-semantics)

Batch Verification은 여러 Signature를 하나의 식으로 묶어 확인한다. 원 논문은 Signature마다 무작위 128 Bit 값 `z_i`를 곱해 합친 식을 확인하는 방식을 제시한다. [High-speed high-security signatures](https://ed25519.cr.yp.to/ed25519-20110926.pdf)

합의에 쓰이는 시스템에서 Ed25519 검증을 구현하거나 Library를 고를 때 확인할 항목은 다음과 같다.

- 검증식이 Cofactored인지 Cofactorless인지
- `S < L` 검사를 하는지
- `R`과 `A`의 Non-canonical Encoding(같은 점을 가리키지만 `y` 값이 `p` 이상으로 표현된 Encoding)을 거부하는지
- Small Order인 `R`과 `A`를 거부하는지

### Double Public Key Oracle

서명 API (Application Programming Interface)가 Private Key와 Public Key를 별도 인자로 받는 Library가 있다. 공격자가 같은 Message에 대해 Public Key 인자만 바꿔서 서명을 두 번 요청할 수 있다면 Secret Scalar가 노출된다. `r`은 Public Key와 무관하게 결정되므로 `R`이 같고, `k`만 달라지기 때문이다. 식은 Nonce 재사용의 경우와 같다.

```
S  = r + k  * s  (mod L),   k  = H(R || A  || M)
S' = r + k' * s  (mod L),   k' = H(R || A' || M)

s = (S - S') * (k - k')^(-1)  (mod L)
```

이 공격을 분석한 논문은 작성 시점에 45개 Library가 영향을 받는다고 보고했다. 대응 방법은 Public Key를 Private Key와 함께 하나의 값으로 저장해서 받거나, 서명할 때마다 Private Key에서 Public Key를 다시 계산하는 것이다. [arXiv 2308.15009](https://arxiv.org/pdf/2308.15009)

### Fault Attack

결정적 서명은 Fault Attack(오류 주입 공격)에 약점이 있다. 같은 Message를 두 번 서명하면 `r`이 같다. 한 번의 서명 계산 도중 오류가 주입되어 `k`가 달라지면, 정상 Signature와 오류 Signature의 차이에서 위와 같은 식으로 `s`를 구할 수 있다. 위 논문은 서명 중 단일 오류로 Key 정보를 복구한 선행 연구를 인용한다. [arXiv 2308.15009](https://arxiv.org/pdf/2308.15009)

이 공격은 공격자가 서명 장치에 물리적으로 오류를 일으킬 수 있는 환경을 전제로 한다.

## ECDSA와 비교

| 항목 | ECDSA | EdDSA (Ed25519) |
|---|---|---|
| 기반 구조 | DSA를 타원곡선으로 옮긴 형태 | Schnorr Signature의 변형 |
| Nonce | 서명마다 새로 필요. 재사용하면 Private Key 노출 | Private Key와 Message에서 결정적으로 유도 |
| 서명 계산 | Nonce의 모듈러 역원 필요 | 역원 없음 |
| Hash Function | 별도로 선택 | Instance에 고정 (SHA-512) |
| 덧셈 공식 | Short Weierstrass 형태의 일반적인 공식은 Doubling과 Identity를 별도 경우로 처리 | Complete한 단일 공식 |
| Public Key | Hash 입력에 들어가지 않음 | Hash 입력에 들어감 |

Public Key가 Hash 입력에 들어간다는 점에서 따라 나오는 차이가 하나 있다. EdDSA 검증자는 `k`를 계산하려면 `A`를 먼저 알아야 한다. 따라서 Signature와 Message만으로 Public Key를 계산하는 절차가 없고, 검증자에게 Public Key를 별도로 전달해야 한다. 이 문단은 검증식의 구조에서 도출한 내용이다.

성능에 대해 원 논문은 Intel Xeon E5620 (Westmere) CPU에서 서명 1회에 87548 Cycle, 검증 1회에 273364 Cycle, 64개를 묶은 Batch Verification에서 Signature당 134000 Cycle 미만을 보고했다. 이 수치는 2011년 당시 논문의 구현과 해당 CPU 기준이며, 구현과 환경에 따라 달라진다. [High-speed high-security signatures](https://ed25519.cr.yp.to/ed25519-20110926.pdf)

## 사용 사례

- Solana: Account(계정) 주소는 32 Byte 값이며, Ed25519 Public Key이거나 PDA (Program Derived Address)이다. [Solana Docs: Accounts](https://solana.com/docs/core/accounts)
- Sui: Transaction 서명 방식 중 하나로 Pure Ed25519를 지원한다. Signature는 RFC 8032에 따라 만들고 ZIP 215 기준으로 유효해야 한다고 명시한다. [Sui Docs](https://docs.sui.io/develop/transactions/transaction-auth/auth-overview)
- Aptos: Account 인증에 Ed25519와 Secp256k1 ECDSA를 지원한다. [Aptos Docs: Accounts](https://aptos.dev/concepts/accounts)
- Zcash: Sprout Transaction의 일부에 Ed25519 Signature를 사용한다. [ZIP 215](https://zips.z.cash/zip-0215)
- SSH (Secure Shell): RFC 8709가 SSH Protocol에서 Ed25519와 Ed448을 사용하는 방법을 표준화했다. [RFC 8709](https://datatracker.ietf.org/doc/html/rfc8709)

## 정리

- EdDSA는 Twisted Edwards Curve 위의 Schnorr Signature 변형이다. Ed25519와 Ed448이 표준 Instance이다.
- Nonce `r`을 Private Key와 Message의 Hash로 결정한다. 서명할 때 난수가 필요 없고, Nonce 재사용으로 Private Key가 노출되는 문제를 구조적으로 피한다.
- Complete한 덧셈 공식을 써서 예외 분기가 없고, 일정한 연산 흐름으로 구현하기 쉽다.
- Ed25519는 Private Key 32 Byte, Public Key 32 Byte, Signature 64 Byte이며 약 128 Bit 보안 강도를 목표로 한다.
- 검증 규칙은 구현마다 다를 수 있다. Cofactored 검증식 사용 여부, `S < L` 검사, Non-canonical Encoding과 Small Order Point 처리를 확인해야 한다. 합의가 필요한 시스템에서는 ZIP 215처럼 규칙을 명시적으로 고정한다.
- 서명 API가 Public Key를 별도 인자로 받는 구조와 Fault Attack 가능 환경에서는 결정적 Nonce가 오히려 `s` 노출 경로가 될 수 있다.
