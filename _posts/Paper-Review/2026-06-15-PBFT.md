Practical Byzantine Fault Tolerance(PBFT)는 Miguel Castro와 Barbara Liskov가 1999년 Symposium on Operating Systems Design and Implementation(OSDI)에서 발표한 논문이자, 그 논문이 제안한 알고리즘의 이름이다.

| 질문 | 내용 |
| --- | --- |
| 무엇을 | Replica(복제본) 3f+1개 중 최대 f개가 임의로 잘못 동작해도, 나머지 Replica가 Client(클라이언트)의 요청을 같은 순서로 실행하게 한다. |
| 왜 | 기존 Byzantine 장애 허용 기법은 실제로 쓰기에 너무 느리거나, 네트워크의 시간 가정에 의존해서 메시지를 지연시키는 공격만으로 Safety(안전성)가 깨졌다. |
| 어떻게 | Primary가 요청의 순서를 제안하고, Pre-prepare, Prepare, Commit 세 단계에서 Replica 2f+1개의 동의를 모아 순서를 확정한다. Primary에 문제가 생기면 View Change로 교체한다. 암호 연산과 메시지 수를 줄이는 Optimization(최적화)으로 비용을 낮춘다. |

## 1. 배경과 용어 정리

### 1.1 Consensus Algorithm

Consensus Algorithm(합의 알고리즘)은 중앙 관리자가 없는 분산 시스템에서 여러 노드가 같은 값 또는 같은 명령 순서에 대해 일관된 결론에 도달하게 하는 프로토콜이다. 네트워크 지연, 메시지 손실, 노드 장애, 일부 참여자의 악의적 행동이 있어도 이 결론은 유지되어야 한다.

분산 시스템은 데이터를 여러 노드에 복제해 저장한다. 그래서 어떤 값을 정본으로 볼지, 어떤 연산을 먼저 반영할지, 어떤 결과를 최종 상태로 확정할지를 정해야 한다. 노드가 하나뿐이면 이런 문제는 없다. 대신 그 노드에 장애가 나면 시스템 전체가 멈춘다. 이런 지점을 Single Point of Failure(단일 장애점)라고 한다. 복제는 이 약점을 없애지만, 노드 사이의 상태 불일치를 조정하는 장치를 새로 요구한다. Consensus Algorithm이 그 장치다.

블록체인에서는 이 요구가 더 중요하다. 각 노드는 원장을 독립적으로 저장하고 검증하며, 네트워크 지연 때문에 같은 트랜잭션을 서로 다른 순서로 받을 수 있다. 같은 자산을 쓰는 상충하는 두 트랜잭션이 거의 동시에 전파되면 노드마다 먼저 본 트랜잭션이 다를 수 있다. 합의가 없으면 노드마다 다른 트랜잭션을 유효하다고 판단해 원장이 갈라지고, Double Spending(이중 지불)으로 이어진다.

이 문제를 다루는 일반적인 틀이 State Machine Replication(상태 기계 복제)이다. 서비스를 State Machine(상태 기계)으로 보고 그 사본을 여러 노드에 둔다. 모든 사본이 같은 상태에서 시작해 같은 명령을 같은 순서로 실행하면 같은 상태에 도달한다. 여기에는 두 가지 조건이 필요하다.

- 사본은 Deterministic(결정적)이어야 한다. 같은 상태에서 같은 명령을 실행하면 항상 같은 결과가 나와야 한다.
- 모든 사본이 같은 명령 순서에 합의해야 한다.

두 번째 조건이 합의의 핵심이다. 필요한 순서는 Total Order(전체 순서)다. Total Order는 임의의 두 명령에 대해 어느 쪽이 먼저인지 정해진 순서다. 일부 쌍에 대해서만 선후가 정해진 순서는 Partial Order(부분 순서)라고 한다.

### 1.2 Safety와 Liveness

Consensus Algorithm의 정확성은 두 가지 성질로 설명한다.

- **Safety(안전성)**: 서로 다른 정상 노드가 상충하는 결정을 내리지 않는다. 한 번 확정된 값은 이후에 바뀌지 않는다.
- **Liveness(진행성)**: 유효한 요청은 결국 확정된다. "정해진 시간 안에"가 아니라 "결국"이다.

### 1.3 Fault Model

Fault Model(장애 모델)은 노드가 어떤 방식으로 잘못될 수 있는지에 대한 가정이다.

- **Crash Fault**: 노드가 멈추거나 응답하지 않는다.
- **Byzantine Fault(비잔틴 장애)**: 노드가 임의로 동작한다. 멈추는 것, 틀린 값을 보내는 것, 상대마다 다른 값을 보내는 것을 모두 포함한다.

Byzantine Fault라는 이름은 Lamport, Shostak, Pease가 1982년에 발표한 Byzantine Generals Problem(비잔틴 장군 문제)에서 왔다.

장애가 Crash Fault뿐이어도 합의에는 근본적인 한계가 있다. FLP Impossibility는 Fischer, Lynch, Paterson이 1985년에 증명한 결과다. Asynchronous(비동기) 시스템에서는 Faulty(장애가 있는) 프로세스가 하나만 있어도 합의의 종료를 보장하는 Deterministic 프로토콜이 없다. 실제 프로토콜은 다음 둘 중 하나로 이 한계를 피한다.

- 네트워크의 시간에 대한 가정을 더한다. Partial Synchrony(부분 동기)와 Timeout이 여기에 해당한다. PBFT가 택한 방법이다.
- Randomization(무작위화)을 써서 Deterministic이라는 조건을 포기한다.

### 1.4 Consensus Algorithm의 분류

**1. Crash Fault Tolerant (CFT)**

노드가 멈추는 장애는 있지만 악의적인 행동은 없다고 가정한다. 참여 노드가 미리 정해진 환경에서 분산 데이터베이스나 클러스터 관리 시스템의 기반으로 쓴다.

- **Paxos**: Leslie Lamport가 제안한 프로토콜이다. 과반수의 동의로 값이나 명령 순서를 정한다.
- **Raft**: Paxos와 같은 결과를 내면서 이해하기 쉽도록 설계한 프로토콜이다. Leader Election(리더 선출), Log Replication(로그 복제), Safety를 나누어 설명한다. etcd, Consul 등이 쓴다.
- **Zab (ZooKeeper Atomic Broadcast)**: Apache ZooKeeper가 쓰는 Leader 기반 프로토콜이다.

Two-Phase Commit(2PC)과 Three-Phase Commit(3PC)은 함께 언급되지만 성격이 다르다. 둘은 분산 트랜잭션을 모든 참여자가 함께 반영하거나 함께 취소하게 하는 Atomic Commit(원자적 커밋) 프로토콜이다. 2PC는 Coordinator(조정자)에 장애가 나면 참여자가 결정을 내리지 못하고 멈추는 Blocking 문제가 있다. 3PC는 Pre-commit 단계를 더해 이 문제를 줄이지만, Synchronous(동기) 네트워크이고 Network Partition(네트워크 분할)이 없다는 가정이 필요하다.

**2. Byzantine Fault Tolerant (BFT)**

노드가 임의로 동작하는 Byzantine Fault가 있어도 합의를 유지한다.

- **PBFT**: 이 글의 주제다. Pre-prepare, Prepare, Commit 세 단계로 합의한다. Byzantine 노드 f개를 견디는 데 3f+1개의 노드가 필요하다.
- **Tendermint**: PBFT를 블록체인에 맞게 바꾼 프로토콜이다. Propose, Prevote, Precommit 단계를 거쳐 블록을 확정하며, 확정된 블록은 되돌릴 수 없다. Cosmos 생태계에서 쓴다. 구현체의 현재 이름은 CometBFT다.
- **HotStuff**: 2018년에 VMware Research 등의 연구진이 제안했다. View Change에 드는 통신량을 노드 수에 비례하는 수준으로 줄였고, 여러 단계를 겹쳐 처리하는 Pipelining을 도입했다. DiemBFT와 AptosBFT가 이를 바탕으로 한다.
- **Istanbul Byzantine Fault Tolerance (IBFT)**: PBFT에서 파생된 프로토콜이다. Hyperledger Besu와 Quorum에 구현되어 있다.

**3. Permissionless 환경의 합의**

퍼블릭 블록체인에서는 참여자가 자유롭게 들어오고 나간다. 노드 집합이 고정되어 있다고 가정하는 BFT 프로토콜을 그대로 쓰기 어렵다. 한 참여자가 여러 신원을 만드는 Sybil Attack(시빌 공격)도 막아야 한다. 그래서 자원을 기준으로 참여 권한을 정한다.

- **Proof of Work (PoW)**: 계산 자원으로 블록 생성 권한을 얻는다. Bitcoin이 대표적이다. 노드는 누적 작업량이 가장 큰 체인을 따른다. 흔히 Longest Chain Rule이라고 부르지만 기준은 블록 수가 아니라 누적 작업량이다.
- **Proof of Stake (PoS)**: 예치한 Stake(지분)를 기준으로 Validator(검증자)를 정한다. Ethereum이 쓴다.
- **Delegated Proof of Stake (DPoS)**: 토큰 보유자가 투표로 소수의 Validator를 뽑고, 뽑힌 Validator가 블록을 만든다.

Proof of Authority(PoA)는 신원이 확인된 소수의 Validator만 블록을 만드는 방식이다. Permissionless가 아니라 참여자가 서로를 아는 Permissioned 환경에서 쓴다. IBFT가 이 계열에 속한다.

### 1.5 Network Model

Consensus Algorithm은 네트워크가 시간에 대해 무엇을 보장하는지에 따라 설계가 달라진다. Network Model(네트워크 모델)은 메시지 전달 시간과 노드의 처리 시간에 상한이 있는지, 그 값을 아는지로 나눈다.

| 모델 | 시간 상한 | Timeout으로 장애를 판단할 수 있는가 |
| --- | --- | --- |
| Synchronous(동기) | 상한이 있고 그 값을 안다. | 가능하다. 상한 안에 응답이 없으면 장애다. |
| Asynchronous(비동기) | 상한이 없다. | 불가능하다. 느린 것과 장애를 구별할 수 없다. |
| Partially Synchronous(부분 동기) | 상한이 있지만 그 값을 모르거나, 값은 알지만 언제부터 성립하는지 모른다. | 바로는 불가능하다. PBFT는 Timeout을 점점 늘려 가며 대응한다. |

**Synchronous Network.** 모든 메시지는 알려진 최대 시간 안에 전달되고 노드의 계산도 알려진 시간 안에 끝난다. 장애 감지가 쉬워 프로토콜 설계가 단순하다. 그러나 실제 인터넷에서는 혼잡, 장애, 운영 체제의 스케줄링 때문에 이 상한을 항상 지키기 어렵다. 가정이 깨지면 이 가정에 의존한 프로토콜의 정확성도 깨질 수 있다.

**Asynchronous Network.** 메시지가 언제 전달될지, 노드가 언제 계산을 끝낼지 보장이 없다. 응답이 늦는 이유가 네트워크 지연인지 노드 장애인지 구별할 수 없다. 가장 약한 가정이라 현실에 가장 넓게 맞지만, 1.3절의 FLP Impossibility가 적용된다.

**Partially Synchronous Network.** Dwork, Lynch, Stockmeyer가 1988년에 정의한 모델이고 두 형태가 있다. 첫째는 상한이 항상 있지만 그 값을 모르는 형태다. 둘째는 상한 값은 알지만 그 상한이 알 수 없는 시점부터 성립하는 형태다. 이 시점을 Global Stabilization Time(GST)이라고 한다. 이 모델을 가정한 프로토콜은 보통 Safety를 네트워크 상태와 무관하게 지키고, Liveness는 네트워크가 안정된 뒤에 보장하도록 설계한다. 네트워크가 불안정한 동안에는 합의가 늦어질 수 있지만 서로 모순된 결정은 나오지 않는다.

### 1.6 PBFT 용어

| 용어 | 뜻 |
| --- | --- |
| Replica(복제본) | 서비스 상태를 유지하고 요청을 실행하는 노드. 전체 수를 N으로 쓴다. |
| Client(클라이언트) | 서비스에 요청을 보내고 응답을 기다리는 주체. |
| f | 동시에 Faulty일 수 있는 Replica의 최대 수. |
| View | Replica들의 구성 하나. 번호 v가 연속으로 붙고, View 하나에는 Primary가 하나 있다. |
| Primary | 한 View에서 요청의 순서를 제안하는 Replica. |
| Backup | 그 View에서 Primary가 아닌 나머지 Replica. |
| Sequence Number(순서 번호) | Primary가 요청에 붙이는 번호 n. 요청은 이 번호 순서로 실행된다. |
| Digest | 메시지 m의 해시값 D(m). |
| Quorum | Replica 2f+1개의 집합. |
| Checkpoint | 정해진 간격의 Sequence Number까지 실행한 뒤의 서비스 상태. |
| Non-faulty | 알고리즘을 따르고, 공격자가 그 서명을 위조할 수 없는 노드. 그렇지 않은 노드는 모두 Faulty다. |

## 2. 문제 정의

### 2.1 풀려는 문제

PBFT가 풀려는 문제는 Byzantine Fault가 있어도 올바르게 동작하는 State Machine Replication이다. 논문은 악의적 공격과 소프트웨어 오류가 늘고 있고, 둘 다 노드를 임의로 동작하게 만들 수 있다는 점을 동기로 든다.

### 2.2 기존 방식의 한계

논문 이전에도 Byzantine Fault를 견디는 기법은 있었다. 논문은 그 한계를 두 가지로 정리한다.

- **너무 느리다.** 이론적으로 가능하다는 것을 보이는 데 목적이 있어 실제로 쓰기 어려웠다.
- **Synchrony에 의존한다.** 메시지 지연과 처리 속도에 알려진 상한이 있다고 가정했다.

두 번째 한계는 보안 문제로 이어진다. 논문과 가장 가까운 시스템인 Rampart와 SecureRing은 응답이 늦는 노드를 Faulty로 보고 Replica 그룹에서 제외한다. 공격자가 Non-faulty 노드나 그 통신을 지연시키기만 해도 그 노드가 제외되고, 그러면 Safety가 깨진다. 논문은 이런 Denial of Service(서비스 거부) 공격이 노드를 장악하는 것보다 대체로 쉽다고 본다.

### 2.3 목표와 가정

논문의 목표는 세 가지다.

| 목표 | 내용 | 필요한 조건 |
| --- | --- | --- |
| Safety | 복제된 서비스가 Linearizability(선형화 가능성)를 만족한다. 연산을 한 번에 하나씩 실행하는 단일 서버처럼 동작한다는 뜻이다. | Faulty Replica가 f개 이하. 시간 가정은 필요 없다. |
| Liveness | Client가 요청에 대한 응답을 결국 받는다. | Faulty Replica가 f개 이하이고, 메시지 지연이 끝없이 빠르게 늘지 않는다. |
| 실용적인 성능 | 복제하지 않은 서비스와 비슷한 속도로 동작한다. | 4.1절의 실험으로 확인한다. |

이를 위해 논문이 두는 가정은 다음과 같다.

- **네트워크**: Asynchronous다. 메시지를 전달하지 못하거나, 지연시키거나, 중복시키거나, 순서를 바꿔 전달할 수 있다.
- **장애**: Byzantine Fault다. Replica N개 중 Faulty는 최대 f = ⌊(N-1)/3⌋개다. 장애는 서로 독립이라고 가정한다.
- **암호 기법**: 공개 키 서명, Message Authentication Code(메시지 인증 코드, 이하 MAC), Digest를 쓴다. 공격자는 서명을 위조하거나 Digest가 같은 두 메시지를 찾지 못한다.
- **구성원**: 모든 Replica는 서로의 공개 키를 안다. 즉 Replica 집합은 미리 정해져 있다.

Safety와 Liveness의 조건이 다르다는 점이 설계의 핵심이다. Safety는 메시지가 아무리 늦거나 순서가 바뀌어도 유지된다. 그래서 2.2절의 지연 공격으로 깨지지 않는다. 대신 FLP Impossibility 때문에 Liveness는 시간 가정에 의존할 수밖에 없다. 논문은 이를 "약한 Synchrony 가정"이라고 부른다. 메시지를 보낸 뒤 도착할 때까지 걸리는 시간이 끝없이 빠르게 늘어나지는 않는다는 가정이다.

논문은 Partial Synchrony라는 용어를 쓰지 않는다. 후속 문헌은 PBFT를 "Safety는 Asynchronous 모델에서, Liveness는 Partially Synchronous 모델에서 보장한다"고 요약한다. 따라서 "PBFT는 부분 동기 네트워크를 가정한다"는 말은 Liveness에 한해서만 맞다.

### 2.4 장애 허용 한계: 왜 3f+1개인가

PBFT는 Faulty Replica f개를 견디는 데 N = 3f+1개의 Replica를 쓴다. 논문의 논증은 최악의 상황을 가정한다.

| 항목 | 개수 |
| --- | --- |
| 전체 Faulty Replica | 최대 f개 |
| 응답하지 않는 Replica | f개. Faulty일 수도 있고, 느릴 뿐인 Non-faulty일 수도 있다. |
| 응답한 Replica | N - f개 |
| 응답한 Replica 중 Faulty | 최대 f개. 응답하지 않은 f개가 모두 Non-faulty인 경우다. |
| 응답한 Replica 중 Non-faulty | 최소 N - 2f개 |

f개가 응답하지 않아도 진행하려면 N - f개의 응답만으로 결정해야 한다. 그 안에서 Non-faulty의 응답이 Faulty의 응답보다 많아야 한다.

```text
Non-faulty 응답 수 > Faulty 응답 수
(N - f) - f > f
N > 3f
N ≥ 3f + 1
```

| Replica 수 N | 견디는 장애 수 f | Quorum 크기 2f+1 |
| --- | --- | --- |
| 4 | 1 | 3 |
| 7 | 2 | 5 |
| 10 | 3 | 7 |

- N을 3f+1보다 늘려도 다음 3f+1에 닿기 전까지는 f가 늘지 않는다. N이 5나 6이어도 f는 1이다. 메시지만 늘어 성능이 떨어진다.
- 멈춘 Replica도 Faulty다. f는 악의적인 Replica와 멈춘 Replica를 합친 수의 상한이다.

## 3. 해결 방법

### 3.1 전체 구조

Replica들은 View라는 구성을 차례로 거친다. 한 View에서 Replica 하나가 Primary이고 나머지는 Backup이다.

- **Primary**: 요청에 Sequence Number를 붙여 순서를 제안한다.
- **Backup**: Primary의 제안을 검증하고 서로 확인한다.

Primary는 투표로 뽑지 않는다. View 번호가 v이면 번호가 `v mod N`인 Replica가 Primary다. Primary에 문제가 있어 보이면 View 번호를 1 올리고, 그 번호에 해당하는 Replica가 다음 Primary가 된다.

각 Replica는 서비스 상태, 받아들인 메시지를 담는 로그, 현재 View 번호를 유지한다.

알고리즘의 큰 흐름은 다음과 같다.

1. Client가 Primary에 요청을 보낸다.
2. Primary가 요청에 순서를 붙여 Backup들에 보낸다.
3. Replica들이 요청을 실행하고 Client에 응답한다.
4. Client는 서로 다른 Replica f+1개에게서 같은 결과를 받으면 그 결과를 받아들인다.

### 3.2 Normal Case

Normal Case는 Primary에 문제가 없을 때의 동작이다. Pre-prepare, Prepare, Commit 세 단계로 이루어진다.

| 단계 | 하는 일 |
| --- | --- |
| Pre-prepare | Primary가 요청에 Sequence Number를 붙여 제안한다. |
| Prepare | Backup들이 같은 제안을 받았는지 서로 확인한다. |
| Commit | 제안이 충분히 확인되었다는 사실을 서로 확인하고 실행한다. |

![PBFT Normal Case의 메시지 흐름, Replica 4개](pbft-normal-case.png)

그림은 Replica 4개(f = 1), View 0의 경우다. Replica 0이 Primary이고 Replica 3은 Faulty여서 아무것도 보내지 않는다.

1. **Request**

    Client c는 연산 o의 실행을 요청하는 메시지를 Primary에 보낸다.

    ```text
    ⟨REQUEST, o, t, c⟩  (Client c가 서명)

    - o: 실행할 연산
    - t: Timestamp(시각 표시). 같은 Client의 나중 요청일수록 크다.
    ```

2. **Pre-prepare**

    Primary는 요청 m에 Sequence Number n을 붙이고 모든 Backup에 `PRE-PREPARE`를 보낸다.

    ```text
    ⟨⟨PRE-PREPARE, v, n, d⟩, m⟩  (Primary가 서명)

    - v: View 번호
    - n: Sequence Number
    - d: 요청 m의 Digest
    ```

    Backup은 다음을 모두 만족할 때만 이 메시지를 받아들인다.

    - 서명이 올바르고 d가 m의 Digest다.
    - 자신이 View v에 있다.
    - 같은 v, 같은 n에 대해 Digest가 다른 `PRE-PREPARE`를 받아들인 적이 없다.
    - n이 허용 범위 안에 있다. 이 범위는 3.5절에서 설명한다.

3. **Prepare**

    `PRE-PREPARE`를 받아들인 Backup i는 다른 모든 Replica에 `PREPARE`를 보낸다. Primary는 `PREPARE`를 보내지 않는다.

    ```text
    ⟨PREPARE, v, n, d, i⟩  (Replica i가 서명)

    - i: 메시지를 보낸 Replica의 번호
    ```

    Replica의 로그에 다음이 모두 있으면 그 Replica에서 `prepared` 조건이 참이 된다.

    - 요청 m
    - m에 대한 `PRE-PREPARE` 1개
    - 그것과 v, n, d가 같은 `PREPARE` 2f개. 서로 다른 Backup이 보낸 것이어야 한다.

    Primary의 `PRE-PREPARE`와 Backup 2f개의 `PREPARE`를 합치면, Replica 2f+1개가 같은 요청과 같은 순서에 동의한 것이다. 이 메시지 묶음을 Prepared Certificate라고 부르기도 하지만 이 논문에는 그 용어가 나오지 않는다.

    `prepared`는 한 View 안에서 한 Sequence Number에 요청이 하나만 선택되었음을 보장한다.

4. **Commit**

    `prepared`가 참이 된 Replica는 다른 Replica들에 `COMMIT`을 보낸다.

    ```text
    ⟨COMMIT, v, n, D(m), i⟩  (Replica i가 서명)
    ```

    `prepared`가 참이고, 서로 다른 Replica가 보낸 일치하는 `COMMIT`을 2f+1개 받아들이면 `committed-local` 조건이 참이 된다. 자신이 보낸 것도 센다.

    - `committed-local`이 참이고 n보다 작은 번호의 요청을 모두 실행했으면 Replica는 요청을 실행한다.
    - Non-faulty Replica에서 `committed-local`이 된 요청은 View Change가 일어나도 다른 요청으로 바뀌지 않는다.
    - `COMMIT`이 2f+1개 모이지 않으면 요청에 문제가 없어도 실행이 늦어진다.

5. **Reply**

    요청을 실행한 Replica는 결과 r을 Client에 직접 보낸다.

    ```text
    ⟨REPLY, v, t, c, i, r⟩  (Replica i가 서명)
    ```

    Client는 서로 다른 Replica f+1개에게서 t와 r이 같은 응답을 받으면 r을 결과로 받아들인다. Faulty Replica는 최대 f개이므로 f+1개 중 적어도 하나는 Non-faulty이기 때문이다.

    응답이 제때 오지 않으면 Client는 요청을 모든 Replica에 다시 보낸다. 이미 실행한 Replica는 응답만 다시 보내고, 아직 실행하지 않은 Backup은 요청을 Primary에 전달한다.

그림의 경우를 따라가 보면 다음과 같다. Replica 1의 로그에는 `PRE-PREPARE`, 자신의 `PREPARE`, Replica 2의 `PREPARE`가 있다. `PREPARE`가 2개이므로 `prepared`가 참이다. Replica 0, 1, 2는 `COMMIT`을 3개씩 갖게 되어 요청을 실행한다. Client는 같은 결과의 `REPLY`를 2개 받으면 결과를 받아들인다. Replica 3이 아무것도 보내지 않아도 요청은 처리된다.

### 3.3 Quorum

PBFT의 Safety는 크기가 2f+1인 Quorum에 기반한다.

| 단계 | 수행 내용 | 모으는 메시지 | 의미 |
| --- | --- | --- | --- |
| Pre-prepare | Primary가 `PRE-PREPARE` 전송 | 없음 | 요청과 순서의 제안 |
| Prepare | Backup이 검증 후 `PREPARE` 전송 | `PREPARE` 2f개. Primary의 `PRE-PREPARE`와 합쳐 2f+1개 | 같은 View, 같은 번호에 요청이 하나만 선택됨 (`prepared`) |
| Commit | `prepared`가 된 Replica가 `COMMIT` 전송 | `COMMIT` 2f+1개 | View Change 뒤에도 결정이 유지됨 (`committed-local`) |
| Reply | 실행한 Replica가 `REPLY` 전송 | Client가 `REPLY` f+1개 | 적어도 하나는 Non-faulty의 결과 |
| Checkpoint | 상태의 Digest를 담은 `CHECKPOINT` 전송 | `CHECKPOINT` 2f+1개 | 상태가 올바르다는 증거 |
| View Change | 새 Primary가 `NEW-VIEW` 전송 | 다른 Replica의 `VIEW-CHANGE` 2f개. 자신의 것과 합쳐 2f+1개 | 새 View 시작 |

### 3.4 Q. 왜 2f+1개의 메시지를 모으는가

2f+1개 안에는 Faulty Replica가 최대 f개 들어 있을 수 있다. 나머지 f+1개 이상은 Non-faulty의 메시지다.

이 수가 중요한 이유는 서로 다른 두 요청에 대해 각각 2f+1개의 동의가 만들어질 수 없기 때문이다. 두 Quorum을 Q1, Q2라고 하자.

```text
Q1의 크기 = Q2의 크기 = 2f + 1
전체 Replica 수 = 3f + 1
Q1과 Q2가 공유하는 Replica 수 ≥ (2f + 1) + (2f + 1) - (3f + 1) = f + 1
```

두 Quorum은 Replica를 f+1개 이상 공유한다. Faulty Replica는 최대 f개이므로 공유된 Replica 중 적어도 하나는 Non-faulty다. Non-faulty Replica는 같은 View, 같은 Sequence Number에 대해 서로 다른 두 요청을 지지하지 않는다. 따라서 서로 다른 두 요청이 같은 번호로 함께 선택될 수 없다.

2f+1은 다음 두 조건을 함께 만족하는 유일한 크기다.

1. 두 Quorum이 Non-faulty Replica를 하나 이상 공유한다. 2f+1보다 작으면 이 보장이 없다.
2. Faulty Replica f개가 응답하지 않아도 모을 수 있다. Non-faulty Replica는 2f+1개뿐일 수 있으므로 이보다 크면 모을 수 없다.

**예시: Faulty Primary가 Backup마다 다른 요청을 보낼 때.** Replica 4개, f = 1, View 0이다. Primary인 Replica 0이 Faulty다. Replica 0은 같은 Sequence Number 1에 대해 Replica 1에는 요청 A를, Replica 2와 3에는 요청 B를 보낸다.

| Replica | 받은 `PRE-PREPARE` | 로그의 일치하는 `PREPARE` | `prepared` |
| --- | --- | --- | --- |
| 1 | A | A에 대해 1개 (자신) | 거짓. 2개가 필요하다. |
| 2 | B | B에 대해 2개 (자신, Replica 3) | 참 |
| 3 | B | B에 대해 2개 (자신, Replica 2) | 참 |

A는 어디서도 `prepared`가 되지 못한다. B는 Replica 2와 3에서 `prepared`가 되지만, 실행하려면 `COMMIT` 3개가 필요하고 Non-faulty Replica가 보내는 것은 2개다. Replica 0이 `COMMIT`을 보내면 B가 실행되고, 보내지 않으면 아무것도 실행되지 않은 채 View Change로 넘어간다. 어느 경우에도 1번으로 A를 실행하는 Non-faulty Replica는 없다.

### 3.5 Checkpoint와 Garbage Collection

로그를 끝없이 쌓을 수는 없으므로 오래된 메시지는 버려야 한다. 이를 Garbage Collection(불필요한 데이터 정리)이라고 한다. 다만 어떤 요청의 메시지는 그 요청이 충분히 많은 Replica에서 실행되었다는 것을 증명할 수 있을 때까지 남아 있어야 한다. 요청마다 증명을 만들면 비용이 크므로 주기적으로 만든다.

1. Replica는 Sequence Number가 일정 간격(논문의 예는 100)에 닿을 때마다 그 시점의 상태를 Checkpoint로 남기고 `⟨CHECKPOINT, n, d, i⟩`를 다른 Replica에 보낸다. d는 상태의 Digest다.
2. n과 d가 같은 `CHECKPOINT`가 서로 다른 Replica에게서 2f+1개 모이면 그 Checkpoint는 Stable Checkpoint가 된다.
3. Replica는 번호가 n 이하인 `PRE-PREPARE`, `PREPARE`, `COMMIT`과 그 이전의 Checkpoint를 버린다.

Checkpoint는 Replica가 받아들이는 Sequence Number의 범위도 정한다. 아래쪽 경계인 Low Water Mark h는 마지막 Stable Checkpoint의 번호이고, 위쪽 경계인 High Water Mark H는 h + k다. 논문의 예에서 k는 200이다. 이 범위는 Faulty Primary가 아주 큰 번호를 골라 번호 공간을 소진시키는 것을 막는다.

### 3.6 View Change

Primary가 Faulty이면 요청이 실행되지 않는다. View Change는 Primary를 바꿔 합의가 계속되게 한다. PBFT의 Liveness를 제공하는 장치다.

1. **Timeout 발생**

    Backup은 요청을 받았을 때 Timer(타이머)가 돌고 있지 않으면 Timer를 시작하고, 그 요청을 실행하면 멈춘다. 기다리는 다른 요청이 있으면 다시 시작한다. Timer가 감시하는 것은 요청의 실행이다. 그래서 다음 경우가 모두 Timeout으로 드러난다.

    - Primary가 `PRE-PREPARE`를 보내지 않는 경우
    - Primary가 Backup마다 다른 요청을 보내 `prepared`가 되지 않는 경우
    - `COMMIT`이 모이지 않아 `committed-local`이 되지 않는 경우

2. **VIEW-CHANGE 전송**

    Timer가 만료된 Backup i는 다음 View인 v+1에 대한 `VIEW-CHANGE`를 모든 Replica에 보낸다. 이때부터 `CHECKPOINT`, `VIEW-CHANGE`, `NEW-VIEW` 외의 메시지는 받아들이지 않는다.

    ```text
    ⟨VIEW-CHANGE, v+1, n, C, P, i⟩  (Replica i가 서명)

    - n: i가 아는 마지막 Stable Checkpoint의 Sequence Number
    - C: 그 Checkpoint를 증명하는 CHECKPOINT 2f+1개
    - P: i에서 prepared가 된 요청마다, 그 근거인 PRE-PREPARE 1개와 PREPARE 2f개
    ```

3. **NEW-VIEW 생성**

    View v+1의 Primary는 번호가 `(v+1) mod N`인 Replica다. 이 Replica는 다른 Replica에게서 유효한 `VIEW-CHANGE` 2f개를 받으면 `NEW-VIEW`를 만들어 모든 Replica에 보낸다.

    ```text
    ⟨NEW-VIEW, v+1, V, O⟩  (새 Primary가 서명)

    - V: 받은 VIEW-CHANGE들과 자신의 VIEW-CHANGE
    - O: 새 View에서 다시 진행할 PRE-PREPARE들
    ```

    O는 V에서 정해진 규칙으로 계산한다. V의 어떤 `VIEW-CHANGE`에 "n번은 요청 m"이라는 근거가 있으면 새 Primary는 n번에 m을 다시 제안해야 한다. 근거가 없는 번호에는 실행해도 아무 일도 하지 않는 Null 요청을 넣는다.

4. **새 View 시작**

    Backup은 `NEW-VIEW`의 서명과 V를 검증하고, V로 O를 직접 다시 계산해 비교한다. 새 Primary가 근거와 다른 요청을 넣었으면 O가 달라지므로 `NEW-VIEW`를 받아들이지 않는다. 받아들이면 O의 요청들에 대해 `PREPARE`를 보내고 View v+1에서 합의를 이어 간다. 이미 실행한 요청은 다시 실행하지 않는다.

### 3.7 Q. 왜 Prepare와 Commit, 두 단계를 거치는가

두 단계는 서로 다른 것을 보장한다.

**Prepare 단계: 같은 View 안에서 요청의 유일성**

`prepared`는 한 View의 한 Sequence Number에 대해 요청이 하나만 선택되었음을 보장한다. 3.4절의 논증이 그 이유다. 그러나 `prepared`만으로는 요청을 실행할 수 없다. `prepared`는 Replica 하나의 로그에 대한 조건이다. 한 Replica에서 참이어도 다른 Non-faulty Replica들은 아직 참이 아닐 수 있다. 이 상태에서 View Change가 일어나면 새 Primary가 모은 `VIEW-CHANGE` 어디에도 그 요청의 근거가 없을 수 있다.

**Commit 단계: View가 바뀌어도 유지되는 결정**

`committed-local`이 되려면 `COMMIT`이 2f+1개 필요하다. Non-faulty Replica는 `prepared`가 참일 때만 `COMMIT`을 보낸다. 따라서 2f+1개 중 f+1개 이상은 `prepared` 상태인 Non-faulty Replica가 보낸 것이다. 새 Primary가 모으는 `VIEW-CHANGE` 2f+1개의 어떤 묶음도 이 f+1개 중 적어도 하나를 포함한다. 그 Replica의 `VIEW-CHANGE`가 요청의 근거를 새 View로 전달한다.

- **Prepare가 없으면**: 같은 번호에 서로 다른 요청이 선택될 수 있다.
- **Commit이 없으면**: 한 Replica가 실행한 요청이 View Change 뒤에 다른 요청으로 바뀔 수 있다. 같은 번호에 Replica마다 다른 요청을 실행하게 된다.

Prepare는 "어떤 요청을 선택할 것인가"를 정하고, Commit은 "그 선택이 이후에도 유지되는가"를 보장한다.

#### Commit 단계가 없을 때 생기는 상황 예시

Commit 단계가 없고, Replica가 `prepared`가 되면 곧바로 요청을 실행한다고 가정한다. Replica 4개, f = 1, View 1이다. Primary는 Replica 1이고(`1 mod 4 = 1`) Faulty다.

1. Replica 1이 요청 m에 7번을 붙여 `PRE-PREPARE`를 보낸다. Replica 0과 3에는 도착하고 Replica 2에는 지연된다.
2. Replica 0과 3이 `PREPARE`를 보낸다. Replica 3은 Replica 0의 `PREPARE`를 받는다. Replica 0은 Replica 3의 `PREPARE`를 아직 받지 못했다.
3. Replica 3은 `PREPARE`가 2개라 `prepared`가 참이다. Replica 0은 1개라 거짓이다.
4. 가정대로 Replica 3은 m을 7번으로 실행한다.
5. Replica 0은 요청을 실행하지 못한 채 Timer가 만료된다. Replica 2도 Client가 다시 보낸 요청을 받고 기다리다 Timer가 만료된다. 둘은 View 2로 가는 View Change를 시작한다. View 2의 Primary는 Replica 2다(`2 mod 4 = 2`).
6. Faulty인 Replica 1도 `VIEW-CHANGE`를 보낸다. Replica 2는 Replica 0과 1의 `VIEW-CHANGE`에 자신의 것을 더해 `NEW-VIEW`를 만든다. Replica 0은 `prepared`가 아니었고, Replica 1은 Faulty라 근거를 넣지 않고, Replica 2는 `PRE-PREPARE`를 받지 못했다. 세 메시지 어디에도 "7번은 m"이라는 근거가 없다.
7. Replica 2는 7번을 다른 요청 m′에 붙일 수 있다. 그러면 Replica 0과 2는 m′을 7번으로 실행하게 된다.

Replica 3은 7번으로 m을, Replica 0과 2는 m′을 실행했다. Non-faulty Replica끼리 순서가 달라져 Safety가 깨진다.

Commit 단계가 있으면 Replica 3은 `COMMIT`을 3개 모을 때까지 실행하지 않는다. 위 상황에서 `COMMIT`을 보낼 수 있는 것은 Replica 3 자신과 Faulty인 Replica 1뿐이라 최대 2개다. Replica 3은 실행하지 못하고 불일치도 생기지 않는다. 반대로 `COMMIT`이 3개 모였다면 Non-faulty Replica 2개 이상이 `prepared` 상태다. `NEW-VIEW`에는 Replica 4개 중 3개의 `VIEW-CHANGE`가 들어가므로 그 둘 중 하나는 반드시 포함된다. 새 Primary는 7번에 m을 다시 제안해야 한다.

### 3.8 Liveness를 지키는 장치

View Change가 너무 자주 일어나도, 너무 늦게 일어나도 요청이 실행되지 않는다. 논문은 세 가지 장치를 둔다.

1. **너무 일찍 시작하지 않는다.** `VIEW-CHANGE`를 보낸 Replica는 같은 View에 대한 `VIEW-CHANGE`를 2f+1개 받은 뒤에 대기 Timer를 길이 T로 시작한다. 새 View에서 요청을 실행하기 전에 이 Timer가 만료되면 그다음 View로 가는 View Change를 시작하고, 이번에는 2T를 기다린다. 대기 시간이 두 배씩 늘어난다.
2. **너무 늦게 시작하지 않는다.** 자신의 View보다 큰 View에 대한 `VIEW-CHANGE`를 다른 Replica f+1개에게서 받으면, 자신의 Timer가 만료되지 않았어도 `VIEW-CHANGE`를 보낸다.
3. **Faulty Replica가 View Change를 남발하지 못한다.** View Change는 Replica f+1개 이상이 `VIEW-CHANGE`를 보내야 일어난다. 또 Primary는 `v mod N`으로 정해지므로 Faulty Primary가 f개를 넘는 연속된 View에 걸쳐 이어질 수 없다.

논문은 T의 초기값이나 구체적인 Timeout 값을 제시하지 않는다.

### 3.9 성능을 만든 Optimization

논문 제목의 Practical은 실제 시스템에서 쓸 수 있는 성능을 뜻한다. 이를 만든 Optimization은 다음과 같다.

| Optimization | 내용 |
| --- | --- |
| MAC으로 인증 | 공개 키 서명은 드물게 보내는 `VIEW-CHANGE`와 `NEW-VIEW`에만 쓴다. 나머지 메시지는 MAC으로 인증한다. 논문의 측정에서 서명 생성은 43 ms, MAC 계산은 10.3 μs다. |
| Tentative Execution(잠정 실행) | `prepared`가 되고 앞 번호의 요청이 모두 Commit되었으면, `COMMIT`을 기다리지 않고 실행해 잠정 응답을 보낸다. Client는 일치하는 잠정 응답 2f+1개를 기다린다. 요청 하나에 드는 메시지 전달 단계가 5에서 4로 줄어든다. |
| Read-only(읽기 전용) 요청 | 상태를 바꾸지 않는 요청은 Client가 모든 Replica에 직접 보내고, Replica가 바로 실행해 응답한다. Client는 같은 결과의 응답 2f+1개를 기다린다. |
| 큰 응답 줄이기 | Client가 지정한 Replica 하나만 결과 전체를 보내고 나머지는 결과의 Digest만 보낸다. |
| 요청 묶음 처리 | 부하가 크면 Primary가 요청을 모아 한 번에 보낸다. |

서명 대신 MAC을 쓰면 메시지가 진짜임을 제3자에게 증명할 수 없다. 논문은 이 문제를 피하도록 알고리즘을 고쳤다고 밝히지만, 고친 알고리즘의 내용은 별도 기술 문서에 있다.

잠정 실행된 요청은 View Change 때 취소될 수 있다. 이때 Replica는 상태를 마지막 Checkpoint로 되돌린다.

## 4. 평가와 한계

### 4.1 실험 결과

논문은 알고리즘을 Replication Library로 구현하고, 이를 써서 Byzantine-fault-tolerant File System(BFS)이라는 Network File System(NFS) 서비스를 만들어 측정했다. 실험 환경은 Replica 4개(f = 1), Client 1개, 133 MHz 프로세서 장비, 10 Mbit/s 네트워크다.

아무 일도 하지 않는 연산을 호출하는 데 걸리는 시간은 다음과 같다. 괄호 안은 복제하지 않은 경우와 비교한 증가율이다.

| 인자/결과 크기 (KB) | 복제, Read-write (ms) | 복제, Read-only (ms) | 복제 없음 (ms) |
| --- | --- | --- | --- |
| 0/0 | 3.35 (309%) | 1.62 (98%) | 0.82 |
| 4/0 | 14.19 (207%) | 6.98 (51%) | 4.62 |
| 0/4 | 8.01 (72%) | 5.94 (27%) | 4.66 |

소프트웨어 개발 작업을 흉내 내는 Andrew Benchmark의 전체 실행 시간은 다음과 같다.

| 구성 | 설명 | 실행 시간 (s) |
| --- | --- | --- |
| `BFS-strict` | BFS 그대로 | 64.48 |
| `BFS-nr` | BFS에서 복제만 뺀 구성 | 51.07 |
| `NFS-std` | 운영 체제에 포함된 표준 NFS 구현 | 62.52 |

- BFS는 표준 NFS보다 3% 느리다. 논문이 내세우는 수치다.
- BFS는 복제를 뺀 구성보다 26% 느리다. 복제 자체의 비용은 이 수치가 보여 준다.
- 측정은 View Change가 없는 Normal Case만 다룬다. 논문 시점의 라이브러리는 View Change와 메시지 재전송을 구현하지 않았다.

### 4.2 특징

| 특징 | 설명 |
| --- | --- |
| Safety와 시간 가정의 분리 | 메시지 지연이나 순서 뒤바뀜이 있어도 Safety가 유지된다. 시간 가정은 Liveness에만 쓴다. |
| 최소 Replica 수 | 3f+1개는 Asynchronous 시스템에서 Safety와 Liveness를 함께 제공하는 데 필요한 최소 수다. f = 1을 견디는 데 4개면 된다. |
| 번복되지 않는 결정 | Non-faulty Replica가 실행한 요청의 순서는 View Change 뒤에도 유지된다. 블록체인에 적용하면 확정된 블록이 되돌려지지 않는 Finality(최종성)에 해당한다. |
| 낮은 암호 비용 | Normal Case에서 공개 키 서명 대신 MAC을 쓴다. |
| 장기 운영을 위한 장치 | Checkpoint와 Garbage Collection으로 로그 크기를 제한하고, View Change로 Primary를 교체하며, 뒤처진 Replica는 다른 Replica에게서 상태를 받아 따라잡는다. |

### 4.3 한계

| 한계 | 설명 |
| --- | --- |
| 메시지 수 | Prepare와 Commit 단계에서 모든 Replica가 서로 메시지를 보낸다. 프로토콜 규칙대로 세면 요청 하나에 `PRE-PREPARE` N-1개, `PREPARE` (N-1)×(N-1)개, `COMMIT` N×(N-1)개다. Replica 수의 제곱에 비례해 늘어난다. |
| 고정된 Replica 집합 | 모든 Replica가 서로의 공개 키를 아는 고정된 구성을 가정한다. 참여자가 자유롭게 들어오고 나가는 Permissionless 환경에는 그대로 적용할 수 없다. |
| Liveness의 조건 | Liveness는 약한 Synchrony 가정에 의존한다. 메시지 지연이 계속 커지는 동안에는 진행이 보장되지 않는다. Liveness를 포기한 것은 아니다. |
| 장애 독립성 가정 | 같은 소프트웨어 오류가 모든 Replica에서 일어나면 막지 못한다. |
| 정보 보호 | Faulty Replica가 정보를 유출하는 것은 막지 않는다. |
| Faulty Client | 권한이 있는 Client가 잘못된 데이터를 쓰는 것은 막지 못한다. 접근 권한 관리로 피해를 제한할 뿐이다. |
| 구현과 측정의 범위 | View Change와 재전송이 구현되지 않았고, View Change의 비용은 측정되지 않았다. |

논문이 순서를 정하는 대상은 블록이 아니라 Client의 요청이다. 블록체인에서는 요청 묶음이 블록에, Sequence Number가 블록 높이에 대응한다고 볼 수 있다. Tendermint나 IBFT처럼 PBFT를 바탕으로 한 블록체인 프로토콜은 블록 단위로 합의한다.
