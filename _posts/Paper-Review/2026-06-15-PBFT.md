Practical Byzantine Fault Tolerance(PBFT)는 이 논문이 제안한 합의 알고리즘의 이름이기도 하다. 논문의 핵심은 다음과 같다.

| 질문 | 내용 |
| --- | --- |
| 무엇을 | Replica(복제본) 3f+1개 중 최대 f개가 임의로 잘못 동작해도, 나머지 Replica가 Client(클라이언트)의 요청을 같은 순서로 실행하게 한다. |
| 왜 | 임의로 잘못 동작하는 노드를 견디는 기존 기법은 실제로 쓰기에 너무 느리거나, 메시지 지연에 상한이 있다는 가정에 의존했다. 이 가정에 의존하면 메시지를 지연시키는 공격만으로 Safety(안전성)가 깨진다. |
| 어떻게 | 순서를 제안하는 Replica 하나(Primary)가 요청에 번호를 붙이고, 세 단계(Pre-prepare, Prepare, Commit)에 걸쳐 Replica 2f+1개의 동의를 모아 순서를 확정한다. Primary에 문제가 생기면 다른 Replica로 교체한다(View Change). 평소에는 공개 키 서명 대신 Message Authentication Code(메시지 인증 코드, MAC)를 써서 비용을 낮춘다. |

## Consensus Algorithm

Consensus Algorithm(합의 알고리즘)은 중앙 관리자가 없는 분산 시스템에서 여러 노드가 같은 값 또는 같은 명령 순서에 대해 일관된 결론에 도달하게 하는 프로토콜이다. 네트워크 지연, 메시지 손실, 노드 장애, 일부 참여자의 악의적 행동이 있어도 이 결론은 유지되어야 한다.

분산 시스템은 데이터를 여러 노드에 복제해 저장한다. 그래서 어떤 값을 정본으로 볼지, 어떤 연산을 먼저 반영할지, 어떤 결과를 최종 상태로 확정할지를 정해야 한다. 노드가 하나뿐이면 이런 문제는 없다. 대신 그 노드에 장애가 나면 시스템 전체가 멈춘다. 이런 지점을 Single Point of Failure(단일 장애점)라고 한다. 복제는 이 약점을 없애지만, 노드 사이의 상태 불일치를 조정하는 장치를 새로 요구한다. Consensus Algorithm이 그 장치다.

블록체인에서는 이 요구가 더 중요하다. 각 노드는 원장을 독립적으로 저장하고 검증하며, 네트워크 지연 때문에 같은 트랜잭션을 서로 다른 순서로 받을 수 있다. 같은 자산을 쓰는 상충하는 두 트랜잭션이 거의 동시에 전파되면 노드마다 먼저 본 트랜잭션이 다를 수 있다. 합의가 없으면 노드마다 다른 트랜잭션을 유효하다고 판단해 원장이 갈라지고, Double Spending(이중 지불)으로 이어진다.

이 문제를 다루는 일반적인 틀이 State Machine Replication(상태 기계 복제)이다. 서비스를 State Machine(상태 기계)으로 보고 그 사본을 여러 노드에 둔다. 모든 사본이 같은 상태에서 시작해 같은 명령을 같은 순서로 실행하면 같은 상태에 도달한다. 여기에는 두 가지 조건이 필요하다.

- 사본은 Deterministic(결정적)이어야 한다. 같은 상태에서 같은 명령을 실행하면 항상 같은 결과가 나와야 한다.
- 모든 사본이 같은 명령 순서에 합의해야 한다.

두 번째 조건이 합의의 핵심이다. 필요한 순서는 Total Order(전체 순서)다. Total Order는 임의의 두 명령에 대해 어느 쪽이 먼저인지 정해진 순서다. 일부 쌍에 대해서만 선후가 정해진 순서는 Partial Order(부분 순서)라고 한다.

Consensus Algorithm의 정확성은 두 가지 성질로 설명한다.

- **Safety(안전성)**: 서로 다른 정상 노드가 상충하는 결정을 내리지 않는다. 한 번 확정된 값은 이후에 바뀌지 않는다.
- **Liveness(진행성)**: 유효한 요청은 결국 확정된다. "정해진 시간 안에"가 아니라 "결국"이다.

장애가 있어도 두 성질을 유지하는 능력을 Fault Tolerance(장애 허용)라고 한다. 장애는 두 종류로 나눈다.

- **Crash Fault**: 노드가 멈추거나 응답하지 않는다.
- **Byzantine Fault(비잔틴 장애)**: 노드가 임의로 동작한다. 멈추는 것, 틀린 값을 보내는 것, 상대마다 다른 값을 보내는 것을 모두 포함한다.

Byzantine Fault라는 이름은 Lamport, Shostak, Pease가 1982년에 발표한 Byzantine Generals Problem(비잔틴 장군 문제)에서 왔다.

장애가 Crash Fault뿐이어도 합의에는 근본적인 한계가 있다. FLP Impossibility는 Fischer, Lynch, Paterson이 1985년에 증명한 결과다. Asynchronous(비동기) 시스템에서는 Faulty(장애가 있는) 프로세스가 하나만 있어도 합의의 종료를 보장하는 Deterministic 프로토콜이 없다. 실제 프로토콜은 다음 둘 중 하나로 이 한계를 피한다.

- 네트워크의 시간에 대한 가정을 더한다. Partial Synchrony(부분 동기)와 Timeout이 여기에 해당한다. PBFT가 택한 방법이다.
- Randomization(무작위화)을 써서 Deterministic이라는 조건을 포기한다.

### 합의 알고리즘의 분류

**1. Crash Fault Tolerant (CFT)**

노드가 멈추는 장애는 있지만 악의적인 행동은 없다고 가정한다. 참여 노드가 미리 정해진 환경에서 분산 데이터베이스나 클러스터 관리 시스템의 기반으로 쓴다.

- **Paxos**: Leslie Lamport가 제안한 프로토콜이다. 과반수의 동의로 값이나 명령 순서를 정한다.
- **Raft**: Paxos와 같은 결과를 내면서 이해하기 쉽도록 설계한 프로토콜이다. Leader Election(리더 선출), Log Replication(로그 복제), Safety를 나누어 설명한다. etcd, Consul 등이 쓴다.
- **Zab (ZooKeeper Atomic Broadcast)**: Apache ZooKeeper가 쓰는 Leader 기반 프로토콜이다.

Two-Phase Commit(2PC)과 Three-Phase Commit(3PC)은 함께 언급되지만 성격이 다르다. 둘은 분산 트랜잭션을 모든 참여자가 함께 반영하거나 함께 취소하게 하는 Atomic Commit(원자적 커밋) 프로토콜이다. 2PC는 Coordinator(조정자)에 장애가 나면 참여자가 결정을 내리지 못하고 멈추는 Blocking 문제가 있다. 3PC는 Pre-commit 단계를 더해 이 문제를 줄이지만, Synchronous(동기) 네트워크이고 Network Partition(네트워크 분할)이 없다는 가정이 필요하다.

**2. Byzantine Fault Tolerant (BFT)**

노드가 임의로 동작하는 Byzantine Fault가 있어도 합의를 유지한다.

- **PBFT**: 이 글의 주제다. Pre-prepare, Prepare, Commit 세 단계로 합의한다. Byzantine 노드 f개를 견디는 데 3f+1개의 노드가 필요하다.
- **Tendermint**: PBFT를 블록체인에 맞게 바꾼 프로토콜이다. Propose, Prevote, Precommit 단계를 거쳐 블록을 확정하며, 확정된 블록은 되돌릴 수 없다. Cosmos 생태계에서 쓴다. 구현체의 현재 이름은 CometBFT다.
- **HotStuff**: 2018년에 VMware Research 등의 연구진이 제안했다. View Change에 드는 통신량을 노드 수에 비례하는 수준으로 줄였고, 여러 단계를 겹쳐 처리하는 Pipelining을 도입했다. DiemBFT와 AptosBFT가 이를 바탕으로 한다.
- **Istanbul Byzantine Fault Tolerance (IBFT)**: PBFT에서 파생된 프로토콜이다. Hyperledger Besu와 Quorum에 구현되어 있다.

**3. Permissionless 환경의 합의**

퍼블릭 블록체인에서는 참여자가 자유롭게 들어오고 나간다. 노드 집합이 고정되어 있다고 가정하는 BFT 프로토콜을 그대로 쓰기 어렵다. 한 참여자가 여러 신원을 만드는 Sybil Attack(시빌 공격)도 막아야 한다. 그래서 자원을 기준으로 참여 권한을 정한다.

- **Proof of Work (PoW)**: 계산 자원으로 블록 생성 권한을 얻는다. Bitcoin이 대표적이다. 노드는 누적 작업량이 가장 큰 체인을 따른다. 흔히 Longest Chain Rule이라고 부르지만 기준은 블록 수가 아니라 누적 작업량이다.
- **Proof of Stake (PoS)**: 예치한 Stake(지분)를 기준으로 Validator(검증자)를 정한다. Ethereum이 쓴다.
- **Delegated Proof of Stake (DPoS)**: 토큰 보유자가 투표로 소수의 Validator를 뽑고, 뽑힌 Validator가 블록을 만든다.

Proof of Authority(PoA)는 신원이 확인된 소수의 Validator만 블록을 만드는 방식이다. Permissionless가 아니라 참여자가 서로를 아는 Permissioned 환경에서 쓴다. IBFT가 이 계열에 속한다.

## Network Model

Consensus Algorithm은 네트워크가 시간에 대해 무엇을 보장하는지에 따라 설계가 달라진다. Network Model(네트워크 모델)은 메시지 전달 시간과 노드의 처리 시간에 상한이 있는지, 그 값을 아는지로 나눈다.

| 모델 | 시간 상한 | Timeout 설정 |
| --- | --- | --- |
| Synchronous(동기) | 상한이 있고 그 값을 안다. | 상한 값으로 정하면 된다. |
| Asynchronous(비동기) | 상한이 없다. | 맞는 값이 없다. 느린 노드와 멈춘 노드를 구별할 수 없다. |
| Partially Synchronous(부분 동기) | 상한이 있지만 그 값을 모르거나, 값은 알지만 언제부터 성립하는지 모른다. | 처음에는 맞는 값을 모르지만, Timeout을 계속 늘려 가면 언젠가 상한보다 커진다. |

### Synchronous Network

모든 메시지는 알려진 최대 시간 안에 전달되고 노드의 계산도 알려진 시간 안에 끝난다. 정해진 시간 안에 응답이 없으면 그 노드에 장애가 났다고 판단할 수 있어 프로토콜 설계가 단순하다. 그러나 실제 인터넷에서는 혼잡, 장애, 운영 체제의 스케줄링 때문에 이 상한을 항상 지키기 어렵다. 가정이 깨지면 이 가정에 의존한 프로토콜의 정확성도 깨질 수 있다.

### Asynchronous Network

메시지가 언제 전달될지, 노드가 언제 계산을 끝낼지 보장이 없다. 응답이 늦는 이유가 네트워크 지연인지 노드 장애인지 구별할 수 없다. 가장 약한 가정이라 현실에 가장 넓게 맞지만, FLP Impossibility가 적용된다. Safety는 지킬 수 있어도 모든 실행에서 합의의 종료를 보장할 수는 없다.

### Partially Synchronous Network

Dwork, Lynch, Stockmeyer가 1988년에 정의한 모델이고 두 형태가 있다. 첫째는 상한이 항상 있지만 그 값을 모르는 형태다. 둘째는 상한 값은 알지만 그 상한이 알 수 없는 시점부터 성립하는 형태다. 이 시점을 Global Stabilization Time(GST)이라고 한다.

이 모델을 가정한 프로토콜은 보통 Safety를 네트워크 상태와 무관하게 지키고, Liveness는 네트워크가 안정된 뒤에 보장하도록 설계한다. 네트워크가 불안정한 동안에는 합의가 늦어질 수 있지만 서로 모순된 결정은 나오지 않는다.

## PBFT (Practical Byzantine Fault Tolerance)

PBFT는 Byzantine Fault를 견디는 State Machine Replication 알고리즘이다. 논문 제목의 Practical은 실제 시스템에서 쓸 수 있다는 뜻이다. 논문은 그 근거로 두 가지를 든다. 인터넷 같은 Asynchronous 환경에서 올바르게 동작하고, 이전 알고리즘보다 응답 시간을 10배 이상 줄이는 Optimization(최적화)을 담았다. 이를 확인하려고 PBFT로 Network File System(네트워크 파일 시스템, NFS) 서비스를 만들었고, 복제하지 않은 표준 NFS보다 3% 느린 결과를 얻었다.

논문이 밝힌 기여는 네 가지다.

1. Asynchronous 네트워크에서 Byzantine Fault를 올바르게 견디는 State Machine Replication 프로토콜. 논문은 이것이 처음이라고 밝힌다.
2. 알고리즘을 실제 시스템에서 쓸 수 있게 하는 여러 Optimization
3. Byzantine Fault를 견디는 분산 파일 시스템의 구현
4. 복제에 드는 비용을 수치로 보인 실험 결과

### 기존 BFT 연구의 한계

논문은 Byzantine Fault Tolerance가 점점 중요해진다고 본다. 산업과 정부가 온라인 서비스에 의존할수록 공격의 동기와 피해가 커지고, 소프트웨어가 커지고 복잡해질수록 오류도 늘어난다. 악의적 공격과 소프트웨어 오류는 둘 다 노드를 임의로 동작하게 만든다.

Byzantine Fault를 견디는 합의와 복제 기법은 이전에도 많이 연구되었다. 논문은 그 대부분이 두 부류에 속한다고 정리한다.

- **너무 느리다.** 이론적으로 가능하다는 것을 보이는 데 목적이 있어 실제로 쓰기 어려웠다.
- **Synchrony(동기성)에 의존한다.** 메시지 지연과 처리 속도에 알려진 상한이 있다고 가정했다.

논문과 가장 가까운 시스템은 Rampart와 SecureRing이다. 둘은 실용을 목표로 설계되었지만 올바른 동작이 Synchrony 가정에 달려 있다.

- **Replica를 그룹에서 제외해야 진행한다.** Faulty Primary를 바꾸거나 오래된 데이터를 정리하려면 Faulty Replica를 그룹에서 빼야 한다. 누가 Faulty인지는 Failure Detector(장애 감지기)로 판단한다.
- **Failure Detector는 Asynchronous 시스템에서 정확할 수 없다.** 느릴 뿐인 Non-faulty(장애가 없는) Replica를 Faulty로 잘못 분류할 수 있다. 정확성은 그룹의 1/3 미만만 Faulty라는 조건에 기대므로, Non-faulty Replica가 하나 잘못 제외되면 정확성이 깨질 수 있다.
- **공격 경로가 생긴다.** 공격자는 Replica 하나를 장악하되 겉으로 드러나게 행동하지 않는다. 그리고 Non-faulty Replica나 그 통신을 늦춰 충분히 많은 Replica가 제외되게 만든다. 논문은 이런 Denial of Service(서비스 거부) 공격이 노드를 장악하는 것보다 대체로 쉽다고 본다.
- **감지를 늦추면 진행이 멈춘다.** 잘못 분류할 확률을 낮추려면 Failure Detector가 판단을 오래 미뤄야 한다. 그러면 Primary가 실제로 멈췄을 때 그 시간 동안 Client 요청을 처리하지 못한다.
- **공개 키 암호가 병목이다.** Rampart에서는 공개 키 암호가 지연 시간과 처리량의 주된 병목으로 지적되었다.

PBFT는 이 문제들에 다음과 같이 답한다.

- Safety가 Synchrony에 의존하지 않으므로 지연 공격으로 Safety가 깨지지 않는다.
- Replica를 그룹에서 제외하지 않는다. Primary만 바꾼다.
- 공개 키 암호는 장애가 있을 때만 쓰고, 평소에는 MAC을 쓴다.
- Read-only(읽기 전용) 연산은 메시지 왕복 1번, Read-write(읽기 쓰기) 연산은 2번으로 처리한다.

### 시스템 모델

논문이 두는 가정은 다음과 같다.

- **네트워크**: 노드들이 네트워크로 연결된 Asynchronous 분산 시스템이다. 네트워크는 메시지를 전달하지 못하거나, 지연시키거나, 중복시키거나, 순서를 바꿔 전달할 수 있다.
- **장애**: Byzantine Fault Model을 쓴다. 노드 장애는 서로 독립이라고 가정한다. 공격 상황에서도 이 가정이 성립하려면 노드마다 서비스 코드와 운영 체제의 구현이 달라야 하고, 루트 비밀번호와 관리자도 달라야 한다. 논문은 그 방법으로 같은 코드에서 서로 다른 구현을 만드는 기법, 여러 운영 체제 공급사의 제품을 쓰는 것, 서로 다른 팀이 따로 구현하는 N-version Programming을 든다.
- **암호 기법**: 메시지 위조와 재전송 공격을 막고 손상된 메시지를 찾기 위해 공개 키 서명, MAC, 충돌 저항 해시 함수로 만든 Digest를 쓴다. 모든 Replica는 서로의 공개 키를 안다.
- **공격자**: Faulty 노드들을 조율하고, 통신을 지연시키고, Non-faulty 노드를 지연시킬 수 있다. 다만 Non-faulty 노드를 무한정 지연시키지는 못한다. 또 계산 능력에 한계가 있어 Non-faulty 노드의 서명을 위조하거나, Digest에서 원래 정보를 계산하거나, Digest가 같은 두 메시지를 찾지 못한다.

표기는 두 가지를 쓴다. `⟨m⟩σi`는 노드 i가 서명한 메시지 m이고, `D(m)`은 m의 Digest다. 서명은 메시지 전체가 아니라 Digest에 하고, 서명을 메시지 원문 뒤에 붙인다.

Non-faulty는 알고리즘을 따르고, 공격자가 그 서명을 위조할 수 없는 Client나 Replica를 뜻한다. 이 조건을 벗어나면 모두 Faulty다. 따라서 멈춘 노드, 응답하지 않는 노드, 틀린 값을 보내는 노드, 상대마다 다른 값을 보내는 노드가 모두 Faulty에 들어간다.

### Safety와 Liveness의 조건

PBFT는 임의의 Deterministic 서비스를 복제하는 데 쓸 수 있다. 연산은 단순한 읽기와 쓰기에 한정되지 않고, 상태와 인자를 써서 임의의 Deterministic 계산을 할 수 있다. Client는 요청을 보내고 응답이 올 때까지 기다린다.

| 성질 | 의미 | 필요한 조건 |
| --- | --- | --- |
| Safety | 복제된 서비스가 Linearizability(선형화 가능성)를 만족한다. 연산을 한 번에 하나씩 원자적으로 실행하는 단일 서버처럼 동작한다는 뜻이다. | Faulty Replica가 ⌊(N-1)/3⌋개 이하. 시간 가정은 필요 없다. |
| Liveness | Client가 요청에 대한 응답을 결국 받는다. | Faulty Replica가 ⌊(N-1)/3⌋개 이하이고, 메시지 지연이 끝없이 빠르게 늘지 않는다. |

N은 전체 Replica 수다. 각 조건의 의미는 다음과 같다.

- **Safety에 Faulty Replica 수의 상한이 필요한 이유**: Faulty Replica는 임의로 동작하므로 자신의 상태를 망가뜨릴 수도 있다.
- **Faulty Client와의 관계**: Safety는 Faulty Client가 몇이든, 그 Client가 Faulty Replica와 공모하든 성립한다. Faulty Client가 수행한 연산도 Non-faulty Client에게는 일관되게 보인다. 서비스 연산이 상태의 Invariant(불변 조건)를 지키도록 설계되어 있으면 Faulty Client도 그 Invariant를 깨지 못한다.
- **Safety만으로 막지 못하는 것**: 권한이 있는 Faulty Client가 공유 파일에 쓸모없는 데이터를 쓰는 것은 Safety 위반이 아니다. 논문은 Client를 인증하고 권한이 없는 요청을 거부하는 Access Control(접근 제어)로 피해를 제한한다. 권한을 회수하는 연산의 결과도 모든 Client에게 일관되게 보이므로, Faulty Client의 공격에서 회복하는 수단이 된다.
- **Liveness가 시간 가정에 의존하는 이유**: Safety가 Synchrony에 의존하지 않으므로 Liveness는 Synchrony에 의존해야 한다. 그렇지 않으면 Asynchronous 시스템에서 합의를 구현한 셈이 되어 FLP Impossibility와 어긋난다.
- **Liveness의 시간 가정**: `delay(t)`가 t보다 끝없이 빠르게 늘어나지 않는다고 가정한다. `delay(t)`는 메시지를 시각 t에 처음 보낸 때부터 수신자가 받을 때까지 걸린 시간이다. 송신자는 메시지가 도착할 때까지 재전송한다고 본다. 논문은 이를 "약한 Synchrony 가정"이라고 부르며, 네트워크 장애가 결국 복구된다면 실제 시스템에서 성립할 가능성이 높다고 설명한다.

논문은 Partial Synchrony라는 용어를 쓰지 않는다. 후속 문헌은 PBFT를 "Safety는 Asynchronous 모델에서, Liveness는 Partially Synchronous 모델에서 보장한다"고 요약한다. 따라서 "PBFT는 부분 동기 네트워크를 가정한다"는 말은 Liveness에 한해서만 맞다.

### 장애 허용 한계

PBFT는 Faulty Replica f개를 견디는 데 N = 3f+1개의 Replica를 쓴다. 논문은 이 수가 Asynchronous 시스템에서 Safety와 Liveness를 함께 제공하는 최소 수라고 밝히고, 증명은 Bracha와 Toueg의 1985년 논문을 가리킨다. 논문의 설명은 최악의 상황을 가정한다.

| 항목 | 개수 |
| --- | --- |
| 전체 Faulty Replica | 최대 f개 |
| 응답하지 않는 Replica | f개. Faulty일 수도 있고, 느릴 뿐인 Non-faulty일 수도 있다. |
| 응답한 Replica | N - f개 |
| 응답한 Replica 중 Faulty | 최대 f개. 응답하지 않은 f개가 모두 Non-faulty인 경우다. |
| 응답한 Replica 중 Non-faulty | 최소 N - 2f개 |

f개가 응답하지 않아도 진행하려면 N - f개의 응답만으로 결정해야 한다. 그 안에서 Non-faulty의 응답이 Faulty의 응답보다 많아야 한다.

```text
Non-faulty 응답 수 > Faulty 응답 수
(N - f) - f > f
N > 3f
N ≥ 3f + 1
```

| Replica 수 N | 견디는 장애 수 f | Quorum 크기 2f+1 |
| --- | --- | --- |
| 4 | 1 | 3 |
| 7 | 2 | 5 |
| 10 | 3 | 7 |

- N을 3f+1보다 늘려도 다음 3f+1에 닿기 전까지는 f가 늘지 않는다. N이 5나 6이어도 f는 1이다. 논문은 이런 추가 Replica가 메시지를 많고 크게 만들어 성능만 떨어뜨린다고 적는다. 그래서 알고리즘은 N = 3f+1을 가정한다.
- 멈춘 Replica도 Faulty다. f는 악의적인 Replica와 멈춘 Replica를 합친 수의 상한이다.

### 노드 구성

Replica는 0부터 N-1까지 번호가 붙는다. Replica들은 View라는 구성을 차례로 거친다. View에는 0부터 연속된 번호 v가 붙는다.

- **Primary**: 한 View에서 요청의 순서를 제안하는 Replica다. View 번호가 v이면 번호가 `v mod N`인 Replica가 Primary다.
- **Backup**: 그 View에서 Primary가 아닌 나머지 Replica다.

Primary는 투표로 뽑지 않는다. Primary에 문제가 있어 보이면 View 번호를 1 올리고, 그 번호에 해당하는 Replica가 다음 Primary가 된다. Viewstamped Replication과 Paxos도 View와 Primary를 쓰는 비슷한 방식으로 장애를 견디지만, 둘은 악의 없는 장애만 다룬다.

각 Replica는 세 가지를 유지한다.

- 서비스 상태
- 받아들인 메시지를 저장하는 로그(Message Log)
- 현재 View 번호

Primary는 요청마다 Sequence Number(순서 번호) n을 붙인다. 요청은 이 번호 순서로 실행된다. 메시지 m의 Digest는 d 또는 D(m)으로 쓴다.

알고리즘의 큰 흐름은 다음과 같다.

1. Client가 Primary에 요청을 보낸다.
2. Primary가 요청에 Sequence Number를 붙여 Backup들에 보낸다.
3. Replica들이 요청을 실행하고 Client에 응답한다.
4. Client는 서로 다른 Replica f+1개에게서 같은 결과를 받으면 그 결과를 받아들인다.

### 합의 과정

2번 단계는 다시 Pre-prepare, Prepare, Commit 세 단계로 이루어진다. 논문은 이를 Three-phase Protocol이라고 부르고, 단계마다 맡은 역할을 다음과 같이 나눈다.

| 단계 조합 | 보장하는 것 |
| --- | --- |
| Pre-prepare와 Prepare | 같은 View 안에서 요청의 Total Order. 순서를 제안하는 Primary가 Faulty여도 성립한다. |
| Prepare와 Commit | Commit된 요청의 Total Order가 View가 바뀌어도 유지된다. |

아래 그림은 Primary에 문제가 없을 때(Normal Case)의 메시지 흐름이다. Replica는 4개(f = 1), View는 0이다. Replica 0이 Primary이고, Replica 3은 Faulty여서 아무것도 보내지 않는다.

![PBFT Normal Case의 메시지 흐름, Replica 4개](pbft-normal-case.png)

1. **Request**

    Client c는 연산 o의 실행을 요청하는 메시지를 Primary에 보낸다.

    ```text
    ⟨REQUEST, o, t, c⟩σc

    - o: 실행할 연산
    - t: Timestamp(시각 표시)
    - c: Client 식별자
    ```

    t는 요청이 정확히 한 번만 실행되게 하는 데 쓴다. 같은 Client의 요청은 나중 것일수록 t가 크다. 예를 들어 요청을 보낼 때 Client의 로컬 시계 값을 쓸 수 있다.

    Replica가 Client에 보내는 메시지에는 현재 View 번호가 들어 있다. Client는 이 번호로 현재 Primary가 누구인지 추적하고, 그 Replica에 요청을 보낸다. 논문은 Client가 요청 하나가 끝난 뒤에 다음 요청을 보낸다고 가정한다.

2. **Pre-prepare**

    Primary p는 요청 m에 Sequence Number n을 붙이고, 모든 Backup에 다음 메시지를 Multicast(여러 수신자에게 함께 전송)한 뒤 자신의 로그에 추가한다.

    ```text
    ⟨⟨PRE-PREPARE, v, n, d⟩σp, m⟩

    - v: 메시지를 보내는 View의 번호
    - n: Sequence Number
    - d: 요청 m의 Digest
    - m: Client의 요청 원문
    ```

    서명되는 부분에는 요청 원문이 아니라 Digest만 들어간다. 논문이 드는 이유는 두 가지다.

    - `PRE-PREPARE`는 View Change 때 "요청이 View v에서 n번을 받았다"는 증거로 쓰이므로 작아야 한다.
    - 순서를 정하는 프로토콜과 요청 원문을 전달하는 방법을 분리할 수 있다. 작은 프로토콜 메시지와 큰 요청에 각각 맞는 전송 방식을 쓸 수 있다.

    Primary는 진행 중인 요청 수가 정해진 최대값을 넘지 않으면 바로 이 단계를 시작한다. 넘으면 요청을 버퍼에 모아 두었다가 나중에 묶어서 보낸다. 부하가 클 때 메시지 수와 CPU 부담을 줄이기 위한 것으로, 트랜잭션 시스템의 Group Commit과 비슷하다.

    Backup은 다음 네 조건을 모두 만족할 때만 `PRE-PREPARE`를 받아들인다.

    - 요청과 `PRE-PREPARE`의 서명이 올바르고, d가 m의 Digest다.
    - 자신이 View v에 있다.
    - 같은 v, 같은 n에 대해 Digest가 다른 `PRE-PREPARE`를 받아들인 적이 없다.
    - n이 Low Water Mark h와 High Water Mark H 사이에 있다. 이 범위는 Checkpoint와 함께 설명한다.

    마지막 조건은 Faulty Primary가 아주 큰 번호를 골라 Sequence Number 공간을 소진시키는 것을 막는다.

3. **Prepare**

    `PRE-PREPARE`를 받아들인 Backup i는 다른 모든 Replica에 `PREPARE`를 Multicast하고, 두 메시지를 로그에 추가한다. 받아들이지 않으면 아무것도 하지 않는다. Primary는 `PREPARE`를 보내지 않는다.

    ```text
    ⟨PREPARE, v, n, d, i⟩σi

    - i: 메시지를 보낸 Replica의 번호
    ```

    Primary를 포함한 모든 Replica는 서명이 올바르고, v가 자신의 현재 View와 같고, n이 h와 H 사이에 있으면 `PREPARE`를 받아들여 로그에 추가한다.

    Replica i의 로그에 다음이 모두 있으면 `prepared(m, v, n, i)`가 참이 된다.

    - 요청 m
    - View v에서 m에 n번을 붙인 `PRE-PREPARE`
    - 그 `PRE-PREPARE`와 일치하는 `PREPARE` 2f개. 서로 다른 Backup이 보낸 것이어야 한다.

    "일치한다"는 v, n, Digest가 같다는 뜻이다. Primary의 `PRE-PREPARE`와 Backup 2f개의 `PREPARE`를 합치면, Replica 2f+1개가 같은 요청과 같은 순서에 동의한 것이다. 이 메시지 묶음을 Prepared Certificate라고 부르기도 하지만 이 논문에는 그 용어가 나오지 않는다.

    Pre-prepare와 Prepare 단계는 다음 Invariant를 보장한다. `prepared(m, v, n, i)`가 참이면, Digest가 다른 어떤 요청 m′에 대해서도 `prepared(m′, v, n, j)`는 어떤 Non-faulty Replica j에서도 거짓이다. j가 i 자신이어도 마찬가지다. 즉 한 View 안에서 한 Sequence Number에 `prepared`가 될 수 있는 요청은 하나뿐이다.

4. **Commit**

    `prepared(m, v, n, i)`가 참이 되면 Replica i는 다른 Replica들에 `COMMIT`을 Multicast한다. `COMMIT`을 받아들이는 조건은 `PREPARE`와 같다.

    ```text
    ⟨COMMIT, v, n, D(m), i⟩σi
    ```

    논문은 두 조건을 정의한다.

    - `committed(m, v, n)`: Non-faulty Replica f+1개로 이루어진 어떤 집합이 있고, 그 집합의 모든 Replica에서 `prepared(m, v, n, i)`가 참이다. 여러 Replica에 걸친 조건이다.
    - `committed-local(m, v, n, i)`: `prepared(m, v, n, i)`가 참이고, i가 그 `PRE-PREPARE`와 일치하는 `COMMIT` 2f+1개를 서로 다른 Replica에게서 받아들였다. 자신의 `COMMIT`도 센다. Replica 하나의 로그에 대한 조건이다.

    Commit 단계는 다음 Invariant를 보장한다. 어떤 Non-faulty Replica i에서 `committed-local(m, v, n, i)`가 참이면 `committed(m, v, n)`도 참이다. 이 Invariant와 View Change 프로토콜이 함께 다음을 보장한다.

    - Non-faulty Replica들은 서로 다른 View에서 `committed-local`이 되더라도, `committed-local`이 된 요청의 Sequence Number에 합의한다.
    - Non-faulty Replica 하나에서 `committed-local`이 된 요청은 결국 Non-faulty Replica f+1개 이상에서 Commit된다.

    Replica i는 `committed-local(m, v, n, i)`가 참이고, n보다 작은 번호의 요청을 모두 순서대로 실행했을 때 m을 실행한다. 그래서 모든 Non-faulty Replica가 같은 순서로 요청을 실행한다.

    PBFT는 메시지가 보낸 순서대로 도착한다고 가정하지 않는다. 그래서 뒤 번호의 요청이 먼저 `committed-local`이 될 수 있다. Replica는 세 종류의 메시지를 요청이 실행될 때까지 로그에 두므로 문제가 없다.

5. **Reply**

    요청을 실행한 Replica i는 결과 r을 Client에 직접 보낸다.

    ```text
    ⟨REPLY, v, t, c, i, r⟩σi

    - v: 현재 View 번호
    - t: 대응하는 요청의 Timestamp
    - r: 실행 결과
    ```

    Client는 서명이 유효하고 t와 r이 같은 응답을 서로 다른 Replica f+1개에게서 받으면 r을 결과로 받아들인다. Faulty Replica는 최대 f개이므로 f+1개 중 적어도 하나는 Non-faulty이기 때문이다.

    Replica는 Client마다 마지막으로 보낸 응답을 기억한다. 그 응답의 Timestamp보다 작은 Timestamp를 가진 요청은 버린다. 이렇게 해서 요청이 정확히 한 번만 실행된다.

    응답이 제때 오지 않으면 Client는 요청을 모든 Replica에 보낸다.

    - 이미 실행한 Replica는 기억해 둔 응답을 다시 보낸다.
    - 아직 실행하지 않았고 Primary가 아닌 Replica는 요청을 Primary에 전달한다.
    - Primary가 그 요청을 Backup들에 보내지 않으면, 충분히 많은 Replica가 Primary를 의심하게 되어 View Change가 일어난다.

그림의 경우를 따라가 보면 다음과 같다.

1. Client가 Replica 0에 `REQUEST`를 보낸다.
2. Replica 0이 Replica 1, 2, 3에 `PRE-PREPARE`를 보낸다.
3. Replica 1과 2가 다른 모든 Replica에 `PREPARE`를 보낸다. Replica 3은 보내지 않는다.
    - Replica 1의 로그에는 `PRE-PREPARE`, 자신의 `PREPARE`, Replica 2의 `PREPARE`가 있다. `PREPARE`가 2개이므로 `prepared`가 참이다. Replica 2도 마찬가지다.
    - Replica 0은 Replica 1과 2의 `PREPARE`를 받아 `prepared`가 참이 된다.
4. Replica 0, 1, 2가 `COMMIT`을 보낸다. 각자 자신의 것을 포함해 `COMMIT` 3개를 갖게 되어 `committed-local`이 참이 되고, 요청을 실행한다.
5. Replica 0, 1, 2가 Client에 `REPLY`를 보낸다. Client는 같은 결과의 `REPLY` 2개를 받으면 결과를 받아들인다.

Replica 3이 아무것도 보내지 않아도 요청은 처리된다. 다만 이 경우 `PREPARE` 2개와 `COMMIT` 3개는 필요한 수와 정확히 같다. Non-faulty Replica 하나의 메시지가 늦어지면 그 메시지가 도착할 때까지 해당 조건은 참이 되지 않는다.

### 정족수(Quorum)

PBFT의 Safety는 크기가 2f+1인 Quorum에 기반한다.

| 단계 | 수행 내용 | 모으는 메시지 | 의미 |
| --- | --- | --- | --- |
| Pre-prepare | Primary가 `PRE-PREPARE` 전송 | 없음 | 요청과 순서의 제안 |
| Prepare | Backup이 검증 후 `PREPARE` 전송 | `PREPARE` 2f개. Primary의 `PRE-PREPARE`와 합쳐 2f+1개 | 같은 View, 같은 번호에 요청이 하나만 선택됨 (`prepared`) |
| Commit | `prepared`가 된 Replica가 `COMMIT` 전송 | `COMMIT` 2f+1개 | View Change 뒤에도 결정이 유지됨 (`committed-local`) |
| Reply | 실행한 Replica가 `REPLY` 전송 | Client가 `REPLY` f+1개 | 적어도 하나는 Non-faulty의 결과 |
| Checkpoint | 상태의 Digest를 담은 `CHECKPOINT` 전송 | `CHECKPOINT` 2f+1개 | 상태가 올바르다는 증거 |
| View Change | 새 Primary가 `NEW-VIEW` 전송 | 다른 Replica의 `VIEW-CHANGE` 2f개. 자신의 것과 합쳐 2f+1개 | 새 View 시작 |

### Q. 왜 2f+1개의 메시지를 모으는가

2f+1개 안에는 Faulty Replica가 최대 f개 들어 있을 수 있다. 나머지 f+1개 이상은 Non-faulty의 메시지다.

이 수가 중요한 이유는 서로 다른 두 요청에 대해 각각 2f+1개의 동의가 만들어질 수 없기 때문이다. 두 Quorum을 Q1, Q2라고 하자.

```text
Q1의 크기 = Q2의 크기 = 2f + 1
전체 Replica 수 = 3f + 1
Q1과 Q2가 공유하는 Replica 수 ≥ (2f + 1) + (2f + 1) - (3f + 1) = f + 1
```

두 Quorum은 Replica를 f+1개 이상 공유한다. Faulty Replica는 최대 f개이므로 공유된 Replica 중 적어도 하나는 Non-faulty다.

논문은 Prepare 단계의 Invariant를 이 성질로 보인다.

1. `prepared(m, v, n, i)`가 참이면 Replica 2f+1개가 View v, Sequence Number n에 대해 m의 `PRE-PREPARE` 또는 `PREPARE`를 보냈다. 그중 Non-faulty는 적어도 f+1개다.
2. Digest가 다른 m′도 같은 v, n에서 `prepared`가 되려면, 1번의 Non-faulty Replica 중 적어도 하나가 m′에 대한 메시지도 보냈어야 한다.
3. 그 Replica는 같은 v, n에 대해 Digest가 다른 `PREPARE` 두 개를 보낸 셈이다. Primary라면 `PRE-PREPARE` 두 개다. Non-faulty Replica는 그렇게 하지 않으므로 모순이다.
4. Digest가 같은데 원문이 다른 두 요청은 공격자가 찾을 수 없다고 가정했으므로, 그런 경우의 확률은 무시할 수 있다.

2f+1은 다음 두 조건을 함께 만족하는 크기다.

1. 두 Quorum이 Non-faulty Replica를 하나 이상 공유한다. 2f+1보다 작으면 이 보장이 없다.
2. Faulty Replica f개가 응답하지 않아도 모을 수 있다. Non-faulty Replica는 2f+1개뿐일 수 있으므로 이보다 크면 모을 수 없다.

**예시: Faulty Primary가 Backup마다 다른 요청을 보낼 때.** Replica 4개, f = 1, View 0이다. Primary인 Replica 0이 Faulty다. Replica 0은 같은 Sequence Number 1에 대해 Replica 1에는 요청 A를, Replica 2와 3에는 요청 B를 `PRE-PREPARE`로 보낸다.

| Replica | 받은 `PRE-PREPARE` | 로그의 일치하는 `PREPARE` | `prepared` |
| --- | --- | --- | --- |
| 1 | A | A에 대해 1개 (자신) | 거짓. 2개가 필요하다. |
| 2 | B | B에 대해 2개 (자신, Replica 3) | 참 |
| 3 | B | B에 대해 2개 (자신, Replica 2) | 참 |

- A는 어디서도 `prepared`가 되지 못한다. Replica 2와 3은 같은 View, 같은 번호에 이미 B의 `PRE-PREPARE`를 받아들였으므로 A에 `PREPARE`를 보내지 않는다.
- B는 Replica 2와 3에서 `prepared`가 된다. 실행하려면 `COMMIT` 3개가 필요한데 Non-faulty Replica가 보내는 것은 2개다. Replica 0이 B의 `COMMIT`을 보내면 B가 1번으로 실행되고, 보내지 않으면 아무것도 실행되지 않은 채 Timer가 만료되어 View Change로 넘어간다.
- 어느 경우에도 1번으로 A를 실행하는 Non-faulty Replica는 없다.

### Checkpoint와 Garbage Collection

로그를 끝없이 쌓을 수는 없으므로 오래된 메시지는 버려야 한다. 이를 Garbage Collection(불필요한 데이터 정리)이라고 한다. 다만 아무 때나 버릴 수는 없다. 어떤 요청의 메시지는 두 가지가 성립할 때까지 로그에 남아야 한다.

- 그 요청이 Non-faulty Replica f+1개 이상에서 실행되었다.
- 그 사실을 View Change 때 다른 Replica에 증명할 수 있다.

또 어떤 Replica가 모든 Non-faulty Replica가 이미 버린 메시지를 놓쳤다면, 상태의 전부나 일부를 받아서 따라잡아야 한다. 그래서 받은 상태가 올바르다는 증거도 필요하다.

요청마다 증거를 만들면 비용이 크다. 그래서 주기적으로 만든다.

- **Checkpoint**: Sequence Number가 어떤 상수의 배수인 요청을 실행한 직후의 상태. 논문은 상수의 예로 100을 든다.
- **Stable Checkpoint**: 올바르다는 증거를 갖춘 Checkpoint.

증거는 다음 절차로 만들어진다.

1. Replica i는 Checkpoint를 만들면 다른 Replica들에 `⟨CHECKPOINT, n, d, i⟩σi`를 Multicast한다. n은 상태에 반영된 마지막 요청의 Sequence Number이고, d는 상태의 Digest다.
2. 각 Replica는 `CHECKPOINT`를 로그에 모은다. n과 d가 같고 서로 다른 Replica가 서명한 메시지가 2f+1개 모이면, 이 2f+1개가 그 Checkpoint의 증거다. 자신의 메시지도 센다.
3. Checkpoint가 Stable이 되면 Replica는 번호가 n 이하인 `PRE-PREPARE`, `PREPARE`, `COMMIT`을 로그에서 버린다. 그 이전의 Checkpoint와 `CHECKPOINT` 메시지도 버린다.

Replica는 서비스 상태의 논리적 사본을 여러 개 유지한다. 마지막 Stable Checkpoint, 아직 Stable이 아닌 Checkpoint 0개 이상, 현재 상태다. 상태의 Digest는 증분 방식으로 계산하고 증거는 드물게 만들기 때문에 비용이 크지 않다.

Checkpoint는 Replica가 받아들이는 Sequence Number의 범위도 정한다.

| 이름 | 값 |
| --- | --- |
| Low Water Mark h | 마지막 Stable Checkpoint의 Sequence Number |
| High Water Mark H | h + k |

k는 Checkpoint가 Stable이 되기를 기다리느라 Replica가 멈추는 일이 없을 만큼 커야 한다. 논문은 Checkpoint 간격이 100이면 k를 200으로 둘 수 있다고 예를 든다.

### View Change

Primary가 Faulty이면 요청이 실행되지 않는다. View Change는 Primary를 바꿔 합의가 계속되게 한다. PBFT의 Liveness를 제공하는 장치다.

1. **Timeout 발생**

    Backup이 유효한 요청을 받았는데 아직 실행하지 않았으면 그 요청을 "기다리는" 상태라고 한다. Backup은 요청을 받았을 때 Timer(타이머)가 돌고 있지 않으면 Timer를 시작한다. 그 요청을 더 기다리지 않게 되면 Timer를 멈추고, 그 시점에 실행을 기다리는 다른 요청이 있으면 다시 시작한다.

    Timer가 감시하는 것은 특정 메시지의 도착이 아니라 요청의 실행이다. 그래서 다음 경우가 모두 Timeout으로 드러난다.

    - Primary가 `PRE-PREPARE`를 보내지 않는 경우
    - Primary가 Backup마다 다른 요청을 보내 `prepared`가 되지 않는 경우
    - `COMMIT`이 모이지 않아 `committed-local`이 되지 않는 경우

2. **VIEW-CHANGE 전송**

    View v에서 Timer가 만료된 Backup i는 View v+1로 가는 View Change를 시작한다. 이때부터 `CHECKPOINT`, `VIEW-CHANGE`, `NEW-VIEW` 외의 메시지는 받아들이지 않고, 다음 메시지를 모든 Replica에 Multicast한다.

    ```text
    ⟨VIEW-CHANGE, v+1, n, C, P, i⟩σi
    ```

    | 필드 | 내용 |
    | --- | --- |
    | n | i가 아는 마지막 Stable Checkpoint s의 Sequence Number |
    | C | s가 올바름을 증명하는 유효한 `CHECKPOINT` 2f+1개 |
    | P | i에서 `prepared`가 된 요청 중 번호가 n보다 큰 요청마다 하나씩 넣는 묶음 Pm의 집합 |

    묶음 Pm 하나는 유효한 `PRE-PREPARE` 1개와, 서로 다른 Backup이 서명한 일치하는 `PREPARE` 2f개다. `PRE-PREPARE`에 붙어 있던 요청 원문은 넣지 않는다. Pm은 `prepared` 조건을 이루는 메시지 그대로다.

3. **NEW-VIEW 생성**

    View v+1의 Primary p는 다른 Replica에게서 View v+1에 대한 유효한 `VIEW-CHANGE` 2f개를 받으면 다음 메시지를 다른 모든 Replica에 Multicast한다.

    ```text
    ⟨NEW-VIEW, v+1, V, O⟩σp

    - V: p가 받은 유효한 VIEW-CHANGE들과 p 자신의 VIEW-CHANGE
    - O: 새 View에서 다시 진행할 PRE-PREPARE들 (요청 원문은 넣지 않는다)
    ```

    O는 다음과 같이 계산한다.

    1. V에서 두 값을 정한다. `min-s`는 V에 있는 가장 최근 Stable Checkpoint의 Sequence Number다. `max-s`는 V에 있는 `PREPARE`의 Sequence Number 중 가장 큰 값이다.
    2. `min-s`와 `max-s` 사이의 각 번호 n에 대해 View v+1의 `PRE-PREPARE`를 하나씩 만든다.
        - V의 어떤 `VIEW-CHANGE`의 P에 n번에 대한 묶음이 있으면 `⟨PRE-PREPARE, v+1, n, d⟩σp`를 만든다. d는 V 안에서 n번에 대한 `PRE-PREPARE` 중 View 번호가 가장 높은 것의 Digest다.
        - 그런 묶음이 없으면 Null 요청의 Digest로 `PRE-PREPARE`를 만든다. Null 요청은 다른 요청처럼 세 단계를 거치지만 실행해도 아무 일도 하지 않는다. 번호의 빈자리를 메우는 데 쓴다.

    Primary는 O의 메시지를 로그에 추가한다. `min-s`가 자신의 마지막 Stable Checkpoint보다 크면, `min-s` Checkpoint의 증거를 로그에 넣고 그 이전 정보를 버린다. 그런 뒤 View v+1에 들어가고, 이때부터 View v+1의 메시지를 받아들인다.

4. **새 View 시작**

    Backup은 다음을 모두 만족하면 `NEW-VIEW`를 받아들인다.

    - 서명이 올바르다.
    - 담긴 `VIEW-CHANGE`들이 View v+1에 대해 유효하다.
    - O가 올바르다. Backup은 V로 O를 직접 다시 계산해 비교한다.

    받아들이면 새 정보를 로그에 추가하고, O의 각 `PRE-PREPARE`에 대해 `PREPARE`를 Multicast한 뒤 View v+1에 들어간다. 이후는 Normal Case대로 진행한다. `min-s`와 `max-s` 사이의 요청은 세 단계를 다시 거치지만, 이미 실행한 Client 요청은 다시 실행하지 않는다. Client마다 저장해 둔 마지막 응답 정보로 구분한다.

`NEW-VIEW`에는 요청 원문과 Checkpoint 상태가 들어 있지 않다. 이를 갖고 있지 않은 Replica는 다른 Replica에게서 받는다. 예를 들어 Checkpoint 상태 s는 V에서 s의 `CHECKPOINT`를 보낸 Replica 2f+1개 중 하나에게서 받을 수 있다. 그중 f+1개는 Non-faulty이므로 s나 그 이후의 증명된 Stable Checkpoint를 항상 얻을 수 있다. Checkpoint 전체를 보내지 않으려면 상태를 여러 부분으로 나누고, 부분마다 마지막으로 그 부분을 바꾼 요청의 번호를 기록해 둔다. 그러면 뒤처진 부분만 보내면 된다.

**예시: 새 Primary가 다른 요청을 끼워 넣으려 할 때.** Replica 4개, f = 1이다. View 5의 Primary는 Replica 1이다(`5 mod 4 = 1`). View 5에서 요청 A가 3번으로 Replica 0과 3에서 `prepared`가 되었다. 그 뒤 View 6으로 가는 View Change가 시작된다. View 6의 Primary는 Replica 2이고(`6 mod 4 = 2`) Faulty다.

1. Replica 2가 `NEW-VIEW`를 만들려면 다른 Replica의 `VIEW-CHANGE` 2개가 필요하다. Replica 0, 1, 3 중 어떤 둘을 골라도 Replica 0이나 3이 들어간다.
2. 따라서 V에는 "3번은 A"라는 묶음이 반드시 들어 있다. `VIEW-CHANGE`는 보낸 Replica가 서명하므로 Replica 2가 내용을 고칠 수 없다.
3. Replica 2가 O의 3번에 B를 넣어 `NEW-VIEW`를 보낸다.
4. Backup들은 V로 O를 직접 계산한다. 3번의 Digest는 A의 것이어야 하는데 B의 것이므로 `NEW-VIEW`를 받아들이지 않는다.
5. 유효한 `NEW-VIEW`를 받지 못한 Replica들은 View 6에 들어가지 않고, 대기 Timer가 만료되면 View 7로 가는 View Change를 시작한다.

A가 Replica 0 하나에서만 `prepared`였다면 결과가 다르다. Replica 2가 Replica 1과 3의 `VIEW-CHANGE`를 고르면 V에 A의 묶음이 없고, 3번에 Null 요청이 들어간다. 이것은 규칙 위반이 아니다. `prepared`가 한 곳뿐이면 `COMMIT`이 3개 모일 수 없으므로 A는 어디서도 Commit되지 않았다. View Change가 보존하는 것은 `prepared`된 모든 요청이 아니라 Commit된 요청이다.

### Q. 왜 Prepare와 Commit, 두 단계를 거치는가

두 단계는 서로 다른 것을 보장한다.

**Prepare 단계: 같은 View 안에서 요청의 유일성**

`prepared`는 한 View의 한 Sequence Number에 대해 요청이 하나만 선택되었음을 보장한다. 그러나 `prepared`만으로는 요청을 실행할 수 없다. `prepared`는 Replica 하나의 로그에 대한 조건이다. 한 Replica에서 참이어도 다른 Non-faulty Replica들은 아직 참이 아닐 수 있다. 이 상태에서 View Change가 일어나면 새 Primary가 모은 `VIEW-CHANGE` 어디에도 그 요청의 묶음이 없을 수 있다.

**Commit 단계: View가 바뀌어도 유지되는 결정**

`committed-local`이 되려면 `COMMIT`이 2f+1개 필요하다. Non-faulty Replica는 `prepared`가 참일 때만 `COMMIT`을 보낸다. 따라서 2f+1개 중 f+1개 이상은 `prepared` 상태인 Non-faulty Replica가 보낸 것이다. 새 Primary가 모으는 `VIEW-CHANGE` 2f+1개의 어떤 묶음도 이 f+1개 중 적어도 하나를 포함한다. 그 Replica의 `VIEW-CHANGE`가 요청의 묶음을 새 View로 전달한다.

- **Prepare가 없으면**: 같은 번호에 서로 다른 요청이 선택될 수 있다.
- **Commit이 없으면**: 한 Replica가 실행한 요청이 View Change 뒤에 다른 요청으로 바뀔 수 있다. 같은 번호에 Replica마다 다른 요청을 실행하게 된다.

Prepare는 "어떤 요청을 선택할 것인가"를 정하고, Commit은 "그 선택이 이후에도 유지되는가"를 보장한다.

#### Commit 단계가 없을 때 생기는 상황 예시

Commit 단계가 없고, Replica가 `prepared`가 되면 곧바로 요청을 실행한다고 가정한다. Replica 4개, f = 1, View 1이다. Primary는 Replica 1이고(`1 mod 4 = 1`) Faulty다.

1. Replica 1이 요청 m에 7번을 붙여 `PRE-PREPARE`를 보낸다. Replica 0과 3에는 도착하고 Replica 2에는 지연된다.
2. Replica 0과 3이 `PREPARE`를 보낸다. Replica 3은 Replica 0의 `PREPARE`를 받는다. Replica 0은 Replica 3의 `PREPARE`를 아직 받지 못했다.
3. Replica 3은 `PREPARE`가 2개라 `prepared`가 참이다. Replica 0은 1개라 거짓이다.
4. 가정대로 Replica 3은 m을 7번으로 실행한다.
5. Replica 0은 요청을 실행하지 못한 채 Timer가 만료된다. Replica 2도 Client가 다시 보낸 요청을 받고 기다리다 Timer가 만료된다. 둘은 View 2로 가는 View Change를 시작한다. View 2의 Primary는 Replica 2다(`2 mod 4 = 2`).
6. Faulty인 Replica 1도 `VIEW-CHANGE`를 보낸다. Replica 2는 Replica 0과 1의 `VIEW-CHANGE`에 자신의 것을 더해 `NEW-VIEW`를 만든다. Replica 0은 `prepared`가 아니었고, Replica 1은 Faulty라 묶음을 넣지 않고, Replica 2는 `PRE-PREPARE`를 받지 못했다. 세 메시지 어디에도 "7번은 m"이라는 묶음이 없다.
7. Replica 2는 7번을 다른 요청 m′에 붙일 수 있다. 그러면 Replica 0과 2는 m′을 7번으로 실행하게 된다.

Replica 3은 7번으로 m을, Replica 0과 2는 m′을 실행했다. Non-faulty Replica끼리 순서가 달라져 Safety가 깨진다.

Commit 단계가 있으면 Replica 3은 `COMMIT`을 3개 모을 때까지 실행하지 않는다. 위 상황에서 `COMMIT`을 보낼 수 있는 것은 Replica 3 자신과 Faulty인 Replica 1뿐이라 최대 2개다. Replica 3은 실행하지 못하고 불일치도 생기지 않는다. 반대로 `COMMIT`이 3개 모였다면 Non-faulty Replica 2개 이상이 `prepared` 상태다. `NEW-VIEW`에는 Replica 4개 중 3개의 `VIEW-CHANGE`가 들어가므로 그 둘 중 하나는 반드시 포함된다. 새 Primary는 7번에 m을 다시 제안해야 한다.

### Safety와 Liveness가 보장되는 이유

논문은 증명의 개요를 싣고, 전체 증명은 I/O Automaton 모델로 쓴 별도 기술 문서에 있다고 밝힌다.

**Safety.** 보여야 할 것은 모든 Non-faulty Replica가 `committed-local`이 되는 요청의 Sequence Number에 합의한다는 것이다.

같은 View 안에서는 Prepare 단계의 Invariant로 충분하다. 한 View의 한 번호에서 `prepared`가 될 수 있는 요청은 하나이고, `committed-local`은 `prepared`를 전제로 한다.

View가 바뀌는 경우는 다음과 같다. 요청 m이 View v에서 n번으로 어떤 Non-faulty Replica에서 `committed-local`이 되었다고 하자.

1. `committed(m, v, n)`이 참이다. 즉 Non-faulty Replica f+1개 이상으로 이루어진 집합 R1이 있고, R1의 모든 Replica에서 m이 n번으로 `prepared` 상태다.
2. Non-faulty Replica는 View v′(v′ > v)의 `NEW-VIEW`를 받기 전에는 View v′의 `PRE-PREPARE`를 받아들이지 않는다. `NEW-VIEW`를 받아야 그 View에 들어가기 때문이다.
3. 올바른 `NEW-VIEW`에는 Replica 2f+1개로 이루어진 집합 R2의 올바른 `VIEW-CHANGE`가 들어 있다.
4. Replica는 3f+1개이므로 R1과 R2는 Non-faulty Replica k를 적어도 하나 공유한다.
5. k의 `VIEW-CHANGE`가 "m이 n번으로 `prepared`되었다"는 사실을 다음 View로 전달한다.

그 뒤는 두 경우로 나뉜다.

| 경우 | 새 View에서 일어나는 일 |
| --- | --- |
| 일반적인 경우 | m에 대해 같은 번호 n, 새 View 번호로 세 단계를 다시 수행한다. 그래서 이전 View에서 n번을 받았던 다른 요청은 결코 Commit되지 않는다. |
| `NEW-VIEW`에 n보다 큰 번호의 Stable Checkpoint를 담은 `VIEW-CHANGE`가 있는 경우 | 새 View의 어떤 Replica도 n보다 낮은 번호의 메시지를 받아들이지 않는다. Low Water Mark가 그 Checkpoint의 번호로 올라가기 때문이다. n번까지의 실행 결과는 그 Checkpoint 상태에 이미 반영되어 있다. |

어느 경우든 Non-faulty Replica들은 n번으로 `committed-local`이 되는 요청에 합의한다.

**Liveness.** Replica는 요청을 실행할 수 없으면 새 View로 옮겨야 한다. 동시에 Non-faulty Replica 2f+1개 이상이 같은 View에 머무는 시간을 최대한 늘려야 하고, 그 시간이 요청이 실행될 때까지 지수적으로 늘어나야 한다. 논문은 세 가지 장치를 둔다.

1. **View Change를 너무 일찍 시작하지 않는다.** View v+1의 `VIEW-CHANGE`를 보낸 Replica는 View v+1에 대한 `VIEW-CHANGE` 2f+1개를 받을 때까지 기다린 뒤, 시간 T 뒤에 만료되는 Timer를 시작한다. 유효한 `NEW-VIEW`를 받기 전에, 또는 새 View에서 이전에 실행하지 않았던 요청을 실행하기 전에 Timer가 만료되면 View v+2로 가는 View Change를 시작한다. 이번에는 2T를 기다린 뒤에야 View v+3으로 가는 View Change를 시작한다.
2. **View Change를 너무 늦게 시작하지 않는다.** 자신의 현재 View보다 큰 View에 대한 유효한 `VIEW-CHANGE`를 다른 Replica f+1개에게서 받으면, 자신의 Timer가 만료되지 않았어도 그중 가장 작은 View에 대한 `VIEW-CHANGE`를 보낸다.
3. **Faulty Replica가 View Change를 남발하지 못한다.** Faulty Replica가 `VIEW-CHANGE`를 보내는 것만으로는 View Change가 일어나지 않는다. Replica f+1개 이상이 보내야 일어난다. Faulty Replica가 Primary이면 메시지를 보내지 않거나 잘못된 메시지를 보내 View Change를 일으킬 수 있다. 그러나 Primary는 `v mod N`으로 정해지므로 Faulty Primary가 f개를 넘는 연속된 View에 걸쳐 이어질 수는 없다.

논문은 이 세 장치가 Liveness를 보장한다고 적는다. 단, 메시지 지연이 Timeout 길이보다 끝없이 빠르게 늘어나는 경우는 제외한다. 앞에서 본 `delay(t)` 가정이 이 조건에 대응한다.

논문에 나오는 시간 기반 동작을 정리하면 다음과 같다.

| 종류 | 시작하는 때 | 멈추거나 만료될 때 |
| --- | --- | --- |
| 요청 실행을 기다리는 Timer (Backup) | 요청을 받았고 Timer가 돌고 있지 않을 때 | 요청을 더 기다리지 않게 되면 멈추고, 기다리는 다른 요청이 있으면 다시 시작한다. 만료되면 View v+1로 가는 View Change를 시작한다. |
| View Change 완료를 기다리는 Timer | View v+1의 `VIEW-CHANGE`를 보냈고, View v+1에 대한 `VIEW-CHANGE` 2f+1개를 받았을 때. 길이는 T | 만료되면 View v+2로 가는 View Change를 시작한다. 다음 대기 길이는 2T다. |
| Client의 재전송 | 요청을 보냈을 때 | 응답을 제때 받지 못하면 요청을 모든 Replica에 보낸다. |

논문은 T의 초기값이나 구체적인 Timeout 값을 제시하지 않는다.

### Non-determinism 처리

Replica는 Deterministic이어야 하지만 실제 서비스에는 실행할 때마다 달라지는 값이 있다. 논문의 예는 NFS의 파일 수정 시각이다. 이 값은 서버의 시계를 읽어 정하므로 Replica마다 따로 읽으면 상태가 갈라진다. Client는 값을 정할 수 없다. 자신의 요청이 다른 Client의 동시 요청과 어떤 순서로 실행될지 모르기 때문이다. 그래서 Primary가 값을 정한다.

- **Primary가 혼자 정하는 방법**: Primary가 값을 요청에 붙이고, 그 묶음에 대해 세 단계를 진행한다. 그러면 Faulty Primary가 Replica마다 다른 값을 보내 상태를 갈라놓을 수 없다. 다만 Faulty Primary가 모두에게 같은 틀린 값을 보낼 수는 있으므로, Replica는 서비스 상태만으로 그 값이 올바른지 판단하고 틀렸을 때 할 일을 정할 수 있어야 한다.
- **Backup이 값 선택에 참여하는 방법**: 서비스에 따라 Replica가 값 선택에 참여해야 할 때는 단계를 하나 더한다. Primary가 Backup들이 제안한 인증된 값을 모아 그중 2f+1개를 요청에 붙이고 세 단계를 시작한다. Replica는 그 2f+1개 값과 상태로 Deterministic한 계산을 해서 값을 정한다. 예를 들어 중앙값을 쓸 수 있다. Replica 시계가 일정 오차 안에서 동기화되어 있고 "로컬 시계와 충분히 가까운 값"이면 되는 경우에는 이 단계를 생략할 수 있다.

논문의 파일 시스템은 첫 번째 방법을 쓴다. Primary가 수정 시각과 접근 시각을 제안하면, Replica는 제안된 값과 이전 요청들에서 선택된 값의 최대값에 1을 더한 값 중 큰 쪽을 고른다.

### 성능을 만든 핵심 최적화

**통신 줄이기**

| Optimization | 내용 |
| --- | --- |
| 큰 응답 줄이기 | Client가 요청에 결과를 보낼 Replica 하나를 지정한다. 그 Replica만 결과 전체를 보내고 나머지는 결과의 Digest만 보낸다. Client는 Digest로 결과가 맞는지 확인한다. 지정한 Replica에게서 올바른 결과를 받지 못하면 요청을 다시 보내 모든 Replica에게서 결과 전체를 받는다. |
| Tentative Execution(잠정 실행) | Replica는 `prepared`가 참이고, 앞 번호의 요청을 모두 실행했으며, 그 요청들이 모두 Commit된 것으로 알려져 있으면 `COMMIT`을 기다리지 않고 요청을 실행해 잠정 응답을 보낸다. Client는 일치하는 잠정 응답 2f+1개를 받으면 그 요청이 결국 Commit된다고 확신할 수 있다. 받지 못하면 요청을 다시 보내고 일반 응답 f+1개를 기다린다. 요청 하나에 드는 메시지 전달 단계가 5에서 4로 줄어든다. |
| Read-only 요청 | Client가 요청을 모든 Replica에 직접 Multicast한다. Replica는 요청이 올바르게 인증되었는지, Client에게 권한이 있는지, 정말 Read-only인지 확인한 뒤 잠정 상태에서 바로 실행한다. 응답은 그 잠정 상태에 반영된 요청이 모두 Commit된 뒤에 보낸다. Client가 Commit되지 않은 상태를 보지 않게 하기 위해서다. Client는 같은 결과의 응답 2f+1개를 기다린다. 결과에 영향을 주는 쓰기가 동시에 진행되어 2f+1개를 모으지 못하면, 재전송 Timer가 만료된 뒤 일반 Read-write 요청으로 다시 보낸다. |

메시지 전달 단계가 5에서 4로 줄어드는 이유는 다음과 같다. 일반 경로는 `REQUEST`, `PRE-PREPARE`, `PREPARE`, `COMMIT`, `REPLY` 다섯 번의 메시지 전달을 거친다. Tentative Execution은 `COMMIT`을 기다리지 않으므로 네 번이 된다. 이것이 Read-write 연산의 메시지 왕복 2번이다. Read-only 요청은 `REQUEST`와 `REPLY`만 거치므로 왕복 1번이다.

잠정 실행된 요청은 View Change 때 Null 요청으로 대체되어 취소될 수 있다. 이때 Replica는 `NEW-VIEW`의 마지막 Stable Checkpoint와 자신의 마지막 Checkpoint 중 번호가 높은 쪽으로 상태를 되돌린다.

**공개 키 서명 대신 MAC 쓰기**

알고리즘 설명은 모든 메시지에 전자 서명을 쓴다고 가정하지만, 실제 설계에서 전자 서명은 드물게 보내는 `VIEW-CHANGE`와 `NEW-VIEW`에만 쓴다. 나머지 메시지는 MAC으로 인증한다. 이전 시스템의 주된 성능 병목을 없앤 것이다.

| 연산 (200 MHz Pentium Pro) | 시간 |
| --- | --- |
| 1024비트 RSA 서명 생성 | 43 ms |
| 1024비트 RSA 서명 검증 | 0.6 ms |
| 64바이트 메시지의 MAC 계산 | 10.3 μs |

- MAC은 전자 서명보다 세 자릿수 빠르다. 타원 곡선 암호처럼 서명 생성이 더 빠른 공개 키 방식도 있지만 검증이 느리다. PBFT에서는 서명 하나를 여러 번 검증하므로 맞지 않는다.
- 각 노드는 활성 Client를 포함해 Replica마다 16바이트 Session Key(세션 키)를 하나씩 공유한다.
- MAC은 메시지 뒤에 비밀 키를 이어 붙여 MD5를 적용한 값이다. 16바이트 결과 중 하위 10바이트만 쓴다. MAC 크기가 줄고 일부 공격에 대한 내성도 좋아진다. 이 방식은 Secret Suffix Method의 변형이며, MD5가 충돌 저항성을 갖는 한 안전하다.
- `REPLY`는 수신자가 하나이므로 MAC 하나를 붙인다. Client 요청을 포함한 나머지 메시지에는 Authenticator를 붙인다. Authenticator는 송신자를 뺀 Replica마다 MAC을 하나씩 담은 벡터다. 각 MAC은 송신자와 해당 Replica가 공유한 키로 계산한다.
- Authenticator를 검증하는 시간은 일정하고, 만드는 시간은 Replica 수에 비례한다. 메시지에 MD5를 한 번 적용한 중간 결과에서 이어서 각 Session Key에 MD5를 적용하는 방식으로 계산한다. Replica 37개(동시 장애 12개)에서도 1024비트 RSA 서명 생성보다 두 자릿수 이상 빠르다.
- Authenticator의 크기는 30 × ⌊(N-1)/3⌋바이트다. N이 13 이하(동시 장애 4개 이하)이면 1024비트 RSA 서명(128바이트)보다 작다.

MAC에는 근본적인 한계가 있다. 메시지가 진짜임을 제3자에게 증명할 수 없다. PBFT의 기본 알고리즘과 이전 BFT 알고리즘은 이 증명 능력에 기대고 있었다. 논문은 "서로 다른 두 요청이 두 Non-faulty Replica에서 같은 View와 Sequence Number로 `prepared`되지 않는다" 같은 Invariant를 이용해 이 문제를 피하도록 알고리즘을 고쳤다고 밝힌다. 고친 알고리즘의 내용은 별도 기술 문서에 있다.

### 구현: BFS

논문은 알고리즘을 Replication Library로 구현하고, 이 라이브러리로 Byzantine-fault-tolerant File System(BFS)을 만들었다.

**Replication Library**

- Client 쪽 인터페이스는 `invoke` 하나다. 연산 요청을 담은 버퍼를 받아 프로토콜로 실행하고, Replica들의 응답 중 올바른 것을 골라 결과 버퍼를 돌려준다.
- 서버 쪽에서는 서비스가 `execute`, `make_checkpoint`, `delete_checkpoint`, `get_digest`, `get_checkpoint`, `set_checkpoint`를 구현해야 한다. 라이브러리가 이 함수들을 호출한다.
- 노드 사이의 1대1 통신은 UDP로, Replica 그룹에 대한 Multicast는 IP Multicast 위에서 UDP로 구현했다. 서비스마다 모든 Replica를 담은 IP Multicast 그룹이 하나 있다. 이 통신은 메시지를 잃거나, 중복시키거나, 순서를 바꿀 수 있다.
- 알고리즘은 순서가 바뀐 메시지를 견디고 중복 메시지를 거른다. 잃어버린 메시지는 View Change로도 복구할 수 있지만 비용이 커서 재전송이 중요하다. 평소에는 수신자가 복구를 주도한다. 뒤처진 Backup은 Primary에 Negative Acknowledgment(부정 응답)를 보내고, Primary는 긴 Timeout 뒤에 `PRE-PREPARE`를 재전송한다. 응답에는 Stable Checkpoint의 일부와 빠진 메시지가 들어갈 수 있다. View Change 중에는 일치하는 `NEW-VIEW`를 받거나 다음 View로 넘어갈 때까지 `VIEW-CHANGE`를 재전송한다.
- 논문 시점의 라이브러리는 View Change와 재전송을 구현하지 않았다. 논문은 View Change를 일으키는 Timer 조작을 포함한 나머지 알고리즘은 모두 구현했고 알고리즘 전체를 형식화해 증명했으므로, 실험 결과의 정확성에는 영향이 없다고 설명한다.

**BFS 구조**

- 파일 시스템은 일반 NFS처럼 Client 장비에 마운트되고, 애플리케이션은 수정 없이 커널의 NFS Client를 통해 접근한다. 커널 소스가 없어 커널의 NFS Client와 서버는 고치지 않았다.
- Client 장비의 사용자 수준 Relay 프로세스가 NFS 요청을 받아 `invoke`를 호출하고 결과를 NFS Client에 돌려준다.
- 각 Replica는 Replication Library와 NFS V2 서버 `snfsd`를 사용자 수준 프로세스로 실행한다. `snfsd`는 크기가 고정된 메모리 매핑 파일에 Inode, 블록, 빈 블록 목록 같은 파일 시스템 자료 구조를 모두 둔다. 블록 크기는 8KB다.
- NFS V2는 수정한 데이터를 응답 전에 디스크에 쓰는 동기 쓰기를 요구한다. BFS는 이 안정성을 디스크 쓰기 대신 복제로 얻으므로 동기 쓰기를 하지 않는다.

**Checkpoint 관리**

- `snfsd`는 메모리 매핑 파일의 512바이트 블록마다 Copy-on-write(쓸 때 복사) 비트를 하나씩 둔다.
- `make_checkpoint`가 호출되면 모든 비트를 켜고, 현재 Sequence Number, 수정된 블록 목록(처음에는 비어 있음), 상태의 Digest를 담은 Checkpoint 기록을 만든다.
- 요청 실행 중 비트가 켜진 블록을 수정하면, 먼저 그 블록의 현재 내용과 식별자를 마지막 Checkpoint 기록에 저장하고 나서 덮어쓰고 비트를 끈다.
- Checkpoint 기록은 더 나중의 Checkpoint가 Stable이 되어 `delete_checkpoint`가 호출될 때까지 유지한다. 최대 2개의 Checkpoint만 유지하므로 비용이 작다. 실험에서 Checkpoint 기록의 평균 크기는 182블록, 최대 500블록이었다.
- 상태의 Digest는 AdHash라는 증분 해시 함수로 계산한다. 상태를 고정 크기 블록으로 나누고, 블록마다 블록 번호와 블록 값을 이어 붙여 MD5를 적용하고, 그 값들을 모두 더한 뒤 어떤 큰 정수로 나눈 나머지를 상태의 Digest로 쓴다. 블록마다 해시 값을 표에 저장해 두고, Checkpoint를 만들 때 수정된 블록만 새 해시를 더하고 옛 해시를 뺀다.

### 성능 평가

실험은 View Change가 없는 Normal Case만 측정했다. 논문은 시스템 성능을 결정하는 것이 이 경우라고 설명한다.

| 항목 | 값 |
| --- | --- |
| Replica | 4개 (f = 1) |
| Client | 1개, Relay 프로세스 2개 |
| 장비 | DEC 3000/400 Alpha, 133 MHz Alpha 21064, 메모리 128 MB, Digital Unix 4.0 |
| 디스크 | Replica마다 DEC RZ26 |
| 네트워크 | 10 Mbit/s Switched Ethernet, 격리된 네트워크 |
| Checkpoint 간격 | 요청 128개 |
| 받아들이는 최대 Sequence Number | 마지막 Stable Checkpoint의 번호 + 256 |

**Micro-benchmark**

상태가 없고 아무 일도 하지 않는 Null 연산을 호출하는 데 걸리는 시간이다. 복제한 구현과 UDP를 직접 쓰는 복제하지 않은 구현을 비교했다. 연산 10,000번을 세 번 돌려 중앙값을 썼고, 편차는 0.3% 미만이었다. 괄호 안은 복제하지 않은 경우 대비 증가율이다.

| 인자/결과 크기 (KB) | 복제, Read-write (ms) | 복제, Read-only (ms) | 복제 없음 (ms) |
| --- | --- | --- | --- |
| 0/0 | 3.35 (309%) | 1.62 (98%) | 0.82 |
| 4/0 | 14.19 (207%) | 6.98 (51%) | 4.62 |
| 0/4 | 8.01 (72%) | 5.94 (27%) | 4.66 |

- **0/0 Read-write**: 늘어난 2.53 ms는 계산 약 1.06 ms와 통신 1.47 ms로 나뉜다. 계산 중 0.55 ms가 암호 연산이다. 통신이 느는 이유는 메시지 왕복이 한 번 더 있고, 메시지가 크고, 노드마다 받는 메시지가 많기 때문이다.
- **0/0 Read-only**: 늘어난 0.80 ms는 계산 0.43 ms(암호 연산 0.23 ms 포함)와 통신 0.37 ms다. 메시지 왕복이 한 번뿐이라 통신 부담이 작다.
- **4/0과 0/4**: 복제 부담의 상당 부분이 인자와 결과 크기와 무관하므로 상대적 증가율이 낮다. 0/4 Read-write에서는 큰 응답이 네트워크를 한 번만 지난다. 4/0 Read-write에서는 큰 요청이 네트워크를 두 번 지나고, 요청과 `PRE-PREPARE` 모두에 암호 연산이 든다.
- **최악의 경우라는 점**: 연산이 아무 일도 하지 않고 비교 대상이 인증 같은 보장을 제공하지 않으므로, 이 수치는 PBFT에 가장 불리한 비교다. MAC으로 인증하는 복제하지 않은 서비스와 비교하면 증가율은 0/0 Read-write에서 243%, 4/0 Read-only에서 4%다.
- **Rampart와 비교**: Rampart는 10 Mbit/s Ethernet에서 SparcStation 10 네 대로 Null 메시지 Multi-RPC에 45 ms가 걸린다고 보고되었다. 임의의 Client가 연산을 호출하려면 메시지 전달 한 번과 Client 인증을 위한 RSA 서명 생성과 검증이 더 필요해, 최소 65 ms가 걸린다고 논문은 추정한다. 장비 성능 차이(SPECint92 비율 1.7)로 나눠도 PBFT는 0/0 Read-write에서 10배 이상, Read-only에서 20배 이상 빠르다. 직접 측정한 비교가 아니라 보고된 수치에서 추정한 값이다. SecureRing은 공개된 수치가 없다.

**Andrew Benchmark**

Andrew Benchmark는 소프트웨어 개발 작업을 흉내 내는 다섯 단계의 파일 시스템 벤치마크다. 세 구성을 비교했다.

- `BFS-strict`: BFS 그대로
- `BFS-nr`: BFS에서 복제를 뺀 구성. Checkpoint 관리 코드가 없고, 수정한 상태를 디스크에 쓰지 않고 응답하므로 NFS V2 규약을 지키지 않는다.
- `NFS-std`: Digital Unix에 포함된 NFS V2 구현

NFS V2의 연산 18개 중 Read-only는 `getattr` 하나뿐이다. `read`나 `lookup`도 마지막 접근 시각을 바꾸기 때문이다. 그래서 Read-only Optimization을 쓸 일이 거의 없다. 그 효과를 보려고 `lookup`을 Read-only로 바꾼 `BFS-r/o lookup`도 측정했다. 이 구성은 엄밀한 Unix 의미를 어기지만 실제로 문제가 될 가능성은 낮다고 논문은 본다.

| 단계 | 내용 | `BFS-strict` (s) | `BFS-r/o lookup` (s) | `BFS-nr` (s) | `NFS-std` (s) |
| --- | --- | --- | --- | --- | --- |
| 1 | 하위 디렉터리를 재귀적으로 생성 | 0.55 | 0.47 | 0.35 | 1.75 |
| 2 | 소스 트리 복사 | 9.24 | 7.91 | 5.08 | 9.46 |
| 3 | 데이터를 읽지 않고 모든 파일의 상태 확인 | 7.24 | 6.45 | 6.11 | 5.36 |
| 4 | 모든 파일의 데이터를 모두 읽기 | 8.77 | 7.87 | 7.41 | 6.60 |
| 5 | 컴파일과 링크 | 38.68 | 38.38 | 32.12 | 39.35 |
| 합계 | | 64.48 | 61.07 | 51.07 | 62.52 |

10회 평균이며, 전체 시간의 표준 편차는 2.6% 이하였다.

- **복제 자체의 비용**: `BFS-strict`는 `BFS-nr`보다 26% 오래 걸린다. Micro-benchmark보다 낮은 이유는 Client가 연산 사이에 계산하는 시간이 길기 때문이다. 1, 2단계는 그 비율이 약 40%, 3~5단계는 약 70%여서 1, 2단계의 증가율이 더 높다.
- **Read-only Optimization의 효과**: `lookup`을 Read-only로 바꾸면 `BFS-nr` 대비 증가율이 20%로 줄어든다. 1~4단계에서는 `lookup`을 기다리는 시간이 전체의 20% 이상이라 효과가 크고, 5단계에서는 5% 미만이라 효과가 작다.
- **표준 NFS와 비교**: `BFS-strict`는 `NFS-std`보다 3% 오래 걸리고, `BFS-r/o lookup`은 2% 빠르다. BFS는 1, 2, 5단계에서 빠르고 3, 4단계에서 느리다. 1, 2, 5단계에서는 Client 연산의 21~40%가 응답 전에 수정 내용의 안정성을 보장해야 하는 동기 연산이다. `NFS-std`는 이를 디스크 쓰기로, BFS는 더 지연이 짧은 복제로 보장한다. 3, 4단계에는 동기 연산이 없어 `NFS-std`가 빠르다.

### 관련 연구와의 차이

| 대상 | 논문이 든 차이 |
| --- | --- |
| Viewstamped Replication, Paxos | View와 Primary, Backup을 쓰는 구조는 같지만 악의 없는 장애만 견딘다. Byzantine Fault를 견디려면 암호 인증, Pre-prepare 단계, View Change를 일으키고 Primary를 정하는 다른 방법이 필요하다. PBFT는 View Change를 새 Primary를 고르는 데만 쓰고, 두 방식과 달리 Replica 집합을 바꾸지 않는다. |
| Asynchronous Byzantine 합의 알고리즘 | Asynchronous 시스템에서 Byzantine Fault를 견디지만 완전한 State Machine Replication을 제공하지 않고, 대부분 실제로 쓰기에는 너무 느리다. PBFT의 Normal Case는 Bracha와 Toueg의 합의 알고리즘과 비슷하지만, 그 알고리즘은 Primary의 장애를 견디지 못한다. |
| Rampart, SecureRing | State Machine Replication을 구현하지만 PBFT보다 10배 이상 느리고 Synchrony 가정에 의존한다. Faulty Replica를 그룹에서 제외해야 진행할 수 있다. |
| Phalanx | Quorum 복제 기법으로 Asynchronous 시스템에서 Byzantine Fault를 견딘다. 일반적인 State Machine Replication이 아니라 변수 읽기, 쓰기와 잠금을 제공하는 데이터 저장소다. 연산마다 Replica 일부만 처리해 확장성의 여지가 있지만, 장애 f개를 견디는 데 N > 4f+1이 필요하고 Replica마다 상태 전체를 가져야 하며 Replica당 부하는 O(1/√N)으로 천천히 줄어든다. |

### PBFT 특징과 한계

**특징**

| 특징 | 설명 |
| --- | --- |
| Safety와 시간 가정의 분리 | 메시지 지연이나 순서 뒤바뀜이 있어도 Safety가 유지된다. 시간 가정은 Liveness에만 쓴다. |
| Replica를 제외하지 않음 | Primary만 바꾸고 Replica 집합은 유지한다. 느린 Replica를 Faulty로 잘못 제외해 생기는 공격 경로가 없다. |
| 최소 Replica 수 | 3f+1개는 Asynchronous 시스템에서 Safety와 Liveness를 함께 제공하는 데 필요한 최소 수다. f = 1을 견디는 데 4개면 된다. |
| 번복되지 않는 결정 | Commit된 요청의 순서는 View Change 뒤에도 유지된다. 블록체인에 적용하면 확정된 블록이 되돌려지지 않는 Finality(최종성)에 해당한다. |
| 낮은 암호 비용 | 평소에는 공개 키 서명 대신 MAC을 쓴다. |
| 장기 운영을 위한 장치 | Checkpoint와 Garbage Collection으로 로그 크기를 제한하고, View Change로 Primary를 교체하며, 뒤처진 Replica는 다른 Replica에게서 상태를 받아 따라잡는다. |

**한계**

| 한계 | 설명 |
| --- | --- |
| 메시지 수 | Prepare와 Commit 단계에서 모든 Replica가 서로 메시지를 보낸다. 프로토콜 규칙대로 세면 요청 하나에 `PRE-PREPARE` N-1개, `PREPARE` (N-1)×(N-1)개, `COMMIT` N×(N-1)개다. Replica 수의 제곱에 비례해 늘어난다. |
| 고정된 Replica 집합 | 모든 Replica가 서로의 공개 키를 아는 고정된 구성을 가정한다. 참여자가 자유롭게 들어오고 나가는 Permissionless 환경에는 그대로 적용할 수 없다. |
| Liveness의 조건 | Liveness는 약한 Synchrony 가정에 의존한다. 메시지 지연이 계속 커지는 동안에는 진행이 보장되지 않는다. Liveness를 포기한 것은 아니다. |
| 장애 독립성 가정 | 같은 소프트웨어 오류가 모든 Replica에서 일어나면 막지 못한다. Replica마다 독립적으로 일어나는 오류는 가릴 수 있다. 논문은 실험 중 실제로 이런 소프트웨어 버그를 만났지만 알고리즘이 계속 올바르게 동작했다고 밝힌다. |
| 정보 보호 | Faulty Replica가 정보를 유출하는 것은 막지 않는다. 연산이 상태와 인자로 임의의 계산을 하므로 Replica는 정보를 평문으로 가져야 한다. 논문은 Secret Sharing(비밀 분산)을 향후 과제로 든다. |
| Faulty Client | 권한이 있는 Client가 잘못된 데이터를 쓰는 것은 막지 못한다. 접근 권한 관리로 피해를 제한할 뿐이다. |
| 자원 비용 | Replica 3f+1개가 각자 상태 사본을 갖는다. 논문은 f개를 평소에는 참여하지 않고 다른 Replica가 실패할 때만 참여하는 Witness(증인)로 두는 방안과, 상태 사본을 f+1개로 줄이는 방안을 향후 과제로 든다. |
| 구현과 측정의 범위 | View Change와 재전송이 구현되지 않았고, View Change의 비용은 측정되지 않았다. 장애 노드의 복구 방법은 지면 문제로 논문에서 다루지 않는다. |

논문이 순서를 정하는 대상은 블록이 아니라 Client의 요청이다. 블록체인에서는 요청 묶음이 블록에, Sequence Number가 블록 높이에 대응한다고 볼 수 있다. Tendermint나 IBFT처럼 PBFT를 바탕으로 한 블록체인 프로토콜은 블록 단위로 합의한다.
