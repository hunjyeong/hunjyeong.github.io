## BFT SMR

### What is SMR?

SMR(State Machine Replication)은 여러 Node가 같은 초기 State에서 같은 Transaction을 같은 순서로 실행해, 모든 Node가 같은 State를 유지하게 하는 방법이다. Blockchain은 Transaction의 순서를 정해 Ledger에 기록하고 실행하는 SMR로 볼 수 있다.

BFT(Byzantine Fault Tolerance) SMR은 일부 Node가 Byzantine Node여도 올바르게 동작하는 SMR이다. Byzantine Node는 프로토콜을 따르지 않고 임의로 행동할 수 있는 Node이고, 프로토콜을 따르는 Node는 Honest Node라고 한다. 이 글에서 SMR은 BFT SMR을 뜻한다.

- **Safety**: 두 Honest Node가 확정한 Transaction 목록은 같은 위치에 같은 Transaction을 가진다. 즉, 모든 Honest Node가 같은 Prefix의 Ledger를 가진다.

- **Liveness**: Honest Node 하나 이상에 전달된 Transaction은 결국 모든 Honest Node가 확정한다.

- **Security Threshold $f$**: Byzantine Node 비율이 $f$ 이하이면 Safety와 Liveness가 모두 보장된다.

Network Model은 메시지 지연에 대한 가정이다.

- **Synchrony**: 메시지 지연이 항상 알려진 상한 $\Delta$ 이하
- **Asynchrony**: 메시지 지연에 상한이 없음
- **Partial Synchrony**: 언제인지 알 수 없는 GST(Global Stabilization Time) 이후에는 Honest Node 사이의 메시지 지연이 $\Delta$ 이하가 됨. Arete는 이 Network Model을 가정한다.

### Why $f < 1/3$?

Partial Synchrony에서는 응답하지 않는 Node가 일부러 응답하지 않는 Byzantine Node인지, 메시지가 늦게 도착하는 Honest Node인지 구별할 수 없다. 따라서 Node는 모든 Node의 응답을 기다리지 않고, 전체의 $(1 - f)$ 비율로부터 투표를 받으면 다음 단계로 넘어간다. 이렇게 진행에 필요한 최소 응답 집합을 Quorum이라 한다.

- 두 Quorum이 같은 위치에 서로 다른 Block을 확정했다고 하자. 두 Quorum은 최소 $(1 - f) + (1 - f) - 1 = 1 - 2f$ 비율의 Node를 공유한다.

- 공유하는 Node가 모두 Byzantine Node이면, 이들이 두 Block에 모두 투표해 Safety가 깨진다. 이처럼 Byzantine Node가 서로 다른 Node에게 충돌하는 메시지를 보내는 것을 Equivocation이라 한다.

- 공유하는 Node 중 Honest Node가 반드시 있으려면 $1 - 2f > f$, 즉 $f < 1/3$이어야 한다.

**⇒ Synchrony를 가정하지 않는 BFT Consensus는 Byzantine Node가 1/3 미만일 때만 Safety와 Liveness를 보장한다.**

### SMR의 세 가지 작업

SMR은 반복되는 세 가지 작업으로 나눌 수 있다.

- **Data Dissemination**: Client에게 받은 Transaction을 다른 Node에 퍼뜨린다. 목표는 Data Availability로, Block이 확정되면 모든 Honest Node가 그 Block의 온전한 Transaction Data를 얻을 수 있어야 한다.

- **Ordering**: 퍼진 Transaction의 순서를 정해 Ledger에 기록한다. 모든 Honest Node가 같은 순서를 출력해야 한다.

- **Execution**: 정해진 순서대로 Transaction을 실행한다. 실행 결과는 모든 Honest Node에서 같아야 하고, 외부에서 검증할 수 있어야 한다.

### 작업별 Fault Tolerance

Equivocation이 문제가 되는 작업은 Ordering뿐이다. 그래서 세 작업이 견딜 수 있는 Byzantine Node 비율이 다르다.

- **Ordering: $f < 1/3$**
    - 두 Quorum이 공유하는 Node 중에 Honest Node가 있어야 함 (위의 설명과 같음)

- **Data Dissemination: $f < 1/2$**
    - Block을 만든 Node는 Block을 퍼뜨리고, Block을 받았다는 서명을 $(1 - f)$ 비율의 Node로부터 모은다.
    - 이 Quorum에 Honest Node가 하나 이상 있으면, 다른 Honest Node는 그 Node에게서 Block을 받아올 수 있다.
    - $1 - f > f$ → $f < 1/2$

- **Execution: $f < 1/2$**
    - 실행은 Deterministic하다. 같은 State에서 같은 순서로 실행하면 같은 결과가 나오므로, 같은 순서를 받은 Honest Node는 모두 같은 결과를 낸다.
    - 외부 검증자(예: Client)는 $(1 - f)$ 비율의 Node가 서명한 결과를 받으면, 그 안에 Honest Node가 하나 이상 있으므로 결과가 올바르다고 판단할 수 있다.
    - $1 - f > f$ → $f < 1/2$

**⇒ Consensus가 필요한 Ordering만 1/3에 묶이고, Data Dissemination과 Execution은 Byzantine Node가 절반 미만이면 된다. 또한 Ordering은 Block의 Metadata만 다루면 되므로 가볍지만, Data Dissemination과 Execution은 Transaction 원본을 주고받고 실행해야 하므로 대역폭, 연산, 저장 공간을 많이 쓴다.**

### Safety-Liveness Separation

기존 SMR은 하나의 $f$로 Safety와 Liveness를 함께 표현한다. 두 Threshold를 따로 두면, 한쪽을 낮추는 대신 다른 쪽을 높일 수 있다.

- **Safety Threshold $f_S$**: Safety를 보장하는 Byzantine Node 비율의 상한
- **Liveness Threshold $f_L$**: Liveness를 보장하는 Byzantine Node 비율의 상한

Quorum은 $(1 - f_L)$ 비율로 둔다. Byzantine Node가 $f_L$ 이하이면 Honest Node만으로 Quorum을 채울 수 있어 진행이 멈추지 않는다(Liveness). Safety 조건은 작업에 따라 다르다.

- **Ordering**: 두 Quorum이 공유하는 비율 $1 - 2f_L$이 $f_S$보다 커야 함 → $f_S + 2f_L < 1$
- **Data Dissemination, Execution**: Quorum 비율 $1 - f_L$이 $f_S$보다 커야 함 → $f_S + f_L < 1$
- $f_S = f_L = f$로 두면 각각 $f < 1/3$, $f < 1/2$가 되어 앞의 결과와 같다.

예: Data Dissemination에서 $f_S = 57\%$, $f_L = 42\%$이면, Byzantine Node가 42% 이하일 때는 Safety와 Liveness가 모두 유지되고, 42%에서 57% 사이일 때는 Safety는 유지되지만 진행이 멈출 수 있다.

## Blockchain Sharding

### What is Sharding?

Sharding은 전체 Node를 여러 그룹으로 나누고, 각 그룹이 독립적인 SMR로 Transaction을 병렬 처리하게 하는 방법이다. 이 그룹을 Shard라고 하고, Shard 안에서 실행하는 Consensus를 Intra-shard Consensus라고 한다. Node가 늘어날수록 Shard를 더 만들 수 있으므로 Throughput이 늘어난다.

- **Intra-shard Transaction**: 한 Shard의 State만 다루는 Transaction

- **Cross-shard Transaction**: 여러 Shard의 State를 다루는 Transaction

- **Random Assignment**: Node를 무작위로 Shard에 배정한다. 공격자가 원하는 Shard에 Byzantine Node를 모을 수 없게 하기 위함이다.

- **Epoch와 Reconfiguration**: 일정 기간(예: 1,000 Block)을 Epoch라 하고, Epoch가 시작될 때마다 Shard를 다시 구성한다. 공격자가 시간을 들여 특정 Shard의 Node를 장악하는 Adaptive Attack을 막기 위함이다.

Sharding 시스템의 보안 속성은 다음과 같다.

- **Sharding Safety**: 같은 Shard의 두 Honest Node는 같은 Prefix의 Ledger를 가진다. 또한 서로 다른 Shard의 두 Honest Node는 두 Shard에 걸친 모든 Cross-shard Transaction에 대해 같은 확정 순서와 같은 결과(Commit 또는 Abort)를 가진다.

- **Sharding Liveness**: Honest Node에 보낸 Transaction은 관련 Shard에서 결국 확정된다.

## Size-Security Dilemma

### Shard 크기와 안전성

Random Assignment로 Shard를 만들면, 어떤 Shard에는 우연히 Byzantine Node가 $f$ 비율을 넘게 들어갈 수 있다. 이런 Shard는 Safety나 Liveness를 보장하지 못한다.

- **Shard가 작으면**: Shard를 많이 만들 수 있지만, Byzantine Node가 $f$를 넘는 Shard가 생길 확률이 커진다.
- **Shard가 크면**: 안전하지만 Shard를 적게 만든다. 또한 대부분의 BFT Consensus는 통신량이 Node 수의 제곱에 비례하므로 큰 Shard는 느려진다.

이 Trade-off를 **Size-Security Dilemma**라 한다.

### 최소 Shard 크기

전체 Node $n$개 중 $s$ 비율이 Byzantine Node일 때, $m$개 Node를 무작위로 뽑아 Shard를 만든다고 하자. Shard에 들어가는 Byzantine Node 수는 Hypergeometric Distribution(비복원 추출에서 특정 종류가 뽑히는 개수의 분포)을 따른다. Shard의 Byzantine Node가 $f$ 비율을 넘는 사건을 FAU라 하면, 그 확률은 다음과 같다.

$$
\Pr[\text{FAU}] = \sum_{x=\lceil mf \rceil}^{m} \frac{\binom{ns}{x}\binom{n-ns}{m-x}}{\binom{n}{m}}
$$

Security Parameter $\lambda$에 대해 아래 식을 만족하는 가장 작은 $m$을 최소 Shard 크기 $m^{\ast}$라 한다. 만들 수 있는 Shard 수는 $k = \lfloor n / m^{\ast} \rfloor$이다.

$$
\Pr[\text{FAU}] \le 2^{-\lambda}
$$

- 예: $\lambda = 30$이면 안전하지 않은 Shard가 생길 확률이 $2^{-30}$(약 10억분의 1) 이하
- 예: $n = 1000$, $s = 25\%$, $f < 1/3$, $\lambda = 30$이면 $m^{\ast} = 486$ → Shard를 2개만 만들 수 있음

$n$과 $\lambda$가 같다면, $m^{\ast}$를 줄이는 방법은 $s$를 작게 가정하거나 $f$를 키우는 것이다.

**⇒ Shard를 작게 만들려면 Shard가 견딜 수 있는 Byzantine Node 비율 $f$를 높여야 한다. 문제는 Network나 공격자에 대한 가정을 강화하지 않고 $f$를 높이는 것이다.**

## Solution 1: Stronger Assumptions

Shard 크기를 줄이기 위해 가정을 강화하는 방식이다.

- **Omniledger**: Byzantine Node 비율 $s$를 25%로 작게 가정한다. 그래도 $f < 1/3$이므로 $m^{\ast} = 486$이고 Shard는 2개다.

- **RapidChain**: Network가 Synchrony라고 가정하고 Synchrony용 BFT Consensus를 써서 $f$를 49%로 높인다. $s = 33\%$에서 $m^{\ast} = 247$, Shard 4개다.

- **AHL**: Trusted Hardware로 Consensus의 Leader가 Equivocation을 하지 못하게 해 $f$를 49%로 높인다. $s = 30\%$에서 $m^{\ast} = 182$, Shard 5개다.

**한계**

- Internet 위에서 Latency가 낮고 Throughput이 높아야 하는 Blockchain에 Synchrony 가정은 비현실적일 수 있다.
- Trusted Hardware를 신뢰해야 한다는 새 가정이 추가된다.

## Solution 2: Safety-Liveness Separation (GearBox)

**GearBox**는 Shard의 Safety와 Liveness를 분리한다. 최소 Shard 크기를 $f$ 대신 더 큰 $f_S$로 계산해 Shard를 작게 만든다. 새로 만든 Shard는 Safety를 확률적으로 보장하지만, $f_S > f_L$이므로 Byzantine Node가 $f_L$을 넘으면 Liveness가 깨질 수 있다. Liveness가 깨진 Shard는 Node를 더 투입해 복구한다.

Liveness가 깨지는 빈도를 나타내기 위해 Arete 논문은 다음 속성을 정의한다.

- **P-probabilistic Liveness**: 새로 만든 Shard가 Liveness를 보장할 확률(Byzantine Node가 $f_L$ 이하일 확률)이 최소 P

GearBox의 Shard는 여전히 Ordering(Intra-shard Consensus)을 직접 하므로 $f_S + 2f_L < 1$을 따라야 한다.

- $f_S = 57\%$로 높이면 $m^{\ast} = 72$, Shard 13개다. 하지만 $f_L$은 21%까지만 가능하다. 새 Shard의 Liveness 확률은 0.3422로, 약 66%의 Shard가 Liveness를 위반한다.
- Liveness 확률 0.9999를 유지하려면 $f_S$를 35%까지만 높일 수 있다. 이때 $m^{\ast} = 403$, Shard 2개다.

**한계**

- Shard를 작게 만들면 Liveness 위반이 자주 생긴다.
- 복구 비용이 크다. 새로 투입된 Node는 Shard의 State를 동기화해야 하며, 논문은 이 과정이 수 시간, 길게는 수 주가 걸릴 수 있다고 본다. 복구하는 동안 해당 Shard는 Transaction을 처리하지 못한다.

## Solution 3: Decoupling Ordering (RIVET)

**RIVET**은 Shard마다 Ordering을 하지 않는다. 전체 시스템이 하나의 SMR을 구현하고, Reference Shard 하나만 Ordering을 맡는다. Worker Shard는 Data Dissemination과 Execution만 하므로 Byzantine Node를 49%까지 견딘다. $s = 33\%$에서 $m^{\ast} = 247$, Shard 4개다.

**한계**

- Safety-Liveness Separation을 쓰지 않으므로 $f$가 1/2 미만에 머문다.
- Worker Shard마다 Leader 하나가 Block을 만들므로, Transaction 전파가 Leader에 의존해 느려진다.
- Ordering만 분리하고, Data Dissemination과 Execution은 여전히 묶여 순차적으로 진행된다.

**⇒ Ordering을 분리하면 Shard의 Threshold가 1/2까지 올라가고(RIVET), Safety와 Liveness를 분리하면 $f_S$를 더 올릴 수 있다(GearBox). 하지만 GearBox는 Ordering의 $f_S + 2f_L < 1$에 묶여 Liveness 위반과 복구 비용이 크고, RIVET은 Safety-Liveness Separation을 쓰지 않는다. Arete는 두 방법을 결합한다.**

## Solution 4: Arete

**Arete**는 더 강한 가정 없이 Size-Security Dilemma를 풀기 위해 제안된 Blockchain Sharding 프로토콜이다(Zhang et al., 2025). 핵심 관찰은 "개별 Shard가 더 높은 비율의 Byzantine Node를 견디면, 더 작은 Shard를 더 많이 안전하게 만들 수 있다"는 것이다. 이를 위해 SMR 자체를 세 작업으로 분해(Deconstructed SMR)하고, 작업별로 필요한 Threshold와 자원에 맞게 Sharding한다.

Arete는 두 가지 구성 요소로 이루어진다.

1. **Ordering-Processing Sharding**: Ordering은 하나의 Ordering Shard가, Data Dissemination과 Execution은 여러 Processing Shard가 맡는다.
2. **Safety-Liveness Separation**: Processing Shard의 Safety와 Liveness를 분리한다.

이 구조 위에서 Transaction을 처리하는 방식으로 COE(Certify-Order-Execute) Architecture를 제안한다.

논문은 같은 시스템 매개변수, 신뢰 가정, Network 가정에서 얻을 수 있는 최소 Shard 크기라는 의미로 Arete를 Optimal Sharding이라고 부른다.

![Arete Overview](/assets/img/arete/arete-overview.png)

### Building Block 1: Ordering-Processing Sharding

| | Ordering Shard $S_O$ | Processing Shard $S_P^1, \dots, S_P^k$ |
| --- | --- | --- |
| 개수 | 1개 | $k$개 |
| 맡는 작업 | Ordering | Data Dissemination, Execution |
| Consensus | BFT Consensus로 Global Order 결정 | 하지 않음 |
| Threshold | $f_S = f_L < 1/3$ | $f_S + f_L < 1$, $f_S > f_L$ |
| 다루는 Data | 서명된 Digest | Transaction 원본, State |

- **Ordering Shard**: BFT Consensus로 시스템 전체의 Transaction 순서를 정한다. Consensus를 수행하므로 $f < 1/3$을 지켜야 한다. 대신 Transaction 원본을 받지 않고 State도 계산하지 않는다. Processing Shard가 보낸, 서명이 붙은 Digest(Data의 Hash 값)만 다루므로 가볍다.

- **Processing Shard**: Transaction을 퍼뜨리고, Ordering Shard가 정한 순서대로 실행해 자기 Ledger를 유지한다. Consensus를 수행하지 않으므로 Equivocation 문제가 없고, Partial Synchrony에서도 Byzantine Node를 절반 미만까지 견딘다.

Arete는 Ledger 유지와 Transaction 실행은 Sharding하고, Consensus는 Sharding하지 않는다. 전체 시스템은 Ordering Shard가 정한 하나의 Global Order를 따른다.

### Building Block 2: Safety-Liveness Separation

Processing Shard에는 GearBox처럼 Safety-Liveness Separation을 적용한다.

- Processing Shard의 크기는 $f_S$로 계산한다. Byzantine Node가 $f_S$ 이하일 확률이 $1 - 2^{-\lambda}$ 이상이므로 Safety는 확률적으로 보장된다.
- Byzantine Node가 $f_L$을 넘을 수 있으므로 Liveness는 일시적으로 깨질 수 있다.
- Processing Shard는 Ordering을 하지 않으므로 $f_S + f_L < 1$만 지키면 된다. GearBox의 $f_S + 2f_L < 1$보다 $f_L$을 훨씬 크게 둘 수 있다.

예: $n = 1000$, $s = 25\%$, $\lambda = 30$에서 $f_S = 57\%$로 두면 $m^{\ast} = 72$, Shard 13개다. 같은 크기에서 GearBox는 $f_L = 21\%$(Liveness 확률 0.3422)까지만 둘 수 있지만, Arete는 $f_L = 42\%$(Liveness 확률 0.9999)까지 둘 수 있다.

**Liveness가 일시적으로 깨져도 되는 이유**

- 0.9999-probabilistic Liveness는 Shard를 10,000개 만들 때 평균 1개가 Liveness를 위반한다는 뜻이다. 논문은 AWS(Amazon Web Services)가 상업 서비스에 적합하다고 보는 99.99% Availability를 근거로 든다.

- P-probabilistic Liveness는 시스템의 Liveness가 확률 P로만 보장된다는 뜻이 아니다. Liveness가 깨진 Shard는 Reconfiguration으로 복구되므로, 결국 모든 Processing Shard가 Transaction을 처리한다.

- 논문은 P-probabilistic Liveness가 P-probabilistic Availability를 뜻함을 보인다.
    - Reconfiguration 주기를 $T$년, Shard 수를 $k$라 하면, Liveness가 깨진 Shard는 평균 $(1 - P)k$개이고 다음 Reconfiguration까지 $T$년 동안 사용할 수 없다.
    - 이를 Shard 전체로 나누면 한 주기에 $(1 - P)T$년이다. 1년에 주기가 $1/T$번이므로 1년 중 사용할 수 없는 시간의 비율은 $(1 - P)$다.

**Liveness가 깨진 Shard의 복구**

- Ordering Shard는 한 Epoch 동안 어떤 Processing Shard $S_P^{sid}$에서 메시지를 보낸 Node가 $f_S \lvert S_P^{sid} \rvert + 1$개보다 적으면, 그 Shard에 Node를 더 배정한다. Shard가 커지므로 $f_L$은 높아지고 $f_S$는 낮아진다.
- 메시지를 보내는 Node가 충분해질 때까지 반복하고, 다음 Epoch에서는 원래의 최소 크기로 되돌린다.
- 새로 배정된 Node는 그 Shard의 과거 Data를 동기화해야 한다. 이 복구 방식은 GearBox의 Reconfiguration 방식을 따른다.

복구 비용 예시: 논문은 약 450 GB의 Ethereum State를 동기화하는 데 약 12시간이 걸린다고 가정하고, 복구 비용의 기댓값을 다음과 같이 계산한다.

- Arete (Liveness 확률 0.9999): $12 \times 0.0001 = 0.0012$시간
- GearBox (Liveness 확률 0.3422): $12 \times 0.6578 = 7.8936$시간
- → 약 6,578배 차이

### Shard 크기 비교

$n = 1000$, $\lambda = 30$일 때 프로토콜별 Shard 크기와 개수는 다음과 같다.

| Protocol | $s$ | $f_S$ | $f_L$ | $m^{\ast}$ | $k$ | Liveness 확률 | Network |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Omniledger | 25% | 33% | 33% | 486 | 2 | $1 - 2^{-30}$ | Partial Synchrony |
| RapidChain | 33% | 49% | 49% | 247 | 4 | $1 - 2^{-30}$ | Synchrony |
| AHL | 30% | 49% | 49% | 182 | 5 | $1 - 2^{-30}$ | Partial Synchrony, Trusted Hardware |
| RIVET | 33% | 49% | 49% | 247 | 4 | $1 - 2^{-30}$ | Partial Synchrony |
| GearBox | 25% | 35% | 32% | 403 | 2 | 0.9999 | Partial Synchrony |
| GearBox | 25% | 57% | 21% | 72 | 13 | 0.3422 | Partial Synchrony |
| Arete | 30% | 54% | 45% | 125 | 8 | 0.9999 | Partial Synchrony |
| Arete | 25% | 57% | 42% | 72 | 13 | 0.9999 | Partial Synchrony |

표의 Liveness 확률은 논문이 제시한 값이며, Byzantine Node 수가 $\lceil m f_L \rceil$개 이하일 확률로 계산한 값과 일치한다. $m = 72$, $f_L = 42\%$에서는 $\lceil 30.24 \rceil = 31$이고 $31/72 \approx 43.1\%$로 $f_L$을 조금 넘는다. Byzantine Node 비율이 42% 이하(30개 이하)일 확률로 계산하면 Arete는 약 0.9996, GearBox($f_L = 21\%$, 15개 이하)는 약 0.2433이다. 어느 방식이든 Arete의 Liveness 확률이 GearBox보다 훨씬 높다는 결론은 같다.

### Shard 구성

- Permissionless(누구나 참여 가능한) 환경에서 Node는 Sybil Attack(한 주체가 여러 신원을 만들어 영향력을 키우는 공격)에 강한 방식(예: Proof-of-Stake)으로 신원을 얻는다. 모든 Node의 신원은 공개되어 있다고 가정한다.

- 각 Node는 자기 신원과 Randomness를 이어 붙여 Hash 값을 계산한다.

- Hash 값이 큰 순서로 $m^{\#}$개 Node가 Ordering Shard를 구성한다.

- 나머지 Node의 Hash 값을 $[0, 1)$ 구간에 대응시키고, 이 구간을 $k$개로 나눠 각 Node가 속할 Processing Shard를 정한다.

- Ordering Shard는 Safety와 Liveness를 모두 확률적으로 보장해야 하므로 $f = 1/3$으로 크기를 계산한다. 따라서 Ordering Shard가 Processing Shard보다 크다($m^{\#} > m^{\ast}$).

- $k$를 계산할 때 Ordering Shard에 들어간 Node 수는 빼지 않는다. 논문은 실제 Network에서는 $m^{\#}$이 $n$보다 훨씬 작다는 점(예: $n = 100{,}000$, $\lambda = 30$, $s = 25\%$에서 $m^{\#}/n \approx 1\%$)과 Shard Overlap(한 Node가 여러 Shard에 속하는 방식)으로 이를 설명한다.

### COE Architecture

COE Architecture는 SMR의 세 작업에 대응하는 세 단계로 Transaction을 처리한다.

1. **CERTIFY**: 각 Processing Shard가 Transaction을 Shard 안에 퍼뜨리고, Transaction 원본을 가진 Honest Node가 있음을 보이는 Certificate를 만든다. (Data Dissemination)
2. **ORDER**: Ordering Shard가 Certificate의 순서를 Consensus로 정한다. (Ordering)
3. **EXECUTE**: 각 Processing Shard가 정해진 순서대로 Transaction을 실행하고 확정한다. (Execution)

Transaction 원본은 CERTIFY 단계에서만 전파된다. ORDER 단계는 서명된 Digest만 다루고, EXECUTE 단계는 각 Processing Shard 안에서 진행된다. 여러 Processing Shard가 병렬로 CERTIFY와 EXECUTE를 하고, Ordering Shard 하나가 ORDER를 한다.

![COE Architecture](/assets/img/arete/arete-coe.png)

#### Step 1: CERTIFY (Data Dissemination)

Leaderless 방식으로 진행된다. Processing Shard의 모든 Node가 Block을 만들 수 있다.

1. Processing Shard $S_P^{sid}$의 Node $N_j$는 Client에게 직접 받은 Transaction으로 Execution Block(EB)을 만든다. Client가 Transaction을 보낼 Shard는 송신자와 수신자 주소로 정해진다.
    - $EB := \langle itxs, ctxs, sid, j \rangle$
    - $itxs$: Intra-shard Transaction 목록, $ctxs$: Cross-shard Transaction 목록, $sid$: Shard ID, $j$: Node ID

2. $N_j$는 EB에 서명해 Shard 안에 퍼뜨린다.

3. EB를 받은 Node는 CERTIFIED 메시지에 서명해 $N_j$에게 돌려준다. 이 서명은 "EB의 온전한 Data를 받았다"는 뜻이다.
    - CERTIFIED 메시지: EB의 Digest $EB_{dst}$, Cross-shard Transaction의 Metadata $M_{ctxs}$, $sid$

4. $N_j$는 서명을 $f_S \lvert S_P^{sid} \rvert + 1$개 이상 모으면 Certificate Block(CB)을 만들어 Ordering Shard에 보낸다.
    - $CB := \langle EB_{dst}, M_{ctxs}, sid, \sigma_{set}^P \rangle$
    - $\sigma_{set}^P$: 모은 서명 집합

**Data Availability**

- Processing Shard의 Byzantine Node는 $f_S \lvert S_P^{sid} \rvert$개 이하이므로, $f_S \lvert S_P^{sid} \rvert + 1$개 서명 중 최소 하나는 Honest Node의 서명이다.
- 그 Honest Node는 EB 원본을 가지고 있으므로, 다른 Honest Node는 그 Node에게서 EB를 받아올 수 있다.
- → Ordering Shard는 EB 원본 대신 크기가 작은 CB로 순서를 정해도 된다.

**Liveness**

- Byzantine Node가 $f_L$ 이하이면 Honest Node는 $(1 - f_L)\lvert S_P^{sid} \rvert$개 이상이다. $f_S + f_L < 1$이므로 Honest Node만으로 Quorum을 채울 수 있다.

#### Step 2: ORDER (Ordering)

Ordering Shard는 Consensus Round마다 Ordering Block(OB)을 하나 만들고 확정한다. Arete는 특정 Consensus 프로토콜에 의존하지 않으며, 구현에서는 BFT Consensus 프로토콜인 HotStuff의 변형을 사용한다.

1. Ordering Shard는 받은 CB의 서명이 $f_S \lvert S_P^{sid} \rvert + 1$개 이상인지 검증하고, 유효한 CB를 cbpool에 저장한다.

2. Round $r$의 Leader는 cbpool에서 CB들을 골라 순서를 정한다. CB 안의 Transaction 순서는 그대로 두고, CB 순서대로 이어 붙여 Global Order를 만든다.

3. Leader는 Cross-shard Transaction의 실행 결과를 모은 Aggregator(ARG)도 OB에 넣는다. (아래 Cross-shard Transaction 처리에서 설명)

4. Consensus로 OB를 확정한 뒤 모든 Processing Shard에 보낸다.
    - $OB := \langle ARGs, \hat{EB}_{dsts}, \hat{M}_{ctxs}, r, \sigma_{set}^O \rangle$
    - $ARGs$: Cross-shard Transaction 실행 결과의 집계, $\hat{EB}_{dsts}$: 정렬된 EB Digest 목록, $\hat{M}_{ctxs}$: 정렬된 Cross-shard Transaction Metadata 목록, $\sigma_{set}^O$: Ordering Shard의 Quorum 서명

#### Step 3: EXECUTE (Execution)

Processing Shard의 Node는 OB를 받으면 서명을 검증하고, 빠진 Round가 있으면 Ordering Shard에서 동기화한 뒤 다음을 순서대로 처리한다.

1. **이전 Round의 Cross-shard Transaction 확정**: OB의 ARGs를 보고, 이전 Round에서 실행해 둔 Cross-shard Transaction을 Commit하거나 Abort한다.

2. **Intra-shard Transaction 실행**: $\hat{EB}_{dsts}$ 중 자기 Shard의 EB 원본을 가져와 실행하고 확정한다. 단, 아직 확정되지 않은 Cross-shard Transaction이 바꾼 State에 접근하면, 그 Cross-shard Transaction이 확정될 때까지 확정을 미룬다.

3. **새 Cross-shard Transaction 실행과 투표**: 새로 정렬된 Cross-shard Transaction을 실행한다. 다른 Shard의 결과가 필요하므로 바로 확정하지 않고, 실행 결과(성공 1, 실패 0)를 VOTE로 만든다. VOTE도 Shard 안에서 $f_S \lvert S_P^{sid} \rvert + 1$개 서명을 모아 Ordering Shard에 보낸다. 최소 하나는 Honest Node의 서명이므로, Ordering Shard는 Transaction을 다시 실행하지 않고 VOTE를 믿을 수 있다.

4. **External Verifiability**: OB를 처리한 뒤 Ledger의 Root에 서명한 COMMIT 메시지를 Shard 안에 퍼뜨린다. 외부 Node(예: 전체 Data 없이 일부 Data와 증명으로 검증하는 Light Client)는 $f_S \lvert S_P^{sid} \rvert + 1$개 서명이 붙은 Ledger를 유효하다고 판단할 수 있다.

### Cross-shard Transaction 처리

Arete는 One-shot Cross-shard Transaction을 다룬다. One-shot은 관련 Shard별 Intra-shard Transaction으로 나눠, Shard끼리 State를 주고받지 않고 각자 실행할 수 있는 Cross-shard Transaction이다. 예로 Cross-shard 송금과 Atomic Swap(두 사용자가 서로 다른 Token을 교환하되 양쪽 전송이 모두 성공하거나 모두 취소되는 Transaction)이 있다. Shard 사이에 State를 여러 번 주고받아야 하는 Multi-shot Cross-shard Transaction은 기존 Sharding 프로토콜에서도 열린 문제로 남아 있다.

**기존 방식 1: Two-Phase Commit with Lock**

대부분의 기존 Sharding 프로토콜은 2PC(Two-Phase Commit)를 쓴다.

1. **Voting Phase**: Coordinator(Client 또는 특정 Shard)가 나눈 Transaction을 관련 Shard에 보낸다. 각 Shard는 실행하고 관련 State에 Lock을 건 뒤 결과를 알린다.
2. **Commit Phase**: Coordinator는 모두 성공이면 Commit, 하나라도 실패면 Abort를 알린다. 이때 Lock이 풀린다.

→ Lock이 걸린 State에 접근하는 다른 Transaction은 Lock이 풀릴 때까지 기다린다. Uniswap처럼 자주 호출되는 Smart Contract에서는 Latency가 크게 늘어난다.

**기존 방식 2: Global Order 없는 Optimistic Execution**

각 Shard가 Lock 없이 먼저 실행하고, 문제가 생기면 Rollback한다.

→ Shard마다 Cross-shard Transaction을 실행하는 순서가 다를 수 있다. 같은 State를 서로 다른 순서로 읽고 쓰면 실행이 실패하고, 관련된 여러 Transaction을 Rollback해야 한다. On-chain에서 Rollback해도 이미 일어난 Off-chain 거래(예: 암호화폐로 음식 구매)는 되돌릴 수 없어 손실이 생길 수 있다.

**⇒ Arete: Lock-free Execution**

Ordering Shard가 정한 Global Order가 있으므로, 모든 Processing Shard는 같은 순서로 Transaction을 실행한다. 순서가 같으면 State 접근 순서도 같으므로 Lock 없이 일관되게 실행할 수 있다.

1. 관련 Processing Shard는 Global Order대로 Cross-shard Transaction을 Lock 없이 실행한다. 결과는 아직 확정하지 않은 Pending State로 둔다.
2. 각 Shard는 실행 결과를 VOTE로 Ordering Shard에 보낸다.
3. Ordering Shard는 관련된 모든 Shard의 VOTE를 AND로 합쳐 ARG를 만든다. 1이면 모든 Shard에서 성공, 0이면 하나 이상의 Shard에서 실패다.
4. ARG는 이후 OB에 담겨 모든 Processing Shard에 전달되고, 각 Shard는 ARG에 따라 Commit하거나 Abort한다.

Ordering Shard는 현재 Round의 VOTE가 모두 도착하기를 기다리지 않고 다음 Round로 진행한다(Non-blocking). 따라서 Cross-shard Transaction은 두 번의 Consensus Round(순서 결정, VOTE 집계)를 거쳐 확정된다.

**→ 문제: Cascading Abort와 일관성**

Lock 없이 실행하면, 뒤의 Transaction이 아직 확정되지 않은 앞 Transaction의 결과를 읽을 수 있다. 앞 Transaction이 Abort되면 그 결과를 읽은 뒤 Transaction도 Abort해야 한다. 이때 Shard마다 판단이 달라지면 일관성이 깨진다.

예: Processing Shard 3개가 각각 Token Contract $TK_1$, $TK_2$, $TK_3$를 관리한다. ($A_2$는 $TK_2$에 있는 A의 잔액)

- $ctx_1$: A가 B에게 100 $T_1$을 주고 50 $T_2$를 받음 ($S_P^1$, $S_P^2$ 관련)
- $ctx_3$: A가 D에게 30 $T_2$를 주고 10 $T_3$를 받음 ($S_P^2$, $S_P^3$ 관련), $ctx_1$ 다음 순서

1. $S_P^1$에서 A의 $T_1$ 잔액이 부족해 $ctx_1$이 실패한다. ARG에서 $ctx_1$은 0이 되어 Abort된다.
2. $S_P^2$는 $ctx_1$의 실패를 알기 전에 $ctx_1$의 자기 부분(B → A 50 $T_2$)을 실행했고, $ctx_3$는 이 50 $T_2$로 A → D 30 $T_2$를 실행해 성공한다.
3. $S_P^2$와 $S_P^3$ 모두 $ctx_3$에 1을 투표해, ARG에서 $ctx_3$는 1이 된다.
4. $S_P^2$는 나중에 $ctx_1$이 Abort된 것을 알고, Abort된 State를 읽은 $ctx_3$도 Abort해야 한다. 하지만 $S_P^3$가 ARG만 보고 $ctx_3$를 Commit하면 두 Shard의 결과가 달라진다.

**⇒ 해결: Deterministic Commitment**

- ARG는 OB에 실려 모든 Processing Shard에 공개된다. 따라서 모든 Processing Shard는 어떤 Cross-shard Transaction이 Abort되었는지 안다.
- 위 예에서 $S_P^3$도 $ctx_1$이 Abort되었고 $ctx_1$이 $TK_2$의 A 계정에 접근한다는 것을 안다. $ctx_3$도 $TK_2$의 A 계정에 접근하므로 $S_P^3$도 $ctx_3$를 Abort한다.
- 모든 Processing Shard가 같은 공개 정보에 같은 규칙을 적용하므로 같은 결론을 낸다.
- Cascading Abort 자체를 줄이는 방법으로, 논문은 Processing Shard가 확정되지 않은 State에 접근하는 새 Transaction을 Certify하지 않는 방식 등을 제안한다.

### Arete 동작 예시

Processing Shard 2개와 Ordering Shard 1개가 있고, Token Contract 두 개가 서로 다른 Processing Shard에 있다고 하자. ($A_1$은 $TK_1$에 있는 A의 잔액)

- $S_P^1$: Token $T_1$의 Contract $TK_1$ 관리. 초기 잔액 $A_1 = 100$, $B_1 = 100$, $C_1 = 0$
- $S_P^2$: Token $T_2$의 Contract $TK_2$ 관리. 초기 잔액 $A_2 = 0$, $B_2 = 50$, $C_2 = 30$

Atomic Swap 2개를 처리한다.

| Transaction | 내용 | $S_P^1$에서 실행할 부분 | $S_P^2$에서 실행할 부분 |
| --- | --- | --- | --- |
| $ctx_1$ | A가 B에게 100 $T_1$을 주고 50 $T_2$를 받음 | A → B 100 $T_1$ | B → A 50 $T_2$ |
| $ctx_2$ | B가 C에게 60 $T_1$을 주고 30 $T_2$를 받음 | B → C 60 $T_1$ | C → B 30 $T_2$ |

1. **CERTIFY**

    $S_P^1$의 한 Node가 $ctx_1$을, $S_P^2$의 한 Node가 $ctx_2$를 Client에게 받아 각자 EB에 담는다. 각 Shard 안에서 서명을 $f_S \lvert S_P \rvert + 1$개 이상 모아 CB를 만들고 Ordering Shard에 보낸다.

2. **ORDER (Round $r$)**

    Ordering Shard는 두 CB를 하나의 OB에 담아 $ctx_1$, $ctx_2$ 순서를 정하고, OB를 $S_P^1$과 $S_P^2$에 보낸다.

3. **EXECUTE (Round $r$)**

    두 Shard는 같은 순서($ctx_1$ → $ctx_2$)로 Lock 없이 실행한다. 결과는 아직 확정하지 않은 Pending State다.

    | | 초기 | $ctx_1$ 실행 후 | $ctx_2$ 실행 후 |
    | --- | --- | --- | --- |
    | $S_P^1$ ($A_1$, $B_1$, $C_1$) | (100, 100, 0) | (0, 200, 0) | (0, 140, 60) |
    | $S_P^2$ ($A_2$, $B_2$, $C_2$) | (0, 50, 30) | (50, 0, 30) | (50, 30, 0) |

    두 Shard 모두 $ctx_1$, $ctx_2$를 성공적으로 실행했으므로, 각자 VOTE($ctx_1 = 1$, $ctx_2 = 1$)를 만들어 Shard 안에서 서명을 모은 뒤 Ordering Shard로 보낸다.

4. **ORDER (이후 Round)**

    Ordering Shard는 두 Shard의 VOTE를 AND로 합쳐 ARG($ctx_1 = 1$, $ctx_2 = 1$)를 만들고, 이후 OB에 담아 보낸다.

5. **EXECUTE (이후 Round)**

    두 Shard는 ARG를 보고 $ctx_1$, $ctx_2$를 Commit해 Pending State를 확정한다.

2PC였다면 $ctx_1$이 B의 계정($B_1$, $B_2$)에 Lock을 걸므로, 같은 계정을 쓰는 $ctx_2$는 $ctx_1$의 Commit Phase가 끝날 때까지 기다려야 한다. Arete에서는 두 Transaction을 한 번의 Consensus Round에서 Lock 없이 실행한다.

### Ordering Shard의 병목

Ordering Shard는 하나뿐이므로 Processing Shard가 늘어나면 결국 병목이 된다. 논문은 다음 최적화로 Ordering Shard가 처리할 Data를 줄인다.

- **Cross-shard Transaction Batching**: CB에 Cross-shard Transaction마다 Digest를 넣는 대신, 같은 상대 Shard와 관련된 것끼리 묶어 Batch Digest 하나만 넣는다. 상대 Shard는 최대 $k - 1$개이므로 CB에는 최대 $k - 1$개 Digest가 들어간다.

- **ARG 압축**: Batch의 순서는 이미 이전 OB에 기록되어 있으므로, ARG를 Batch당 1 bit(1: Commit, 0: Abort)인 Bit String으로 바꾼다. CB 하나당 $k - 1$ bit면 된다.

- **Signature Aggregation**: BLS(Boneh-Lynn-Shacham) 서명으로 Quorum 서명을 하나로 합친다.

**병목 시점 추정**

Digest는 SHA-256(Secure Hash Algorithm 256-bit)으로 32 B라고 가정한다.

- Processing Shard Node가 CB 하나를 만들 때 처리하는 Data
    - EB: Transaction 5,000개 × 512 B + Shard ID 2 B + Node ID 2 B ≈ 2.56 MB
    - CB: EB Digest 32 B + Batch Digest $32(k-1)$ B + Shard ID 2 B + BLS 서명 96 B = $32k + 98$ B
    - 합계 약 $32k$ B + 2.56 MB

- Ordering Shard가 OB에서 CB 하나당 처리하는 Data
    - ARG $(k-1)/8$ B + EB Digest 32 B + Batch Digest $32(k-1)$ B + Round 번호 $8/k$ B + 서명 $96/k$ B
    - Round 번호와 서명은 OB 하나에 하나씩이므로 $k$개 CB가 나눠 쓴다.

Ordering Shard는 $k$개 Processing Shard의 CB를 모두 처리하므로, CB 하나당 비율이 $1/k$가 되는 지점에서 두 쪽이 처리하는 Data 양이 같아진다.

$$
\frac{(k-1)/8 + 32 + 32(k-1) + 8/k + 96/k}{32k + 2{,}560{,}000} = \frac{1}{k} \quad \Rightarrow \quad k \approx 283
$$

→ Processing Shard가 약 283개가 되어야 Ordering Shard가 Processing Shard Node와 비슷한 양의 Data를 처리한다. Processing Shard의 실행 연산 비용을 빼고 계산했으므로 하한값이다.

### 보안 분석

분석은 한 Epoch 안을 기준으로 한다. Epoch 사이의 보안은 GearBox의 Reconfiguration 분석을 따른다.

**Sharding Safety**

- Ordering Shard는 BFT Consensus를 수행하므로 Ordering Shard의 Honest Node는 같은 Prefix의 Ledger를 가진다. Cross-shard Transaction은 Processing Shard의 State만 바꾸므로 Processing Shard만 따지면 된다.

- **Shard 내부 일관성**: Processing Shard의 Ledger는 OB에 담긴 EB Digest 목록으로 정해진다. 두 Honest Node의 Ledger가 다르려면 Ordering Shard가 같은 Round에 서로 다른 OB를 확정해야 하므로 모순이다.

- **Cross-shard Atomicity**: Cross-shard Transaction은 관련된 모든 Shard에서 Commit되거나 모두 Abort된다. 결과가 다르려면 Shard들이 서로 다른 ARG를 받아야 하고, 이는 같은 Round에 서로 다른 OB가 확정되었다는 뜻이므로 모순이다.

- **Cross-shard Consistency**: 두 Cross-shard Transaction의 확정 순서는 관련된 모든 Shard에서 같다. Cross-shard Transaction은 ARG의 순서대로 확정되므로, 순서가 다르려면 역시 서로 다른 OB가 필요하다.

**⇒ Sharding Safety는 Ordering Shard의 Safety로 귀결된다.**

**Sharding Liveness**

- Reconfiguration은 각 Processing Shard에서 $f_S \lvert S_P^{sid} \rvert + 1$개 이상의 Node가 결국 Ordering Shard에 메시지를 보내게 한다. 그중 최소 하나는 Honest Node이므로, Honest Node에 보낸 Transaction은 CB에 담겨 결국 정렬된다.
- 정렬된 Transaction은 유효한 CB를 가지므로, Data Availability에 의해 모든 Honest Node가 원본을 받아 실행할 수 있다.

### 실험 결과

**구현과 환경**

- Rust로 약 6,500줄 구현. Ordering Shard의 Consensus는 HotStuff의 변형
- 비교 대상은 GearBox와 RIVET. 두 프로토콜은 공개 구현이 없어 같은 Codebase 위에 구현해 비교
- AWS c5a.8xlarge 인스턴스, 전 세계 8개 Region
- $s = 15\%$, $\lambda = 20$: 제한된 비용으로 Shard를 더 많이 만들기 위해 앞의 표($\lambda = 30$)보다 약한 설정 사용
- Processing Shard는 0.9999-probabilistic Liveness, Ordering Shard는 Safety와 Liveness를 모두 보장하도록 크기를 정함
- Transaction 크기 512 B, Cross-shard Transaction 비율 기본 20%

$n = 500$일 때 설정은 다음과 같다. GearBox에서는 Control Shard가 Ordering Shard 자리에, Consensus를 수행하는 일반 Shard가 Processing Shard 자리에 해당한다.

| | GearBox | RIVET | Arete |
| --- | --- | --- | --- |
| Ordering Shard 크기 $m^{\#}$ | 81 | 81 | 81 |
| Processing Shard 크기 $m^{\ast}$ | 63 | 31 | 24 |
| Processing Shard의 $f_L$ | 31% | 49% | 43% |
| Processing Shard 수 $k$ | 7 | 16 | 20 |

**결과**

- **Throughput**: Arete는 약 180K TPS(Transactions Per Second)로, GearBox(약 45K)의 4배, RIVET(약 125K)의 1.4배다.

- **Intra-shard Confirmation Latency**: Arete는 GearBox와 비슷한 수준이며, $n$이 커지면서 약 4초에서 6초로 늘어난다. 최대 Throughput 지점에서 Arete는 7초 미만, RIVET은 약 23초다.

- **Cross-shard Confirmation Latency**: Arete는 약 8초에서 12초, GearBox는 80초에서 223초다($n$에 따라). GearBox는 2PC로 Lock을 기다리므로 Arete가 10배 이상 짧다. 최대 Throughput 지점에서 RIVET은 약 27초다.

- **Cross-shard Transaction 비율**: 20%에서 80%로 높이면 모든 프로토콜의 Throughput이 줄고 Latency가 늘지만, Arete가 모든 비율에서 가장 좋다.

- **Crash Fault**: Shard마다 Crash Node 비율을 0%에서 30%로 늘리면 Arete의 Throughput은 180K에서 88K로, GearBox는 약 45K에서 38K로, RIVET은 약 125K에서 86K로 줄어든다. Arete는 Leaderless 방식이라 모든 Node의 대역폭이 Throughput에 기여하므로, Node가 멈추면 Throughput이 더 크게 줄어든다. 활성 Node가 줄면 다음 단계로 넘어가는 데 필요한 서명이 활성 Node 중 더 큰 비율을 차지하므로, 모든 프로토콜의 Latency가 늘어난다.

논문은 Arete의 Throughput이 높은 이유를 세 가지로 든다. 작은 Shard를 더 많이 만들 수 있고, $f_L$이 커서 다음 단계로 넘어가는 Quorum $(1 - f_L)$이 작아지며, Leaderless 방식으로 Data Dissemination 부담을 여러 Node가 나눠 진다.

### 한계

- **단일 Ordering Shard**: Processing Shard가 늘어나면 결국 병목이 된다. 283개는 실행 비용을 뺀 하한 추정이다.

- **큰 Ordering Shard**: Ordering Shard는 $f < 1/3$을 지켜야 하므로 Processing Shard보다 크다. Shard 수 $k$는 Ordering Shard에 쓰인 Node를 빼지 않고 계산하는데, 실험 설정($n = 500$)에서는 $m^{\#} + k \times m^{\ast} = 81 + 20 \times 24 = 561$로 전체 Node 수보다 크다. 논문은 이를 Shard Overlap으로 해결할 수 있다고 설명하지만, 실험에서 Node를 어떻게 배치했는지는 설명하지 않는다.

- **One-shot Cross-shard Transaction만 지원**: Multi-shot Cross-shard Transaction은 열린 문제로 남아 있다.

- **Cascading Abort**: Lock-free Execution에서는 앞 Transaction의 Abort가 뒤 Transaction의 Abort로 이어질 수 있다.

- **Liveness 위반 Shard**: 확률은 낮지만(0.9999 기준 0.01%) 생길 수 있고, 복구할 때 새 Node가 State를 동기화해야 한다.

- **Crash Node에 민감**: Crash Node 비율이 늘 때 Throughput 감소 폭이 비교 대상보다 크다.

### 결론

Arete는 SMR을 Data Dissemination, Ordering, Execution으로 분해하고, 작업마다 필요한 Threshold와 자원이 다르다는 점을 이용한다. Ordering은 Consensus가 필요해 1/3에 묶이지만 Digest만 다루면 되므로 하나의 Ordering Shard가 맡는다. Data Dissemination과 Execution은 자원을 많이 쓰지만 Byzantine Node를 절반 미만까지 견디므로 여러 Processing Shard로 나눈다. 여기에 Safety-Liveness Separation을 더해 Processing Shard는 $f_S + f_L < 1$을 따르며, 같은 크기의 Shard에서 GearBox보다 훨씬 높은 Liveness 확률을 얻는다. 그 결과 더 강한 가정 없이 Shard를 작게 만들고, 복구 비용도 낮춘다.

COE Architecture는 이 구조 위에서 CERTIFY로 Data Availability를 보장하고, ORDER로 Digest의 Global Order를 정하며, EXECUTE로 Lock 없이 Transaction을 실행한다. 대가는 하나의 Ordering Shard에 몰리는 부담, Processing Shard보다 큰 Ordering Shard, One-shot으로 제한된 Cross-shard Transaction이다.
