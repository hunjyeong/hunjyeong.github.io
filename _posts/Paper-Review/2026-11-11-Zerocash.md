## Bitcoin

### What is Bitcoin?

Bitcoin은 은행과 같은 중앙 기관 없이 사용자 간에 직접 주고받을 수 있도록 설계된 탈중앙화 P2P(Peer-to-Peer) 전자화폐 시스템이다.

- **Decentralization**: 중앙 관리자 없이 네트워크에 참여하는 Node들이 독립적으로 Block과 Transaction을 검증하고 Blockchain을 유지함

- **Public Ledger**: Blockchain에 기록된 Transaction 내역이 공개되어 누구나 조회하고 검증할 수 있음

- **Proof-of-Work(PoW)**: Miner가 연산 작업을 통해 새로운 Block을 생성하고, Node는 합의 규칙에 따라 Block을 검증함

- **UTXO Model**: Account별 잔액을 직접 기록하지 않고, UTXO의 집합으로 상태를 관리함. 잔액은 소비 가능한 UTXO의 금액 합계로 계산함

- **Limited Supply**: BTC의 최대 발행량은 약 2,100만 개로 제한됨

- **Currency Unit**: 기본 단위는 BTC, 최소 단위는 Satoshi
	- 1 BTC = $$10^8$$ Satoshi (100,000,000 Satoshi)

#### UTXO (Unspent Transaction Output)

UTXO는 이전 Transaction에서 생성된 Output 중 아직 다른 Transaction의 Input으로 소비되지 않은 Output이다. Transaction은 기존 UTXO를 Input으로 소비하고, 새로운 UTXO를 Output으로 생성한다.

Full Node는 **UTXO Set(현재 소비되지 않은 Output의 집합)**을 유지한다. Transaction이 유효하려면 Input이 참조하는 UTXO가 UTXO Set에 존재하고, 해당 UTXO의 잠금 조건을 비롯한 합의 규칙을 충족해야 한다.

검증된 Block이 Chain(누적 작업량이 가장 큰 Chain)에 연결되면, 해당 Block에서 소비된 UTXO는 UTXO Set에서 제거되고 새로 생성된 UTXO는 추가된다.

### How Bitcoin Works

- 예시: A가 B에게 0.3 BTC를 전송하는 상황 (수수료 0.001 BTC 가정)

	- A의 UTXO: 1 BTC UTXO
	- B의 UTXO: 0.5 BTC UTXO

1. **Transaction 생성**

	UTXO는 부분적으로 소비할 수 없다. 따라서 A는 1 BTC UTXO 전체를 Input으로 사용한다.

	| 구분 | UTXO | 설명 |
	| --- | --- | --- |
	| Input | 1 BTC | A의 기존 UTXO |
	| Output 1 | 0.3 BTC | B에게 전송 |
	| Output 2 | 0.699 BTC | A의 새 주소로 반환할 거스름돈 |
	| Transaction Fee | 0.001 BTC | $$\sum$$ Input - $$\sum$$ Output |

	기존 UTXO 전체를 소비한 뒤, 남은 금액에서 수수료를 제외한 0.699 BTC를 새로운 Output(거스름돈)으로 생성한다.

2. **서명 및 전파**

	A는 개인키로 Input에 서명하여 1 BTC UTXO를 소비할 권한을 증명하고, Transaction을 Bitcoin P2P 네트워크에 전파한다.

3. **Transaction 검증**

	각 Node는 다음을 포함한 합의 규칙에 따라 Transaction을 검증하고, Mempool 정책(최소 수수료 등)을 충족하면 Mempool(아직 Block에 포함되지 않은 Transaction의 대기 목록)에 저장한다.

	- A의 1 BTC UTXO가 UTXO Set에 존재하는지(아직 소비되지 않았는지)
	- A의 서명이 해당 UTXO의 소비 조건을 충족하는지
	- Output 합계(0.999 BTC)가 Input(1 BTC)을 초과하지 않는지

4. **Block 생성**

	Miner는 Mempool에서 A의 Transaction을 골라 후보 Block에 포함한다.
	또한 Block의 첫 Transaction으로 Coinbase Transaction을 직접 만들어, Block 보조금과 Block 내 수수료 합계(A의 Transaction 수수료 0.001 BTC 포함) 이하의 금액을 자신에게 지급한다.
	이후 Block Header의 Hash가 Target(목표값) 이하가 될 때까지 Nonce를 바꿔 가며 계산한다(PoW).

5. **Block 검증 및 UTXO Set 갱신**

	PoW 조건을 만족하는 Block이 전파되면, 각 Node는 해당 Block의 PoW와 Block 내 모든 Transaction의 유효성을 검증한다.
	검증을 통과한 Block은 이전 Block Header의 Hash를 참조하여 기존 Blockchain에 연결되며, 누적 작업량이 가장 큰 Chain(활성 Chain)에 포함될 경우 UTXO Set이 다음과 같이 갱신된다.

	- 제거된 UTXO: 1 BTC UTXO(A)
	- 추가된 UTXO: 0.3 BTC UTXO(B), 0.699 BTC UTXO(A)
	- 유지된 UTXO: 0.5 BTC(B)

6. **Confirmation**

	해당 Transaction이 활성 Chain의 Block에 포함되면 1 Confirmation을 얻으며, 이후 그 위에 Block이 추가될 때마다 Confirmation 수가 증가한다.

	관행적으로 6 Confirmation을 충분히 신뢰할 수 있는 기준으로 사용하지만, Chain 재구성 가능성이 완전히 사라지는 것은 아니다.

	결과(다음 Transaction의 Input으로 사용 가능한 UTXO)

	- A의 UTXO: 0.699 BTC UTXO
	- B의 UTXO: 0.5 BTC UTXO, 0.3 BTC UTXO (총 잔액 0.8 BTC)

	(수수료 0.001 BTC: Miner의 Coinbase Output에 포함되며, 이 Output은 생성된 Block보다 높이가 100 이상 높은 Block에서부터 소비할 수 있다.)


## Double Spending Problem

**Double Spending(이중 지불)**은 복사가 가능한 디지털 화폐의 특성을 이용해 동일한 자산을 두 번 이상 지불하려는 시도이다. Bitcoin에서는 같은 UTXO를 서로 충돌하는 두 Transaction에서 중복 소비하려는 것을 의미한다.

### **→ Bitcoin이 Double Spending을 방지하는 방법**

- **UTXO Set**: 이미 소비된 UTXO는 UTXO Set에서 제거되므로, 같은 UTXO를 참조하는 Transaction은 유효하지 않다. 그러나 Node마다 Transaction을 수신하는 순서가 다를 수 있으므로, 이것만으로는 충돌하는 두 Transaction 중 어느 것을 인정할지 정할 수 없다.

- **Public Ledger**: 모든 On-chain Transaction을 공개 원장에 기록하여, 어떤 Node든 각 UTXO의 소비 여부를 중앙 기관 없이 직접 검증할 수 있게 한다.

- **Consensus (Proof-of-Work)**: 충돌하는 두 Transaction이 서로 다른 Block에 포함되어 Chain이 갈라지면, 각 Node는 유효한 Chain 중 누적 작업량이 가장 큰 Chain을 선택한다. 이를 통해 네트워크는 하나의 Transaction 기록과 순서로 수렴한다.

- **Confirmation**: 기록된 Transaction을 뒤집으려면 해당 Block부터 새로운 Block들을 PoW로 만들어, 기존 Chain보다 누적 작업량이 큰 대체 Chain을 구성해야 한다. 따라서 Confirmation이 쌓일수록 Transaction이 뒤집힐 가능성은 낮아진다.

**⇒ Bitcoin은 중앙 기관 없이 누구나 Transaction을 검증할 수 있도록 Public Ledger를 사용하며, 이로 인해 모든 Transaction 내역이 공개되는 Privacy 문제가 발생한다.**

## Bitcoin's Privacy Problem

Bitcoin Transaction의 Input, Output 및 금액은 누구나 확인할 수 있도록 공개되며, 일반적인 주소 기반 거래에서는 다음 정보를 추적할 수 있다.

- **Origin Address(송신 주소)**: Input이 참조하는 이전 Output의 잠금 조건에서 알 수 있음
- **Destination Address(수신 주소)**: Output의 잠금 조건에서 도출할 수 있음
- **Payment Amount(결제 금액)**: 각 Output의 금액이 공개됨

Bitcoin은 완전한 Anonymity(익명성)이 아닌 **Pseudonymity(가명성)**을 제공한다. 사용자의 실명은 기록되지 않고 사용자는 여러 주소를 생성할 수 있지만, 위 정보가 형성하는 Transaction Graph를 분석하면 동일한 사용자의 주소들이 연결되고 **자금 흐름이 추적**될 수 있다.

- **Transaction Graph**: Transaction의 Input과 이전 Output의 참조 관계로 형성되는 그래프다. UTXO의 생성 이력을 거슬러 올라가면 궁극적으로 Coinbase Transaction에 도달한다.

- **Address Clustering Heuristics**: Transaction Graph를 분석할 때 다음과 같은 추정 기법으로 같은 사용자의 주소들을 묶는다.

	- **Common-Input-Ownership Heuristic**: 하나의 Transaction에 함께 사용된 여러 Input을 동일한 소유자의 것으로 추정한다. 예: B가 0.7 BTC를 보내기 위해 서로 다른 주소에 있는 0.5 BTC와 0.3 BTC UTXO를 함께 사용하면, 두 주소는 모두 B의 것으로 추정된다.

	- **Change Address Heuristic**: 금액이 딱 떨어지지 않는 Output이나 처음 쓰이는 주소로 가는 Output을 잔돈으로 추정한다. 예: A의 Transaction에서 0.3 BTC는 금액이 딱 떨어지고 0.699 BTC는 그렇지 않으므로, 0.699 BTC Output을 잔돈으로 추정하여 A의 새 주소를 기존 주소와 연결한다.

	- 두 휴리스틱은 추정이므로 틀릴 수 있다. 특히 여러 사용자가 Input을 모아 하나의 Transaction을 만드는 CoinJoin에서는 Common-Input-Ownership Heuristic이 성립하지 않는다.

- **신원 식별과 노출**: Transaction Graph, 금액, Block 타임스탬프 등의 On-chain 정보를 외부 정보(거래소의 KYC 기록, 가맹점 결제 정보 등)와 결합하면 실제 사용자를 식별하거나 추정할 수 있다. 특정 주소가 실명과 연결되면 해당 주소의 거래 내역과 자금 흐름이 드러나며, 주소 연결 휴리스틱을 통해 같은 사용자의 다른 주소와 잔액까지 추정될 수 있다.

- **Fungibility(대체 가능성)**: 동일한 단위의 화폐가 거래 이력과 관계없이 동등하게 취급되는 성질이다. Bitcoin에서는 UTXO의 이력을 추적할 수 있으므로 특정 이력을 가진 UTXO가 다르게 취급될 수 있으며, 이는 대체 가능성을 약화시킨다.

**⇒ Transaction 정보가 공개되어 있는 한 소비 내역, 잔액 및 자금 흐름이 노출될 위험은 근본적으로 제거할 수 없다. 그러나 이 정보를 단순히 숨기면 기존 방식으로는 Transaction의 유효성을 검증할 수 없다. 따라서 Transaction 정보를 공개하지 않으면서도 그 유효성을 누구나 검증할 수 있는 방법이 필요하다.**

## Solution 1: Mixing

**Mix(Laundry, Tumbler)**는 중앙 운영자가 관리하는 풀에 여러 사용자의 코인을 모은 뒤, 일정 시간이 지나면 같은 총액의 **다른 코인**을 돌려주는 방식이다. 입금과 출금 사이의 대응 관계를 숨겨 Transaction Graph만으로 어떤 입금이 어떤 출금에 대응하는지 파악하기 어렵게 한다.

- 예: A가 1 BTC를 Mix에 맡기고, 일정 시간 후 다른 사용자들이 맡긴 코인 중 1 BTC를 새 주소로 돌려받는다.

**한계**

- **지연**: 충분한 코인이 섞이려면 돌려받기까지 오래 기다려야 한다.
- **추적 가능성**: 운영자는 누가 어떤 코인을 맡기고 돌려받았는지 알 수 있다.
- **도난 위험**: 운영자가 맡긴 코인을 돌려주지 않을 수 있다.

**⇒ Mix를 쓰려면 기다려야 하고, 운영자를 믿어야 하며, 사용자가 프라이버시를 지키기 위해 계속 직접 노력해야 한다. 그러나 일반 사용자에게 필요한 것은 즉각적이고, 위험이 없으며, 자동으로 제공되는 프라이버시다.**

## Solution 2: Zerocoin

**Zerocoin**은 Bitcoin을 확장해, Mix의 중앙 운영자 없이 코인을 섞는 프로토콜이다. 기존 e-cash처럼 은행이 디지털 서명으로 코인을 보증하는 대신, 소비하려는 코인이 원장에 기록된 유효한 코인 중 하나임을 **Zero-Knowledge Proof(영지식 증명)**로 증명한다. Double Spending은 원장에 공개된 Serial Number(sn)로 막으므로, 중앙 기관이 필요 없다.

- **Commitment**: 값을 숨긴 채 고정하는 암호학적 약속이다.

	- **Hiding**: Commitment만 보고는 숨긴 값을 알 수 없다.
	- **Binding**: 한 번 생성한 Commitment를 서로 다른 값으로 여는 것이 계산적으로 어렵다.

1. **Mint**: 사용자는 정해진 액면의 BTC를 내고, 무작위 Serial Number(sn)와 난수 r로 만든 Commitment(cm)를 원장에 기록한다. 이 시점에는 sn과 r이 공개되지 않는다.

2. **Spend**: 나중에 사용자는 받을 주소, sn, 그리고 다음을 증명하는 Zero-Knowledge Proof를 담은 Spend Transaction을 제출한다.

	- "나는 원장에 Mint된 Commitment 중 하나인 cm과, 해당 cm을 공개된 sn으로 열 수 있는 난수 r을 알고 있다."

	이 증명은 **어느 Mint Transaction의 코인인지 드러내지 않는다.** 증명이 유효하고 sn이 이전에 사용되지 않았다면, 해당 금액의 BTC가 지정한 주소로 가는 일반 Bitcoin Output으로 지급된다.

3. **Double Spending 방지**: 이미 공개된 sn이 다시 제출되면 Transaction을 거부한다.

⇒ 결과적으로 Spend Transaction과 원래의 Mint Transaction 사이의 연결, 즉 **결제의 출처(Origin)**가 숨겨진다.

**한계**

- **일부 정보만 숨김**: 출처는 숨기지만, Spend가 일반 Bitcoin Output을 만들므로 받는 주소(Destination)와 금액(Amount)은 공개된다.
- **고정 액면**: 정해진 단위의 코인만 지원하므로, 임의 금액 결제나 잔돈 처리(코인 분할)가 불가능하다.
- **직접 지불 불가**: Zerocoin 상태로 다른 사용자에게 바로 지불할 수 없다.
- **비효율**: Spend에 필요한 Double-Discrete-Logarithm(이중 이산 로그) 지식 증명은 공개된 수치로 크기가 45 kB를 넘고 검증에 450 ms가 걸린다. 이 수치는 일부 구성 요소에 80-bit 파라미터를 섞어 쓴 값이라, 모두 128-bit 보안 수준으로 맞추면 비용은 더 커진다. 이 증명은 네트워크에 전파되어 모든 Node가 검증하고 원장에 영구 저장해야 하므로, 비용이 Bitcoin보다 몇 자릿수 높다.

**⇒ Zerocoin은 Mix의 중앙 운영자 없이 출처를 숨겼지만, 수신자와 금액은 여전히 공개되며 일상적인 거래는 결국 Bitcoin으로 해야 한다. 완전한 익명 화폐라기보다 주기적으로 BTC를 "세탁"하는 탈중앙 Mix에 가깝다.**

## Solution 3: Zerocash

**Zerocash**는 Zerocoin의 한계를 해결하기 위해 제안된 탈중앙화 익명 결제 시스템이다(Ben-Sasson et al., 2014). Zerocoin은 출처만 숨기고 고정 액면만 지원했지만, Zerocash는 **zk-SNARK(Zero-Knowledge Succinct Non-Interactive Argument of Knowledge)**로 Origin(출처), Destination(수신자), Amount(금액)을 모두 숨기면서도 누구나 거래의 유효성을 검증할 수 있게 한다. 논문은 이를 **DAP(Decentralized Anonymous Payment, 탈중앙화 익명 결제) Scheme**으로 정의한다. DAP Scheme은 Bitcoin 같은 공개 원장 기반 화폐(Basecoin) 위에서 동작하며, 익명 코인의 발행, 분할, 병합, 직접 전송, 공개 인출을 지원한다.

| | Zerocoin | Zerocash |
| --- | --- | --- |
| 숨기는 정보 | 출처 | 출처, 수신자, 금액 |

### 핵심 아이디어

Bitcoin Transaction은 "어떤 UTXO를, 누구에게, 얼마나" 보내는지 공개하고, Node가 이를 직접 확인한다. Zerocash는 이 정보 대신 다음을 원장에 기록한다.

- **코인을 만들 때: Commitment(cm)** → 코인의 소유자와 Serial Number를 정하는 값은 드러나지 않는다.

- **코인을 쓸 때: Serial Number(sn) + zk-SNARK Proof** → Proof는 "원장에 있는 코인 중 하나를 내가 소유하고, 이 sn은 그 코인의 것이며, Value(가치) 합이 보존된다"를 보인다.

Node는 코인의 내용을 보지 않고 Proof를 검증하며, sn이 처음 나온 값인지 확인해 Double Spending을 막는다.

### Zerocash 단계별 동작 원리

#### Step 1: User Anonymity with Fixed-Value Coins

목적: Mint와 Spend 사이의 연결 관계를 숨겨 코인의 출처를 보호함

- 모든 코인이 1 BTC처럼 동일한 금액을 가진다고 가정

- zk-SNARK + Commitment Scheme 사용

- Mint(코인 생성 시): 원장에는 Commitment(cm)만 기록하고, 비밀값(r, sn)은 지갑에 보관

- Spend(코인 소비 시): Serial Number(sn)을 공개하고, "CMList 안의 어떤 cm을 sn으로 여는 r을 안다"는 것을 ZKP로 증명해 소유권을 보임

**Mint** (코인 생성)

$$
Tx_{Mint} := (cm)
$$

- 사용자가 무작위 sn, Trapdoor r을 선택 → $cm := COMM_r(sn)$

- 코인: $c := (r, sn, cm)$

- cm은 공개되지만 sn, r은 비공개

- 이 Transaction은 사용자가 실제로 1 BTC를 예치했을 때만 원장에 추가됨

**Spend** (코인 소비)

$$
Tx_{Spend} := (sn, \pi)
$$

- $sn$: 코인의 Serial Number

- $\pi$: zk-SNARK Proof
	- Proof가 증명하는 NP Statement: "I know r such that $COMM_r(sn)$ appears in the list CMList of coin commitments"

→ 사용자는 $Tx_{Spend}$를 생성하여 코인 c를 사용할 수 있음

- 만약 sn이 원장에 존재하지 않는 경우(= 이전에 소비된 적 없는 경우), 사용자는 1 BTC 사용 가능
- 만약 sn이 원장에 이미 존재하는 경우, Double Spending 시도로 간주되어 Transaction은 무효 처리됨

**익명성이 보장되는 이유**

1. sn은 공개되지만, r은 공개되지 않음

2. zk-SNARK Proof $\pi$는 영지식이므로, $COMM_r(sn)$이 CMList에 있다는 사실만 증명하고 r이나 해당 cm이 무엇인지는 드러내지 않음

3. 원장에는 수많은 cm이 존재하지만, 이중에 어떤게 $COMM_r(sn)$인지 찾아낼 수 없음

4. 즉, $\pi$를 통해 해당 코인을 정당하게 사용했다는 사실은 증명되지만, 그 코인이 어느 Mint에서 만들어졌는지(결제의 출처)는 알 수 없음

#### Step 2: Compressing the List of Coin Commitments

Step 1의 NP Statement는 CMList를 코인 Commitment의 명시적인 목록 그대로 사용함

**→ 문제: Scalability(확장성) 한계**

1. 증명 검증 등 대부분의 프로토콜 알고리즘의 시간, 공간 복잡도가 CMList 길이에 선형으로 증가함
2. 이미 소비된 코인의 cm도 CMList에서 삭제할 수 없음 (영지식성 때문에 어떤 cm이 소비되었는지 아무도 알 수 없음)

**⇒ 해결 방법: NP Statement가 전체 CMList 대신 Merkle Tree의 Root(rt)만 참조하도록 함**

- Tree(CMList): CMList 위에 만든 Append-Only Merkle Tree

	- Leaf: 각 cm
	- 내부 노드: 두 자식 값을 CRH(Collision-Resistant Hash, 충돌 저항 해시 함수)로 해시한 값

- 새 Leaf를 추가할 때 rt를 갱신하는 시간과 공간 비용이 트리의 깊이에 비례

	- CMList 크기 N에 대해 선형 → $\log_2 N$ 수준으로 복잡도 감소
	- Tree Depth: 64 사용
		- 최대 $2^{64}$개의 코인 지원 가능

- $\pi$의 NP Statement도 변경됨

	- "I know r such that $COMM_r(sn)$ appears as a leaf in a CRH-based Merkle tree whose root is rt"
	- → 공개 입력은 CMList 대신 rt (sn은 그대로 공개 입력)이고, 증명자는 자기 cm의 Authentication Path를 Witness로 사용
	- → 전체 목록이 아니라 Root에 대해 증명하므로 효율적이고, 같은 zk-SNARK 구현이 지원할 수 있는 코인 수가 지수적으로 증가함

- 주의: 노드가 rt만 저장하면 되는 것은 아님 (Authentication Path를 계산하려면 CMList가 필요)

#### Step 3: Extending Coins for Direct Anonymous Payments

코인 c의 cm은 해당 코인의 sn에 대한 Commitment임

**→ 문제: 이 코인을 다른 사용자에게 전송 시 문제 발생**

- $u_A$ → $u_B$에게 코인 c를 전송한다고 가정하자

	1. $u_A$가 sn을 알고 있으므로 $u_B$가 c를 사용하면 $u_A$가 알아봄(익명성 깨짐). 또한 $u_A$가 먼저 c를 써 버릴 수도 있음(위험) → $u_B$는 c를 즉시 사용하고 새 코인 c'를 만들어 보관해야 함

	2. $u_A$가 $u_B$에게 100 BTC를 전송하고 싶은 경우, 1 BTC × 100번 전송해야 함(번거로움 + 전송 금액 노출)

	3. 코인의 고정된 단위(예: 1 BTC)의 배수가 아닌 금액은 전송 불가

→ 즉, sn만 Commit하는 구조는 결제 수단으로 적합하지 않음

**⇒ 해결: 코인 Commitment 구조를 바꾸고, Target Payment(지불 대상 지정)과 sn 생성에 PRF(Pseudorandom Function, 의사 난수 함수)를 사용함**

- 하나의 PRF에서 입력 앞에 서로 다른 접두 비트를 붙여 세 가지 PRF를 유도함. x는 PRF의 Seed

	- $\text{PRF}^{\text{addr}}_x$: 주소 생성

	- $\text{PRF}^{\text{sn}}_x$: Serial Number 생성

	- $\text{PRF}^{\text{pk}}_x$: Step 6에서 사용

	→ 이 중 $\text{PRF}^{\text{sn}}$ 은 PRF 성질에 더해 Collision-Resistant(충돌 저항성)도 가정함

**Address 생성**

사용자는 Address Key Pair $(a_{pk}, a_{sk})$를 생성

- $a_{sk}$: Address Secret Key
	- 무작위로 선택한 Seed

- $a_{pk}$: Address Public Key
	- $a_{pk} := \text{PRF}^{\text{addr}}_{a_{sk}}(0)$

- 사용자는 여러 개의 Address Key Pair 생성 가능

→ 코인에는 $a_{pk}$가 들어가고, 그 코인은 $a_{sk}$를 알아야 사용 가능

**Mint (코인 발행)**

사용자가 Value v의 코인 c를 만들고자 함

1. 사용자가 먼저 $\rho$ 선택

	- $\rho$: 코인의 Serial Number sn을 결정하는 비밀값
	- $\text{sn} := \text{PRF}^{\text{sn}}_{a_{sk}}(\rho)$

2. 사용자는 Tuple $(a_{pk}, v, \rho)$를 두 단계로 Commit함

	- $k := \text{COMM}_r(a_{pk} \| \rho)$ for a random r
	- $cm := \text{COMM}_s(v \| k)$ for a random s

3. 발행된 코인 구조

	- $c := (a_{pk}, v, \rho, r, s, cm)$

4. 생성된 Mint Transaction

	- $Tx_{Mint} := (v, k, s, cm)$
	- 사용자가 v BTC를 예치한 경우에만 원장에 추가됨

Why 두 단계 Commit을 하는가?

- 누구든지 공개된 $(v, k, s)$로 $\text{COMM}_s(v \| k) = cm$을 확인 가능
	- → cm이 예치한 금액 v에 대한 Commitment인지 검증 가능 (v는 공개)

- but, $a_{pk}$와 $\rho$는 k 안에 숨겨져 알 수 없음(사용자의 Privacy 보호 가능)
	- → 코인의 소유자가 드러나지 않음
	- → $\rho$를 모르므로 sn도 알 수 없어, 나중에 Pour에서 공개될 sn과 이 Mint를 연결할 수 없음

**Pour (코인 소비와 생성)**

입력 코인을 소비하고, 그 Value를 새 출력 코인들로 옮기는 연산 (전송, 분할, 병합에 모두 사용)

- 출력 Value의 합 = 입력 Value의 합
- 여기서는 입력 1개 → 출력 2개로 설명 (정식 구성은 입력 2개 → 출력 2개)

Address Key Pair $(a^{old}_{pk}, a^{old}_{sk})$를 가진 사용자 u가 코인 $c^{old}$를 소비하고, 새 코인 $c^{new}_1, c^{new}_2$를 만들고자 함

- Value: $v^{new}_1 + v^{new}_2 = v^{old}$

- 받는 주소: $a^{new}_{pk,1}, a^{new}_{pk,2}$ (u 자신의 주소일 수도 있음)

1. 각 새 코인 $i \in \{1, 2\}$를 Mint와 같은 방식으로 생성

	- $\rho^{new}_i$ 선택

	- $k^{new}_i := \text{COMM}_{r^{new}_i}(a^{new}_{pk,i} \| \rho^{new}_i)$ for a random $r^{new}_i$

	- $cm^{new}_i := \text{COMM}_{s^{new}_i}(v^{new}_i \| k^{new}_i)$ for a random $s^{new}_i$

	- $c^{new}_i := (a^{new}_{pk,i}, v^{new}_i, \rho^{new}_i, r^{new}_i, s^{new}_i, cm^{new}_i)$

2. 소비할 코인의 Serial Number 계산

	- $\text{sn}^{old} := \text{PRF}^{\text{sn}}_{a^{old}_{sk}}(\rho^{old})$

3. NP Statement POUR에 대한 zk-SNARK Proof $\pi_{POUR}$ 생성

	- 공개 입력: rt, $\text{sn}^{old}$, $cm^{new}_1$, $cm^{new}_2$

	- "나는 다음을 만족하는 $c^{old}, c^{new}_1, c^{new}_2, a^{old}_{sk}$를 안다"

		- 세 코인 모두 올바른 형식(Well-Formed): 각 cm이 코인의 값으로 올바르게 계산됨

		- $a^{old}_{pk} = \text{PRF}^{\text{addr}}_{a^{old}_{sk}}(0)$ → 소비 권한

		- $\text{sn}^{old} = \text{PRF}^{\text{sn}}_{a^{old}_{sk}}(\rho^{old})$ → sn이 그 코인의 것

		- $cm^{old}$가 Root가 rt인 Merkle Tree의 Leaf → 원장에 존재

		- $v^{new}_1 + v^{new}_2 = v^{old}$ → Value 보존

4. 생성된 Pour Transaction

	- $Tx_{Pour} := (rt, \text{sn}^{old}, cm^{new}_1, cm^{new}_2, \pi_{POUR})$

	- $\text{sn}^{old}$가 이미 원장에 있으면 거부

Why 이 구조로 Step 3의 문제가 해결되는가? ($a^{new}_{pk,1}$이 받는 사람의 주소일 때)

- 문제 1 (익명성, 위험)

	- u는 $a^{new}_{sk,1}$을 모름 → $c^{new}_1$을 쓸 수 없음
	- 수신자가 나중에 공개할 $\text{sn}^{new}_1 = \text{PRF}^{\text{sn}}_{a^{new}_{sk,1}}(\rho^{new}_1)$은 $a^{new}_{sk,1}$이 있어야 계산 가능
	- → u는 $\rho^{new}_1$을 알아도 수신자의 사용을 추적할 수 없음

- 문제 2 (번거로움, 금액 노출)
	- Pour 한 번으로 원하는 금액 전송
	- $Tx_{Pour}$는 Value가 어떻게 나뉘었는지, 어떤 cm이 소비되었는지, 새 코인이 어느 주소로 갔는지 드러내지 않음

- 문제 3 (임의 금액)
	- Value v를 임의로 정할 수 있고, 분할과 병합 가능

입출력 개수

- 입력 2개 미만 → Value가 0인 코인을 Mint해 빈 입력으로 사용
- 출력 2개 미만 → Value가 0인 코인을 만든 뒤 버림
- 2개 초과 → 2입력 2출력 Pour를 여러 개 조합

#### Step 4: Sending Coins

**→ 문제: 새 코인의 비밀값을 받는 사람에게 전달해야 함**

- Pour로 만든 $c^{new}_1$을 받는 사람 $u_1$이 쓰려면 $v^{new}_1, \rho^{new}_1, r^{new}_1, s^{new}_1$을 알아야 함

	- 이 값들이 있어야 sn을 계산하고 $\pi_{POUR}$를 만들 수 있음

- u가 $u_1$에게 비밀 메시지로 보낼 수는 있지만, Private Channel(비밀 통신 채널)이 필요함 → 추가 인프라나 가정이 필요

→ Out-of-Band(원장 밖) 채널 없이, 원장 자체로 비밀값을 전달

**⇒ 해결: 비밀값을 암호화해 Pour Transaction에 포함**

**Address Key Pair 확장**

- $addr_{pk} := (a_{pk}, pk_{enc})$, $addr_{sk} := (a_{sk}, sk_{enc})$

	- $(a_{pk}, a_{sk})$: 이전과 같은 방식으로 생성
	- $(pk_{enc}, sk_{enc})$: Key-Private Encryption(키 비공개 암호화) 방식의 키 쌍

- Key-Private Encryption이 만족하는 두 성질

	- IND-CCA(Indistinguishability under Chosen-Ciphertext Attack, 선택 암호문 공격에서의 암호문 구별 불가능성): 암호문을 보고 어떤 평문을 암호화했는지 구별할 수 없음
	- IK-CCA(Key Indistinguishability under Chosen-Ciphertext Attack, 선택 암호문 공격에서의 키 구별 불가능성): 암호문이 어떤 공개키로 암호화됐는지 알 수 없고, 같은 공개키로 만든 다른 암호문과도 연결할 수 없음

- 구현에서는 Key-Private ECIES(Elliptic-Curve Integrated Encryption Scheme, 타원 곡선 통합 암호화 방식) 사용

- 코인에 저장하는 주소도 $addr_{pk}$로 바뀜: $c := (addr_{pk}, v, \rho, r, s, cm)$

	- k는 그대로 $a_{pk}$만 Commit: $k := COMM_r(a_{pk} \| \rho)$

**Pour에 암호문 추가**

1. $C_1 := E_{enc}(pk^{new}_{enc,1}, (v^{new}_1, \rho^{new}_1, r^{new}_1, s^{new}_1))$

	- $pk^{new}_{enc,1}$: $u_1$의 주소 공개키 $addr^{new}_{pk,1}$에 들어 있는 암호화 공개키

2. $c^{new}_2$도 같은 방식으로 $C_2$ 생성

3. $Tx_{Pour} := (rt, sn^{old}, cm^{new}_1, cm^{new}_2, \pi_{POUR}, C_1, C_2)$

**Receive (코인 수신)**

1. $u_1$은 원장의 Pour Transaction을 차례로 훑으며, 각 $C_i$를 $sk_{enc}$로 복호화 시도

2. 복호화에 성공하면, 얻은 $(v_i, \rho_i, r_i, s_i)$로 아래를 확인

	- $cm^{new}_i = COMM_{s_i}(v_i \| COMM_{r_i}(a_{pk} \| \rho_i))$ → 복호화한 값이 원장의 cm과 일치
	- $sn_i := PRF^{sn}_{a_{sk}}(\rho_i)$가 원장에 없음 → 이미 받아서 쓴 코인은 제외

3. 둘 다 통과하면 코인 $c_i := (addr_{pk}, v_i, \rho_i, r_i, s_i, cm^{new}_i)$를 얻음 → 이후 Pour로 사용 가능

Why 이 구조로 Step 4의 문제가 해결되는가?

- 비밀값이 원장을 통해 전달됨 → 별도 비밀 채널이 필요 없음
- IND-CCA → $C_i$에서 Value 등 코인의 비밀값이 드러나지 않음
- IK-CCA → $C_i$가 누구의 공개키로 암호화됐는지 알 수 없음
- → $C_1, C_2$를 추가해도 보낸 금액과 받는 주소가 노출되지 않음
- 대신 받는 사람은 원장의 모든 Pour Transaction에 대해 복호화를 시도해야 함

#### Step 5: Public Outputs

**→ 문제: 코인을 다시 Bitcoin으로 바꿀 방법이 없음**

- 지금까지의 구성으로는 Mint, 병합, 분할만 가능
- 코인을 Base Currency(기본 통화, 여기서는 Bitcoin)로 되돌리는 Redeem(환전)은 불가능

**⇒ 해결: Pour에 Public Output(공개 출력) 추가**

- 코인을 소비할 때 u가 두 값을 추가로 지정

	- $v_{pub} \geq 0$: 공개적으로 꺼낼 Value
	- $info \in \{0,1\}^*$: 임의 길이의 문자열, $v_{pub}$를 보낼 곳을 지정 (예: Bitcoin 지갑 공개키)

- POUR의 Value 보존 식 변경

	- $v^{new}_1 + v^{new}_2 + v_{pub} = v^{old}$
	- 정식 구성(입력 2개): $v^{new}_1 + v^{new}_2 + v_{pub} = v^{old}_1 + v^{old}_2$

- $v_{pub}$는 $\pi_{POUR}$의 공개 입력에 추가됨

- $Tx_{Pour} := (rt, sn^{old}, cm^{new}_1, cm^{new}_2, v_{pub}, info, \pi_{POUR}, C_1, C_2)$

- 공개 출력은 선택 사항: 꺼내지 않으면 $v_{pub} = 0$

$v_{pub}$의 사용 (Bitcoin과 통합할 때)

- info에 Bitcoin 출력 Script를 넣음 → $v_{pub}$를 Bitcoin 방식 Transaction의 입력처럼 사용

- $v_{pub}$는 다음 중 하나로 쓰임

	- 일반 Bitcoin 출력 (예: 공개키로 지불)
	- Mint Transaction의 입력 (새 코인 발행)
	- 가져가지 않은 부분은 Transaction Fee(수수료)

- Transaction Fee = Bitcoin 입력 합($v_{pub}$ 포함) − Bitcoin 출력 합(Mint의 v 포함)
	- 수수료는 $v_{pub}$로 내므로 항상 공개됨

- Mint에서는 v BTC가 사라지고 같은 Value의 코인이 생김. Pour에서는 $v_{pub}$만큼 코인이 사라지고 같은 양의 BTC가 새로 생김

Why 이 구조로 Step 5의 문제가 해결되는가?

- $v_{pub}$만큼 Bitcoin으로 꺼낼 수 있음 → Redeem과 수수료 지불 가능
- Step 5에서 새로 공개되는 것은 $v_{pub}$와 info뿐 → $v^{new}_1, v^{new}_2$와 받는 주소는 여전히 숨겨짐
- 단, info는 $\pi_{POUR}$의 공개 입력에 들어가지 않음 → Step 6의 문제

#### Step 6: Non-Malleability

**→ 문제: 남의 Pour Transaction을 고쳐도 여전히 유효함**

- Malleability Attack(가변성 공격): 원장에 추가되기 전의 유효한 Transaction을 가로채 일부를 바꾸고, 바꾼 Transaction도 유효하게 만드는 공격
- 예: info를 바꿔 $v_{pub}$를 공격자의 Bitcoin 주소로 보냄 (횡령)
- info, $C_1, C_2$는 $\pi_{POUR}$의 공개 입력에 포함되지 않음 → 바꿔도 $\pi_{POUR}$는 그대로 유효

**⇒ 해결: 일회용 서명 + 서명 키를 소비 권한에 묶기**

여기부터는 정식 구성(입력 2개 → 출력 2개) 기준 ($h_i$가 입력 코인마다 하나씩 필요)

1. One-Time Signature(일회용 서명) 키 쌍 $(pk_{sig}, sk_{sig})$를 Pour마다 새로 생성

2. $h_{Sig} := CRH(pk_{sig})$

3. 입력 코인마다 $h_i := PRF^{pk}_{a^{old}_{sk,i}}(i \| h_{Sig})$ ($i \in \{1, 2\}$)

	- MAC(Message Authentication Code, 메시지 인증 코드) 역할: $h_{Sig}$를 각 입력 코인의 $a^{old}_{sk,i}$에 묶음

4. POUR 수정

	- 공개 입력에 $h_{Sig}, h_1, h_2$ 추가: $x := (rt, sn^{old}_1, sn^{old}_2, cm^{new}_1, cm^{new}_2, v_{pub}, h_{Sig}, h_1, h_2)$

	- 조건 추가: $h_i = PRF^{pk}_{a^{old}_{sk,i}}(i \| h_{Sig})$

5. $\pi_{POUR}$를 만든 뒤, Pour에 관련된 값 전체에 서명

	- $m := (x, \pi_{POUR}, info, C_1, C_2)$

	- $\sigma := S_{sig}(sk_{sig}, m)$

6. 최종 Pour Transaction

	- $Tx_{Pour} := (rt, sn^{old}_1, sn^{old}_2, cm^{new}_1, cm^{new}_2, v_{pub}, info, *)$

	- $* := (pk_{sig}, h_1, h_2, \pi_{POUR}, C_1, C_2, \sigma)$

서명 방식 조건

- SUF-1CMA(One-Time Strong Unforgeability against Chosen-Message Attacks, 선택 메시지 공격에 대한 일회용 강한 위조 불가능성): 공격자가 고른 메시지 하나의 서명을 본 뒤에도, 그와 다른 유효한 (메시지, 서명) 쌍을 만들 수 없음 (같은 메시지의 다른 서명도 포함)

- 구현에서는 ECDSA(Elliptic Curve Digital Signature Algorithm, 타원 곡선 디지털 서명 알고리즘) 사용
	- 표준 ECDSA는 $(r, s)$와 $(r, -s)$가 모두 유효한 서명이라 가변적 → s를 하위 절반으로 제한한 변형 사용
	- 논문 저자들도 이 변형의 SUF-1CMA 형식 증명은 알지 못한다고 밝힘

검증 (VerifyTransaction)

- $h_{Sig} := CRH(pk_{sig})$를 계산해 x와 m을 다시 구성

- $pk_{sig}$로 m에 대한 σ 검증 + x에 대한 $\pi_{POUR}$ 검증 → 둘 다 통과해야 유효

Why 이 구조로 Step 6의 문제가 해결되는가?

- info나 $C_1, C_2$를 바꿈 → m이 바뀜 → σ 검증 실패
- $pk_{sig}$는 그대로 두고 다시 서명 → $sk_{sig}$를 모름 → SUF-1CMA이므로 위조 불가

- 자신의 키 $pk'_{sig}$로 교체 → $h'_{Sig}$가 바뀜 → 새 $h'_i$와 새 $\pi_{POUR}$가 필요
	- $h'_i = PRF^{pk}_{a^{old}_{sk,i}}(i \| h'_{Sig})$는 $a^{old}_{sk,i}$를 모르면 계산할 수 없음
	- $a^{old}_{sk,i}$는 비밀이고 $h_{Sig}$는 높은 확률로 Pour마다 다름 → $h_1, h_2$는 예측 불가

- 다른 $pk'_{sig}$로 같은 $h_{Sig}$를 만들기 → CRH 충돌을 찾아야 함
- → 서명이 x($h_{Sig}, h_1, h_2$ 포함), $\pi_{POUR}$, info, $C_1, C_2$를 하나로 묶음
- 이 성질이 보안 속성 Transaction Non-Malleability(트랜잭션 가변 불가능성)


### Final Zerocash Protocol

Zerocash의 최종 DAP Scheme은 6개 알고리즘으로 구성됨

1. **Setup**: 신뢰할 수 있는 주체가 최초 1회 실행해 공개 파라미터 pp 생성 ($pk_{POUR}, vk_{POUR}$, 암호화와 서명의 파라미터)
2. **CreateAddress**: 코인을 받고 쓰는 데 필요한 Address Key Pair $(addr_{pk}, addr_{sk})$ 생성
3. **Mint**: Basecoin을 예치하고 같은 Value의 코인 생성, $Tx_{Mint} := (v, k, s, cm)$을 원장에 기록
4. **Pour**: 입력 코인 2개를 소비해 새 코인 2개를 만들고, $\pi_{POUR}$, 암호문, 서명을 담은 $Tx_{Pour}$ 생성
5. **VerifyTransaction**
	- Mint: $\text{COMM}_s(v \| k) = cm$ 확인
	- Pour: sn 중복 여부, rt가 원장에 나온 Root인지, 서명 σ, $\pi_{POUR}$ 확인
6. **Receive**: 원장의 Pour Transaction 암호문을 복호화하고, cm 일치와 sn 미사용을 확인해 자기 코인 찾기

⇒ Mint로 만든 코인은 Pour로 전송, 분할, 병합할 수 있고, 필요하면 Public Output으로 Basecoin으로 꺼낼 수 있음


### 보안 속성

- **Ledger Indistinguishability(원장 구별 불가능성)**: 원장은 공개 정보(Mint한 코인의 Value, $v_{pub}$, info, 전체 Transaction 수 등) 외에 새로운 정보를 드러내지 않음
- **Transaction Non-Malleability(트랜잭션 가변 불가능성)**: 유효한 Pour Transaction을 바꿔, 같은 코인을 다른 방식으로 소비하게 만들 수 없음
- **Balance(잔액 보존)**: 누구도 자신이 Mint하거나 받은 것보다 많은 Value를 가질 수 없음

논문은 이 구성이 세 성질을 모두 만족함을 증명한다. 단, zk-SNARK 때문에 공개 파라미터를 만드는 Trusted Setup(신뢰 설정)이 한 번 필요하다.

- Setup이 오염되면 증명의 Soundness(건전성)가 보장되지 않음 → Transaction Non-Malleability와 Balance가 깨질 수 있음
- Ledger Indistinguishability(익명성)는 Setup이 오염되어도 유지됨

### 한계

- **Trusted Setup**: 1회의 신뢰 설정이 필요함
- **증명 생성 비용**: Pour 1회에 2분 2.01초(Intel Core i7-4770 Desktop, 단일 스레드), Proving Key 896 MiB 필요
- **저장 공간**: SNList(소비된 코인의 sn 목록)는 Bitcoin의 UTXO Set과 달리 줄어들지 않고 계속 커짐
- **수신 비용**: 자기 코인을 찾으려면 모든 Pour Transaction의 암호문에 복호화를 시도해야 함
- **Network Layer**: 원장만 익명화함 → IP 주소 등은 Tor 같은 별도 익명 네트워크 필요

### 결론

Zerocash는 Bitcoin 같은 공개 원장 위에서 Origin(출처), Destination(수신자), Amount(금액)를 모두 숨기면서도, 누구나 Transaction의 유효성을 검증할 수 있는 DAP Scheme을 정의하고 구현했다. 핵심은 코인의 내용 대신 Commitment를 원장에 기록하고, 코인을 쓸 때는 어느 Commitment를 소비하는지 밝히지 않은 채 sn을 공개하고 zk-SNARK Proof로 소비 권한과 Value 보존을 증명하는 것이다. 이미 공개된 sn은 거부해 Double Spending을 막는다. 그 위에 Step 2~6을 더해 확장성, 임의 Value와 직접 지불, 비밀값 전달, Bitcoin과의 연결, Transaction 변조 방지를 해결했다. 대가는 한 번의 Trusted Setup과 무거운 증명 생성이다.

논문은 Zerocash가 규제와 감독을 어렵게 한다는 비판을 받을 수 있다고 인정하면서도, zk-SNARK를 쓰면 거래 내역을 드러내지 않고 세금 납부 같은 정책 준수를 증명할 수 있다고 본다. 이 구성은 이후 Zcash의 기반이 되었다([Zcash 프로토콜 명세](https://data.kando.tech/sites/default/files/2022-03/zcash-whitepaper.pdf)).
