## Bitcoin

### What is Bitcoin?

Bitcoin은 은행과 같은 Trusted Third Party(신뢰할 수 있는 제3자)의 중개 없이 사용자 간 직접 가치를 전송할 수 있도록 설계된 탈중앙화 P2P(Peer-to-Peer) 전자화폐 시스템이다.
 
Bitcoin 네트워크에서 사용하는 화폐 단위는 BTC이며, 최소 단위는 Satoshi(1 BTC = $$10^8$$ Satoshi)이다.

### UTXO (Unspent Transaction Output)

UTXO는 아직 다른 트랜잭션의 Input으로 소비되지 않은 Output이다. Bitcoin 프로토콜은 계정별 잔액을 직접 저장하지 않으며, 사용자의 잔액은 해당 사용자가 소비할 수 있는 UTXO의 금액 합계로 계산한다.

노드는 **UTXO Set(현재 소비되지 않은 Output의 집합)**을 유지한다. 트랜잭션의 Input이 참조하는 UTXO가 존재하고 소비 조건을 충족해야 유효하다. 블록이 체인에 연결되면 소비된 UTXO를 제거하고 새로 생성된 UTXO를 추가한다.

예시: A가 0.5 BTC와 0.3 BTC의 UTXO를 사용하여 B에게 0.6 BTC를 전송

    - Input: 0.5 BTC UTXO, 0.3 BTC UTXO (총 0.8 BTC)
    - Output 1: 0.6 BTC → B의 주소
    - Output 2: 0.1999 BTC → A의 새 주소(잔돈)
    - Transaction Fee: 0.8 − 0.7999 = 0.0001 BTC

- 결과: 기존 UTXO 2개(0.5, 0.3 BTC)가 UTXO Set에서 제거되고, 새로운 UTXO 2개(0.6, 0.1999 BTC)가 추가된다.

**UTXO Model vs. Account Model**
 
| | UTXO Model (Bitcoin) | Account Model (Ethereum) |
| --- | --- | --- |
| 상태 | 미사용 Output의 집합 | 계정별 잔액, Nonce, 코드 및 저장 상태 |
| 트랜잭션 | UTXO 소비 및 새 Output 생성 | 계정 및 컨트랙트 상태 변경 |
| 잔액 | 소비 가능한 UTXO의 금액 합계 | 계정 상태에 직접 저장 |
| Double Spending 방지 | 참조한 UTXO가 UTXO Set에 있는지 확인 | Nonce 및 상태 전이 검증 |
| 병렬 검증 | 서로 다른 UTXO를 쓰는 트랜잭션끼리 독립적으로 검증 가능 | Nonce 및 공유 상태에 따른 순서 의존성 존재 |

### What is a Bitcoin Transaction?

Bitcoin Transaction은 기존 UTXO를 Input으로 소비하고, 새로운 Output을 생성하여 BTC의 소유권을 이전하는 데이터 구조다.

- **Input**: 이전 트랜잭션의 Output을 참조하고, 해당 Output을 소비할 권한을 증명하는 데이터(일반적으로 서명 등)를 포함한다.

- **Output**: 금액(satoshi 단위)과 해당 Output을 소비하기 위해 충족해야 하는 잠금 조건(scriptPubKey)으로 구성된다. Address(주소)는 수신 조건에 관한 정보를 문자열로 인코딩한 것이며, 트랜잭션에 별도 필드로 저장되지는 않는다.

- UTXO 소비: UTXO는 부분적으로 소비할 수 없으므로 전체 금액을 소비해야 한다. 남는 금액은 송신자가 통제하는 새로운 Output(잔돈)으로 반환 가능
- Transaction Fee = Input 금액 합 − Output 금액 합. 별도로 명시되지 않으며, 잔돈 Output이 없다면 다른 Output에 할당되지 않은 차액이 모두 수수료가 됨
- Coinbase Transaction: 블록의 첫 트랜잭션. 이전 UTXO를 참조하지 않고 블록 보조금(새로 발행되는 BTC)과 트랜잭션 수수료를 새로운 Output으로 만듦. BTC는 블록 보조금을 통해서만 발행됨

### What Information Is Public?

Bitcoin 트랜잭션의 입력과 출력, 금액은 누구나 확인할 수 있으며, 일반적인 주소 기반 거래에서는 송신 및 수신 주소도 추적할 수 있다.

- Origin Address(송신 주소): Input이 가리키는 이전 Output에서 알 수 있음
- Destination Address(수신 주소): Output의 잠금 스크립트에서 도출할 수 있음
- Payment Amount(결제 금액): 각 Output의 금액이 공개됨

Input 금액도 이전 Output을 조회하여 확인할 수 있으므로, 전체 수수료를 계산하고 잔돈 Output을 추정할 수 있다.

### How Are Transactions Recorded?

Bitcoin 트랜잭션은 Block에 포함되어 Public Ledger(공개 원장)인 Blockchain에 기록된다.

- 각 블록은 이전 블록의 해시를 포함하여 체인 형태로 연결된다.

- 블록은 **Proof-of-Work(PoW, 작업 증명)**를 통해 생성된다. Miner(채굴자)는 블록 헤더의 해시가 목표값 이하가 되는 값을 찾기 위해 반복적으로 해시를 계산한다.

- Blockchain은 다수의 Peer(피어)가 복제하고 검증하는 Distributed Ledger(분산 원장)으로, 기록된 트랜잭션 정보는 누구나 조회할 수 있다.

### Double Spending and the Public Ledger

**중앙 기관이 없는 Bitcoin은 Double Spending을 어떻게 방지하는가?**

- Double Spending(이중 지불): 동일한 자금을 두 번 사용하는 행위로, Bitcoin에서는 같은 UTXO를 서로 충돌하는 트랜잭션에서 중복 소비하려는 것을 의미한다.

- 이미 소비된 UTXO는 UTXO Set에서 제거되므로 다시 소비할 수 없다.

하지만 UTXO Set 검사만으로는 충분하지 않다. 노드마다 트랜잭션을 수신하는 순서가 다를 수 있으므로, 모든 노드가 유효한 거래 기록과 그 순서에 합의해야 한다.

**→ Bitcoin의 해결책: Public Ledger + Consensus**

- 모든 온체인 트랜잭션이 공개 원장에 기록되므로, 각 UTXO가 중복 소비되지 않았는지 누구나 검증할 수 있다.

- 동일한 UTXO를 소비하는 두 트랜잭션이 경쟁하면, 노드는 유효한 체인 중 누적 작업량이 가장 큰 체인을 선택한다. 해당 체인에 포함된 트랜잭션이 인정되며, 충돌하는 트랜잭션은 같은 체인에 함께 포함될 수 없다.

- Bitcoin의 확정성은 확률적이다. 후속 블록이 쌓일수록 기존 거래가 뒤집힐 가능성은 일반적으로 낮아진다.

**→ 하지만 Privacy(프라이버시) 문제가 발생한다.**

- 누구나 거래를 검증할 수 있도록 Input이 참조하는 Output과 거래 금액 등이 공개되며, 이러한 참조 관계는 Transaction Graph를 형성한다. Transaction Graph를 거슬러 올라가면 모든 UTXO의 생성 이력은 궁극적으로 Coinbase Transaction에 도달한다.

- 주소와 실제 사용자의 신원이 연결되면 해당 사용자의 소비 내역, 주소별 잔액 및 자금 흐름이 제3자에게 노출될 수 있다.

### Bitcoin's Privacy Problem

Bitcoin은 완전한 Anonymity(익명성)이 아닌 **Pseudonymity(가명성)**을 제공한다. 사용자는 실명 대신 주소를 사용하고 여러 주소를 생성할 수 있지만, Transaction Graph 분석을 통해 동일한 사용자의 주소들이 연결될 수 있다.
    - Transaction Graph: 트랜잭션의 Input과 이전 Output의 참조 관계로 형성되는 그래프다. UTXO의 생성 이력을 거슬러 올라가면 궁극적으로 Coinbase Transaction에 도달한다.

- Common-Input-Ownership Heuristic(공통 입력 소유 휴리스틱): 하나의 트랜잭션에서 사용된 여러 Input이 동일한 소유자에게 속한다고 추정하는 기법이다.
    - 예시: 0.5 BTC와 0.3 BTC UTXO가 하나의 트랜잭션에 사용되었다면, 두 UTXO를 모두 A의 것으로 추정한다.

- Change Address Heuristic(잔돈 주소 휴리스틱): Output 중 송신자에게 반환되는 잔돈을 식별하여 기존 주소와 새로운 주소를 연결하는 기법이다. 금액이 딱 떨어지지 않는 Output이나 처음 쓰이는 주소로 가는 Output을 잔돈으로 추정한다.
    - 예시: 0.1999 BTC Output은 금액이 딱 떨어지지 않으므로 잔돈으로 추정할 수 있고, 그러면 A의 새로운 주소도 기존 주소와 연결할 수 있다.

- 두 휴리스틱 모두 추정에 기반하므로 잘못된 결과를 낼 수 있다. 특히 여러 사용자가 공동으로 트랜잭션을 생성하는 CoinJoin에서는 Common-Input-Ownership Heuristic이 성립하지 않을 수 있다.

- Transaction Graph, 거래 금액, 블록 타임스탬프 등의 온체인 정보와 외부 정보를 분석하면 주소 간 관계를 파악하고 실제 사용자를 식별할 가능성이 있다.

- Fungibility(대체 가능성): 동일한 단위의 화폐가 거래 이력과 관계없이 동등하게 취급되는 성질이다. Bitcoin은 UTXO의 거래 이력을 추적할 수 있으므로 특정 이력을 가진 UTXO가 다르게 취급될 수 있으며, 이는 대체 가능성을 약화시키는 요인이 된다.

- 중앙화 결제 시스템과의 차이: 기존 결제 시스템에서는 거래 내역에 대한 접근이 은행, 결제 처리업체 등 제한된 당사자에게 주어지는 반면, Bitcoin의 온체인 거래 내역은 누구나 조회할 수 있다. 따라서 Bitcoin은 기존 결제 시스템과 다른 프라이버시 위험을 가진다.

## Problem Definition

Bitcoin은 중앙 기관 없이 Double Spending을 방지하기 위해 트랜잭션의 Input, Output 및 금액을 공개하고, 누구나 이를 검증할 수 있도록 한다.

→ 공개된 거래 정보로 자금 흐름을 추적할 수 있다.

→ 주소가 실제 사용자와 연결되면 소비 내역, 잔액 및 자금 흐름이 노출될 수 있으며, Fungibility도 위협받는다.

→ 그러나 거래 정보를 단순히 숨기면 기존 방식으로는 거래의 유효성을 공개적으로 검증하기 어렵다.

**해결책이 만족해야 하는 조건**
 
- 송신자, 수신자 및 금액을 숨기면서도 Double Spending과 부당한 자금 생성이 발생하지 않았음을 누구나 검증할 수 있어야 한다.

- 이러한 프라이버시와 검증 가능성은 사용자의 별도 조치나 특정 제3자에 대한 신뢰 없이 기본적으로 제공되어야 한다.

## Solutions

### Solution 1: Mixing

- Mix(믹서): Laundry 또는 Tumbler라고도 부름. 사용자가 중앙 운영자의 풀에 코인을 맡기고, 일정 시간 뒤 같은 총액의 다른 코인을 돌려받는 서비스
- 한계
  - 충분히 많은 코인이 섞이려면 돌려받기까지의 지연이 길어야 함
  - 운영자가 코인을 추적할 수 있음
  - 운영자가 코인을 훔칠 수 있음
- 논문: 숨길 것이 있는 사용자는 이 위험을 감수할 수 있음. 그러나 일반 사용자는 위험을 피하려 하고, 프라이버시 보호에 계속 노력을 들이고 싶어 하지 않으며, 프라이버시가 침해된 사실을 잘 알아채지 못함
- CoinJoin: 중앙 운영자 대신 여러 사용자가 함께 서명하는 Multi-Signature(다중 서명) 트랜잭션으로 코인을 섞음
  - 현재 온라인인 사용자끼리 적은 양만 섞을 수 있음
  - 제3자의 Denial-of-Service(서비스 거부) 공격에 취약함
  - 섞을 상대를 찾는 노력이 필요함

### Solution 2: Zerocoin

- Zerocoin(Miers, Garman, Green, Rubin, IEEE S&P 2013): Bitcoin에 익명성을 더하는 프로토콜. 논문은 이를 완전한 익명 화폐가 아니라 Decentralized Mix(탈중앙화 믹서)로 봄
- 쓰는 도구
  - Serial Number(일련번호): 코인마다 하나뿐인 값. 코인을 쓸 때 공개하며, 같은 값이 다시 나오면 Double Spending으로 판단함
  - Commitment(커밋먼트): 값을 숨긴 채 고정해 두는 암호 도구. 나중에 값과 비밀 난수를 공개하면 누구나 맞는지 확인할 수 있음 (Notation and Building Blocks 절)
  - Zero-Knowledge Proof(영지식 증명): 명제가 참이라는 사실 외에는 아무것도 드러내지 않는 증명
- 동작
  - Mint: Bitcoin을 내고, 임의의 Serial Number $$sn$$에 대한 Commitment $$cm$$을 원장에 기록함
  - Spend: 수신 주소, $$sn$$, 그리고 "나는 $$sn$$으로 열리는 $$cm$$과 그 난수 $$r$$을 알고, 그 $$cm$$은 과거에 발행되었다"는 Zero-Knowledge Proof를 제출함
  - 증명이 맞고 $$sn$$이 처음 나온 값이면, 해당 금액의 Bitcoin이 수신 주소로 감
  - 증명이 Zero Knowledge이므로 Spend가 어느 Mint에서 왔는지 연결할 수 없음 → 결제의 Origin(출처)이 숨겨짐
  - Commitment로 Pedersen Commitment $$cm := g^{sn} h^{r}$$를 씀
- 한계
  - Destination(목적지)과 금액은 숨기지 못함
  - 고정 액면 코인만 씀. 정확한 금액을 지불할 수 없고, 거스름돈을 줄 수 없음. 슬라이드는 단일 액면이라 금액이 드러난다고 설명함
  - 다른 사용자에게 직접 지불하는 방법이 없음 → 일상 거래는 Bitcoin으로 하고, 사용자가 주기적으로 Bitcoin을 "세탁"하는 별도 절차를 거쳐야 함
  - 성능: Spend 증명이 45 kB를 넘고 검증에 450 ms가 걸림 (128-bit 보안 수준)
    - 이 증명은 네트워크로 전파되고, 모든 노드가 검증하고, 원장에 영구 저장됨 → 비용이 Bitcoin보다 몇 자릿수 큼
    - 이 공개 수치는 일부 구성 요소에 80-bit 파라미터를 섞어 쓴 값이며, 모두 128-bit로 맞추면 비용이 더 커짐
- 정리: Zerocoin은 Origin만 숨기는 Decentralized Mix임. Destination과 금액까지 숨기고, 임의 금액을 상대에게 직접 지불하는 완전한 화폐가 필요함 → Zerocash

### Solution 3: Zerocash

- DAP Scheme(Decentralized Anonymous Payment Scheme, 탈중앙화 익명 결제 스킴): 논문이 새로 정의한 개념. 임의 금액을 직접 익명으로 지불할 수 있는 탈중앙 전자화폐
- Zerocash: DAP Scheme을 실제로 구현한 시스템
- Bitcoin(또는 비슷한 원장 기반 화폐) 위에 얹히도록 설계된 Privacy-Preserving Protocol(프라이버시 보호 프로토콜)
  - 논문: 어떤 원장 위에도 얹을 수 있음 (중앙은행이 관리하는 원장 포함)
- 할 수 있는 것
  - 사용자끼리 직접 지불
  - 금액을 자유롭게 정함 (Variable Denomination, 가변 액면)
  - 결제 트랜잭션이 Origin, Destination, Amount(금액)를 드러내지 않음
  - 상대의 고정 주소로 상호작용 없이 지불
- 기존 Bitcoin 결제를 대체하는가
  - 논문은 기능과 성능이 크게 나아졌으므로, Zerocash로 기존 Bitcoin 결제를 익명 결제로 완전히 대체할 수 있다고 주장함. 1000노드 실험 결과를 근거로, Bitcoin에서 갈라져 나온 화폐로서 같은 규모에서 운영할 수 있다고 봄
  - 다만 논문은 Bitcoin 자체에 바로 넣는 것은 가까운 시일 안에 기대하지도 권하지도 않고, 별도 화폐로 쓰기를 제안함 (Integration with Bitcoin 절)

**Basecoin과 zerocoin**

- Basecoin: Zerocash가 얹히는 Base Currency(기반 화폐, 예: Bitcoin)를 일반화해 부르는 이름. 거래 내역이 공개되는 기존 화폐
- zerocoin: 논문은 Zerocash의 익명 화폐를 Bitcoin과 같은 원장에서 함께 쓰는 방식(Hybrid Currency, 혼합 화폐)을 설명하면서, 그 익명 화폐를 zerocoin이라 부름. Bitcoin과 1:1로 바꿀 수 있음
  - 논문은 화폐 단위를 소문자로 적음(bitcoin, zerocoin). 이 글도 논문 표기를 따름
  - 논문은 Zerocoin 프로토콜의 코인도 같은 단어로 부르기도 하므로, 어느 쪽인지는 문맥으로 구별해야 함

**Mint와 Pour**

- Zerocash가 원장에 추가하는 새 트랜잭션은 두 종류뿐임
  - Mint(발행): Basecoin을 내고 같은 가치의 익명 코인을 만듦
  - Pour(붓기): 익명 코인을 소비하고, 그 가치를 새 익명 코인에 부어 넣음
- Pour 하나로 송금, 거스름돈, Bitcoin으로 환전, 트랜잭션 수수료를 모두 처리함. 코인의 Split(분할)과 Merge(병합)도 Pour로 함
- Redeem(Basecoin으로 되돌리기)은 별도 트랜잭션이 아님. Pour의 Public Output(공개 출력) $$v_{\mathrm{pub}}$$로 처리함 (Step 5)
- JoinSplit은 Zerocash의 용어가 아님. 후속 시스템 Zcash가 Mint와 Pour를 합쳐 만든 연산의 이름임 (After Zerocash: Zcash 절)

**무엇이 공개되고 무엇이 숨겨지는가**

- Coin Commitment(코인 커밋먼트): 코인을 원장에 기록할 때 쓰는 Commitment (Step 1)

| 트랜잭션 | 공개되는 것 | 숨겨지는 것 |
| --- | --- | --- |
| Mint | 발행 금액 $$v$$, Coin Commitment $$cm$$(검증용 값 $$k$$, $$s$$ 포함) | 코인을 소유하는 주소, Serial Number |
| Pour | 소비한 코인들의 Serial Number, 새 코인들의 Coin Commitment, 공개 출력 금액 $$v_{\mathrm{pub}}$$와 그 목적지 정보 $$\mathrm{info}$$ | 어떤 코인을 소비했는지, 입력 코인과 출력 코인의 금액, 새 코인을 받는 주소 |

- Pour에는 증명, 서명, 암호문도 함께 오르지만, 이 값들은 숨겨진 정보를 드러내지 않음 (Security 절의 Ledger Indistinguishability)
- 공개되는 금액은 Basecoin과 익명 코인 사이를 오가는 금액($$v$$, $$v_{\mathrm{pub}}$$)임
- 트랜잭션 수수료는 Zerocash만 쓰는 시스템에서도 숨길 수 없는 유일한 출력임
- 즉 모든 단계에서 아무것도 드러나지 않는 것은 아님. 익명 코인끼리 오가는 부분의 송신자, 수신자, 금액이 숨겨짐

**In Proofs We Trust**

- 슬라이드의 비유: 사용자가 "이 돈은 지난밤 받은 것이고, 이전 거래에서 쓴 적이 없다"고 주장하면, 회계사의 서명 대신 Zero-Knowledge Proof가 이 주장을 보증함 → 암호학적 증명이 "Virtual Accountant(가상 회계사)" 역할을 함
- 원장에 코인 정보를 공개하는 대신 증명을 신뢰함
- Zerocash가 쓰는 증명은 zk-SNARK(Zero-Knowledge Succinct Non-Interactive Argument of Knowledge)임. 증명이 매우 짧고 검증이 빠른 Zero-Knowledge Proof (Notation and Building Blocks 절)
- 실제 구성에서는 이 주장이 두 부분으로 나뉨
  - zk-SNARK 증명이 보이는 것: 소비하는 코인을 소유함, 그 코인의 Commitment가 원장에 있음, 공개한 Serial Number가 그 코인의 것임, 새 Coin Commitment가 새 코인의 것임, 금액 합이 맞음
  - 원장 검사가 보장하는 것: "이전에 쓴 적 없음". 검증자는 공개된 Serial Number가 원장에 이미 있으면 트랜잭션을 거절함
- → Double Spending을 막을 수 있음. 코인 하나에는 유효한 Serial Number가 하나뿐이고(Step 1, Step 3), 같은 Serial Number는 원장에 두 번 들어갈 수 없기 때문

**주요 결과**

| 항목 | 값 | 조건 |
| --- | --- | --- |
| Spend당 증명 크기 | 288 B | 128-bit 보안 수준 |
| 증명 검증 시간 | 6 ms 미만 | Desktop 1 Thread에서 zk-SNARK 검증 5.4 ms, Pour 트랜잭션 검증 5.7 ms. Laptop 1 Thread에서는 zk-SNARK 검증 8.5 ms |
| 증명 생성 시간 | 1분 미만 | Desktop 4 Threads에서 46 s. Desktop 1 Thread에서는 1 min 59 s, Laptop 1 Thread에서는 2 min 55 s |
| 지원 코인 수 | $$2^{64}$$개 | 코인 목록을 담는 트리의 깊이가 64 (Step 2). 슬라이드는 증명 생성 시간이 코인 수의 로그에 비례한다고 설명함 |
| 시스템 파라미터 | 896 MiB | 대부분 증명용 키. 한 번 만들고 시스템 수명 내내 고정됨 (슬라이드는 896MB로 표기) |
| Pour 트랜잭션 크기 | 996 B + $$\mathrm{info}$$ 길이 | 논문의 "1 kB 미만"은 $$\mathrm{info}$$를 뺀 크기 |

- Desktop과 Laptop의 사양, Thread 수별 전체 수치는 Evaluation 절에 있음
- Zerocoin과 비교: 트랜잭션 크기 45 kB 초과 → 1 kB 미만, 검증 시간 450 ms → 6 ms 미만. 논문은 개선율을 각각 97.7% 초과, 98.6% 초과로 적음. Zerocoin 수치로 계산하면 약 97.8%, 98.7%로 일치함
- 코인 수에 대한 복잡도: 키 생성과 증명은 Polylogarithmic(코인 수 $$n$$에 대해 $$(\log n)^c$$ 꼴로 증가), 검증은 상수
  - 비교: Pinocchio Coin(Danezis, Fournet, Kohlweiss, Parno, 2013)은 Zerocoin의 증명을 zk-SNARK로 바꿔 Spend당 344 B로 줄였지만, 회로가 모든 코인에 대한 곱을 직접 계산하므로 세 비용이 모두 코인 수에 대해 초선형으로 늘어남. 고정 액면만 지원함
- Trusted Setup(신뢰 설정): 처음에 신뢰 당사자가 시스템 파라미터를 만드는 과정. 한 번 신뢰해야 함
- 암호 가정
  - Pairing-Based Elliptic Curve Cryptography(페어링 기반 타원곡선 암호)
  - Knowledge of Exponent 가정: 덜 일반적인 가정. 논문은 상당히 강한 가정이지만 zk-SNARK 구성에 본질적으로 필요할 수 있다는 근거가 있다고 설명함
  - SHA256(Secure Hash Algorithm 256), 암호화 스킴, 서명 스킴의 성질

## Zerocash Construction

- 논문은 단순한 구성에서 시작해 문제를 하나씩 해결하며 6단계로 최종 구성에 도달함. 6단계는 개요 설명이며, 논문의 정식 구성과 세부가 다른 곳은 따로 표시함
- 각 Step은 다음 순서로 정리함
  1. 문제: 이 단계가 해결하려는 것
  2. 구조: 이 단계에서 새로 생기거나 바뀌는 데이터
  3. 동작 순서: 각 연산을 실행 순서대로 나열한 것
  4. 해결되는 이유
  5. 남은 문제: 다음 Step으로 넘어가는 이유
- Step 1~6을 모두 반영한 최종 구조와 전체 동작 순서는 Final Construction 절에 있음

### Notation and Building Blocks

| 표현 | 이름 | 의미 |
| --- | --- | --- |
| $$\mathrm{COMM}_r(m)$$ | Commitment | 값 $$m$$을 숨긴 채 고정해 둔 값. $$r$$과 $$m$$을 공개하면 누구나 다시 계산해 확인할 수 있음 |
| $$r$$, $$s$$ | Trapdoor(트랩도어) | Commitment를 만들 때 쓰는 비밀 난수. 이 값을 모르면 공개된 Serial Number를 보고도 어느 Commitment에 해당하는지 알 수 없음 |
| $$sn$$ | Serial Number | 코인마다 하나뿐인 값. 코인을 쓸 때만 공개함 |
| $$cm$$ | Coin Commitment | 코인을 나타내는 Commitment. 코인을 만들 때 원장에 기록됨 |
| $$c$$ | Coin(코인) | 코인의 비밀값 묶음. 소유자의 지갑에만 있음 |
| CMList | Coin Commitment List | 원장에 기록된 모든 Coin Commitment의 목록 |
| SNList | Serial Number List | 원장에 공개된 모든 Serial Number의 목록. 즉 이미 쓴 코인의 목록 |
| $$rt$$ | Merkle Tree Root | CMList의 모든 Coin Commitment를 Leaf로 하는 Merkle Tree의 Root (아래 설명) |
| $$\pi$$ | zk-SNARK Proof | 비밀값을 드러내지 않고 규칙대로 코인을 쓴다는 것을 보이는 증명. 코인을 아직 쓰지 않았다는 사실은 증명하지 않음 |

**Commitment의 성질**

- Hiding(은닉): Commitment만 보고 값을 알 수 없음
- Binding(결속): 한 번 만든 Commitment를 다른 값으로 열 수 없음
- Zerocash의 Commitment는 Statistically Hiding(통계적 은닉: 계산 능력이 무한한 공격자도 값을 알 수 없음)이고 Computationally Binding(계산적 결속: 현실적인 계산 능력으로는 다른 값으로 열 수 없음)임
- Zerocash는 SHA256 기반 Commitment를 씀. Pedersen Commitment는 Zerocoin의 방식임 (Implementation 절)

**CRH와 Merkle Tree**

- CRH(Collision-Resistant Hash, 충돌 저항 해시 함수): 같은 출력을 내는 서로 다른 두 입력을 찾기 어려운 해시 함수
- Merkle Tree(머클 트리): Leaf(리프) 값들을 두 개씩 CRH로 묶어 올라가 하나의 Root(루트)로 요약하는 트리
- Authentication Path(인증 경로): Leaf에서 Root까지의 경로에 있는 형제 노드 값 목록. 이것만으로 어떤 값이 Root가 $$rt$$인 트리의 Leaf임을 확인할 수 있음
- 새 Leaf를 넣을 때 Root 갱신 비용은 트리 깊이에 비례함

**PRF**

- PRF(Pseudorandom Function, 의사 난수 함수): Seed(시드) $$x$$로 정해지는 함수 $$\mathrm{PRF}_x$$. Seed를 모르면 출력이 난수와 구별되지 않음

**Zero-Knowledge Proof와 zk-SNARK**

- NP Statement(NP 명제, NP는 Nondeterministic Polynomial time): 보조 입력이 주어지면 참임을 효율적으로 확인할 수 있는 명제
  - Instance(인스턴스): 누구나 아는 공개 입력
  - Witness(증인): 증명자만 아는 보조 입력
- Zero-Knowledge Proof of Knowledge(영지식 지식 증명): "Witness를 안다"는 사실만 보이고, Witness에 대한 정보는 드러내지 않는 증명
  - 예: Alice가 "나는 30 BTC를 가지고 있다"를 증명할 때, 코인 30개를 가리키고 각 코인의 비밀 키로 서명하면 어떤 코인이 Alice의 것인지 드러남. Zero-Knowledge Proof of Knowledge를 쓰면 "코인 30개를 통제하는 비밀 키들을 안다"는 사실만 드러남
- zk-SNARK: Zero-Knowledge Proof of Knowledge 중 증명이 짧고(Succinct) 상호작용이 없는(Non-Interactive) 것
  - 검증할 명제를 Arithmetic Circuit(산술 회로)로 표현해 다룸. Field(체) 위의 덧셈, 곱셈 같은 Gate(게이트)로 이루어진 회로임
  - KeyGen: 회로로부터 Proving Key(증명 키) $$pk$$와 Verification Key(검증 키) $$vk$$를 만듦. 신뢰 당사자가 한 번 실행하며, 이것이 Trusted Setup임. 두 키는 공개되어 계속 재사용됨
  - Prove: $$pk$$, Instance, Witness로 증명 $$\pi$$를 만듦. 누구나 실행할 수 있음
  - Verify: $$vk$$, Instance, $$\pi$$로 증명을 검증함. 누구나 증명자와 상호작용 없이 실행할 수 있음
- zk-SNARK의 성질
  - Succinctness(간결성): 증명 크기가 상수이고, 검증 시간은 Instance 크기에 선형임(회로 크기와 무관)
  - Proof of Knowledge(지식 증명): 검증을 통과한 증명자로부터 Witness를 추출할 수 있음. 즉 증명자는 Witness를 "앎". 이 보장은 계산 능력이 제한된 증명자에 대해서만 성립하므로 Proof가 아니라 Argument라고 부름
  - Perfect Zero Knowledge(완전 영지식): 증명은 명제가 참이라는 사실 외에 Witness 정보를 전혀 드러내지 않음
- 두 성질이 모두 필요한 이유: Zerocash의 회로는 "SHA256 원상을 안다"처럼 암호 프리미티브에 대한 주장을 검증함. 그래서 Witness가 존재한다는 사실만으로는 부족하고, 증명자가 실제로 안다는 보장과 아무것도 새지 않는다는 보장이 모두 필요함
- Zerocash가 쓰는 구현: Ben-Sasson, Chiesa, Tromer, Virza의 구현(인용 표기 BCTV14). Parno, Gentry, Howell, Raykova의 프로토콜(인용 표기 PGHR13)에 기반하며 128-bit 보안을 제공함

**Key-Private Encryption, One-Time Signature, MAC (Step 4, Step 6에서 사용)**

- Key-Private Encryption(키 비공개 암호화): 다음 두 성질을 만족하는 공개 키 암호화
  - IND-CCA(Indistinguishability under Chosen-Ciphertext Attack): 암호문에서 평문 정보를 얻을 수 없음
  - IK-CCA(Key Indistinguishability under Chosen-Ciphertext Attack): 암호문을 그것을 만든 공개 키나, 같은 공개 키로 만든 다른 암호문과 연결할 수 없음 → 암호문만 보고 수신자를 알 수 없음
- One-Time Signature(일회용 서명): 키 쌍 하나로 한 번만 서명하는 디지털 서명. Zerocash는 SUF-1CMA(One-Time Strong Unforgeability against Chosen-Message Attacks)를 만족하는 서명을 씀. 서명 하나를 본 공격자도 그와 다른 유효한 메시지와 서명 쌍을 만들 수 없다는 뜻임
- MAC(Message Authentication Code, 메시지 인증 코드): 비밀 키를 아는 사람만 만들 수 있는 인증 값. Zerocash는 PRF 출력을 MAC처럼 씀 (Step 6)

### Step 1: User Anonymity with Fixed-Value Coins

**문제**

- 결제의 Origin을 숨기면서 Double Spending을 막아야 함
- 이 단계는 모든 코인의 가치가 1 BTC로 같다고 가정한 단순한 구성임. Zerocoin과 비슷함

**구조**

| 요소 | 정의 |
| --- | --- |
| Serial Number, Trapdoor | $$sn$$, $$r$$: 사용자가 임의로 고르는 값 |
| Coin Commitment | $$cm := \mathrm{COMM}_r(sn)$$ |
| 코인 | $$c := (r, sn, cm)$$. 소유자의 지갑(Private Wallet)에만 있음 |
| Mint 트랜잭션 | $$\mathrm{tx}_{\mathrm{Mint}}$$($$\mathrm{tx}$$는 Transaction 표기): $$cm$$을 담고, $$sn$$과 $$r$$은 담지 않음 |
| Spend 트랜잭션 | $$\mathrm{tx}_{\mathrm{Spend}}$$: $$sn$$과 zk-SNARK 증명 $$\pi$$를 담음 |
| 원장에서 쓰는 목록 | CMList(원장의 모든 Coin Commitment), 이전 Spend 트랜잭션에 나온 Serial Number |
| NP Statement | "나는 $$\mathrm{COMM}_r(sn)$$이 CMList에 나타나게 하는 $$r$$을 안다". Instance는 $$sn$$과 CMList, Witness는 $$r$$ |

**동작 순서**

- Mint (사용자 $$u$$)
  1. 임의의 $$sn$$과 $$r$$을 고름
  2. $$cm := \mathrm{COMM}_r(sn)$$을 계산함
  3. 코인 $$c := (r, sn, cm)$$을 지갑에 보관함
  4. $$cm$$을 담은 $$\mathrm{tx}_{\mathrm{Mint}}$$를 원장에 보냄
  5. 원장은 $$u$$가 Backing Escrow Pool(담보 예치 풀)에 1 BTC를 낸 경우에만 $$\mathrm{tx}_{\mathrm{Mint}}$$를 추가함. 1 BTC는 $$\mathrm{tx}_{\mathrm{Mint}}$$에 평문으로 적은 지불 정보로 낼 수 있음
     - → Mint 트랜잭션은 예치 증명서이고, 코인의 가치는 예치 풀에서 나옴
- Spend (사용자 $$u$$)
  1. Instance $$(sn, \mathrm{CMList})$$와 Witness $$r$$로 zk-SNARK 증명 $$\pi$$를 만듦
  2. $$sn$$과 $$\pi$$를 담은 $$\mathrm{tx}_{\mathrm{Spend}}$$를 게시함
- 검증
  1. $$\pi$$를 검증함
  2. $$sn$$이 원장(이전 Spend 트랜잭션)에 이미 있으면 Double Spending으로 보고 트랜잭션을 버림
  3. 통과하면 $$u$$는 예치된 1 BTC를 회수함. 자신이 갖거나, 다른 사람에게 보내거나, 새 코인을 Mint하는 데 쓸 수 있음

**해결되는 이유**

- 익명성
  - $$\pi$$는 Zero Knowledge → $$sn$$은 공개되지만 $$r$$에 대한 정보는 드러나지 않음
  - CMList의 수많은 $$cm$$ 중 이 Spend에 해당하는 것을 찾는 일은 $$f(x) := \mathrm{COMM}_x(sn)$$을 역산하는 일임. 논문은 이것이 불가능하다고 가정함
  - → Spend가 어느 Mint(어느 예치)에서 왔는지 알 수 없음 → 결제의 Origin이 숨겨짐
  - Step 1에는 아직 소유자 주소가 없음. 숨겨지는 것은 "어느 Mint에서 온 코인인지"임
- Double Spending 방지
  - Commitment의 Binding → $$cm$$ 하나를 서로 다른 $$sn$$으로 열 수 없음 → 코인 하나에 $$sn$$ 하나
  - 원장이 이미 나온 $$sn$$을 거절함 → 같은 코인을 두 번 쓸 수 없음
  - $$\pi$$ 자체는 "아직 쓰지 않았다"를 증명하지 않음. 미사용 여부는 원장의 $$sn$$ 중복 검사가 판단함

**남은 문제**

- Statement가 CMList 전체를 다루므로, 코인이 늘수록 비용이 커짐 → Step 2

### Step 2: Compressing the List of Coin Commitments

**문제: Scalability(확장성)**

- Step 1의 Statement는 CMList를 명시적인 목록으로 다룸
- → 증명 검증을 비롯한 대부분의 알고리즘의 시간, 공간 복잡도가 CMList 크기에 선형으로 증가함
- 이미 쓴 코인의 $$cm$$을 지워서 줄일 수도 없음. Zero Knowledge 성질 때문에 어떤 $$cm$$이 쓰였는지 아무도 모르기 때문

**구조** (Step 1에서 바뀌는 것)

| 요소 | 정의 |
| --- | --- |
| Merkle Tree | CMList 위에 유지하는 Append-Only(추가만 가능) CRH 기반 Merkle Tree. Leaf는 Coin Commitment. Sander와 Ta-Shma(1999)의 방식과 같음 |
| Root | $$rt$$: Merkle Tree의 Root. 원장은 과거의 모든 Root를 저장함 |
| Authentication Path | 자기 $$cm$$에서 $$rt$$까지의 경로. CMList로부터 계산함 |
| NP Statement | "나는 $$\mathrm{COMM}_r(sn)$$이 Root가 $$rt$$인 CRH 기반 Merkle Tree의 Leaf로 나타나게 하는 $$r$$을 안다". Instance에 CMList 대신 $$rt$$가 들어감 |
| 코인, Mint 트랜잭션 | Step 1과 같음 |

**동작 순서**

- Mint
  1. Step 1과 같은 방식으로 $$\mathrm{tx}_{\mathrm{Mint}}$$가 원장에 추가됨
  2. 새 $$cm$$이 Merkle Tree의 Leaf로 추가되고 Root가 갱신됨. 갱신에 드는 시간과 공간은 트리 깊이에 비례함
- Spend
  1. CMList에서 자기 $$cm$$의 Authentication Path를 계산함
  2. Instance $$(sn, rt)$$로 증명 $$\pi$$를 만듦. Witness는 $$r$$과 Authentication Path임 (정식 구성의 Witness에 Authentication Path가 들어감)
  3. $$sn$$과 $$\pi$$를 게시함
     - 검증자도 증명에 쓴 $$rt$$를 알아야 함. Step 2의 트랜잭션 형식은 논문에 따로 적혀 있지 않으며, Step 3부터 트랜잭션이 $$rt$$를 담음
- 검증
  1. $$rt$$가 원장에 나온 적 있는 Root인지 확인함 (정식 구성 기준)
  2. $$\pi$$를 검증함
  3. $$sn$$이 원장에 이미 있으면 거절함

**해결되는 이유**

- Root 갱신 비용이 트리 깊이에 비례하므로, 복잡도가 CMList 크기에 대해 선형에서 로그로 줄어듦
- 같은 zk-SNARK 구현으로 지원할 수 있는 CMList 크기가 지수적으로 늘어남. Zerocash 구현은 깊이 64를 써서 최대 $$2^{64}$$개 코인을 지원함
- CMList 자체가 사라지는 것은 아님. Coin Commitment는 원장에 계속 남고, 사용자는 CMList에서 Authentication Path를 계산함

**남은 문제**

- 코인을 다른 사람에게 보내기 어려움 → Step 3

### Step 3: Extending Coins for Direct Anonymous Payments

**문제**

지금까지 $$cm$$은 $$sn$$에 대한 Commitment임. $$u_A$$가 만든 코인 $$c$$를 $$u_B$$에게 보내면 다음 문제가 생김.

1. $$u_A$$가 $$sn$$을 앎
   - 비익명: $$u_B$$가 $$c$$를 쓰면 $$u_A$$가 $$sn$$을 보고 알아챔
   - 위험: $$u_A$$가 $$c$$를 먼저 써 버릴 수 있음
   - → $$u_B$$는 받자마자 $$c$$를 쓰고 새 코인 $$c'$$을 발행해야 함
2. 100 BTC를 보내려면 1 BTC 코인을 100번 보내야 함 → 번거롭고, 전송 금액도 드러남
3. 1 BTC의 배수가 아닌 금액은 보낼 수 없음

→ 단순한 Commitment 구조로는 결제 수단이 될 수 없음. 논문은 Coin Commitment를 만드는 방식을 바꾸고, PRF로 지불 받을 주소를 만들고 Serial Number를 유도해 해결함

**구조** (Step 2에서 바뀌는 것)

- $$\Vert$$는 비트열 연결

| 요소 | 정의 |
| --- | --- |
| PRF 세 개 | 하나의 PRF에서 입력 앞 비트를 다르게 붙여 만듦: $$\mathrm{PRF}^{\mathrm{addr}}_x(z) := \mathrm{PRF}_x(00 \Vert z)$$, $$\mathrm{PRF}^{\mathrm{sn}}_x(z) := \mathrm{PRF}_x(01 \Vert z)$$, $$\mathrm{PRF}^{\mathrm{pk}}_x(z) := \mathrm{PRF}_x(10 \Vert z)$$ |
| Address Key Pair(주소 키 쌍) | Address Secret Key(주소 비밀 키) $$a_{\mathrm{sk}}$$: 임의로 고른 PRF Seed. Address Public Key(주소 공개 키) $$a_{\mathrm{pk}} := \mathrm{PRF}^{\mathrm{addr}}_{a_{\mathrm{sk}}}(0)$$ |
| $$\rho$$ | Serial Number를 결정하는 비밀값 |
| Serial Number | $$sn := \mathrm{PRF}^{\mathrm{sn}}_{a_{\mathrm{sk}}}(\rho)$$ |
| Coin Commitment | $$k := \mathrm{COMM}_r(a_{\mathrm{pk}} \Vert \rho)$$, $$cm := \mathrm{COMM}_s(v \Vert k)$$ |
| 코인 | $$c := (a_{\mathrm{pk}}, v, \rho, r, s, cm)$$. 가치 $$v$$는 자유롭게 정함 |
| Mint 트랜잭션 | $$\mathrm{tx}_{\mathrm{Mint}} := (v, k, s, cm)$$ |
| Pour 트랜잭션 | $$\mathrm{tx}_{\mathrm{Pour}} := (rt, sn^{\mathrm{old}}, cm^{\mathrm{new}}_1, cm^{\mathrm{new}}_2, \pi_{\mathrm{POUR}})$$. 코인을 쓸 때는 Spend 대신 Pour를 씀 |
| NP Statement | POUR: Pour가 규칙대로 이루어졌는지 검사하는 NP Statement. 내용은 아래 |

- $$\mathrm{PRF}^{\mathrm{sn}}$$은 Collision-Resistant(충돌 저항)하다고 추가로 가정함. 즉 $$(x, z) \neq (x', z')$$이면서 $$\mathrm{PRF}^{\mathrm{sn}}_x(z) = \mathrm{PRF}^{\mathrm{sn}}_{x'}(z')$$인 쌍을 찾기 어려움
- $$\mathrm{PRF}^{\mathrm{pk}}$$는 Step 6에서 씀
- Pour: 입력 코인을 소비하고, 그 가치를 새 출력 코인에 부어 넣는 연산. 출력 코인의 총 가치는 입력 코인의 총 가치와 같음. 논문의 개요 설명은 입력 1개, 출력 2개이고, 정식 구성은 입력 2개, 출력 2개임

**동작 순서**

- CreateAddress (각 사용자)
  1. 임의의 PRF Seed $$a_{\mathrm{sk}}$$를 고름
  2. $$a_{\mathrm{pk}} := \mathrm{PRF}^{\mathrm{addr}}_{a_{\mathrm{sk}}}(0)$$을 계산함
  3. $$a_{\mathrm{pk}}$$를 공개하고 $$a_{\mathrm{sk}}$$는 비밀로 보관함. 주소 키 쌍은 몇 개든 만들 수 있음
- Mint (가치 $$v$$인 코인)
  1. $$\rho$$를 고름 → 이 코인의 Serial Number $$sn = \mathrm{PRF}^{\mathrm{sn}}_{a_{\mathrm{sk}}}(\rho)$$가 정해짐
  2. 임의의 $$r$$로 $$k := \mathrm{COMM}_r(a_{\mathrm{pk}} \Vert \rho)$$를 계산함
  3. 임의의 $$s$$로 $$cm := \mathrm{COMM}_s(v \Vert k)$$를 계산함
  4. 코인 $$c := (a_{\mathrm{pk}}, v, \rho, r, s, cm)$$을 지갑에 보관함
  5. $$\mathrm{tx}_{\mathrm{Mint}} := (v, k, s, cm)$$를 원장에 보냄
  6. 검증: 누구나 $$\mathrm{COMM}_s(v \Vert k) = cm$$인지 확인함. 원장은 $$u$$가 $$v$$ BTC를 예치한 경우에만 받아들임
- Pour ($$u$$가 자기 코인 $$c^{\mathrm{old}} = (a^{\mathrm{old}}_{\mathrm{pk}}, v^{\mathrm{old}}, \rho^{\mathrm{old}}, r^{\mathrm{old}}, s^{\mathrm{old}}, cm^{\mathrm{old}})$$을 소비해, 주소 $$a^{\mathrm{new}}_{\mathrm{pk},1}, a^{\mathrm{new}}_{\mathrm{pk},2}$$로 새 코인 2개를 만듦)
  1. 새 코인의 가치를 $$v^{\mathrm{new}}_1 + v^{\mathrm{new}}_2 = v^{\mathrm{old}}$$가 되도록 정함. 새 주소는 다른 사용자의 것일 수도, $$u$$ 자신의 것일 수도 있음
  2. $$sn^{\mathrm{old}} := \mathrm{PRF}^{\mathrm{sn}}_{a^{\mathrm{old}}_{\mathrm{sk}}}(\rho^{\mathrm{old}})$$을 계산함
  3. 각 $$i \in \{1, 2\}$$에 대해 새 코인을 만듦
     - $$\rho^{\mathrm{new}}_i$$를 고름
     - 임의의 $$r^{\mathrm{new}}_i$$로 $$k^{\mathrm{new}}_i := \mathrm{COMM}_{r^{\mathrm{new}}_i}(a^{\mathrm{new}}_{\mathrm{pk},i} \Vert \rho^{\mathrm{new}}_i)$$를 계산함
     - 임의의 $$s^{\mathrm{new}}_i$$로 $$cm^{\mathrm{new}}_i := \mathrm{COMM}_{s^{\mathrm{new}}_i}(v^{\mathrm{new}}_i \Vert k^{\mathrm{new}}_i)$$를 계산함
     - $$c^{\mathrm{new}}_i := (a^{\mathrm{new}}_{\mathrm{pk},i}, v^{\mathrm{new}}_i, \rho^{\mathrm{new}}_i, r^{\mathrm{new}}_i, s^{\mathrm{new}}_i, cm^{\mathrm{new}}_i)$$
  4. CMList에서 $$cm^{\mathrm{old}}$$의 Authentication Path를 계산하고, 아래 POUR에 대한 zk-SNARK 증명 $$\pi_{\mathrm{POUR}}$$를 만듦
  5. $$\mathrm{tx}_{\mathrm{Pour}} := (rt, sn^{\mathrm{old}}, cm^{\mathrm{new}}_1, cm^{\mathrm{new}}_2, \pi_{\mathrm{POUR}})$$를 원장에 보냄
- Pour 검증
  1. $$sn^{\mathrm{old}}$$이 이전 트랜잭션에 나온 적이 있으면 거절함
  2. $$\pi_{\mathrm{POUR}}$$를 검증함. 정식 구성에서는 $$rt$$가 원장에 나온 Root인지도 확인함
  3. 통과하면 원장에 추가됨 → $$cm^{\mathrm{new}}_1, cm^{\mathrm{new}}_2$$는 CMList에, $$sn^{\mathrm{old}}$$은 SNList에 들어감

> **POUR** (Instance: $$rt$$, $$sn^{\mathrm{old}}$$, $$cm^{\mathrm{new}}_1$$, $$cm^{\mathrm{new}}_2$$)
>
> 나는 코인 $$c^{\mathrm{old}}, c^{\mathrm{new}}_1, c^{\mathrm{new}}_2$$와 주소 비밀 키 $$a^{\mathrm{old}}_{\mathrm{sk}}$$를 알고, 다음이 성립함
>
> - 코인이 올바른 형식임: $$k^{\mathrm{old}} = \mathrm{COMM}_{r^{\mathrm{old}}}(a^{\mathrm{old}}_{\mathrm{pk}} \Vert \rho^{\mathrm{old}})$$, $$cm^{\mathrm{old}} = \mathrm{COMM}_{s^{\mathrm{old}}}(v^{\mathrm{old}} \Vert k^{\mathrm{old}})$$. 새 코인도 같음
> - 주소 비밀 키가 공개 키와 맞음: $$a^{\mathrm{old}}_{\mathrm{pk}} = \mathrm{PRF}^{\mathrm{addr}}_{a^{\mathrm{old}}_{\mathrm{sk}}}(0)$$
> - Serial Number가 올바르게 계산됨: $$sn^{\mathrm{old}} = \mathrm{PRF}^{\mathrm{sn}}_{a^{\mathrm{old}}_{\mathrm{sk}}}(\rho^{\mathrm{old}})$$
> - $$cm^{\mathrm{old}}$$이 Root가 $$rt$$인 Merkle Tree의 Leaf임
> - 가치의 합이 맞음: $$v^{\mathrm{new}}_1 + v^{\mathrm{new}}_2 = v^{\mathrm{old}}$$

**해결되는 이유**

- 두 단계 Commitment
  - Mint 때 $$v$$, $$k$$, $$s$$가 공개되므로, 누구나 $$cm$$이 가치 $$v$$인 코인임을 확인할 수 있음
  - 소유자($$a_{\mathrm{pk}}$$)와 Serial Number(를 결정하는 $$\rho$$)는 $$k$$ 안에 숨어 있어 알 수 없음
  - → 예치 금액은 공개적으로 검증하면서, 소유자와 Serial Number는 숨김
- 문제 1
  - $$u$$는 $$a^{\mathrm{new}}_{\mathrm{sk},1}$$을 모름. 다음 Pour의 Witness로 $$a^{\mathrm{new}}_{\mathrm{sk},1}$$이 필요하므로 $$u$$는 $$c^{\mathrm{new}}_1$$을 쓸 수 없음 → 위험 해소
  - 수신자가 $$c^{\mathrm{new}}_1$$을 쓸 때 공개되는 $$sn^{\mathrm{new}}_1 = \mathrm{PRF}^{\mathrm{sn}}_{a^{\mathrm{new}}_{\mathrm{sk},1}}(\rho^{\mathrm{new}}_1)$$은 $$u$$가 모르는 키로 계산됨 → $$u$$는 $$\rho^{\mathrm{new}}_1$$을 알아도 추적할 수 없음 → 익명성 확보
- 문제 2, 3: 코인 가치 $$v$$를 자유롭게 정하고 나눌 수 있으므로, 임의 금액을 한 번에 보냄
- 원장에서 보이는 것: $$\mathrm{tx}_{\mathrm{Pour}}$$는 가치가 어떻게 나뉘었는지, 어떤 Coin Commitment가 소비되었는지, 새 코인이 어느 주소로 갔는지 드러내지 않음

**입력과 출력 개수**

- 입력이 2개보다 적으면: 가치 0인 코인을 Mint해 Null 입력으로 씀
- 출력이 2개보다 적으면: 가치 0인 코인을 만들어 버림
- 2개보다 많으면: 2입력 2출력 Pour를 조합함
  - 논문은 $$\log N^{\mathrm{old}} + \log N^{\mathrm{new}}$$개의 Pour를 조합한다고 적음($$N^{\mathrm{old}}$$, $$N^{\mathrm{new}}$$는 입력, 출력 코인 수)
  - 논문이 Bitcoin 통합을 설명하며 든 예시는 입력 4개를 Pour 3번으로 처리함(입력 2개씩 묶는 Pour 2번, 그 결과를 합치는 Pour 1번). 중간 결과는 같은 트랜잭션 안에서 바로 소비되므로 전역 Merkle Tree에 기록하지 않음

**Double Spending 방지**

- POUR는 공개된 $$sn^{\mathrm{old}}$$이 소비되는 코인의 $$\rho^{\mathrm{old}}$$와 $$a^{\mathrm{old}}_{\mathrm{sk}}$$로 올바르게 계산되었음을 증명함
- 원장은 이미 나온 Serial Number를 거절함
- 이 논증은 코인 하나에 유효한 Serial Number가 하나뿐이어야 성립함. 이후 Zcash 명세는 이를 위해 $$\mathrm{PRF}^{\mathrm{addr}}$$의 Collision Resistance도 필요하다고 지적함 (Limitations 절)

**남은 문제**

- 수신자가 $$c^{\mathrm{new}}_1$$을 쓰려면 비밀값 $$v, \rho, r, s$$를 알아야 함 → Step 4

### Step 4: Sending Coins

**문제**

- 수신자 $$u_1$$이 $$c^{\mathrm{new}}_1$$을 쓰려면 비밀값 $$(v^{\mathrm{new}}_1, \rho^{\mathrm{new}}_1, r^{\mathrm{new}}_1, s^{\mathrm{new}}_1)$$이 필요함
- 이를 별도의 비밀 채널(Out-of-Band Channel, 대역 외 채널)로 보내려면 추가 인프라나 가정이 필요함

**구조** (Step 3에서 바뀌는 것)

| 요소 | 정의 |
| --- | --- |
| 주소 | $$\mathrm{addr}_{\mathrm{pk}} = (a_{\mathrm{pk}}, pk_{\mathrm{enc}})$$, $$\mathrm{addr}_{\mathrm{sk}} = (a_{\mathrm{sk}}, sk_{\mathrm{enc}})$$. $$(pk_{\mathrm{enc}}, sk_{\mathrm{enc}})$$는 Key-Private Encryption의 공개 키와 비밀 키 |
| 암호문 | $$C_i$$: 새 코인 $$c^{\mathrm{new}}_i$$의 비밀값 $$(v^{\mathrm{new}}_i, \rho^{\mathrm{new}}_i, r^{\mathrm{new}}_i, s^{\mathrm{new}}_i)$$을 $$pk^{\mathrm{new}}_{\mathrm{enc},i}$$로 암호화한 것 |
| Pour 트랜잭션 | $$C_1, C_2$$가 추가됨 |

**동작 순서**

- CreateAddress
  1. Step 3과 같이 $$(a_{\mathrm{pk}}, a_{\mathrm{sk}})$$를 만듦
  2. 암호화 키 쌍 $$(pk_{\mathrm{enc}}, sk_{\mathrm{enc}})$$를 만듦
  3. $$\mathrm{addr}_{\mathrm{pk}}$$를 공개하고 $$\mathrm{addr}_{\mathrm{sk}}$$는 비밀로 보관함
- Pour (송신자, Step 3에 추가되는 부분)
  1. 각 새 코인 $$c^{\mathrm{new}}_i$$의 비밀값을 수신 주소의 $$pk^{\mathrm{new}}_{\mathrm{enc},i}$$로 암호화해 $$C_i$$를 만듦
  2. $$C_1, C_2$$를 $$\mathrm{tx}_{\mathrm{Pour}}$$에 넣음
- Receive (수신자)
  1. 원장의 Pour 트랜잭션을 훑으며 $$C_1, C_2$$를 자기 $$sk_{\mathrm{enc}}$$로 복호화해 봄
  2. 복호화에 성공하면 그 값이 자기 주소로 온 코인의 비밀값임
  3. 정식 구성에서는 다시 계산한 Coin Commitment가 $$cm^{\mathrm{new}}_i$$와 같은지, 그 코인의 Serial Number가 원장에 없는지도 확인함 (Final Construction 절)

**해결되는 이유**

- 원장을 통해 전달하므로 별도의 비밀 채널이 필요 없음
- Key-Private Encryption이므로 암호문만 보고 어느 공개 키로 암호화했는지 알 수 없음 → $$C_i$$를 넣어도 금액과 수신 주소가 드러나지 않음

**남은 문제**

- 익명 코인을 다시 Basecoin으로 바꿀 방법이 없음 → Step 5

### Step 5: Public Outputs

**문제**

- 지금까지의 구성으로는 코인을 Mint, Merge, Split할 수만 있음
- 코인을 Basecoin(Bitcoin)으로 되돌리는 Redeem 방법이 없음

**구조** (Step 4에서 바뀌는 것)

| 요소 | 정의 |
| --- | --- |
| 공개 출력 | $$v_{\mathrm{pub}}$$: 음이 아닌 값. 공개적으로 내보내는 금액 |
| 문자열 | $$\mathrm{info}$$: 임의의 문자열. $$v_{\mathrm{pub}}$$의 목적지(예: Bitcoin 지갑 공개 키)를 적음 |
| POUR의 잔액 식 | $$v^{\mathrm{new}}_1 + v^{\mathrm{new}}_2 + v_{\mathrm{pub}} = v^{\mathrm{old}}$$ |
| Pour 트랜잭션 | $$v_{\mathrm{pub}}$$와 $$\mathrm{info}$$가 추가됨 |

**동작 순서** (Pour에 추가되는 부분)

1. 공개적으로 내보낼 금액 $$v_{\mathrm{pub}}$$와 목적지 $$\mathrm{info}$$를 정함. 공개 출력이 필요 없으면 $$v_{\mathrm{pub}} = 0$$
2. 새 코인의 가치를 $$v^{\mathrm{new}}_1 + v^{\mathrm{new}}_2 + v_{\mathrm{pub}} = v^{\mathrm{old}}$$가 되도록 정함
3. POUR는 바뀐 잔액 식을 증명함
4. $$v_{\mathrm{pub}}$$와 $$\mathrm{info}$$를 $$\mathrm{tx}_{\mathrm{Pour}}$$에 넣음

**해결되는 이유**

- Redeem = $$v_{\mathrm{pub}} > 0$$인 Pour
- 공개 출력은 Bitcoin 방식 트랜잭션의 "입력"으로 볼 수 있으며, $$\mathrm{info}$$에 Bitcoin 출력 스크립트를 담음. 같은 방식으로 Bitcoin의 공개 Transaction Fee(트랜잭션 수수료)도 지원함

**남은 문제**

- 트랜잭션이 원장에 오르기 전에 누군가 $$\mathrm{info}$$를 바꿔 $$v_{\mathrm{pub}}$$의 목적지를 가로챌 수 있음 → Step 6

### Step 6: Non-Malleability

**문제: Malleability(가변성) 공격**

- Malleability: 정직한 사용자의 Pour 트랜잭션을 고쳐, 같은 Serial Number를 공개하는 다른 유효한 트랜잭션을 만드는 것. 즉 같은 코인을 다른 방식으로 쓰게 만듦
- 예: 다른 사람의 $$\mathrm{tx}_{\mathrm{Pour}}$$가 원장에 오르기 전에 $$\mathrm{info}$$를 바꿔 공개 출력의 목적지를 자신에게 돌림

**구조** (Step 5에서 바뀌는 것)

| 요소 | 정의 |
| --- | --- |
| One-Time Signature 키 쌍 | $$(pk_{\mathrm{sig}}, sk_{\mathrm{sig}})$$: Pour마다 새로 만듦 |
| $$h_{\mathrm{Sig}}$$ | $$\mathrm{CRH}(pk_{\mathrm{sig}})$$ |
| $$h_1, h_2$$ | $$h_i := \mathrm{PRF}^{\mathrm{pk}}_{a^{\mathrm{old}}_{\mathrm{sk},i}}(h_{\mathrm{Sig}})$$. MAC처럼 $$h_{\mathrm{Sig}}$$를 입력 코인 $$i$$의 주소 비밀 키에 묶음 |
| 서명 | $$\sigma$$: Pour의 모든 값에 대한 $$sk_{\mathrm{sig}}$$의 서명 |
| POUR | Instance에 $$h_{\mathrm{Sig}}, h_1, h_2$$가 추가되고, $$h_1, h_2$$가 올바르게 계산되었는지도 검사함 |
| Pour 트랜잭션 | $$pk_{\mathrm{sig}}, h_1, h_2, \sigma$$가 추가됨 |

- 이 단계는 주소 비밀 키 두 개를 쓰므로 입력 코인 2개를 전제함. 정식 구성과 같음

**동작 순서**

- Pour (Step 5에 추가되는 부분)
  1. One-Time Signature 키 쌍 $$(pk_{\mathrm{sig}}, sk_{\mathrm{sig}})$$를 만듦
  2. $$h_{\mathrm{Sig}} := \mathrm{CRH}(pk_{\mathrm{sig}})$$를 계산함
  3. $$h_1 := \mathrm{PRF}^{\mathrm{pk}}_{a^{\mathrm{old}}_{\mathrm{sk},1}}(h_{\mathrm{Sig}})$$, $$h_2 := \mathrm{PRF}^{\mathrm{pk}}_{a^{\mathrm{old}}_{\mathrm{sk},2}}(h_{\mathrm{Sig}})$$를 계산함
  4. $$h_{\mathrm{Sig}}, h_1, h_2$$를 넣은 POUR에 대해 $$\pi_{\mathrm{POUR}}$$를 만듦
  5. $$sk_{\mathrm{sig}}$$로 Pour의 모든 값에 서명해 $$\sigma$$를 얻음
  6. $$pk_{\mathrm{sig}}, h_1, h_2, \sigma$$를 $$\mathrm{tx}_{\mathrm{Pour}}$$에 넣음
- Pour 검증에 추가되는 부분
  1. $$pk_{\mathrm{sig}}$$로 $$h_{\mathrm{Sig}}$$를 다시 계산함
  2. 서명 $$\sigma$$를 검증함
  3. $$h_{\mathrm{Sig}}, h_1, h_2$$를 포함한 Instance로 $$\pi_{\mathrm{POUR}}$$를 검증함

**해결되는 이유**

- $$\mathrm{info}$$를 바꾸면 → 서명 $$\sigma$$가 맞지 않음
- 새 서명 키로 다시 서명하면 → $$pk_{\mathrm{sig}}$$가 바뀌어 $$h_{\mathrm{Sig}}$$가 바뀜 → 그에 맞는 $$h_1, h_2$$와 증명을 새로 만들어야 하는데, 입력 코인의 $$a^{\mathrm{old}}_{\mathrm{sk},i}$$를 모르면 불가능함
- $$a^{\mathrm{old}}_{\mathrm{sk},i}$$는 비밀이고 $$h_{\mathrm{Sig}}$$는 Pour마다 높은 확률로 달라지므로, $$h_1, h_2$$는 예측할 수 없음

### Final Construction

논문의 정식 구성으로, Step 1~6을 모두 반영함.

**최종 구조**

| 요소 | 정의와 역할 |
| --- | --- |
| 원장 $$L$$ | Basecoin 트랜잭션과 Mint, Pour 트랜잭션이 함께 기록되는 Append-Only 원장. 과거의 모든 Merkle Tree Root도 저장함 |
| 공개 파라미터 $$pp$$ | $$(pk_{\mathrm{POUR}}, vk_{\mathrm{POUR}}, pp_{\mathrm{enc}}, pp_{\mathrm{sig}})$$. Setup이 한 번 만들고 모두가 씀. $$pk_{\mathrm{POUR}}$$는 크지만 Pour에만 필요하고, VerifyTransaction은 $$vk_{\mathrm{POUR}}$$만 씀 |
| 주소 | $$\mathrm{addr}_{\mathrm{pk}} = (a_{\mathrm{pk}}, pk_{\mathrm{enc}})$$, $$\mathrm{addr}_{\mathrm{sk}} = (a_{\mathrm{sk}}, sk_{\mathrm{enc}})$$. $$a_{\mathrm{sk}}$$는 코인을 쓸 때, $$sk_{\mathrm{enc}}$$는 받은 코인을 찾을 때 씀 |
| 코인 | $$c = (\mathrm{addr}_{\mathrm{pk}}, v, \rho, r, s, cm)$$. 소유자의 지갑에만 있음 |
| $$v$$ | 코인 가치. 0 이상 $$v_{\max}$$ 이하의 정수이며, 구현에서는 64-bit 정수 |
| $$\rho$$ | Serial Number Randomness. Serial Number를 결정함 |
| $$r, s$$ | 두 단계 Commitment에 쓰는 Trapdoor |
| $$k$$ | 내부 Commitment $$\mathrm{COMM}_r(a_{\mathrm{pk}} \Vert \rho)$$. 소유자와 Serial Number를 숨김 |
| Coin Commitment | $$cm = \mathrm{COMM}_s(v \Vert k)$$. 코인을 만들 때 원장에 기록됨 |
| Serial Number | $$sn = \mathrm{PRF}^{\mathrm{sn}}_{a_{\mathrm{sk}}}(\rho)$$. 코인을 쓸 때만 공개되며, Double Spending 검사에 씀 |
| Mint 트랜잭션 | $$\mathrm{tx}_{\mathrm{Mint}} = (cm, v, \ast)$$, $$\ast = (k, s)$$ |
| Pour 트랜잭션 | $$\mathrm{tx}_{\mathrm{Pour}} = (rt, sn^{\mathrm{old}}_1, sn^{\mathrm{old}}_2, cm^{\mathrm{new}}_1, cm^{\mathrm{new}}_2, v_{\mathrm{pub}}, \mathrm{info}, \ast)$$, $$\ast = (pk_{\mathrm{sig}}, h_1, h_2, \pi_{\mathrm{POUR}}, C_1, C_2, \sigma)$$. 드러나는 금액은 $$v_{\mathrm{pub}}$$뿐이고, 입력 코인과 출력 코인의 주소와 가치는 드러나지 않음 |
| CMList | 원장의 Mint, Pour 트랜잭션에 나온 모든 Coin Commitment |
| SNList | 원장의 Pour 트랜잭션에 나온 모든 Serial Number |
| Merkle Tree | CMList 위의 Merkle Tree. Root $$rt$$로 입력 코인이 원장에 있음을 증명함 |

**전체 동작 순서**

1. Setup: 신뢰 당사자가 한 번 실행해 $$pp$$를 공개함. 이후 신뢰 당사자는 필요 없고, 전역 비밀이나 Trapdoor도 남지 않음
2. CreateAddress: 각 사용자가 주소 키 쌍을 만들고 $$\mathrm{addr}_{\mathrm{pk}}$$를 공개함. 상호작용 없이 몇 개든 만들 수 있음
3. Mint: Basecoin $$v$$를 내고 가치 $$v$$인 코인을 만듦 → VerifyTransaction을 통과하면 원장에 기록되고, $$cm$$이 CMList에 들어감
4. Pour: 코인 2개를 소비해 새 코인 2개를 만들고, 필요하면 $$v_{\mathrm{pub}}$$를 공개 출력으로 내보냄 → VerifyTransaction을 통과하면 원장에 기록되고, 새 $$cm$$은 CMList에, 소비한 $$sn$$은 SNList에 들어감
5. Receive: 수신자가 원장을 훑어 자기 주소로 온 미사용 코인을 찾음 → 받은 코인은 4의 Pour로 다시 씀

- VerifyTransaction은 원장을 유지하는 노드와, 그 트랜잭션을 믿고 쓰는 사용자가 실행함
- Receive는 Pour로 받은 코인만 찾으면 되고, 사용자가 직접 Mint한 코인은 찾지 않아도 됨

**알고리즘별 동작 순서**

- Setup
  1. 보안 파라미터 $$\lambda$$에 맞춰, POUR를 검사하는 산술 회로 $$C_{\mathrm{POUR}}$$를 만듦
  2. $$(pk_{\mathrm{POUR}}, vk_{\mathrm{POUR}}) := \mathrm{KeyGen}(1^\lambda, C_{\mathrm{POUR}})$$. $$1^\lambda$$는 보안 파라미터를 1진법으로 적은 입력임
  3. 암호화 스킴의 공개 파라미터 $$pp_{\mathrm{enc}}$$를 만듦
  4. 서명 스킴의 공개 파라미터 $$pp_{\mathrm{sig}}$$를 만듦
  5. $$pp := (pk_{\mathrm{POUR}}, vk_{\mathrm{POUR}}, pp_{\mathrm{enc}}, pp_{\mathrm{sig}})$$를 출력함
- CreateAddress
  1. 암호화 키 쌍 $$(pk_{\mathrm{enc}}, sk_{\mathrm{enc}})$$를 만듦
  2. PRF Seed $$a_{\mathrm{sk}}$$를 임의로 고름
  3. $$a_{\mathrm{pk}} := \mathrm{PRF}^{\mathrm{addr}}_{a_{\mathrm{sk}}}(0)$$
  4. $$\mathrm{addr}_{\mathrm{pk}} := (a_{\mathrm{pk}}, pk_{\mathrm{enc}})$$와 $$\mathrm{addr}_{\mathrm{sk}} := (a_{\mathrm{sk}}, sk_{\mathrm{enc}})$$를 출력함
- Mint (입력: 코인 가치 $$v$$, 코인을 받을 주소 $$\mathrm{addr}_{\mathrm{pk}}$$)
  1. $$\mathrm{addr}_{\mathrm{pk}}$$에서 $$a_{\mathrm{pk}}$$를 꺼냄
  2. $$\rho$$와 Trapdoor $$r, s$$를 임의로 고름
  3. $$k := \mathrm{COMM}_r(a_{\mathrm{pk}} \Vert \rho)$$
  4. $$cm := \mathrm{COMM}_s(v \Vert k)$$
  5. $$c := (\mathrm{addr}_{\mathrm{pk}}, v, \rho, r, s, cm)$$
  6. $$\mathrm{tx}_{\mathrm{Mint}} := (cm, v, \ast)$$, $$\ast := (k, s)$$
  7. $$c$$와 $$\mathrm{tx}_{\mathrm{Mint}}$$를 출력함
- Pour (입력: $$rt$$, 서로 다른 입력 코인 $$c^{\mathrm{old}}_1, c^{\mathrm{old}}_2$$와 그 주소 비밀 키, Authentication Path $$\mathrm{path}_1, \mathrm{path}_2$$, 새 가치 $$v^{\mathrm{new}}_1, v^{\mathrm{new}}_2$$, 새 주소 $$\mathrm{addr}^{\mathrm{new}}_{\mathrm{pk},1}, \mathrm{addr}^{\mathrm{new}}_{\mathrm{pk},2}$$, $$v_{\mathrm{pub}}$$, $$\mathrm{info}$$)
  1. 각 $$i \in \{1, 2\}$$에 대해
     - $$sn^{\mathrm{old}}_i := \mathrm{PRF}^{\mathrm{sn}}_{a^{\mathrm{old}}_{\mathrm{sk},i}}(\rho^{\mathrm{old}}_i)$$
     - $$\rho^{\mathrm{new}}_i$$와 Trapdoor $$r^{\mathrm{new}}_i, s^{\mathrm{new}}_i$$를 임의로 고름
     - $$k^{\mathrm{new}}_i := \mathrm{COMM}_{r^{\mathrm{new}}_i}(a^{\mathrm{new}}_{\mathrm{pk},i} \Vert \rho^{\mathrm{new}}_i)$$, $$cm^{\mathrm{new}}_i := \mathrm{COMM}_{s^{\mathrm{new}}_i}(v^{\mathrm{new}}_i \Vert k^{\mathrm{new}}_i)$$
     - $$c^{\mathrm{new}}_i := (\mathrm{addr}^{\mathrm{new}}_{\mathrm{pk},i}, v^{\mathrm{new}}_i, \rho^{\mathrm{new}}_i, r^{\mathrm{new}}_i, s^{\mathrm{new}}_i, cm^{\mathrm{new}}_i)$$
     - $$(v^{\mathrm{new}}_i, \rho^{\mathrm{new}}_i, r^{\mathrm{new}}_i, s^{\mathrm{new}}_i)$$를 $$pk^{\mathrm{new}}_{\mathrm{enc},i}$$로 암호화해 $$C_i$$를 만듦
  2. One-Time Signature 키 쌍 $$(pk_{\mathrm{sig}}, sk_{\mathrm{sig}})$$를 만듦
  3. $$h_{\mathrm{Sig}} := \mathrm{CRH}(pk_{\mathrm{sig}})$$
  4. $$h_1 := \mathrm{PRF}^{\mathrm{pk}}_{a^{\mathrm{old}}_{\mathrm{sk},1}}(1 \Vert h_{\mathrm{Sig}})$$, $$h_2 := \mathrm{PRF}^{\mathrm{pk}}_{a^{\mathrm{old}}_{\mathrm{sk},2}}(2 \Vert h_{\mathrm{Sig}})$$
     - Extended Version의 정식 구성은 Step 6의 개요와 달리 입력 번호를 함께 넣음. Conference Version의 정식 구성은 번호 없이 적음
  5. Instance $$x := (rt, sn^{\mathrm{old}}_1, sn^{\mathrm{old}}_2, cm^{\mathrm{new}}_1, cm^{\mathrm{new}}_2, v_{\mathrm{pub}}, h_{\mathrm{Sig}}, h_1, h_2)$$
  6. Witness $$a := (\mathrm{path}_1, \mathrm{path}_2, c^{\mathrm{old}}_1, c^{\mathrm{old}}_2, \mathrm{addr}^{\mathrm{old}}_{\mathrm{sk},1}, \mathrm{addr}^{\mathrm{old}}_{\mathrm{sk},2}, c^{\mathrm{new}}_1, c^{\mathrm{new}}_2)$$
  7. $$\pi_{\mathrm{POUR}} := \mathrm{Prove}(pk_{\mathrm{POUR}}, x, a)$$
  8. $$m := (x, \pi_{\mathrm{POUR}}, \mathrm{info}, C_1, C_2)$$에 $$sk_{\mathrm{sig}}$$로 서명해 $$\sigma$$를 얻음
  9. $$\mathrm{tx}_{\mathrm{Pour}} := (rt, sn^{\mathrm{old}}_1, sn^{\mathrm{old}}_2, cm^{\mathrm{new}}_1, cm^{\mathrm{new}}_2, v_{\mathrm{pub}}, \mathrm{info}, \ast)$$, $$\ast := (pk_{\mathrm{sig}}, h_1, h_2, \pi_{\mathrm{POUR}}, C_1, C_2, \sigma)$$
  10. $$c^{\mathrm{new}}_1, c^{\mathrm{new}}_2$$와 $$\mathrm{tx}_{\mathrm{Pour}}$$를 출력함
- VerifyTransaction (Mint 트랜잭션)
  1. $$\ast$$에서 $$k, s$$를 꺼냄
  2. $$cm = \mathrm{COMM}_s(v \Vert k)$$이면 유효함
- VerifyTransaction (Pour 트랜잭션)
  1. $$sn^{\mathrm{old}}_1$$이나 $$sn^{\mathrm{old}}_2$$가 원장에 있거나, 둘이 같으면 거절함 → Double Spending 검사
  2. $$rt$$가 원장에 나온 적 없는 Root면 거절함
  3. $$h_{\mathrm{Sig}} := \mathrm{CRH}(pk_{\mathrm{sig}})$$를 다시 계산함
  4. $$x$$와 $$m$$을 재구성함
  5. 서명 $$\sigma$$와 증명 $$\pi_{\mathrm{POUR}}$$가 모두 맞으면 유효함
- Receive (입력: 자기 주소 키 쌍, 현재 원장)
  1. 원장의 각 Pour 트랜잭션에서 $$C_1, C_2$$를 $$sk_{\mathrm{enc}}$$로 복호화해 봄
  2. 복호화에 성공해 $$(v_i, \rho_i, r_i, s_i)$$를 얻으면 다음 두 가지를 확인함
     - $$cm^{\mathrm{new}}_i = \mathrm{COMM}_{s_i}(v_i \Vert \mathrm{COMM}_{r_i}(a_{\mathrm{pk}} \Vert \rho_i))$$
     - $$sn_i := \mathrm{PRF}^{\mathrm{sn}}_{a_{\mathrm{sk}}}(\rho_i)$$가 원장에 없음
  3. 둘 다 맞으면 코인 $$c_i := (\mathrm{addr}_{\mathrm{pk}}, v_i, \rho_i, r_i, s_i, cm^{\mathrm{new}}_i)$$를 출력함
  - Serial Number를 확인하는 이유: 자신이 이미 받아서 써 버린 코인을 다시 출력하지 않기 위함. 다른 사용자는 어차피 이 주소로 온 코인을 쓸 수 없음

**정식 POUR**

Witness가 유효하려면 각 $$i \in \{1, 2\}$$에 대해 다음이 성립해야 함.

- (a) $$\mathrm{path}_i$$가 Leaf $$cm^{\mathrm{old}}_i$$의 Root $$rt$$에 대한 유효한 Authentication Path임 → 입력 코인이 원장에 있음
- (b) $$a^{\mathrm{old}}_{\mathrm{pk},i} = \mathrm{PRF}^{\mathrm{addr}}_{a^{\mathrm{old}}_{\mathrm{sk},i}}(0)$$ → 소유
- (c) $$sn^{\mathrm{old}}_i = \mathrm{PRF}^{\mathrm{sn}}_{a^{\mathrm{old}}_{\mathrm{sk},i}}(\rho^{\mathrm{old}}_i)$$ → 공개한 Serial Number가 그 코인의 것임
- (d) $$cm^{\mathrm{old}}_i$$가 $$(a^{\mathrm{old}}_{\mathrm{pk},i}, \rho^{\mathrm{old}}_i, v^{\mathrm{old}}_i)$$에 대한 올바른 두 단계 Commitment임
- (e) $$cm^{\mathrm{new}}_i$$가 $$(a^{\mathrm{new}}_{\mathrm{pk},i}, \rho^{\mathrm{new}}_i, v^{\mathrm{new}}_i)$$에 대한 올바른 두 단계 Commitment임
- (f) $$h_i = \mathrm{PRF}^{\mathrm{pk}}_{a^{\mathrm{old}}_{\mathrm{sk},i}}(i \Vert h_{\mathrm{Sig}})$$ → 변조 방지

그리고 잔액이 보존되어야 함: $$v^{\mathrm{new}}_1 + v^{\mathrm{new}}_2 + v_{\mathrm{pub}} = v^{\mathrm{old}}_1 + v^{\mathrm{old}}_2$$, $$v^{\mathrm{old}}_1, v^{\mathrm{old}}_2 \geq 0$$, $$v^{\mathrm{old}}_1 + v^{\mathrm{old}}_2 \leq v_{\max}$$ ($$v_{\max}$$는 코인 가치의 최댓값)

- Merkle Tree 깊이 $$d_{\mathrm{tree}}$$는 회로에 고정되므로, 지원하는 최대 코인 수는 $$2^{d_{\mathrm{tree}}}$$임
- Coin Commitment의 입력 순서는 논문의 정식 POUR 조건 (d), (e)에서 $$k \Vert v$$, 개요와 알고리즘 설명에서 $$v \Vert k$$로 서로 다르게 적혀 있음

### Example: A Single Payment

아래 이름과 금액은 설명을 위해 정한 값이며 논문에 없음. 절차는 논문의 정식 알고리즘과 Null 입력 규칙을 따름.

1. Alice가 10 BTC를 Mint함
   - 원장: $$\mathrm{tx}_{\mathrm{Mint}} = (cm_A, 10, (k, s))$$
   - 공개: 금액 10 / 숨김: 소유자, Serial Number
2. Pour에는 입력 코인 2개가 필요하므로, Alice는 가치 0인 코인을 하나 더 Mint해 Null 입력으로 씀. 이 Mint의 금액 0도 공개됨
3. Alice가 Bob에게 3 BTC를 보냄
   - 입력: 가치 10인 코인, 가치 0인 코인
   - 출력: Bob의 주소로 가는 가치 3인 코인, Alice 자신의 주소로 가는 가치 7인 코인(거스름돈)
   - $$v_{\mathrm{pub}} = 0$$
   - 잔액 식: $$3 + 7 + 0 = 10 + 0$$
4. 원장에 $$\mathrm{tx}_{\mathrm{Pour}} = (rt, sn_1, sn_2, cm_1, cm_2, 0, \mathrm{info}, \ast)$$가 오름
   - 관찰자가 아는 것: Pour가 한 번 일어났고, $$v_{\mathrm{pub}} = 0$$
   - 관찰자가 모르는 것: 어떤 Coin Commitment가 소비되었는지, 3과 7이라는 금액, Bob의 주소
5. Bob은 Receive로 원장의 Pour 트랜잭션을 훑음
   - $$C_1$$이 자신의 $$sk_{\mathrm{enc}}$$로 복호화되면 $$(3, \rho, r, s)$$를 얻음
   - $$cm_1$$을 다시 계산해 맞는지 확인함
6. Bob이 이 코인을 쓸 때 공개되는 Serial Number는 $$\mathrm{PRF}^{\mathrm{sn}}_{a_{\mathrm{sk}}}(\rho)$$이고, 여기서 $$a_{\mathrm{sk}}$$는 Bob의 키임
   - Alice는 $$\rho$$를 알지만 Bob의 $$a_{\mathrm{sk}}$$를 모르므로 이 값을 계산할 수 없음
   - → Alice는 Bob이 코인을 쓰는 시점을 알 수 없고, 코인을 먼저 써 버릴 수도 없음
7. Bob이 1 BTC를 Bitcoin으로 되돌림
   - Bob도 가치 0인 코인을 Mint해 Null 입력으로 씀
   - 입력: 가치 3인 코인, 가치 0인 코인
   - 출력: 자신에게 가는 가치 2인 코인, 가치 0인 코인
   - $$v_{\mathrm{pub}} = 1$$, $$\mathrm{info}$$에는 1 BTC를 받을 Bitcoin 출력 조건을 적음
   - 잔액 식: $$2 + 0 + 1 = 3 + 0$$
   - 공개되는 금액은 1뿐임

## Security

- 논문은 이 구성이 Completeness와 세 보안 성질을 모두 만족하는 DAP Scheme임을 증명함
- Completeness(완전성): Coin Commitment는 원장에 있고 Serial Number는 원장에 없는 코인 두 개는 Pour로 쓸 수 있어야 함. 그 결과 트랜잭션은 VerifyTransaction을 통과하고, 수신자는 Receive로 새 코인을 받을 수 있어야 함

**보안 성질의 정의 방식**

- 공격자와 Challenger(도전자) 사이의 게임으로 정의함
- 정직한 사용자의 행동은 원장을 관리하는 Oracle(오라클)이 대신 수행함
- 공격자는 정직한 사용자에게 원하는 행동(CreateAddress, Mint, Pour, Receive)을 시킬 수 있고, 임의의 트랜잭션을 원장에 직접 넣을 수도 있음
- 공격자는 결과 트랜잭션을 보지만, 그것을 만드는 데 쓴 비밀값은 볼 수 없음

**세 보안 성질**

| 성질 | 의미 | 공격자가 이기는 조건 |
| --- | --- | --- |
| Ledger Indistinguishability(원장 구별 불가능성) | 원장은 공개 정보(발행 금액, 공개 출력, $$\mathrm{info}$$, 트랜잭션 수 등) 외에 아무것도 드러내지 않음 | 공개 정보와 자신이 통제하는 주소 관련 정보가 같도록 맞춘 두 쿼리 시퀀스로 원장 두 개를 만들게 한 뒤, 어느 원장이 어느 시퀀스에서 나왔는지를 1/2보다 무시할 수 없을 만큼 높은 확률로 맞힘 |
| Transaction Non-Malleability(트랜잭션 비가변성) | 정직한 사용자의 Pour 트랜잭션을 원장에 오르기 전에 변조할 수 없음 | 정직한 사용자의 Pour 트랜잭션과 다르면서 같은 Serial Number를 공개하는 유효한 트랜잭션을 만듦 |
| Balance(잔액 보존) | Mint했거나 받은 것보다 많은 가치를 가질 수 없음 | 아래 부등식을 성립시킴 |

$$v_{\mathrm{Unspent}} + v_{\mathrm{Basecoin}} + v_{\mathcal{A} \to \mathrm{ADDR}} > v_{\mathrm{Mint}} + v_{\mathrm{ADDR} \to \mathcal{A}}$$

- $$\mathcal{A}$$: 공격자, $$\mathrm{ADDR}$$: 정직한 사용자들의 주소 집합
- $$v_{\mathrm{Unspent}}$$: 공격자가 게임 끝에 내놓은 코인 중 아직 쓰지 않은 코인의 총 가치
- $$v_{\mathrm{Basecoin}}$$: 공격자가 원장에 올린 공개 출력의 총 가치
- $$v_{\mathcal{A} \to \mathrm{ADDR}}$$: 공격자가 정직한 사용자의 주소로 보낸 총 가치
- $$v_{\mathrm{Mint}}$$: 공격자가 Mint한 총 가치
- $$v_{\mathrm{ADDR} \to \mathcal{A}}$$: 공격자가 정직한 사용자의 주소에서 받은 총 가치

**Trusted Setup의 영향**

- Setup에 대한 신뢰는 Transaction Non-Malleability와 Balance에 필요하고, Ledger Indistinguishability에는 필요 없음
- → Setup이 오염되면 공격자가 나중에 코인을 위조할 수 있지만, 익명성은 유지됨. 논문은 강력한 첩보 기관이 Setup을 오염시켜도 익명성은 유지된다고 설명함
- Setup은 한 번만 실행함. 끝난 뒤 중간 결과를 지우면, 기반 암호 가정 외에 추가 신뢰가 필요 없음
- 신뢰 요구를 줄이려면 Setup을 Secure Multi-Party Computation(안전한 다자간 계산)으로 수행할 수 있음. 논문은 이를 향후 과제로 남김

## Implementation

목표 보안 수준은 128-bit임.

**SHA256으로 만든 CRH, PRF, COMM**

- $$H$$: SHA256의 Compression Function(압축 함수). 512-bit 입력을 256-bit 출력으로 바꿈
- 전체 SHA256 대신 $$H$$를 쓰는 이유: 입력이 고정 크기의 한 블록이라 $$H$$로 충분하고, 회로도 단순해짐
- CRH: $$\mathrm{CRH}(z) := H(z)$$. 입력을 절반 길이로 압축하므로 Binary Merkle Tree(이진 머클 트리)에 바로 씀
  - 예외: $$h_{\mathrm{Sig}}$$는 회로에서 검증할 필요가 없으므로 전체 SHA256으로 계산함
- PRF: $$\mathrm{PRF}_x(z) := H(x \Vert z)$$. Seed $$x$$는 256-bit
  - 예: $$\mathrm{PRF}^{\mathrm{sn}}_x(z) := H(x \Vert 01 \Vert z)$$, $$z$$는 254-bit
- COMM: $$a_{\mathrm{pk}}$$와 $$\rho$$는 256-bit, $$r$$은 384-bit
  - $$k := H(r \Vert [H(a_{\mathrm{pk}} \Vert \rho)]_{128})$$
  - $$cm := H(k \Vert 0^{192} \Vert v)$$
  - $$[y]_{128}$$: 256-bit 문자열 $$y$$를 128-bit로 자른 값. 구현은 하위 비트를 버림
  - Statistically Hiding 성질의 근거: 128-bit $$z$$에 대해 $$H(r \Vert z)$$의 분포가 휴리스틱하게 균등 분포와 $$2^{-128}$$ 거리 안에 있다고 봄
  - $$cm$$에는 Trapdoor $$s$$를 쓰지 않음. $$k$$가 이미 Statistically Hiding Commitment의 출력이라 다음 Commitment의 난수 역할을 하기 때문
- 코인 가치는 64-bit 정수 → $$v_{\max} = 2^{64} - 1$$
- Merkle Tree 깊이 $$d_{\mathrm{tree}} = 64$$ → 최대 $$2^{64}$$개 코인

**서명과 암호화**

- 서명: 기존 bitcoind 코드와의 일관성과 호환성을 위해 ECDSA(Elliptic Curve Digital Signature Algorithm)를 씀
  - 표준 ECDSA는 $$(r, s)$$와 $$(r, -s)$$가 모두 유효한 서명이라 Malleable함 → $$s$$를 하위 절반으로 제한한 변형을 씀
  - 저자들은 이 변형의 SUF-1CMA 형식 증명은 알지 못한다고 밝힘
- 암호화: Key-Private ECIES(Elliptic Curve Integrated Encryption Scheme). 구현이 있는 몇 안 되는 표준 Key-Private 암호화 스킴임

**산술 회로**

- POUR 검증 작업의 대부분은 $$H$$ 계산 검증임
- $$C_H$$: SHA256 Compression Function 검증 회로. 저자들이 SHA256 명세를 따라 직접 설계함. 27,904 Gate
  - 비교: 널리 쓰이는 암호 라이브러리 PolarSSL의 SHA256 구현을 바탕으로 $$H$$를 계산하는 C 프로그램을 작성해 PGHR13의 회로 생성기에 넣으면 58,160 Gate로 2배를 넘음
  - 비교: 같은 C 프로그램을 TinyRAM(인용 표기 BCG+13인 zk-SNARK 구현이 지원하는 기계 아키텍처)용으로 컴파일해 회로로 바꾸면 최소 $$5.7 \times 10^6$$ Gate로 190배를 넘음
- $$C_{\mathrm{POUR}}$$: 4,109,330 Gate. 99%를 넘는 Gate가 $$H$$ 검증에 쓰임
  - 입력 코인 하나의 Merkle Tree 소속 검증: 1,802,304 Gate
  - 이 수치로 계산하면 입력 코인 두 개의 소속 검증은 3,604,608 Gate로 전체의 약 88%임

- 슬라이드의 "증명 생성 1분 미만"은 Desktop 4 Threads의 Prove 46 s에 해당함

**Zerocash 알고리즘** (Desktop 1 Thread)

| Algorithm | 시간 | 크기 |
| --- | --- | --- |
| Setup | 5 min 17 s | $$pp$$ 896 MiB(대부분 $$pk_{\mathrm{POUR}}$$) |
| CreateAddress | 326.0 ms | $$\mathrm{addr}_{\mathrm{pk}}$$ 343 B, $$\mathrm{addr}_{\mathrm{sk}}$$ 319 B |
| Mint | 23 µs | 코인 463 B, $$\mathrm{tx}_{\mathrm{Mint}}$$ 72 B |
| Pour | 2 min 2.01 s | $$\mathrm{tx}_{\mathrm{Pour}}$$ 996 B + $$\mathrm{info}$$ 길이 |
| VerifyTransaction | Mint 8.3 µs, Pour 5.7 ms | |
| Receive | Pour 트랜잭션당 1.6 ms | |

- 표준편차는 2.5% 이하이며, 예외로 Mint는 3.3 µs 이하, VerifyTransaction은 1.9 µs 이하임
- $$\mathrm{tx}_{\mathrm{Pour}}$$ 996 B의 구성: $$rt$$ 32 B, Serial Number $$2 \times 32$$ B, Coin Commitment $$2 \times 32$$ B, $$v_{\mathrm{pub}}$$ 8 B, $$pk_{\mathrm{sig}}$$ 66 B, $$h_1, h_2$$ $$2 \times 32$$ B, $$\pi_{\mathrm{POUR}}$$ 288 B, $$C_1, C_2$$ $$2 \times 173$$ B, $$\sigma$$ 64 B
  - 코인 정보를 원장 대신 Out-of-Band로 전달하면 $$C_1, C_2$$가 필요 없어 크기가 줄어듦
- Pour 검증 시간 5.7 ms는 원장 조회(Serial Number 중복 확인 등)를 뺀 값임
- Merkle Tree 유지 비용은 포함되지 않음. Root 갱신마다 $$H$$를 64번 호출하고, Authentication Path는 2 KiB임
- Pour 시간은 증명 생성이 대부분을 차지함

**대규모 네트워크 시뮬레이션**

- 목적
  - 모든 노드가 VerifyTransaction을 실행하므로, 검증이 느려지면 블록 전파가 늦어질 수 있음
  - Bitcoin은 트랜잭션 검증 결과를 캐시하므로, 실제 영향은 캐시가 얼마나 효과적인지에 달림
- 설정
  - 노드 1000개, 노드당 평균 Peer 32개. 당시 Bitcoin 네트워크 고유 IP(Internet Protocol) 주소의 약 1/16, 특정 시점에 접속 가능한 노드의 약 1/3 규모
  - 블록 생성 간격 평균 150 s(Litecoin과 같은 값), 트랜잭션 생성 간격 평균 1 s, 1시간 실행
  - Zerocash 트랜잭션 비율을 0%, 25%, 50%, 75%, 100%로 바꿈. Zerocash 트랜잭션은 캐시에 없을 때 10 ms 검증 지연을 넣어 흉내 냄
  - Amazon EC2(Elastic Compute Cloud) m1.medium 인스턴스 200대, 인스턴스당 bitcoind 5개
  - 실제 트랜잭션 속도는 평균 1.4 s에 1건이었음
- 결과
  - 캐시가 없다면 블록당 최대 $$150 \times 10$$ ms = 1500 ms의 검증 지연이 예상되지만, 실제 블록 검증 시간은 최악의 경우에도 80 ms였음 → 캐시가 효과적이며, 블록 전파에 미치는 영향은 무시할 수준
  - 트랜잭션이 확정되어 쓸 수 있게 되기까지 약 190 s가 걸림
  - 노드가 공유 EC2 인스턴스의 외부 부하를 받았으므로 측정 정밀도에 한계가 있음

## Integration with Bitcoin

- Zerocash는 새 트랜잭션 유형을 쓰므로 Bitcoin 네트워크와 호환되지 않음
- Flag Day(채굴자의 압도적 다수가 동시에 새 소프트웨어를 채택하는 날)로 Bitcoin에 넣을 수는 있음
- 그러나 저자들은 가까운 시일 안에 이를 기대하지도 권하지도 않고, 별도 Altcoin(Bitcoin에서 갈라져 나온 다른 화폐, 예: Litecoin)으로 쓰기를 제안함

**통합 방식 두 가지**

| 방식 | 내용 | 특징 |
| --- | --- | --- |
| Base Currency 대체 | 모든 거래를 Zerocash로 처리함 | 모든 거래가 익명. 단, 모든 Pour가 증명 생성 비용을 치르고, Bitcoin Script(코인 사용 조건을 적는 스크립트 언어) 같은 기능이 사라지며, 확정되지 않은 트랜잭션의 출력은 쓸 수 없음 |
| Hybrid Currency | Bitcoin과 zerocoin을 같은 원장에서 함께 쓰고 1:1로 바꿈 | Bitcoin 기능이 그대로 유지됨. Mint는 Bitcoin을 사실상 소멸시키고 같은 가치의 zerocoin을 만듦. Pour의 $$v_{\mathrm{pub}}$$는 Coinbase 트랜잭션(채굴 보상으로 새 Bitcoin을 만드는 트랜잭션)처럼 새 Bitcoin으로 생기고, 같은 가치의 zerocoin이 소멸됨 |

**지불 받기**

- 모든 Pour 트랜잭션에 Receive를 실행해 자기 코인을 찾음. 최악의 경우 원장의 모든 암호문을 복호화해 봐야 함
- 또는 암호화된 이메일 같은 Out-of-Band 수단으로 코인 정보를 받음

**네트워크 계층**

- Zerocash는 원장만 익명화함. 트랜잭션을 알리고, 블록을 받고, 상점에 연락하는 네트워크 트래픽은 IP 주소 같은 식별 정보를 노출함 → Tor(The Onion Router) 같은 익명 네트워크가 필요함
- Poison-Pill 공격: 강력한 공격자가 특정 사용자에게만 가짜 블록을 보여 주고, 사용자가 그 블록의 Merkle Tree로 코인을 쓰면 그 사용자가 식별됨
  - 대응: 신뢰하는 Peer와 Blockchain 상태를 비교하고, 민감한 거래에서는 더 이전 블록을 기준으로 코인을 씀

## Limitations

**논문이 밝힌 한계**

- Trusted Setup: Setup이 오염되면 코인 위조가 가능해질 수 있음. 익명성은 영향을 받지 않음
- 증명 생성 비용: Desktop 1 Thread에서 Pour 약 2분, Proving Key 896 MiB
- SNList 증가
  - Bitcoin 노드는 사용되면 지워지는 UTXO(Unspent Transaction Output, 미사용 트랜잭션 출력) 목록만 유지하면 됨
  - Zerocash 노드는 계속 커지기만 하는 SNList를 유지해야 함
  - 논문은 3단계 완화책을 제안하지만 구현 결과는 제시하지 않음
- 네트워크 계층의 익명성은 제공하지 않음
- 기본 구성은 계산적 프라이버시만 제공함
  - 계산 능력이 무한한 공격자는 $$h_i$$에서 송신자의 $$a_{\mathrm{sk}}$$를, $$C_i$$를 복호화해 수신자를 알아낼 수 있음
  - Everlasting Anonymity(영구 익명성)를 얻으려면 주소를 한 번만 쓰고, 코인 정보를 정보 이론적으로 안전한 Out-of-Band 채널로 보내야 함
- 트랜잭션 수수료는 공개됨
- 구현에 쓴 ECDSA 변형은 SUF-1CMA 형식 증명이 없음

**이후 지적된 문제**

[Zcash 프로토콜 명세](https://bravenewcoin.com/assets/Whitepapers/Zcash-Protocol-Specification.pdf)(Version 2016.0-beta-1.8, 2016년 10월 4일)가 지적한 내용임.

- Faerie Gold 공격
  - 공격자가 같은 $$\rho$$에 $$v$$와 $$r$$만 다른 코인을 여러 개 보내면, 모두 Receive를 통과하지만 Serial Number가 같으므로 수신자는 그중 하나만 쓸 수 있음
  - 명세는 이 공격이 논문의 보안 정의를 위반하지는 않으며, 정의 자체에 보완이 필요하다고 봄
- 내부 해시 충돌 공격
  - 구현은 $$H(a_{\mathrm{pk}} \Vert \rho)$$를 128-bit로 자름
  - 이 때문에 약 $$2^{64}$$의 작업으로 같은 Coin Commitment를 갖는 서로 다른 $$\rho$$를 찾을 수 있고, Double Spending으로 Balance를 깨뜨릴 수 있음
- PRF 입력 절단
  - 구현은 $$\mathrm{PRF}^{\mathrm{sn}}$$에서 $$\rho$$를 254-bit로, $$\mathrm{PRF}^{\mathrm{pk}}$$에서 $$h_{\mathrm{Sig}}$$를 253-bit로 자름
  - 보안 증명은 이 절단을 고려하지 않음. 명세는 이것이 Ledger Indistinguishability 증명에 쓰인 Lemma(보조정리)의 증명 스케치의 타당성에 영향을 준다고 지적함
- 보안 증명의 누락
  - 논문은 $$\mathrm{PRF}^{\mathrm{addr}}$$의 Collision Resistance를 요구하지 않음
  - 충돌을 찾으면 서로 다른 두 $$a_{\mathrm{sk}}$$가 같은 $$a_{\mathrm{pk}}$$를 갖게 되어, 같은 코인을 서로 다른 Serial Number로 두 번 쓸 수 있음. 명세에 따르면 논문의 Balance 증명이 이 부분을 잘못 서술함
  - 다만 SHA256 Compression Function이 충돌 저항이라는 가정 아래, 실제 구현의 $$\mathrm{PRF}^{\mathrm{addr}}$$는 충돌 저항이므로 악용할 수 없음
- 증명 크기: 논문은 288 B로 적지만 Zcash 명세는 296 B로 정의함. 명세는 논문이 압축된 y좌표의 인코딩을 고려하지 않았기 때문이라고 설명함
- 암호화: 논문은 ECIES의 곡선과 옵션을 정하지 않았음. 명세는 Key Privacy가 모든 곡선 파라미터와 키 분포에서 성립하는지 분명하지 않다고 지적함

**논문 안의 오기**

- 논문은 Bitcoin을 소개하는 부록에서 $$10^9$$ Satoshi가 1 bitcoin이라고 적음. Bitcoin에서 1 BTC는 $$10^8$$ Satoshi임
- 논문의 Step 4 설명은 $$pk_{\mathrm{enc}}$$가 속한 주소를 $$\mathrm{addr}^{\mathrm{new}}_{\mathrm{sk},1}$$로 적음. $$pk_{\mathrm{enc}}$$는 주소 공개 키 $$\mathrm{addr}^{\mathrm{new}}_{\mathrm{pk},1}$$에 속함
- 논문의 정식 POUR 설명은 Witness가 "두 새 Coin Commitment의 Authentication Path"를 담는다고 설명하지만, 조건 (a)에 따르면 Path의 대상은 소비되는 코인의 Coin Commitment임
- Coin Commitment의 입력 순서가 개요 설명과 정식 POUR 조건에서 다름 (Final Construction 절)

## After Zerocash: Zcash

이 절은 Zerocash를 구현한 Zcash의 변화를 NU5(Network Upgrade 5, 2022년)까지만 다룸.

**Zcash와 Zerocash의 관계**

- Zcash: Zerocash DAP Scheme의 구현. 보안 수정과 용어, 기능, 성능 조정을 더함 ([Zcash 명세 2016](https://bravenewcoin.com/assets/Whitepapers/Zcash-Protocol-Specification.pdf))
- 첫 버전 [Sprout](https://electriccoin.co/blog/zcash-sprout-launch)는 2016년 10월 28일 출시됨
- 용어 변경: Coin → Note, Serial Number → Nullifier
- JoinSplit
  - Pour를 투명한 UTXO 입력까지 받도록 일반화한 연산. Mint 기능까지 포함하므로 Mint와 Pour의 구분이 없음
  - 모든 JoinSplit이 zk-SNARK 증명을 담음. Zerocash에서는 Pour만 증명을 담았음
- Note Commitment
  - Zerocash의 두 단계 Commitment는 Mint를 증명 없이 공개 검증하기 위한 것이었음
  - Zcash는 모든 연산이 증명을 쓰므로 중첩 없이 SHA256 한 번으로 계산함
  - 대신 Statistically Hiding이 아니므로 Everlasting Anonymity를 지원하지 않음

**Trusted Setup의 변화**

- Sprout(2016)
  - MPC(Multi-Party Computation, 다자간 계산) [Ceremony](https://www.zcashcommunity.com/?p=458)로 공개 파라미터를 만듦. 계산은 2016년 10월 22~23일에 진행됨
  - 참여자는 [6명](https://bitzecbzc.github.io/technology/paramgen.html). 참여자 전원이 부정직하거나 침해되지 않는 한 결과 파라미터는 안전함
- Sapling(2018년 10월 28일 활성화)
  - 증명 시스템을 Groth16으로 바꿈 ([현행 Zcash 명세](https://zips.z.cash/protocol/protocol.pdf))
  - 파라미터는 회로와 무관한 Powers of Tau(87명 참여)와 회로 전용 Sapling MPC(90건 넘는 기여)의 [두 단계](https://electriccoin.co/blog/sapling-mpc)로 만듦. 각 단계는 참여자 중 한 명만 정직하면 안전함
- NU5(2022년 5월 31일 활성화)
  - Halo 2 증명 시스템을 쓰는 Orchard 프로토콜을 도입해, Orchard에서는 Trusted Setup이 필요 없어짐 ([NU5 Activates on Mainnet](https://electriccoin.co/blog/nu5-activates-on-mainnet-eliminating-trusted-setup-and-launching-a-new-era-for-zcash))

**BCTV14 위조 취약점** (CVE-2019-7167, CVE는 Common Vulnerabilities and Exposures)

- [CVE 기록](https://osv.dev/vulnerability/CVE-2019-7167): Sapling 이전 Zcash가 쓰던 BCTV14의 키 생성 과정에서 특정 값(Bypass Element)이 만들어졌음. 이 값을 가진 부정직한 증명자는 한 명제의 증명을 다른 명제의 유효해 보이는 증명으로 바꿀 수 있었음 → 증명 시스템의 Soundness(건전성: 거짓 명제에 대한 증명이 검증을 통과하지 않는 성질)가 깨져 위조가 가능했음
- [Zcash 측 공지](https://electriccoin.co/blog/zcash-counterfeiting-vulnerability-successfully-remediated)(2019년 2월 5일)
  - 2018년 3월 1일 Zcash Company 소속 암호학자가 발견했고, 2018년 10월 28일 활성화된 Sapling 업그레이드로 수정됨
  - 위조에만 해당하며 사용자 프라이버시에는 영향이 없음
  - 위조가 일어났다는 증거는 찾지 못했다고 밝힘
- Zerocash 논문의 구현도 BCTV14 구현을 씀. 논문의 구현이 이 취약점에 실제로 노출되었는지는 이 글에서 확인하지 않았음
