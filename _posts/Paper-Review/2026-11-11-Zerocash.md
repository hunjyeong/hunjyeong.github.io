## Bitcoin

### What is Bitcoin?

Bitcoin은 은행과 같은 중앙 기관 없이 사용자 간에 직접 주고받을 수 있도록 설계된 탈중앙화 P2P(Peer-to-Peer) 전자화폐 시스템이다.

- **Decentralization**: 중앙 관리자 없이 네트워크에 참여하는 Node들이 독립적으로 Block과 Transaction을 검증하고 Blockchain을 유지함

- **Public Ledger**: Blockchain에 기록된 Transaction 내역이 공개되어 누구나 조회하고 검증할 수 있음

- **Proof-of-Work(PoW)**: Miner가 연산 작업을 통해 새로운 Block을 생성하고, Node는 합의 규칙에 따라 Block을 검증함

- **UTXO Model**: Account별 잔액을 직접 기록하지 않고, UTXO의 집합으로 상태를 관리함. 잔액은 소비 가능한 UTXO의 금액 합계로 계산함

- **Limited Supply**: BTC의 최대 발행량은 약 2,100만 개로 제한됨

- **Currency Unit**: 기본 단위는 BTC, 최소 단위는 Satoshi
	- 1 BTC = $$10^8$$ Satoshi (100,000,000 Satoshi)

#### UTXO (Unspent Transaction Output)

UTXO는 이전 Transaction에서 생성된 Output 중 아직 다른 Transaction의 Input으로 소비되지 않은 Output이다. Transaction은 기존 UTXO를 Input으로 소비하고, 새로운 UTXO를 Output으로 생성한다.

Full Node는 **UTXO Set(현재 소비되지 않은 Output의 집합)**을 유지한다. Transaction이 유효하려면 Input이 참조하는 UTXO가 UTXO Set에 존재하고, 해당 UTXO의 잠금 조건을 비롯한 합의 규칙을 충족해야 한다.

검증된 Block이 Chain(누적 작업량이 가장 큰 Chain)에 연결되면, 해당 Block에서 소비된 UTXO는 UTXO Set에서 제거되고 새로 생성된 UTXO는 추가된다.

### How Bitcoin Works

- 예시: A가 B에게 0.3 BTC를 전송하는 상황 (수수료 0.001 BTC 가정)

	- A의 UTXO: 1 BTC UTXO
	- B의 UTXO: 0.5 BTC UTXO

1. **Transaction 생성**

	UTXO는 부분적으로 소비할 수 없다. 따라서 A는 1 BTC UTXO 전체를 Input으로 사용한다.

	| 구분 | UTXO | 설명 |
	| --- | --- | --- |
	| Input | 1 BTC | A의 기존 UTXO |
	| Output 1 | 0.3 BTC | B에게 전송 |
	| Output 2 | 0.699 BTC | A의 새 주소로 반환할 거스름돈 |
	| Transaction Fee | 0.001 BTC | $$\sum$$ Input - $$\sum$$ Output |

	기존 UTXO 전체를 소비한 뒤, 남은 금액에서 수수료를 제외한 0.699 BTC를 새로운 Output(거스름돈)으로 생성한다.

2. **서명 및 전파**

  	A는 개인키로 Input에 서명하여 1 BTC UTXO를 소비할 권한을 증명하고, Transaction을 Bitcoin P2P 네트워크에 전파한다.

3. **Transaction 검증**
	
	각 Node는 다음을 포함한 합의 규칙에 따라 Transaction을 검증하고, Mempool 정책(최소 수수료 등)을 충족하면 Mempool(아직 Block에 포함되지 않은 Transaction의 대기 목록)에 저장한다.

	- A의 1 BTC UTXO가 UTXO Set에 존재하는지(아직 소비되지 않았는지)
	- A의 서명이 해당 UTXO의 소비 조건을 충족하는지
	- Output 합계(0.999 BTC)가 Input(1 BTC)을 초과하지 않는지

4. **Block 생성**

	Miner는 Mempool에서 A의 Transaction을 골라 후보 Block에 포함한다. 
	또한 Block의 첫 Transaction으로 Coinbase Transaction을 직접 만들어, Block 보조금과 Block 내 수수료 합계(A의 Transaction 수수료 0.001 BTC 포함) 이하의 금액을 자신에게 지급한다. 
	이후 Block Header의 Hash가 Target(목표값) 이하가 될 때까지 Nonce를 바꿔 가며 계산한다(PoW).

5. **Block 검증 및 UTXO Set 갱신**
  
	PoW 조건을 만족하는 Block이 전파되면, 각 Node는 해당 Block의 PoW와 Block 내 모든 Transaction의 유효성을 검증한다. 
	검증을 통과한 Block은 이전 Block Header의 Hash를 참조하여 기존 Blockchain에 연결되며, 누적 작업량이 가장 큰 Chain(활성 Chain)에 포함될 경우 UTXO Set이 다음과 같이 갱신된다.

	- 제거된 UTXO: 1 BTC UTXO(A)
	- 추가된 UTXO: 0.3 BTC UTXO(B), 0.699 BTC UTXO(A)
	- 유지된 UTXO: 0.5 BTC(B)

6. **Confirmation**

	해당 Transaction이 활성 Chain의 Block에 포함되면 1 Confirmation을 얻으며, 이후 그 위에 Block이 추가될 때마다 Confirmation 수가 증가한다. 

	관행적으로 6 Confirmation을 충분히 신뢰할 수 있는 기준으로 사용하지만, Chain 재구성 가능성이 완전히 사라지는 것은 아니다.

	결과(다음 Transaction의 Input으로 사용 가능한 UTXO)

	- A의 UTXO: 0.699 BTC UTXO
	- B의 UTXO: 0.5 BTC UTXO, 0.3 BTC UTXO (총 잔액 0.8 BTC)

	(수수료 0.001 BTC: Miner의 Coinbase Output에 포함되며, 이 Output은 생성된 Block보다 높이가 100 이상 높은 Block에서부터 소비할 수 있다.)


### Double Spending Problem

**Double Spending(이중 지불)**은 복사가 가능한 디지털 화폐의 특성을 이용해 동일한 자산을 두 번 이상 지불하려는 시도이다. Bitcoin에서는 같은 UTXO를 서로 충돌하는 두 Transaction에서 중복 소비하려는 것을 의미한다.

**→ Bitcoin이 Double Spending을 방지하는 방법**

- **UTXO Set**: 이미 소비된 UTXO는 UTXO Set에서 제거되므로, 같은 UTXO를 참조하는 Transaction은 유효하지 않다. 그러나 Node마다 Transaction을 수신하는 순서가 다를 수 있으므로, 이것만으로는 충돌하는 두 Transaction 중 어느 것을 인정할지 정할 수 없다.

- **Public Ledger**: 모든 On-chain Transaction을 공개 원장에 기록하여, 어떤 Node든 각 UTXO의 소비 여부를 중앙 기관 없이 직접 검증할 수 있게 한다.

- **Consensus (Proof-of-Work)**: 충돌하는 두 Transaction이 서로 다른 Block에 포함되어 Chain이 갈라지면, 각 Node는 유효한 Chain 중 누적 작업량이 가장 큰 Chain을 선택한다. 이를 통해 네트워크는 하나의 Transaction 기록과 순서로 수렴한다.

- **Confirmation**: 기록된 Transaction을 뒤집으려면 해당 Block부터 새로운 Block들을 PoW로 만들어, 기존 Chain보다 누적 작업량이 큰 대체 Chain을 구성해야 한다. 따라서 Confirmation이 쌓일수록 Transaction이 뒤집힐 가능성은 낮아진다.

**⇒ Bitcoin은 중앙 기관 없이 누구나 Transaction을 검증할 수 있도록 Public Ledger를 사용하며, 이로 인해 모든 Transaction 내역이 공개되는 Privacy 문제가 발생한다.**

### Bitcoin's Privacy Problem

Bitcoin Transaction의 Input, Output 및 금액은 누구나 확인할 수 있도록 공개되며, 일반적인 주소 기반 거래에서는 다음 정보를 추적할 수 있다.

- **Origin Address(송신 주소)**: Input이 참조하는 이전 Output의 잠금 조건에서 알 수 있음
- **Destination Address(수신 주소)**: Output의 잠금 조건에서 도출할 수 있음
- **Payment Amount(결제 금액)**: 각 Output의 금액이 공개됨

Bitcoin은 완전한 Anonymity(익명성)이 아닌 **Pseudonymity(가명성)**을 제공한다. 사용자의 실명은 기록되지 않고 사용자는 여러 주소를 생성할 수 있지만, 위 정보가 형성하는 Transaction Graph를 분석하면 동일한 사용자의 주소들이 연결되고 **자금 흐름이 추적**될 수 있다.

- **Transaction Graph**: Transaction의 Input과 이전 Output의 참조 관계로 형성되는 그래프다. UTXO의 생성 이력을 거슬러 올라가면 궁극적으로 Coinbase Transaction에 도달한다.

- **Address Clustering Heuristics**: Transaction Graph를 분석할 때 다음과 같은 추정 기법으로 같은 사용자의 주소들을 묶는다.

	- **Common-Input-Ownership Heuristic**: 하나의 Transaction에 함께 사용된 여러 Input을 동일한 소유자의 것으로 추정한다. 예: B가 0.7 BTC를 보내기 위해 서로 다른 주소에 있는 0.5 BTC와 0.3 BTC UTXO를 함께 사용하면, 두 주소는 모두 B의 것으로 추정된다.

	- **Change Address Heuristic**: 금액이 딱 떨어지지 않는 Output이나 처음 쓰이는 주소로 가는 Output을 잔돈으로 추정한다. 예: A의 Transaction에서 0.3 BTC는 금액이 딱 떨어지고 0.699 BTC는 그렇지 않으므로, 0.699 BTC Output을 잔돈으로 추정하여 A의 새 주소를 기존 주소와 연결한다.

	- 두 휴리스틱은 추정이므로 틀릴 수 있다. 특히 여러 사용자가 Input을 모아 하나의 Transaction을 만드는 CoinJoin에서는 Common-Input-Ownership Heuristic이 성립하지 않는다.

- **신원 식별과 노출**: Transaction Graph, 금액, Block 타임스탬프 등의 On-chain 정보를 외부 정보(거래소의 KYC 기록, 가맹점 결제 정보 등)와 결합하면 실제 사용자를 식별하거나 추정할 수 있다. 특정 주소가 실명과 연결되면 해당 주소의 거래 내역과 자금 흐름이 드러나며, 주소 연결 휴리스틱을 통해 같은 사용자의 다른 주소와 잔액까지 추정될 수 있다.

- **Fungibility(대체 가능성)**: 동일한 단위의 화폐가 거래 이력과 관계없이 동등하게 취급되는 성질이다. Bitcoin에서는 UTXO의 이력을 추적할 수 있으므로 특정 이력을 가진 UTXO가 다르게 취급될 수 있으며, 이는 대체 가능성을 약화시킨다.

**⇒ Transaction 정보가 공개되어 있는 한 소비 내역, 잔액 및 자금 흐름이 노출될 위험은 근본적으로 제거할 수 없다. 그러나 이 정보를 단순히 숨기면 기존 방식으로는 Transaction의 유효성을 검증할 수 없다. 따라서 Transaction 정보를 공개하지 않으면서도 그 유효성을 누구나 검증할 수 있는 방법이 필요하다.**

## Solution 1: Mixing

**Mix(Laundry, Tumbler)**는 중앙 운영자가 관리하는 풀에 여러 사용자의 코인을 모은 뒤, 일정 시간이 지나면 같은 총액의 **다른 코인**을 돌려주는 방식이다. 입금과 출금 사이의 대응 관계를 숨겨 Transaction Graph만으로 어떤 입금이 어떤 출금에 대응하는지 파악하기 어렵게 한다.

- 예: A가 1 BTC를 Mix에 맡기고, 일정 시간 후 다른 사용자들이 맡긴 코인 중 1 BTC를 새 주소로 돌려받는다.

**한계**

- **지연**: 충분한 코인이 섞이려면 돌려받기까지 오래 기다려야 한다.
- **추적 가능성**: 운영자는 누가 어떤 코인을 맡기고 돌려받았는지 알 수 있다.
- **도난 위험**: 운영자가 맡긴 코인을 돌려주지 않을 수 있다.

**⇒ Mix를 쓰려면 기다려야 하고, 운영자를 믿어야 하며, 사용자가 프라이버시를 지키기 위해 계속 직접 노력해야 한다. 그러나 일반 사용자에게 필요한 것은 즉각적이고, 위험이 없으며, 자동으로 제공되는 프라이버시다.**

## Solution 2: Zerocoin

**Zerocoin**은 Bitcoin을 확장해, Mix의 중앙 운영자 없이 코인을 섞는 프로토콜이다. 기존 e-cash처럼 은행이 디지털 서명으로 코인을 보증하는 대신, 소비하려는 코인이 원장에 기록된 유효한 코인 중 하나임을 **Zero-Knowledge Proof(영지식 증명)**로 증명한다. Double Spending은 원장에 공개된 Serial Number(sn)로 막으므로, 중앙 기관이 필요 없다.

- **Commitment**: 값을 숨긴 채 고정하는 암호학적 약속이다. 

	- **Hiding**: Commitment만 보고는 숨긴 값을 알 수 없다.
	- **Binding**: 한 번 생성한 Commitment를 서로 다른 값으로 여는 것이 계산적으로 어렵다.

1. **Mint**: 사용자는 정해진 액면의 BTC를 내고, 무작위 Serial Number(sn)와 난수 r로 만든 Commitment(cm)를 원장에 기록한다. 이 시점에는 sn과 r이 공개되지 않는다.

2. **Spend**: 나중에 사용자는 받을 주소, sn, 그리고 다음을 증명하는 Zero-Knowledge Proof를 담은 Spend Transaction을 제출한다.

   - "나는 원장에 Mint된 Commitment 중 하나인 cm과, 해당 cm을 공개된 sn으로 열 수 있는 난수 r을 알고 있다."

   이 증명은 **어느 Mint Transaction의 코인인지 드러내지 않는다.** 증명이 유효하고 sn이 이전에 사용되지 않았다면, 해당 금액의 BTC가 지정한 주소로 가는 일반 Bitcoin Output으로 지급된다.

3. **Double Spending 방지**: 이미 공개된 sn이 다시 제출되면 Transaction을 거부한다.

⇒ 결과적으로 Spend Transaction과 원래의 Mint Transaction 사이의 연결, 즉 **결제의 출처(Origin)**가 숨겨진다.

**한계**

- **일부 정보만 숨김**: 출처는 숨기지만, Spend가 일반 Bitcoin Output을 만들므로 받는 주소(Destination)와 금액(Amount)은 공개된다.
- **고정 액면**: 정해진 단위의 코인만 지원하므로, 임의 금액 결제나 잔돈 처리(코인 분할)가 불가능하다.
- **직접 지불 불가**: Zerocoin 상태로 다른 사용자에게 바로 지불할 수 없다.
- **비효율**: Spend에 필요한 Double-Discrete-Logarithm(이중 이산 로그) 지식 증명은 공개된 수치로 크기가 45 kB를 넘고 검증에 450 ms가 걸린다. 이 수치는 일부 구성 요소에 80-bit 파라미터를 섞어 쓴 값이라, 모두 128-bit 보안 수준으로 맞추면 비용은 더 커진다. 이 증명은 네트워크에 전파되어 모든 Node가 검증하고 원장에 영구 저장해야 하므로, 비용이 Bitcoin보다 몇 자릿수 높다.

**⇒ Zerocoin은 Mix의 중앙 운영자 없이 출처를 숨겼지만, 수신자와 금액은 여전히 공개되며 일상적인 거래는 결국 Bitcoin으로 해야 한다. 완전한 익명 화폐라기보다 주기적으로 BTC를 "세탁"하는 탈중앙 Mix에 가깝다.**

## Solution 3: Zerocash

**Zerocash**는 Zerocoin의 한계를 해결하기 위해 제안된 탈중앙화 익명 결제 시스템이다(Ben-Sasson et al., 2014). **zk-SNARK(zero-knowledge Succinct Non-interactive ARgument of Knowledge)**를 이용하여 Transaction의 송신자(Origin), 수신자(Destination), 금액(Amount)을 숨기면서도 거래의 유효성을 공개적으로 검증할 수 있게 한다.

Zerocoin은 Coin의 생성(Mint)과 소비(Spend) 사이의 연결을 숨긴다. 그러나 다음과 같은 한계가 있다.

- 수신자와 금액이 공개된다.
- 고정 액면만 지원한다.
- 사용자 간 직접 지불과 잔돈 처리(Coin 분할)를 지원하지 않는다.

논문은 이를 해결하기 위해 **DAP(Decentralized Anonymous Payment) scheme**을 정의하고 그 구성(construction)을 제시한다. 이 구성을 실제로 구현한 시스템이 Zerocash다.

DAP scheme은 Bitcoin 같은 원장 기반 화폐(논문에서는 **Basecoin**이라 부름) 위에서 동작한다. 익명 Coin의 발행, 분할, 병합, 직접 전송, 그리고 Basecoin으로의 공개 출금을 지원한다.

| | Zerocoin | Zerocash |
| --- | --- | --- |
| 숨기는 정보 | 출처 | 출처, 수신자, 금액 |
| 금액 | 고정 액면 | 임의 금액, Coin 분할 및 병합 |
| 직접 지불 | 불가 | 수신자 주소로 직접 지불 |
| 증명 크기 | 45 kB 초과 | 288 B |
| Transaction 크기 | - | 1 kB 미만 |
| 검증 시간 | 약 450 ms | 6 ms 미만 |

Zerocoin의 수치는 일부 구성 요소에 80-bit 파라미터를 섞어 측정한 값이며, 모두 128-bit로 맞추면 비용이 더 커진다. 논문은 Zerocash가 Transaction 크기를 97.7% 이상, 검증 시간을 98.6% 이상 줄였다고 보고한다.

### 핵심 아이디어

Bitcoin에서는 Transaction이 "어떤 UTXO를, 누구에게, 얼마나" 보내는지 공개하고, Node가 이를 직접 확인한다.

Zerocash에서는 Coin의 내용 대신 **Coin Commitment(cm)**를 원장에 기록한다. Coin을 소비할 때는 그 Coin의 **Serial Number(sn)**를 공개하고, 다음 사실에 대한 **zk-SNARK 증명**을 함께 제출한다.

- "원장에 기록된 Coin 중 하나를 내가 소유하고 있고, 공개한 sn은 그 Coin의 것이며, 입력과 출력의 금액이 보존된다."

Node는 Coin의 내용을 보지 않고, 증명과 서명이 유효한지, sn이 이미 쓰였는지를 검증한다.

### Address와 Coin의 구조

**Address Key Pair**

- $addr_{pk} := (a_{pk}, pk_{enc})$: 공개하는 수신 주소
- $addr_{sk} := (a_{sk}, sk_{enc})$: Coin 소비($a_{sk}$)와 수신($sk_{enc}$)에 쓰는 비밀키
- $a_{sk}$는 무작위 seed이고, $a_{pk} := PRF^{addr}_{a_{sk}}(0)$이다.
- $(pk_{enc}, sk_{enc})$는 key-private 공개키 암호의 키 쌍이다.
- 사용자는 Address Key Pair를 원하는 만큼 만들 수 있으며, 생성에 다른 사람과의 상호작용이 필요 없다.

**Coin**

$$c := (addr_{pk}, v, \rho, r, s, cm)$$

- $v$: Coin의 가치 (0 이상 $v_{max}$ 이하)
- $\rho$: Serial Number를 결정하는 비밀값
- $r, s$: Commitment용 무작위값
- Coin Commitment $cm := COMM_s(v \| COMM_r(a_{pk} \| \rho))$
	- Coin이 생성될 때 원장에 기록된다.
- Serial Number $sn := PRF^{sn}_{a_{sk}}(\rho)$
	- Coin을 소비할 때만 공개된다.

cm과 sn은 모두 $\rho$에서 나오지만, 둘을 서로 연결할 수 없다.

- cm은 통계적 은닉(statistically-hiding) Commitment이므로 $a_{pk}$와 $\rho$에 대한 정보를 드러내지 않는다.
- sn은 $a_{sk}$를 seed로 한 PRF의 출력이므로, $a_{sk}$ 없이는 계산할 수 없고 무작위 값과 구별되지 않는다.

Coin을 소비하는 데 필요한 $\rho$, $r$과 Address 비밀키 $a_{sk}$는 소유자만 안다.

### Transaction 종류

| Transaction | 역할 | 공개되는 정보 | 숨겨지는 정보 |
| --- | --- | --- | --- |
| Mint | Basecoin을 예치하고 같은 가치의 Coin 발행 | cm, 금액 v, k, s, 예치한 Basecoin | Coin의 주소, $\rho$와 sn |
| Pour | Coin을 소비하여 새 Coin 생성(전송, 분할, 병합). 일부를 Basecoin으로 공개 출금 가능 | rt, 소비된 Coin의 sn, 새 Coin의 cm, $v_{pub}$, info, 증명 $\pi_{POUR}$, 암호문 $C_1, C_2$, $pk_{sig}, h_1, h_2, \sigma$ | 어느 Coin을 소비했는지, 송신자·수신자 주소, 각 Coin의 금액 |

논문은 Pour Transaction이 드러내는 금액은 공개 출금액 $v_{pub}$ 하나뿐이라고 정의한다(3.2절).

논문은 Basecoin과 결합한 구조(6.2절)에서 익명 Coin을 "zerocoin"이라고 부른다. 이는 Solution 2의 Zerocoin 프로토콜과 이름만 같고 다른 것이다. 이 구조에서 Coin의 생애는 다음과 같다.

- **Mint**: Basecoin을 내고 zerocoin을 발행한다. 낸 Basecoin은 사실상 소멸한다.
- **Pour**: zerocoin을 전송, 분할, 병합한다.
- **출금**: 필요하면 Pour의 $v_{pub}$를 통해 Basecoin으로 되돌린다. $v_{pub}$는 일반 Bitcoin Output, 수수료, 또는 새 Mint의 입력으로 쓰인다.

### Zerocash 동작 과정 (논문 1.3절)

논문은 단순한 구조에서 시작해 기능을 하나씩 추가하는 6단계로 구성을 설명한다.

#### Step 1: user anonymity with fixed-value coins

- 모든 Coin의 가치가 1 BTC로 같다고 가정한다.
- 도구: zk-SNARK와 statistically-hiding commitment scheme COMM
  - 메시지 m과 무작위값 r로 $COMM_r(m)$을 만든다.
  - 나중에 r과 m을 공개하여 Commitment를 연다.

**Mint**

- 사용자 u는 무작위 sn과 trapdoor r을 고르고, $cm := COMM_r(sn)$을 계산한다.
- Coin: $c := (r, sn, cm)$
- $Tx_{Mint}$에는 cm만 포함된다(sn, r은 비공개).
- 이 Transaction은 u가 1 BTC를 예치 풀(escrow pool)에 냈을 때만 원장에 추가된다. 즉, Mint Transaction은 예치 증서 역할을 한다.

**Spend**

- $Tx_{Spend} := (sn, \pi)$
- $\pi$: NP statement **"I know r such that $COMM_r(sn)$ appears in the list CMList of coin commitments"**에 대한 zk-SNARK proof
- sn이 원장에 없으면 u는 1 BTC를 받아 보관하거나, 다른 사람에게 보내거나, 새 Coin을 Mint할 수 있다.
- sn이 이미 원장에 있으면 Double Spending으로 간주하여 거부한다.

**익명성이 보장되는 이유**

1. sn은 공개되지만 r은 공개되지 않는다.
2. $\pi$는 영지식 증명이므로 r에 대한 어떤 정보도 드러내지 않는다.
3. CMList의 수많은 cm 중 이 Spend에 해당하는 것을 찾는 일은 $f(x) := COMM_x(sn)$의 역함수를 구하는 것과 같으며, 이는 계산상 불가능하다고 가정한다.
4. 따라서 Coin이 정당하게 소비되었다는 사실은 증명되지만, **어느 Mint의 Coin인지(결제의 출처)는 알 수 없다.**

Step 1은 Zerocoin과 유사한 구조이며, 결제의 출처를 숨기는 방법을 보여준다.

#### Step 2: compressing the list of coin commitments

Step 1의 NP statement는 CMList를 cm의 목록 그대로 사용한다.

**→ 문제: Scalability 한계**

1. 증명 검증 등 대부분의 알고리즘에서 시간·공간 복잡도가 CMList 길이에 비례하여 증가한다.
2. 이미 소비된 Coin의 cm도 CMList에서 지울 수 없다. 영지식성 때문에 어떤 cm이 소비되었는지 아무도 알 수 없기 때문이다.

**⇒ 해결: CRH 기반 Merkle Tree**

- CMList 위에 CRH(Collision-Resistant Hash) 기반의 추가 전용(append-only) Merkle Tree를 만들고, 그 Root를 rt라 한다.
  - Leaf: 각 cm
  - 내부 Node: 두 자식 값을 CRH로 해시한 값
- 새 Leaf를 추가할 때 rt를 갱신하는 시간과 공간은 트리 깊이에 비례한다. 즉, 선형에서 로그 수준으로 줄어든다.
- NP statement가 다음과 같이 바뀐다.
  - **"I know r such that $COMM_r(sn)$ appears as a leaf in a CRH-based Merkle tree whose root is rt"**
- 증명 생성에는 rt와 Authentication Path가, 검증에는 rt만 필요하다. 따라서 같은 zk-SNARK 구현이 지원할 수 있는 CMList 크기가 지수적으로 늘어난다.
- Zerocash는 깊이 64의 트리를 사용하여 최대 $2^{64}$개의 Coin을 지원한다.

#### Step 3: extending coins for direct anonymous payments

**→ 문제: $u_A$가 만든 Coin c를 $u_B$에게 넘길 때**

1. $u_A$가 sn을 알고 있으므로, $u_B$가 c를 쓰는 순간 $u_A$가 이를 알아본다(익명성 깨짐). 또한 $u_A$가 먼저 c를 써버릴 수도 있다(위험). 그래서 $u_B$는 c를 즉시 소비하고 새 Coin을 만들어야 한다.
2. 100 BTC를 보내려면 1 BTC Coin을 100번 보내야 한다(번거로움, 금액 노출).
3. 1 BTC의 배수가 아닌 금액은 보낼 수 없다.

**⇒ 해결: Coin Commitment 구조를 바꾸고, 결제 대상 지정과 sn 생성에 PRF(Pseudorandom Function) 사용**

하나의 PRF에서 겹치지 않는 세 가지 PRF를 유도한다.

- $PRF^{addr}_x(\cdot)$: Address 생성
- $PRF^{sn}_x(\cdot)$: Serial Number 생성 (충돌 저항성을 추가로 가정)
- $PRF^{pk}_x(\cdot)$: Step 6에서 사용

**Address 생성**

- 무작위 $a_{sk}$를 고르고 $a_{pk} := PRF^{addr}_{a_{sk}}(0)$을 계산한다.
- Coin에는 $a_{pk}$가 들어가며, 그 Coin은 $a_{sk}$를 아는 사람만 소비할 수 있다.

**Mint (가치 v의 Coin 발행)**

1. $\rho$를 고른다. 이 값으로 $sn := PRF^{sn}_{a_{sk}}(\rho)$가 결정된다.
2. 두 단계로 Commit한다.
   - $k := COMM_r(a_{pk} \| \rho)$
   - $cm := COMM_s(v \| k)$
3. Coin: $c := (a_{pk}, v, \rho, r, s, cm)$
4. $Tx_{Mint} := (v, k, s, cm)$. u가 v BTC를 예치한 경우에만 원장에 추가된다.

두 단계로 Commit하는 이유는 다음과 같다.

- 누구나 $COMM_s(v \| k) = cm$을 확인하여, cm이 가치 v인 Coin의 Commitment임을 검증할 수 있다.
- 그러나 소유자($a_{pk}$)와 sn을 결정하는 $\rho$는 k 안에 숨겨진다.

**Pour (Coin 전송)**

Pour는 입력 Coin들을 소비하고, 그 가치를 새 출력 Coin들에 "붓는" 연산이다. 출력 Coin 가치의 합은 입력 Coin 가치의 합과 같아야 한다. 1.3절은 입력 1개, 출력 2개로 설명한다(정식 구성은 입력 2개).

- $(a^{old}_{pk}, a^{old}_{sk})$를 가진 u가 $c^{old}$를 소비하고 $c^{new}_1, c^{new}_2$를 만든다.
  - 가치: $v^{new}_1 + v^{new}_2 = v^{old}$
  - 대상: $a^{new}_{pk,1}, a^{new}_{pk,2}$ (u 자신일 수도, 다른 사용자일 수도 있음)
- 각 $i$에 대해 $\rho^{new}_i$를 고르고, $k^{new}_i := COMM_{r^{new}_i}(a^{new}_{pk,i} \| \rho^{new}_i)$, $cm^{new}_i := COMM_{s^{new}_i}(v^{new}_i \| k^{new}_i)$를 계산한다.
- NP statement **POUR**에 대한 zk-SNARK proof $\pi_{POUR}$를 만든다.
  - "rt, $sn^{old}$, $cm^{new}_1$, $cm^{new}_2$가 주어졌을 때, 나는 다음을 만족하는 $c^{old}$, $c^{new}_1$, $c^{new}_2$, $a^{old}_{sk}$를 알고 있다."
    - 세 Coin이 모두 올바른 구조다.
    - $a^{old}_{pk} = PRF^{addr}_{a^{old}_{sk}}(0)$
    - $sn^{old} = PRF^{sn}_{a^{old}_{sk}}(\rho^{old})$
    - $cm^{old}$가 Root가 rt인 Merkle Tree의 Leaf다.
    - $v^{new}_1 + v^{new}_2 = v^{old}$
- $Tx_{Pour} := (rt, sn^{old}, cm^{new}_1, cm^{new}_2, \pi_{POUR})$를 원장에 추가한다. $sn^{old}$가 이미 원장에 있으면 거부한다.

**Step 3의 세 가지 문제가 해결되는 이유**

- u는 $a^{new}_{sk,1}$을 모르므로 $c^{new}_1$을 소비할 수 없다.
- 수신자가 나중에 공개할 $sn^{new}_1 = PRF^{sn}_{a^{new}_{sk,1}}(\rho^{new}_1)$은 수신자의 비밀키가 있어야 계산된다. 따라서 u는 그 sn을 알아볼 수 없고, 사용 시점도 추적할 수 없다.
- $Tx_{Pour}$는 가치가 어떻게 나뉘었는지, 어떤 cm이 소비되었는지, 새 Coin이 어느 주소로 갔는지 드러내지 않는다.
- 임의 금액의 Coin을 만들 수 있고, 분할 및 병합이 가능하다.

일반적으로 $N^{old}$개의 Coin을 $N^{new}$개로 Pour할 수 있지만, 논문은 2-입력·2-출력으로 고정해도 일반성을 잃지 않는다고 설명한다.
- 입력이 2개보다 적으면 가치 0인 Coin을 Mint하여 빈 입력으로 쓴다.
- 출력이 2개보다 적으면 가치 0인 Coin을 만들어 버린다.
- 2개보다 많으면 2-입력·2-출력 Pour 여러 개를 조합한다.

#### Step 4: sending coins

**→ 문제**: 수신자가 새 Coin을 쓰려면 그 비밀값($v, \rho, r, s$)을 받아야 한다. 별도 비밀 채널을 쓰면 추가 인프라나 가정이 필요하다.

**⇒ 해결: 원장을 통해 암호문으로 전달**

- Address에 암호화 키 쌍 $(pk_{enc}, sk_{enc})$를 추가한다.
- u는 $C_i := E_{enc}(pk^{new}_{enc,i}, (v^{new}_i, \rho^{new}_i, r^{new}_i, s^{new}_i))$를 $Tx_{Pour}$에 넣는다.
- 수신자는 원장의 Pour Transaction들을 훑으며 자신의 $sk_{enc}$로 복호화를 시도하여 자기 Coin을 찾는다.
- 암호문에는 금액이 암호화되어 있고, key-private 암호는 암호문만으로 어떤 공개키로 암호화했는지 알 수 없게 한다. 따라서 금액과 수신자가 드러나지 않는다.

#### Step 5: public outputs

**→ 문제**: Coin을 다시 Basecoin으로 바꾸는 방법이 없다.

**⇒ 해결: 공개 출력 추가**

- Pour에 공개 출금액 $v_{pub} \geq 0$과 문자열 info를 추가한다.
- 가치 보존 조건이 $v^{new}_1 + v^{new}_2 + v_{pub} = v^{old}$로 바뀐다.
- info로 받을 곳(예: Bitcoin 주소)을 지정한다. Transaction 수수료도 이 방식으로 낸다.
- $v_{pub} = 0$이면 공개 출력은 없다.

#### Step 6: non-malleability

**→ 문제**: 공격자가 원장에 기록되기 전의 $Tx_{Pour}$를 가로채 info를 바꾸면, $v_{pub}$를 자기 주소로 돌릴 수 있다.

**⇒ 해결: 일회용 서명과 PRF 기반 MAC**

1. 일회용 서명 키 쌍 $(pk_{sig}, sk_{sig})$를 만든다.
2. $h_{Sig} := CRH(pk_{sig})$를 계산한다.
3. $h_i := PRF^{pk}_{a^{old}_{sk,i}}(i \| h_{Sig})$를 계산한다. 이 값이 $h_{Sig}$를 각 입력 Coin의 비밀키에 묶는 MAC 역할을 한다.
4. POUR에 $h_{Sig}, h_1, h_2$를 추가하고, $h_i$가 올바르게 계산되었음을 함께 증명한다.
5. Pour의 모든 값을 $sk_{sig}$로 서명하여 $\sigma$를 만들고, $pk_{sig}$와 함께 넣는다.

1.3절은 $h_i := PRF^{pk}_{a^{old}_{sk,i}}(h_{Sig})$로 설명하지만, 정식 구성(4.2절, Figure 2)은 입력 번호 i를 붙인 위 형태를 사용한다.

값을 하나라도 바꾸면 $\sigma$가 무효가 된다. 다른 서명 키로 다시 서명하려면 새 $h_{Sig}$에 맞는 $h_i$가 필요한데, 이를 만들려면 $a^{old}_{sk,i}$를 알아야 한다.

### DAP Scheme 알고리즘 (논문 3.2절, 4절 Figure 2)

| 알고리즘 | 실행 주체 | 입력 | 출력 |
| --- | --- | --- | --- |
| Setup | 신뢰 기관 (최초 1회) | 보안 파라미터 $\lambda$ | 공개 파라미터 pp |
| CreateAddress | 사용자 | pp | $(addr_{pk}, addr_{sk})$ |
| Mint | 사용자 | pp, v, $addr_{pk}$ | Coin c, $Tx_{Mint}$ |
| Pour | 사용자 | pp, rt, 입력 Coin 2개와 비밀키, Authentication Path 2개, 새 금액 2개, 새 주소 2개, $v_{pub}$, info | 새 Coin 2개, $Tx_{Pour}$ |
| VerifyTransaction | Node | pp, Transaction, 원장 L | 유효 여부 |
| Receive | 사용자 | pp, $(addr_{pk}, addr_{sk})$, 원장 L | 받은 미사용 Coin들 |

**Setup**

1. POUR를 검증하는 산술 회로 $C_{POUR}$를 만든다.
2. $(pk_{POUR}, vk_{POUR}) := KeyGen(1^\lambda, C_{POUR})$
3. 암호화와 서명의 공개 파라미터 $pp_{enc}, pp_{sig}$를 만든다.
4. $pp := (pk_{POUR}, vk_{POUR}, pp_{enc}, pp_{sig})$를 공개한다.

Setup은 한 번만 수행한다. 이후에는 신뢰 기관이 필요 없으며, 전역 비밀값이나 trapdoor도 보관하지 않는다. 각 알고리즘은 pp의 일부만 사용한다.
- 크기가 큰 $pk_{POUR}$는 Pour에만 필요하다.
- Node의 검증(VerifyTransaction)에는 $vk_{POUR}$만 필요하다.

**CreateAddress**

1. $(pk_{enc}, sk_{enc}) := K_{enc}(pp_{enc})$
2. 무작위 $a_{sk}$를 고르고 $a_{pk} := PRF^{addr}_{a_{sk}}(0)$을 계산한다.
3. $addr_{pk} := (a_{pk}, pk_{enc})$, $addr_{sk} := (a_{sk}, sk_{enc})$

**Mint**

1. 무작위 $\rho$, $r$, $s$를 고른다.
2. $k := COMM_r(a_{pk} \| \rho)$, $cm := COMM_s(v \| k)$
3. $c := (addr_{pk}, v, \rho, r, s, cm)$, $Tx_{Mint} := (cm, v, *)$, $* := (k, s)$

**Pour**

1. 각 입력 Coin $i$에 대해 다음을 수행한다.
   - $sn^{old}_i := PRF^{sn}_{a^{old}_{sk,i}}(\rho^{old}_i)$를 계산한다.
   - 새 Coin $c^{new}_i$를 만든다($\rho^{new}_i, r^{new}_i, s^{new}_i$를 무작위로 고르고 $cm^{new}_i$ 계산).
   - 암호문 $C_i$를 만든다.
2. $(pk_{sig}, sk_{sig})$를 만들고 $h_{Sig} := CRH(pk_{sig})$, $h_i := PRF^{pk}_{a^{old}_{sk,i}}(i \| h_{Sig})$를 계산한다.
3. 증명을 만든다.
   - 공개 입력(instance): $x := (rt, sn^{old}_1, sn^{old}_2, cm^{new}_1, cm^{new}_2, v_{pub}, h_{Sig}, h_1, h_2)$
   - 비밀 입력(witness): $a := (path_1, path_2, c^{old}_1, c^{old}_2, addr^{old}_{sk,1}, addr^{old}_{sk,2}, c^{new}_1, c^{new}_2)$
   - $\pi_{POUR} := Prove(pk_{POUR}, x, a)$
4. $m := (x, \pi_{POUR}, info, C_1, C_2)$에 서명하여 $\sigma := S_{sig}(sk_{sig}, m)$을 만든다.
5. 결과는 다음과 같다.

$$Tx_{Pour} := (rt, sn^{old}_1, sn^{old}_2, cm^{new}_1, cm^{new}_2, v_{pub}, info, *)$$
$$* := (pk_{sig}, h_1, h_2, \pi_{POUR}, C_1, C_2, \sigma)$$

**POUR statement (정식, 4.2절)**: 증인 a는 각 $i \in \{1, 2\}$에 대해 다음을 만족해야 한다.

1. $path_i$가 Root rt에 대한 $cm^{old}_i$의 올바른 Authentication Path다.
2. $a^{old}_{pk,i} = PRF^{addr}_{a^{old}_{sk,i}}(0)$
3. $sn^{old}_i = PRF^{sn}_{a^{old}_{sk,i}}(\rho^{old}_i)$
4. $cm^{old}_i = COMM_{s^{old}_i}(COMM_{r^{old}_i}(a^{old}_{pk,i} \| \rho^{old}_i) \| v^{old}_i)$
5. $cm^{new}_i = COMM_{s^{new}_i}(COMM_{r^{new}_i}(a^{new}_{pk,i} \| \rho^{new}_i) \| v^{new}_i)$
6. $h_i = PRF^{pk}_{a^{old}_{sk,i}}(i \| h_{Sig})$

또한 가치 보존 조건을 만족해야 한다: $v^{new}_1 + v^{new}_2 + v_{pub} = v^{old}_1 + v^{old}_2$ (단, $v^{old}_1, v^{old}_2 \geq 0$이고 $v^{old}_1 + v^{old}_2 \leq v_{max}$).

4.2절은 cm 안의 순서를 $k \| v$로 적는다. 반면 1.3절과 Figure 2는 $v \| k$로 적으며, 5.1절의 구현은 $k \| 0^{192} \| v$를 사용한다.

**VerifyTransaction**

- Mint: $cm = COMM_s(v \| k)$인지 확인한다.
- Pour:
  1. $sn^{old}_1$이나 $sn^{old}_2$가 원장에 있거나, 둘이 같으면 거부한다.
  2. rt가 원장에 기록된 적 없는 Root면 거부한다. 원장은 과거의 모든 Root를 보관한다.
  3. $h_{Sig} := CRH(pk_{sig})$를 계산하여 x와 m을 재구성한다.
  4. 서명 $V_{sig}(pk_{sig}, m, \sigma)$와 증명 $Verify(vk_{POUR}, x, \pi_{POUR})$가 모두 통과해야 유효하다.

**Receive**

각 Pour Transaction의 $C_i$를 $sk_{enc}$로 복호화한다. 결과 $(v, \rho, r, s)$가 나오면 다음 두 가지를 확인한다.
- $cm^{new}_i = COMM_s(v \| COMM_r(a_{pk} \| \rho))$인지
- $PRF^{sn}_{a_{sk}}(\rho)$가 원장에 없는지

둘 다 만족하면 그 Coin을 자신의 것으로 저장한다. Receive는 Pour로 받은 Coin만 찾으며, 사용자가 직접 Mint한 Coin은 대상이 아니다.

| Problem의 검증 항목 | Zerocash의 대응 |
| --- | --- |
| 소비하는 Coin이 원장에 존재하는가 | Merkle Tree 포함 증명 (POUR 조건 1) |
| 소비 권한이 있는가 | $a_{sk}$와 $a_{pk}$의 일치 증명 (조건 2) |
| 이미 소비되지 않았는가 | sn 공개(조건 3), 중복 sn 거부 |
| 새로운 자금이 생성되지 않았는가 | Coin 구조(조건 4, 5)와 가치 보존 조건 증명 |
| Transaction이 변조되지 않았는가 | $h_i$ 증명(조건 6)과 서명 $\sigma$ |

### 예시: A가 B에게 0.3 BTC 전송 (수수료 0.001 BTC 가정)

앞의 Bitcoin 예시와 같은 상황을 Zerocash로 처리한다.

- A의 Coin: 이전에 Mint한 1 BTC Coin $c_A$. 이 Mint Transaction에는 $v = 1$과 예치한 Basecoin이 공개되어 있다.

1. **주소 준비**
   - B는 CreateAddress로 $addr^B_{pk}$를 만들어 A에게 알려준다.
   - A도 잔돈을 받을 새 주소 $addr^{A'}_{pk}$를 만든다.

2. **Pour 생성** (A)

   Pour는 입력이 2개이므로, A는 가치 0인 Coin $c_0$를 미리 Mint하여 두 번째 입력으로 쓴다(이 Mint에도 $v = 0$이 공개된다).

   | 구분 | 내용 |
   | --- | --- |
   | 입력 1 | $c_A$ (1 BTC) |
   | 입력 2 | $c_0$ (0 BTC, 빈 입력용) |
   | 출력 1 | $c^{new}_1$: 0.3 BTC → $addr^B_{pk}$ |
   | 출력 2 | $c^{new}_2$: 0.699 BTC → $addr^{A'}_{pk}$ (잔돈) |
   | $v_{pub}$ | 0.001 BTC (아무도 청구하지 않아 수수료가 됨) |
   | 가치 보존 | $0.3 + 0.699 + 0.001 = 1 + 0$ |

   - $C_1$은 B의 $pk_{enc}$로, $C_2$는 A의 새 $pk_{enc}$로 암호화한다.
   - Basecoin과 결합한 구조에서는, 이 Pour를 담는 Bitcoin Transaction 전체가 info로 들어가 함께 서명된다(6.2절).
   - 증명 생성에 약 2분이 걸린다.

3. **검증 및 기록** (Node)
   - Node는 VerifyTransaction을 실행한다(약 5.7 ms).
   - Block에 포함되어야 $cm^{new}_1, cm^{new}_2$가 CMList(Merkle Tree)에, $sn^{old}_1, sn^{old}_2$가 SNList에 추가된다.
   - $c_A$의 cm은 CMList에서 삭제되지 않는다. 어느 cm이 소비되었는지 아무도 알 수 없기 때문이다.

4. **수신** (B)
   - B는 Receive로 $C_1$을 복호화하여 $(0.3, \rho_1, r_1, s_1)$을 얻는다.
   - $cm^{new}_1$과 일치하는지, sn이 원장에 없는지 확인한 뒤 Coin을 저장한다.

**Bitcoin과 공개 정보 비교**

| 정보 | Bitcoin | Zerocash Pour |
| --- | --- | --- |
| 소비된 Coin | 1 BTC UTXO가 특정됨 | 특정 불가 (sn만 공개) |
| 송신자 주소 | 공개 | 비공개 |
| 수신자 주소 | 공개 | 비공개 (cm과 key-private 암호문만 공개) |
| 송금액 0.3 BTC | 공개 | 비공개 |
| 잔돈 0.699 BTC | 공개 | 비공개 |
| 수수료 0.001 BTC | 공개 (Input − Output) | 공개 ($v_{pub}$) |
| 상태 변화 | UTXO 1개 제거, 2개 추가 | cm 2개, sn 2개 추가 (삭제 없음) |

### 구현 (논문 5절)

Zerocash는 128-bit 보안 수준을 목표로 한다. CRH, PRF, COMM을 모두 SHA256 압축 함수 H(512-bit 입력 → 256-bit 출력)로 구현하여 zk-SNARK 회로를 작게 만든다.

| 구성 요소 | 구현 |
| --- | --- |
| CRH (Merkle Tree) | $H(z)$, $z$는 512-bit(두 자식 값) |
| $PRF^{addr}_x(z)$ | $H(x \Vert 00 \Vert z)$ |
| $PRF^{sn}_x(z)$ | $H(x \Vert 01 \Vert z)$ |
| $PRF^{pk}_x(z)$ | $H(x \Vert 10 \Vert z)$ |
| $k = COMM_r(a_{pk} \Vert \rho)$ | $H(r \Vert [H(a_{pk} \Vert \rho)]_{128})$, r은 384-bit |
| $cm = COMM_s(v \Vert k)$ | $H(k \Vert 0^{192} \Vert v)$, v는 64-bit, s는 사용하지 않음 |
| Merkle Tree 깊이 | 64 (최대 $2^{64}$개 Coin) |
| $v_{max}$ | $2^{64} - 1$ |
| 서명 Sig | ECDSA (s를 하위 절반으로 제한한 비가변 변형) |
| 암호화 Enc | key-private ECIES |
| zk-SNARK | [BCTV14] 구현, 256-bit 소수 위수의 체 |

- 기본 PRF는 $PRF_x(z) := H(x \| z)$이다. 유도된 세 PRF의 seed x는 256-bit, 입력 z는 254-bit다.
- cm에서 s를 쓰지 않는 이유는 k가 이미 통계적 은닉 Commitment의 출력이라 무작위값 역할을 하기 때문이다.
- $[\cdot]_{128}$은 256-bit 값을 128-bit로 자르는 연산이다(하위 비트 제거).
- $h_{Sig}$는 회로 안에서 검증할 필요가 없으므로 압축 함수가 아닌 전체 SHA256으로 계산한다.
- ECDSA 변형은 기존 bitcoind와의 호환을 위해 선택했다. 논문은 이 변형에 대한 SUF-1CMA 형식 증명은 알려져 있지 않다고 밝힌다.

이 구현에서 POUR가 확인하는 조건은 각 $i$에 대해 다음과 같다.

- $path_i$가 rt에 대한 $cm^{old}_i$의 올바른 경로
- $a^{old}_{pk,i} = H(a^{old}_{sk,i} \| 0^{256})$
- $sn^{old}_i = H(a^{old}_{sk,i} \| 01 \| [\rho^{old}_i]_{254})$
- $cm^{old}_i = H(H(r^{old}_i \| [H(a^{old}_{pk,i} \| \rho^{old}_i)]_{128}) \| 0^{192} \| v^{old}_i)$
- $cm^{new}_i$도 같은 형태
- $h_i = H(a^{old}_{sk,i} \| 10 \| b_i \| [h_{Sig}]_{253})$ ($b_1 = 0$, $b_2 = 1$)

또한 가치 보존 조건 $v^{new}_1 + v^{new}_2 + v_{pub} = v^{old}_1 + v^{old}_2$와 $v^{old}_1 + v^{old}_2 < 2^{64}$를 확인한다.

**회로 크기**

- SHA256 압축 함수 회로: 27,904 게이트
- POUR 전체 회로 $C_{POUR}$: 4,109,330 게이트. 이 중 99% 이상이 H 계산 검증이다.
- Merkle Tree 경로 검증은 Coin 1개당 1,802,304 게이트(층당 28,161 × 64층)를 차지한다.

### 성능 (논문 7절)

Intel Core i7-4770 데스크톱, 단일 스레드 기준이다.

| 알고리즘 | 시간 | 크기 |
| --- | --- | --- |
| Setup | 5분 17초 | pp 896 MiB (Proving Key 896 MiB, Verification Key 749 B) |
| CreateAddress | 326.0 ms | $addr_{pk}$ 343 B, $addr_{sk}$ 319 B |
| Mint | 23 µs | Coin 463 B, $Tx_{Mint}$ 72 B |
| Pour | 2분 2.01초 | $Tx_{Pour}$ 996 B + info 길이 |
| VerifyTransaction | Mint 8.3 µs, Pour 5.7 ms (원장 조회 제외) | - |
| Receive | Pour Transaction 1개당 1.6 ms | - |

- **$Tx_{Pour}$ 996 B의 구성**:
  - rt 32 B
  - sn 2 × 32 B
  - cm 2 × 32 B
  - $v_{pub}$ 8 B
  - $pk_{sig}$ 66 B
  - $h_1, h_2$ 2 × 32 B
  - $\pi_{POUR}$ 288 B
  - $C_1, C_2$ 2 × 173 B
  - $\sigma$ 64 B

- **증명 생성(Prove) 시간**: 단일 스레드 1분 59초, 4 스레드 46초다.
- **Merkle Tree 유지 비용**: Root 갱신 1회에 H 64회가 필요하고, Authentication Path 저장에 2 KiB가 든다.
- **네트워크 시뮬레이션**: 1,000 Node, Block 간격 150초 조건에서, Zerocash Transaction의 검증 시간을 10 ms 지연으로 모사하여 측정했다.
  - 모든 Transaction이 Zerocash여도 Block 검증 시간은 최대 약 80 ms였다. 검증 캐시가 없다면 예상치는 약 1,500 ms다.
  - Block 전파에 미치는 영향은 미미했다.
  - Transaction이 Block에 포함되어 사용 가능해지기까지 약 190초가 걸렸다.

### 보안 속성 (논문 3.4절, 정리 4.1)

- **Ledger Indistinguishability**: 원장은 공개 정보(Mint 금액, $v_{pub}$, info, Transaction 수 등) 외에 어떤 정보도 드러내지 않는다.
- **Transaction Non-malleability**: 유효한 Pour Transaction을 변조하여 같은 Coin을 다른 방식으로 소비하게 만들 수 없다.
- **Balance**: 누구도 자신이 Mint하거나 받은 금액보다 많이 쓸 수 없다.

논문은 4절의 구성이 완전성(Completeness)과 위 세 성질을 모두 만족함을 증명한다(정리 4.1). 이 증명은 다음 구성 요소의 안전성을 전제로 한다.
- zk-SNARK
- PRF ($PRF^{sn}$의 충돌 저항성 포함)
- COMM (Hiding은 통계적, Binding은 계산적)
- CRH
- 일회용 서명(SUF-1CMA)
- 암호화(IND-CCA, IK-CCA)

Zerocash 구현은 이 구성 요소들을 SHA256 압축 함수 H에 대한 가정과 ECDSA 변형으로 대체한다.

### 특징 및 한계

- **Privacy**: Pour Transaction은 송신자, 수신자, 각 Coin의 금액을 숨긴다. 단, Mint의 금액 v와 예치 Basecoin, Pour의 $v_{pub}$와 info는 공개된다.
- **Public Verifiability**: 거래 세부 정보 없이 zk-SNARK Proof로 유효성을 누구나 검증할 수 있다.
- **Double Spending Prevention**: 이미 공개된 sn의 중복 사용을 거부한다.
- **Variable Amounts**: 임의 금액, Coin 분할 및 병합, 수신자 주소로의 직접 지불을 지원한다.
- **Trusted Setup**: zk-SNARK 공개 파라미터를 만드는 1회의 신뢰 설정이 필요하다.
  - 설정이 오염되면 증명의 건전성이 깨져 Non-malleability와 Balance가 성립하지 않는다(Coin 위조 가능).
  - Ledger Indistinguishability(익명성)는 유지된다.
  - 논문은 Setup을 다자간 계산(MPC)으로 수행하여 신뢰 요구를 줄이는 것을 향후 과제로 남겼다.
- **Proof Generation Cost**: 검증은 빠르지만, 증명 생성에 약 2분과 896 MiB의 Proving Key가 필요하다.
- **확정 전 사용 불가**: 받은 Coin은 Block에 포함되어 원장에 기록된 뒤에야 사용할 수 있다.
- **저장 공간**: SNList는 Bitcoin의 UTXO Set과 달리 줄어들지 않고 계속 늘어난다(완화 방안은 8.3절).
- **수신 비용**: 자신에게 온 Coin을 찾으려면, 최악의 경우 모든 Pour Transaction의 암호문에 복호화를 시도해야 한다.
- **계산적 익명성**: 익명성은 계산적 가정에 기반한다. 무제한 계산 능력을 가진 공격자는 $h_i$ 등으로부터 송신자와 수신자를 알아낼 수 있다. 영구적(everlasting) 익명성을 얻으려면 주소 일회 사용, 외부 채널 전달 등의 수정이 필요하다(8.1절).
- **Network Layer**: 원장만 익명화하며, IP 주소 등은 Tor 같은 별도 수단이 필요하다.
- **Poison-pill 공격**: 강력한 공격자가 특정 사용자에게만 가짜 Block을 보여주면, 그 Block의 rt를 쓰는 Pour로 사용자가 식별될 수 있다. 논문은 신뢰할 수 있는 Peer와 Chain을 대조하고, 민감한 거래에서는 더 오래된 Block의 rt를 쓰도록 권고한다.

**⇒ Zerocash는 Transaction 정보를 원장에 공개하는 대신 "Transaction이 유효하다는 zk-SNARK 증명"을 기록한다. 이를 통해 송신자, 수신자, 금액을 숨기면서도 Double Spending과 부당한 자금 생성이 없었음을 누구나 검증할 수 있게 한다.**
