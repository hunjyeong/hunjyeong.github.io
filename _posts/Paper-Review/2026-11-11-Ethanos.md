이 글을 읽을 때 주의할 점이 하나 있다. 논문은 Ethereum이 Proof of Work(작업 증명, 이하 PoW)를 쓰던 시기에 쓰였다. 본문의 Miner, Fast Sync, 저장 용량 수치는 모두 그 시점 기준이다. 이후 달라진 내용은 10장에 따로 정리했다. 논문에 적힌 내용과 이 글의 해석은 구분해서 적었다.

## 한 줄 요약

Ethanos는 일정 주기마다 State Trie를 비우고, 그 주기에 실제로 쓰인 Account만으로 State Trie를 다시 만드는 기법이다. 오래 쓰이지 않은 Account는 현재 State Trie에서 빠지며, 필요해지면 Restore Transaction으로 복원한다. 그 결과 새 Node는 최근 주기의 작은 State Trie만 받아도 Full Node로 동작할 수 있다.

## 1. 배경과 필요성

### 1.1 Account-based Blockchain과 State

Blockchain(블록체인)이 "누가 얼마를 가지고 있는가"를 표현하는 방식은 크게 두 가지다.

- Bitcoin은 Unspent Transaction Output(미사용 트랜잭션 출력, 이하 UTXO) 방식을 쓴다. 아직 쓰이지 않은 Transaction 출력들의 집합이 곧 전체 상태다. 전체 상태가 암묵적으로 표현된다.
- Ethereum은 Account-based(계정 기반) 방식을 쓴다. Account(계정)와 잔액으로 이루어진 Global State(전역 상태)를 Transaction(트랜잭션)과 별도로 명시적으로 기록한다.

논문은 Account-based 방식이 Smart Contract(스마트 컨트랙트) 개발에 더 단순하고 직관적이라고 설명한다. Smart Contract는 Transaction에 의해 호출되어 Account의 상태를 사용해 특정 작업을 수행하는 프로그램이다.

Account-based 방식에는 비용이 따른다. Block(블록)이 Transaction뿐 아니라 Account의 상태까지 저장해야 하므로 데이터가 빠르게 늘어난다. 논문은 2020년 1월 기준 Ethereum 데이터가 3.6TB를 넘었다고 적는다. 이 수치의 출처는 Etherscan의 Archive Node 크기 차트다.

### 1.2 Full Node와 Light Node

- Full Node(풀 노드)는 Transaction을 스스로 완전히 검증할 수 있는 Node다.
- Light Node(라이트 노드)는 스스로 완전히 검증하지 못하고, 다른 Full Node에 Transaction 전송과 검증을 맡기는 Node다.

저장 공간과 네트워크 대역폭이 제한된 개인 기기는 Full Node로 Bootstrapping하기 어렵다. Bootstrapping(부트스트래핑)은 새 Node가 네트워크에 처음 참여해 현재 상태까지 따라잡는 과정이다.

논문이 지적하는 문제는 두 가지다.

1. Light Node 사용자는 검증을 위임하므로 금융 사기나 Transaction 검열에 취약해진다.
2. Full Node와 Miner(채굴자)의 수가 적으면 네트워크 자체가 조작에 취약해진다.

따라서 Full Node가 되는 데 필요한 데이터를 줄여야 한다는 것이 논문의 출발점이다.

### 1.3 Synchronization 방식

Synchronization(동기화)은 Node가 현재 State까지 도달하는 방법이다. 논문은 Go Ethereum(이하 Geth) Client의 두 방식을 설명한다.

**Full Sync**

1. 모든 Block을 내려받는다.
2. Genesis Block(최초 블록)부터 현재 Block까지 모든 Transaction을 다시 실행(Replay)한다.
3. 그 과정에서 현재 State Trie와 모든 과거 갱신 기록을 재생성하고, Block Header를 검증한다.

논문은 Full Sync에 큰 저장 공간과 수 주의 시간이 든다고 적는다.

**Fast Sync**

1. 모든 Block을 내려받는다. 이 점은 Full Sync와 같다.
2. Pivot Block의 State Trie Snapshot을 내려받는다. Pivot Block은 현재 Block보다 64 Block 이전의 Block이다. Snapshot은 그 Block 시점의 State Trie 사본이다.
3. Pivot Block부터 현재 Block까지의 Transaction만 Replay해서 현재 State Trie를 만든다.

오래된 Block일수록 위조하기 어려우므로 검증 필요성이 낮다는 생각에 기반한다. Pivot Block 이전의 Transaction은 내려받지만 Replay하지 않는다.

Fast Sync의 저장 용량은 2020년 1월 기준 약 235GB였다. 논문은 이것을 전체의 6.7%라고 적는다. 그래도 일반 기기에는 무겁고, 동기화에 하루 정도가 걸린다.

### 1.4 병목은 State Trie

235GB 가운데 State Trie는 70GB 이상으로 추정되고, 나머지는 대부분 Transaction 데이터다. 크기만 보면 Transaction이 더 크다. 그런데 논문은 State Trie 내려받기가 더 큰 병목이라고 본다. 이유는 다음과 같다.

- State Trie는 Hash를 Key로 하는 Database 접근이 필요하다. 접근 위치가 무작위로 흩어진다.
- 그래서 State Trie를 순회하고, 전송하고, 재구축하는 과정이 Disk Input/Output(디스크 입출력, 이하 I/O)에 크게 묶인다.
- 반면 Transaction 데이터는 Block의 Transaction Index를 써서 묶음으로 빠르게 내려받을 수 있다.

5장의 실험에서 이 차이가 수치로 확인된다.

## 2. 사전 지식: State Trie와 Proof

Ethanos의 복원 방식은 Merkle Proof와 Void Proof에 의존한다. 이 둘을 이해하려면 State Trie 구조를 먼저 알아야 한다.

### 2.1 Account

Ethereum의 Account는 16진수 40자로 된 Address(주소)로 접근한다. Account는 네 가지 값을 가진다.

| 필드 | 의미 |
|---|---|
| Nonce | 이 Account가 보낸 Transaction 수. 같은 Transaction이 여러 번 실행되는 것을 막는다. |
| Balance | 보유한 Ether(ETH)의 양 |
| StorageRoot | Smart Contract의 상태를 담은 Storage를 가리키는 Key |
| CodeHash | Contract Code를 Database에서 찾는 데 쓰는 Hash |

Account는 두 종류다. Externally Owned Account(외부 소유 계정, 이하 EOA)는 사용자의 Account다. Contract Account(컨트랙트 계정, 이하 CA)는 Smart Contract의 Account다. 논문은 EOA의 StorageRoot와 CodeHash가 Null이라고 적는다. 정확히는 Null이 아니라 빈 Trie의 Root Hash와 빈 Code의 Hash 값이다(9장 참고).

### 2.2 Transaction과 State Transition

Transaction은 Sender(보내는 계정)에서 Receiver(받는 계정)로 값을 옮긴다. 두 Account의 Balance가 바뀌고 Sender의 Nonce가 1 늘어난다. Transaction이 유효하려면 Sender의 Balance가 충분해야 하고, Transaction의 Nonce가 Sender의 Nonce와 같아야 한다. Transaction에는 Sender의 서명과, Miner에게 지급될 Fee(수수료)가 들어 있다.

Block i의 State를 σ_i, Block i의 Transaction 목록을 Tx_i라고 하면 State Transition(상태 전이)은 다음과 같다.

```
σ_i = Π(σ_(i-1), Tx_i)
```

Π는 Tx_i의 Transaction을 순서대로 σ_(i-1)에 적용하는 함수다. 따라서 Genesis Block의 State σ_0에 Transaction 목록을 차례로 적용하면 σ_i를 얻는다.

**예시 (논문 Figure 1)**

Block i에 Account 다섯 개(a1부터 a5)가 있다. Block i+1에 Transaction이 하나 있다. a2가 a4에게 5 ETH를 보내고 Fee는 0.01 ETH다. Miner는 a5다.

| Account | 변화 |
|---|---|
| a2 (Sender) | Balance 45.01 → 40.00, Nonce 10 → 11 |
| a4 (Receiver) | Balance 0.12 → 5.12, Nonce 2 그대로 |
| a5 (Miner) | Balance 32.01 → 34.02 (Fee 0.01 + Block Reward 2) |

### 2.3 Merkle Patricia Trie

Ethereum은 각 Block의 Account 상태를 Merkle Patricia Trie(머클 패트리샤 트라이, 이하 MPT)에 저장한다. MPT는 두 구조를 합친 것이다.

- Patricia Trie는 Address의 문자열이 곧 경로가 되는 탐색 트리다. 데이터는 Leaf에 있다. Address의 앞부분이 같은 Account들은 경로를 공유한다. Address 검색이 효율적이다.
- Merkle Tree는 Leaf에 데이터의 Hash를 붙이고, 중간 Node에는 자식들의 Hash를 다시 Hash한 값을 붙인다. 이 과정을 Root까지 반복한다. 데이터가 하나라도 바뀌면 Root Hash가 달라지므로 큰 트리를 효율적으로 검증할 수 있다.

MPT의 중간 Node는 두 종류다.

| 종류 | 형태 | 역할 |
|---|---|---|
| Branch Node | 17개 항목 [v0, v1, ..., vf, Value] | 한 문자(0부터 f)에 따라 갈라진다. v_i는 해당 자식의 Hash이고, 자식이 없으면 Null이다. |
| Extension Node | 2개 항목 [Key, Path] | Path는 후손들이 공유하는 공통 Prefix다. Key는 유일한 자식의 Hash다. |

각 Node는 자신의 데이터(Value)로 계산한 Hash(Key)로 식별된다. 그래서 MPT는 LevelDB 같은 Key-Value Database로 구현할 수 있다.

Account가 갱신되면 Ethereum은 기존 Node를 고치지 않는다. 새 Hash와 새 데이터를 가진 Node를 새로 만들어 Database에 덧붙인다. 부모 Node도 같은 방식으로 새로 만들어지고, 이 과정은 새 Root가 만들어질 때까지 이어진다. 이전 Block의 Root와 그 후손은 그대로 남는다. 그래서 모든 State Trie의 이력을 추적할 수 있지만 저장 공간이 많이 든다.

### 2.4 Merkle Proof와 Void Proof

Block Header에는 State Root(State Trie의 Root Hash)가 들어 있다. 이 값만 있으면 State Trie 전체가 없어도 다음 두 가지를 검증할 수 있다.

**Merkle Proof: 존재 증명**

어떤 Account의 Merkle Proof는 Root Node부터 그 Account Node까지 경로에 있는 모든 Node 데이터의 목록이다. 검증자는 Leaf부터 Root 방향으로 Hash를 다시 계산한다. 마지막에 얻은 Root Hash가 Block Header의 State Root와 같으면, 그 Account가 그 Block에 그 데이터로 존재했다는 것이 증명된다.

Figure 1의 a5(주소 0xd815fc)를 예로 들면 Proof는 다음 다섯 개의 Node 데이터로 이루어진다.

```
B(hashA)     = {a: hashB, d: hashC}        Branch
B(hashC)     = [hashE, 81]                 Extension
B(hashE)     = {3: hashH, 5: hashI}        Branch
B(hashI)     = [hash(a5), fc]              Extension
B(hash(a5))  = {balance: 32.01, nonce: 30} Leaf
```

**Void Proof: 부재 증명**

같은 방식으로 어떤 Account가 존재하지 않는다는 것도 증명할 수 있다. 주소 0xa7ec6b인 Account가 σ_i에 없다는 것을 보이려면 다음 세 개를 제시한다.

```
B(hashA) = {a: hashB, d: hashC}
B(hashB) = [hashD, 7]
B(hashD) = {d: hashF, f: hashG}
```

검증자는 세 Hash를 다시 계산해 Proof가 유효한지 확인한다. 그다음 B(hashD)에 Key e가 없다는 것을 본다. 이는 0xa7e로 시작하는 Account가 σ_i에 없다는 뜻이다.

## 3. 관찰: 대부분의 Account는 쓰이지 않는다

논문은 Genesis Block부터 800만 번째 Block까지 Account 활동을 추적했다. Active Account(활성 계정)는 해당 기간에 Transaction을 보내거나, 받거나, 채굴한 Account다. Dormant Account(휴면 계정)는 그렇지 않은 Account다.

관찰 결과는 두 가지다.

**관찰 1. Active Account는 소수다.** 1주 기준 Active Account는 전체의 약 3%, 1달 기준으로는 약 5%다. 즉 95% 이상이 Dormant Account다. 2020년 1월 기준 Account 수는 8,500만 개를 넘었고 하루 5만에서 15만 개씩 늘고 있었다.

**관찰 2. 한번 쓰인 Account는 곧 다시 쓰인다.** Account별로 연속한 두 갱신 사이의 평균 간격을 구한 누적 분포는 다음과 같다(논문 Table 1).

| 평균 갱신 간격 | 1일 이내 | 1주 이내 | 2주 이내 | 1달 이내 | 6개월 이내 |
|---|---|---|---|---|---|
| 비율(%) | 62.3 | 76.0 | 82.4 | 89.0 | 98.4 |

1주는 약 40,320 Block, 1달은 약 172,800 Block이다(Block 간격 15초 기준).

두 관찰을 합치면 Ethanos의 발상이 나온다.

- Dormant Account를 주기적으로 비우면 State Trie가 크게 줄어든다.
- 이번 주기의 Transaction 대부분은 직전 주기의 State Trie만 있어도 처리할 수 있다.
- 직전 주기에도 없는 Account는 복원이 필요하지만 그 빈도는 낮다.
- 한 주기에 채굴되는 Transaction 수에는 상한이 있다. 따라서 Active Account 수와 State Trie 크기도 시간이 지나도 계속 커지지 않는다.

## 4. Ethanos의 동작 원리

### 4.1 Epoch, Checkpoint, Sweep

- Epoch(에폭) λ는 Sweep 주기를 이루는 Block 수다. 1주 주기라면 약 40,320 Block이다.
- Checkpoint(체크포인트)는 Epoch의 마지막 Block이다.
- Sweep(스윕)은 Dormant Account를 State Trie에서 걸러 내는 동작이다.

State Trie를 순회하며 Dormant Account를 찾아 지우는 것은 비용이 매우 크다. 그래서 Ethanos는 반대로 접근한다.

1. 새 Epoch가 시작되면 빈 State Trie를 만든다. 이것이 Current Trie다.
2. 직전 Checkpoint의 State Trie를 보관한다. 이것이 Cached Trie다.
3. Transaction을 실행할 때 필요한 Account를 Current Trie에서 먼저 찾는다.
4. 없으면 Cached Trie에서 찾는다. 있으면 Current Trie로 복사한 뒤 갱신한다.
5. 두 Trie 모두에 없고 그 Account가 Sender가 되려는 경우, 먼저 복원해야 한다(4.3절).
6. Epoch가 끝나면 Current Trie가 새 Cached Trie가 된다. 이전 Cached Trie는 버린다.

이렇게 하면 한 Epoch 동안 실제로 쓰인 Account만 Current Trie에 남는다. 지우는 작업 없이 Sweep이 이루어진다.

**Cached Trie를 하나만 두는 이유**

논문은 세 가지 이유를 든다. 첫째, Full Node가 Trie 하나로 Bootstrapping할 수 있어 내려받는 크기가 줄어든다. 둘째, 모든 Full Node가 같은 방식으로 동작한다. 셋째, 연속한 Checkpoint의 State Trie에는 겹치는 Active Account가 많아 여러 개를 두는 것이 비효율적이다.

### 4.2 예시 (논문 Figure 3)

2.2절의 예시를 Ethanos에 그대로 옮긴다. n번째 Epoch가 Block i에서 끝난다고 하자. 즉 i = n × λ이고 Block i가 Checkpoint다. Cached Trie에는 a1부터 a5가 있다. n+1번째 Epoch는 빈 Trie로 시작한다.

**Block i+1: a2가 a4에게 송금, Miner는 a5**

a2, a4, a5 모두 Current Trie에 없다. Cached Trie에서 찾아 Current Trie로 복사하고 갱신한다.

**Block i+2: a4가 a6에게 송금, Miner는 a1**

| Account | 찾은 위치 | 처리 |
|---|---|---|
| a4 (Sender) | Current Trie | 바로 갱신 |
| a1 (Miner) | Cached Trie | 복사 후 갱신 |
| a6 (Receiver) | 두 Trie 모두에 없음 | 새 Account로 생성 |

이 시점의 Current Trie에는 a1, a2, a4, a5, a6만 있다. 이번 Epoch에 쓰이지 않은 a3는 들어 있지 않다.

### 4.3 Dormant Account를 다시 쓸 때

두 Trie 모두에 없는 Account가 Transaction에 등장하는 경우는 역할에 따라 다르게 처리한다.

**Sender인 경우.** Restore Transaction을 먼저 보내야 한다. Restore Transaction은 그 Account를 마지막 상태 그대로 Current Trie에 다시 만든다.

**Receiver인 경우.** 복원하지 않는다. Ethereum에서는 존재하지 않는 Address로 값을 보내면 그 Address의 Account가 새로 만들어진다. Ethanos는 Receiver가 사실은 Dormant Account인 경우에도 똑같이 새 Account를 만든다. 이렇게 만들어진 Account를 Crumb Account(크럼 계정)라고 부른다.

Crumb Account는 Balance가 충분하면 그대로 Sender가 될 수 있다. Balance가 부족하면 Restore Transaction을 보내야 하고, 이때 Crumb Account들이 원래 Account와 합쳐진다. Crumb Account는 여러 Epoch에 걸쳐 여러 개 생길 수 있다.

값을 받기만 하는 경우에는 복원이 필요 없으므로 Restore Transaction의 빈도가 줄어든다.

### 4.4 Restore Transaction

Restore Transaction에는 세 역할이 관여한다.

| 역할 | 하는 일 |
|---|---|
| Owner (Account 소유자) | 자신의 Account가 Dormant 상태인지 판단하고 복원을 요청한다. |
| Archive Node | 과거 Checkpoint들의 State Trie에 접근해 Proof를 모으고 Restore Transaction을 만들어 전송한다. |
| Miner와 Verifier | Proof를 검증하고 Current Trie에 Account를 만든다. |

Owner는 두 방법 중 하나로 Dormant 여부를 판단한다. 자신의 마지막 Transaction 이후 두 Epoch가 지났는지 확인하거나, 현재 Epoch에서 자신의 Account에 접근할 수 있는지 조회한다.

Archive Node가 Transaction을 만드는 이유는 다음과 같다. 일반 Ethanos Full Node는 Bootstrapping한 Checkpoint 이전의 State Trie를 갖고 있지 않다. Last Active Checkpoint가 그보다 오래되었다면 Proof를 만들 수 없다. 그렇지 않은 경우에는 Full Node가 직접 만든다.

**Restore Transaction에 담기는 Proof**

Account의 Last Active Checkpoint(마지막으로 State Trie에 들어 있던 Checkpoint)를 k, 최신 Checkpoint를 n이라고 하자(k < n).

- Checkpoint k에 대한 Merkle Proof. Account가 그 시점에 그 상태로 존재했음을 증명한다.
- Checkpoint k 이후부터 n-1까지 각 Checkpoint에 대한 Void Proof. k가 정말 마지막이었음을 증명한다.

Checkpoint n에 대한 Void Proof는 필요 없다. Cached Trie로 직접 확인할 수 있기 때문이다. 검증에는 각 Checkpoint Block Header의 State Root만 쓰인다.

이 구성은 오래된 상태로 되돌리는 공격을 막는다. 누군가 Balance가 더 많았던 과거 Checkpoint j(j < k)의 상태로 복원하려 한다고 하자. 그러면 Checkpoint k에 대한 Void Proof를 내야 하는데, k에는 Account가 실제로 존재하므로 이 Proof는 통과하지 못한다.

**Bloom Filter로 Void Proof 줄이기**

n과 k의 차이가 커지면 Void Proof가 많아져 Restore Transaction이 커진다. 이를 줄이기 위해 각 Checkpoint의 Block Header에 Bloom Filter(블룸 필터)를 저장한다.

Bloom Filter는 원소의 포함 여부를 적은 공간으로 판정하는 확률적 자료구조다. 포함된 원소에 대해서는 항상 "있다"고 답한다. 포함되지 않은 원소에 대해서도 낮은 확률로 "있다"고 답할 수 있다(False Positive). 반대로 "없다"고 답하면 정말 없는 것이다.

따라서 어떤 Checkpoint의 Bloom Filter가 "없다"고 답하면 그 Checkpoint의 Void Proof를 생략할 수 있다. Verifier는 실행 시 Bloom Filter로 부재를 직접 확인한다. 논문은 False Positive 확률을 약 10%로 설정해 Void Proof의 90%를 생략한다.

### 4.5 Crumb Account와 Replay Attack

일반 Ethanos Full Node는 모든 Checkpoint의 State Trie를 갖고 있지 않다. 그래서 새로 만들어지는 Account가 정말 새 Account인지, Crumb Account인지 구별할 수 없다.

Crumb Account의 Nonce를 0으로 두면 문제가 생긴다. 원래 Account가 과거에 Nonce 0부터 보냈던 Transaction을 공격자가 다시 전송하면 유효한 것으로 처리될 수 있다. 이것이 Replay Attack(재전송 공격)이다.

Ethanos는 모든 새 Account의 초기 Nonce를 다음과 같이 정한다.

```
초기 Nonce = 현재 Block 번호 × (Account당 Block당 평균 Transaction 수)
```

논문은 이 값이 과거에 등장한 어떤 Nonce보다 항상 크다고 설명한다.

### 4.6 Crumb Account를 합치는 복원과 Restored Flag

Crumb Account가 있는 Account를 복원할 때는 Last Active Checkpoint의 Account와 Crumb Account들을 합쳐야 한다. 그래서 Restore Transaction에는 Crumb Account가 있는 Checkpoint마다 Merkle Proof가 추가된다. 연속한 여러 Checkpoint에 Crumb Account가 있으면 마지막 Checkpoint의 Balance만 합친다. 그 값에 앞선 Checkpoint들의 활동이 이미 반영되어 있기 때문이다.

여기서 검증 문제가 하나 생긴다. Merkle Proof가 두 개(P1, P2) 있는 Restore Transaction은 "P1은 Last Active Account, P2는 Crumb Account"로 해석된다. 그런데 P2가 사실은 P1을 이미 복원한 Account라면, P1의 Balance가 한 번 더 더해진다.

Ethanos는 Account 상태에 1비트 Restored Flag를 추가해 이를 막는다. 기본값은 0이고, 복원될 때 Verifier가 1로 바꾼다. P2의 Flag가 1이면 Verifier는 이미 복원된 Account를 Crumb Account로 속이는 시도로 보고 거부한다.

**보안 속성**

Checkpoint에서 Account의 상태는 네 가지다. Active(a), Restored(r), Crumb(c), Void(v)다. 논문이 제시하는 보안 속성은 "Restore Transaction은 유효하지 않은 상태를 만들 수 없다"이다. 유효한 Proof 열은 다음 정규식으로 표현된다.

```
(a+|r+)v+(c+v)*v*
```

- `avvvcccvv`는 유효하다. Active 이후 Void가 이어지고, Crumb 구간이 나온 뒤 다시 Void다.
- `avvvvvrvv`는 유효하지 않다. Void 뒤에 Restored가 나온다.

### 4.7 Ethanos의 Synchronization

| 방식 | 대응하는 Ethereum 방식 | 동작 |
|---|---|---|
| Archive Sync | Full Sync | 모든 Block을 내려받고 Genesis Block부터 모든 Transaction을 Replay한다. |
| Compact Sync | Fast Sync | Pivot Block의 State Trie를 내려받고 Pivot Block부터 현재까지만 Replay한다. |

Compact Sync는 Fast Sync와 두 가지가 다르다.

1. 최신 Checkpoint의 State Trie도 내려받는다. Cached Trie로 쓰기 위해서다.
2. Genesis Block부터 Pivot Block까지의 오래된 Transaction을 내려받지 않는다. 어차피 Replay하지 않기 때문이다. 필요하면 Archive Node에 요청한다.

State Trie를 두 개 받지만 둘 다 한 Epoch의 Active Account만 담고 있어 작다.

### 4.8 Restore Transaction의 Fee

논문은 Fee에 대해 구체적 규칙 대신 방향을 제시한다. 사용자는 Account의 가치가 Fee보다 크면 Fee를 내고 복원한다. 과거 State Trie를 보관하며 Restore Transaction을 만들어 주는 Archive Node도 Fee를 받아야 한다. Archive Node와 Miner의 수가 늘면 Fee가 내려가고, 줄면 올라간다. 수요와 공급이 수와 Fee를 결정한다는 것이다.

## 5. 평가

### 5.1 실험 설정

| 항목 | 값 |
|---|---|
| 대상 구간 | Ethereum 700만 번째 Block부터 730만 번째 Block (300,000 Block, 2019년 초 약 2개월) |
| Transaction 수 | 30,575,237 |
| 갱신된 Account 수 | 4,588,065 |
| 구현 기반 | Geth v1.9 |
| Epoch | 40,320 Block (약 1주) |
| Checkpoint 수 | 7 |
| 추가된 Restore Transaction | 198,121 |
| Bloom Filter 크기 | Checkpoint Block당 512KB |

실험은 700만 번째 Block을 Genesis Block으로 삼아 Ethanos Blockchain을 새로 시작하는 것으로 볼 수 있다. 비교 대상인 Ethereum도 같은 지점에서 시작했다. 300,000번째 Block 시점에 1주 Active Account는 약 100만 개이고 비율은 23.5%다.

실험은 두 단계로 진행됐다. 먼저 Pre-simulation으로 Account를 분류하고 Restore Transaction이 들어갈 위치를 정했다. 그다음 수정한 Geth로 실제 실행했다.

실험의 제약도 논문에 명시되어 있다.

- 모든 Transaction의 전송 값을 0으로 두었다. 빈 State에서 시작하므로 Balance 부족 오류를 피하기 위해서다.
- 모든 Transaction을 Delegated Transaction(대리 트랜잭션)으로 만들었다. 실제 Sender의 Private Key를 알 수 없기 때문이다. Transaction당 20 Byte가 늘어난다.
- CA를 EOA처럼 취급했다. Smart Contract가 호출하는 Internal Transaction은 제외했다.

### 5.2 저장 용량

**Archive Sync (300,000번째 Block까지, 논문 Table 2)**

| 구분 | Geth (MB) | Ethanos (MB) | 차이 (MB) |
|---|---|---|---|
| Trie Nodes | 46,333.43 | 40,342.62 | -5,990.81 |
| Headers | 110.26 | 119.98 | +9.72 |
| Bodies | 3,220.84 | 3,852.75 | +631.91 |
| 전체 | 52,031.68 | 46,676.61 | -5,355.07 |

전체가 약 5.3GB(10.3%) 줄었다. 대부분 Trie Nodes 감소에서 온다. 두 시스템의 Account 수와 갱신 횟수는 같다. 차이는 Trie의 크기다. Geth는 모든 Account(약 450만 개)를 담은 큰 Trie 하나를 유지하고, Ethanos는 Epoch마다 Active Account(약 100만 개)만 담은 작은 Trie를 유지한다. Trie가 작으면 Account까지의 깊이가 얕아져, 갱신 때 새로 추가되는 Node 수가 적다. Headers는 Bloom Filter 때문에, Bodies는 Restore Transaction 때문에 늘었다.

**Fast Sync와 Compact Sync (7번째 Checkpoint, 논문 Table 3)**

| 구분 | Geth (MB) | Ethanos (MB) |
|---|---|---|
| Fast Sync 전체 | 6,020.87 | 5,966.79 |
| Compact Sync 전체 | 977.67 | 374.23 |
| Trie Nodes | 약 832 | 220.03 |

Fast Sync에서는 전체 크기 차이가 거의 없다. 300,000 Block만 지난 시점이라 Transaction 데이터가 Trie보다 훨씬 크기 때문이다. Transaction 내려받기를 생략하는 Compact Sync에서는 Ethanos가 Geth의 38% 크기다.

논문이 가장 중요하게 보는 결과는 Ethanos의 State Trie 크기가 약 220MB 수준에서 유지된다는 점이다. 단, 이것은 조건부 결론이다. 논문은 1주 Active Account 수가 약 100만 개 수준으로 유지되는 한 그렇다고 적는다.

Epoch 끝 무렵에 Compact Sync를 하는 경우를 보자. 직전 Checkpoint의 State Trie 220MB와 현재 Pivot Block 기준 Compact Sync 저장량 374MB를 합쳐 594MB다.

### 5.3 동기화 시간

각 경우를 15회씩 측정해 평균을 냈다. 네트워크 변동을 줄이기 위해 두 기기를 Ethernet으로 직접 연결했다. 7번째 Checkpoint의 결과는 다음과 같다.

- Ethanos Fast Sync는 Geth Fast Sync보다 17% 짧다. 데이터 크기는 거의 같은데도 그렇다.
- Ethanos Compact Sync는 Geth Compact Sync보다 75% 짧다.

두 경우 모두 Geth와 Ethanos의 차이는 약 290초이고, State Trie 크기 차이는 약 610MB다. 따라서 State Trie 내려받기 속도는 약 475 sec/GB다. 같은 방식으로 구한 Transaction 등 나머지 데이터의 속도는 234에서 257 sec/GB다. State Trie 내려받기가 약 2배 느리다. 1.4절에서 말한 병목이 수치로 확인된 것이다.

### 5.4 Checkpoint별 Account 유형

한 Epoch에서 Account가 처음 쓰일 때의 유형은 네 가지다.

| 유형 | 조건 |
|---|---|
| New | Genesis Block부터 지금까지 한 번도 쓰인 적이 없다. |
| Cached | 직전 Checkpoint의 State Trie에 있다. |
| Crumb | Cached가 아니고 Receiver로 쓰인다. |
| Restored | Cached가 아니고, Balance가 부족한 Sender로 쓰인다. Restore Transaction이 선행된다. |

Checkpoint 1의 Account 약 120만 개는 모두 New다. 그중 약 35만 개가 Checkpoint 2에서 Cached다. Crumb과 Restored는 Checkpoint 3부터 나타난다. Restored Account는 전체의 5% 미만이다. Crumb Account보다 훨씬 적은데, 많은 Dormant Account가 복원 없이 Crumb Account로 다시 쓰였다는 뜻이다.

### 5.5 Restore Transaction의 Overhead

- **수.** Restore Transaction은 Epoch별 전체 Transaction의 1.5% 미만이다.
- **크기.** 일반 Transaction은 0.12KB로 일정하다. Restore Transaction은 3KB 이상이고 편차가 크다. Merkle Proof 하나가 약 3KB이고 Void Proof가 여러 개 붙기 때문이다. Bloom Filter가 크기를 절반 이상 줄였다.
- **실행 시간.** 일반 Transaction은 평균 1ms 미만이다. Restore Transaction은 Last Active Checkpoint까지 Checkpoint를 차례로 확인해야 해서 더 오래 걸린다.

7번째 Epoch 기준으로 한 Block은 평균 일반 Transaction 248개(99.2ms)와 Restore Transaction 2.7개(10.5ms)를 실행한다. 실행 시간이 약 10% 늘어난다. 논문은 Block 간격이 15초이므로 이 증가는 채굴 시간에 비해 작다고 평가한다.

### 5.6 Epoch 길이 평가

Epoch가 길면 State Trie가 커져 Bootstrapping 부담이 늘고, Restore Transaction은 줄어든다. 논문은 구간을 864,000 Block으로 늘려 네 가지 길이를 비교했다. 이 실험은 Pre-simulation만으로 수행했다.

| Epoch 길이 | Epoch 수 | 마지막 Epoch의 State Trie |
|---|---|---|
| 3일 | 50 | 138MB |
| 1주 | 20 | 278MB |
| 2주 | 10 | 454MB |
| 1달 | 5 | 817MB |

State Trie 크기는 Epoch 길이에 비례하지 않고 그보다 완만하게 늘어난다. Epoch 길이의 증가 배율과 비교하면 86%, 70%, 60% 수준이다. 예를 들어 3일에서 1달로 길이가 10배가 되어도 크기는 5.9배다. Transaction이 최근에 쓰인 Account에 쏠려 있기 때문이다.

Restore Transaction 수도 비례해서 줄지 않는다. 1달 Epoch의 Restore Transaction 수는 3일 Epoch의 약 1/5이다.

논문의 판단은 다음과 같다. 1달 Epoch가 비용 대비 효과가 좋아 보인다. 다만 모바일 기기에는 817MB가 무거우므로 당분간은 1주 Epoch가 적절하다. 2주 Epoch는 Restore Transaction을 줄이는 효과가 작아 효율적이지 않다. 고정 길이 대신 Trie 크기가 기준값에 도달하면 Checkpoint를 만드는 가변 Epoch도 대안으로 언급한다.

## 6. 논의

### 6.1 Contract Account의 복원

논문은 실험에서 CA를 다루지 않았다. 다만 CA 복원도 원리는 같다고 설명한다. 차이는 Restore Transaction이 더 커질 수 있다는 점이다. Last Active Checkpoint 시점의 Contract 상태 Snapshot이 들어가야 하기 때문이다. 예를 들어 ERC-20 Token의 소유 기록 하나가 52 Byte(Address 20 + Balance 32)라면, 사용자 100만 명은 52MB가 된다.

논문이 드는 고려 사항은 세 가지다.

1. 서비스 중인 Smart Contract는 계속 갱신되므로 Dormant 상태가 되기 어렵다. 반대로 서비스가 끝난 Contract는 다시 복원될 가능성이 낮다. Ethanos는 이런 무거운 Dormant Contract를 걸러 낼 수 있다.
2. Crumb CA는 Contract 상태를 가질 수 없고 Balance만 가진다. CA의 Address는 배포자의 Address와 Nonce로 결정되므로 같은 Address에 새 Contract를 배포할 수 없기 때문이다. 따라서 Contract 상태는 원래 CA의 Snapshot으로 복원하고, Balance만 합치면 된다.
3. Snapshot 크기를 줄이기 위해 Ethanos의 발상을 Storage Trie에 재귀적으로 적용할 수 있다. 필요한 기록만 복원하는 방식이다. 논문은 이를 위한 구체적 Protocol은 다른 곳에서 다루겠다고 적는다.

### 6.2 Block Header 크기 줄이기

State Trie와 Transaction을 줄이고 나면 Block Header가 병목이 될 수 있다. 2020년 1월 기준 Block Header는 약 3GB다.

논문은 Non-Interactive Proofs of Proof-of-Work(이하 NIPoPoW)를 활용하자고 제안한다. NIPoPoW는 채굴 난이도가 더 높은 Super Block의 Header만 표본으로 내려받아 검증하는 방식이다. Ethanos는 Checkpoint의 Block Header가 필요하다. 그래서 Checkpoint를 정확히 Epoch 경계에 두지 않고 경계 근처의 Super Block으로 정하자는 것이다.

이 경우 2020년 1월(910만 Block)에 동기화한다면 Header 226개(9.1M / 40,320)만 받으면 되고, 크기는 약 84KB(226 × 370 Byte)다. 논문은 이를 근거로 전체 내려받기 크기가 1GB 미만이 될 수 있다고 본다. 이 절의 내용은 제안이며 실험으로 검증된 결과가 아니다.

## 7. 관련 연구

| 연구 | 접근 | Ethanos와의 차이 |
|---|---|---|
| EIP-158, EIP-161 | Nonce와 Balance가 0이고 Code와 Storage가 빈 Empty Account를 삭제한다. | 빈 Account만 대상이다. |
| EIP-168 | Balance가 Transaction Fee보다 적은 Dust Account를 제거한다. | 논문 시점에 논의 중이었고 채택되지 않았다. |
| Vault | Algorand용. Transaction에 만료 기한을 두어 Balance가 0인 Account를 안전하게 제거한다. | 논문은 Vault가 Algorand에만 적용 가능하다고 본다. |
| Utreexo | Bitcoin의 UTXO 집합을 Hash 기반 Accumulator로 표현한다. Proof가 있으면 전체 UTXO 집합 없이 검증한다. | 발상이 유사하다. 최근 UTXO만 보관하는 것이 Active Account만 보관하는 것에 대응한다. |

EIP는 Ethereum Improvement Proposal(이더리움 개선 제안)이다.

## 8. 정리와 해석

**논문의 결론**

- State Trie 크기를 약 220MB로 줄일 수 있다.
- 오래된 Transaction과 덜 중요한 Block Header를 생략하는 최적화와 결합하면, 1GB 미만으로 수백 초 안에 Bootstrapping할 수 있다고 본다.
- Full Node와 Miner 수가 늘어 Blockchain의 보안이 좋아지고, 가끔 접속하는 사용자도 Transaction을 보낼 때 Full Node가 되어 직접 검증할 수 있다.

**이 글의 해석 (논문에 명시된 평가가 아님)**

- 실험 규모와 실제 효과 사이에는 간격이 있다. 실험은 빈 State에서 시작한 300,000 Block이다. 이 구간의 Active Account 비율은 23.5%로, 실제 Ethereum의 3% 미만과 다르다. 논문은 실제 효과가 더 클 것이라고 예상하지만 이는 측정값이 아니라 예상이다.
- 전송 값을 0으로 두고 CA를 EOA로 취급했으므로, Smart Contract가 많은 환경에서의 복원 비용은 실험에 반영되지 않았다. 6.1절의 CA 복원은 설계 방향 수준이다.
- 복원은 Archive Node에 의존한다. 오래된 Account를 복원하려면 과거 Checkpoint의 State Trie를 가진 Archive Node가 있어야 한다. Archive Node가 충분히 유지되는지는 4.8절의 Fee 논의에 달려 있고, 이 부분은 실험되지 않았다.
- "1GB 미만" 수치는 측정된 Compact Sync 결과(약 600MB)에, 실험되지 않은 NIPoPoW 추정치를 더한 값이다.

## 10. 논문 이후 달라진 점

논문의 전제 가운데 현재는 다른 것들이다. 이 글은 2026년 11월에 작성했다.

- **합의 방식.** Ethereum은 2022년 9월 15일 The Merge로 Proof of Stake(지분 증명)로 전환했다. Miner는 Validator로 대체되었고 PoW Block Reward는 없다. Block 간격은 PoW 시기 약 13에서 15초였고, 현재는 12초 Slot이다.
- **Fast Sync.** Geth는 v1.10.0에서 Snap Sync를 도입했고 v1.10.4부터 기본값으로 쓴다. Fast Sync는 v1.10.14에서 제거되었다. 논문의 Fast Sync 비교는 Geth v1.9 기준이다.
- **Database.** Geth는 v1.12.0부터 새 Database의 기본 Backend로 LevelDB 대신 Pebble을 쓴다.
- **Client.** 논문 시기의 주요 Client였던 Parity Ethereum은 OpenEthereum으로 이름이 바뀐 뒤 개발이 중단되었고 저장소가 보관(Archived) 처리되었다.
- **State Expiry.** Ethanos처럼 Dormant Account를 State에서 내보내는 Protocol 수준의 State Expiry는 Ethereum Mainnet에 도입되지 않았다. ethereum.org의 Roadmap 문서는 State Expiry를 연구 단계로 설명한다.
- **History Expiry.** State Expiry와는 다른 것으로, 오래된 Block 이력을 내려놓는 EIP-4444는 부분적으로 적용되었다. 2025년 7월 Ethereum Foundation 공지 기준으로 The Merge 이전 이력을 Client가 보관하지 않아도 되게 되었다. 이 글에서 확인한 자료는 2025년 시점까지이며 그 이후의 변화는 확인하지 않았다.
- **수치의 시점.** 3.6TB, 235GB, 70GB, Account 8,500만 개는 모두 2020년 1월 기준이다.

## 11. 용어 정리

| 용어 | 의미 |
|---|---|
| Account-based Blockchain | Account와 Balance로 이루어진 State를 명시적으로 기록하는 Blockchain |
| State Trie | 모든 Account의 상태를 MPT로 저장한 구조 |
| Full Node | Transaction을 스스로 완전히 검증할 수 있는 Node |
| Light Node | 검증을 다른 Full Node에 맡기는 Node |
| Archive Node | 과거의 모든 State Trie까지 보관하는 Node |
| Bootstrapping | 새 Node가 네트워크에 참여해 현재 State까지 따라잡는 과정 |
| Pivot Block | Fast Sync에서 State Trie Snapshot을 내려받는 기준 Block. 현재 Block보다 64 Block 이전 |
| Active Account | 해당 기간에 Transaction을 보내거나 받거나 채굴한 Account |
| Dormant Account | 해당 기간에 쓰이지 않은 Account |
| Epoch (λ) | Sweep 주기를 이루는 Block 수 |
| Checkpoint | Epoch의 마지막 Block |
| Current Trie | 현재 Epoch에서 빈 상태로 시작해 채워 가는 State Trie |
| Cached Trie | 직전 Checkpoint의 State Trie |
| Restore Transaction | 두 Trie 모두에 없는 Account를 Current Trie에 다시 만드는 Transaction |
| Crumb Account | Dormant Account가 Receiver일 때 복원 없이 새로 만들어지는 Account |
| Last Active Checkpoint | Account가 마지막으로 State Trie에 들어 있던 Checkpoint |
| Merkle Proof | Account가 특정 Block의 State에 존재함을 State Root만으로 검증하게 해 주는 Node 데이터 목록 |
| Void Proof | Account가 특정 Block의 State에 존재하지 않음을 검증하게 해 주는 Node 데이터 목록 |
| Bloom Filter | 원소의 포함 여부를 적은 공간으로 판정하는 확률적 자료구조. "없다"는 답은 항상 정확하다. |
| Restored Flag | Account가 복원된 적이 있는지 나타내는 1비트 값 |
| Archive Sync | Ethanos의 동기화 방식. Ethereum의 Full Sync에 대응 |
| Compact Sync | Ethanos의 동기화 방식. Fast Sync에서 오래된 Transaction 내려받기를 생략하고 Cached Trie를 추가로 받는다. |
