## Scope

논문은 2021년에 발표되었고, Proof of Work(작업 증명, 이하 PoW)를 쓰던 2019년에서 2020년의 Ethereum(이더리움)을 대상으로 한다. 이 글의 설명과 수치도 그 시점 기준이다. 실제 Ethereum과 논문의 설명이 다른 부분은 해당 위치에 따로 적었다. 논문 원문에서 확인한 오류는 Errors in the Paper에, 논문 이후 Ethereum에서 달라진 점은 Changes Since Publication에 모았다.

## Summary

각 용어는 본문에서 처음 나올 때 자세히 설명한다.

| 단계 | 내용 |
|---|---|
| 배경 | Ethereum은 모든 Account(계정)의 현재 값을 State Trie(상태 트라이)라는 자료구조에 따로 기록한다. |
| 문제 | Network(네트워크)에 새로 참여하는 Node(노드)가 Transaction(트랜잭션)을 스스로 검증하려면 State Trie 전체를 내려받아야 한다. 이 작업이 동기화의 병목이다. 그런데 State Trie에 든 Account의 95% 이상은 최근 1주 또는 1달 동안 한 번도 쓰이지 않았다. |
| 해결 | 일정 주기마다 빈 State Trie에서 시작해, 그 주기에 쓰인 Account만 담는다. 빠진 Account가 다시 필요하면, 과거 값을 증명하는 Proof(증명)를 담은 Restore Transaction(복원 트랜잭션)으로 되살린다. |
| 결과 | 1주 주기 실험에서 State Trie가 약 220MB로 유지되었다. 새 Node의 동기화 시간은 같은 조건의 비교 대상보다 75% 짧았다(Synchronization Time 참고). |

## Account-based Blockchain

이 장은 논문이 다루는 Account-based Blockchain(계정 기반 블록체인)의 구조를 설명한다. 뒤에 나오는 문제 상황과 해결 방법은 모두 이 구조에서 나온다.

### How Blockchains Record State

Blockchain(블록체인)은 Transaction을 Block(블록) 단위로 묶어 순서대로 이어 붙인 기록이다. Transaction은 값을 옮기거나 프로그램을 호출하는 요청이다. Network에 참여하는 컴퓨터를 Node라고 한다. Node들은 같은 Block 사슬을 나눠 갖는다. Block을 만드는 Node를 Miner(채굴자)라고 한다. 새 Block을 받은 Node는 그 안의 Transaction을 다시 실행해 결과가 맞는지 확인하며, 이렇게 검증하는 Node를 Verifier(검증자)라고 한다.

Blockchain이 "누가 얼마를 가졌는가"를 기록하는 방식은 크게 두 가지다.

- **Bitcoin(비트코인)**: Unspent Transaction Output(미사용 트랜잭션 출력, 이하 UTXO) 방식을 쓴다. 아직 쓰이지 않은 Transaction 출력들의 집합이 곧 전체 상태다. 전체 상태를 따로 기록하지 않고, Transaction들로 암묵적으로 표현한다.
- **Ethereum**: Account-based 방식을 쓴다. 각 Account가 얼마를 가졌는지를 Transaction과 별도로 명시적으로 기록한다. 모든 Account의 현재 값을 묶은 것을 Global State(전역 상태)라고 하며, 이 글에서는 State(상태)라고 줄여 쓴다.

논문은 Account-based 방식이 Smart Contract(스마트 컨트랙트) 개발에 더 단순하고 직관적이라고 설명한다. Smart Contract는 Transaction이 호출하면 Account의 State를 사용해 정해진 작업을 수행하는 프로그램이다. 대신 Block마다 Transaction뿐 아니라 State까지 관리해야 하므로 데이터가 빠르게 늘어난다. 이 비용이 논문이 다루는 문제의 출발점이다.

### Account Structure

Ethereum의 Account는 Address(주소)로 찾는다. Address는 20 Byte이며, 16진수 40자로 쓴다([Ethereum Accounts](https://ethereum.org/developers/docs/accounts/)).

Account를 설명하려면 Hash(해시)를 먼저 알아야 한다. Hash는 임의 길이의 데이터를 고정 길이 값으로 바꾼 결과다. 데이터가 조금만 바뀌어도 Hash가 달라지고, 같은 Hash를 갖는 다른 데이터를 찾기는 사실상 불가능하다. Ethereum은 Keccak-256이라는 Hash 함수를 쓴다.

Account는 두 종류다.

- **Externally Owned Account(외부 소유 계정, 이하 EOA)**: 사용자의 Account다. 사용자는 Private Key(개인 키)로 Transaction에 서명해 EOA를 사용한다.
- **Contract Account(컨트랙트 계정, 이하 CA)**: Smart Contract의 Account다. 프로그램 Code(코드)와 그 프로그램의 데이터를 함께 가진다.

두 종류 모두 다음 네 가지 값을 가진다.

| 필드 | 의미 |
|---|---|
| Nonce(논스) | 같은 Transaction이 두 번 실행되지 않게 하는 순번이다. EOA에서는 보낸 Transaction 수이고, CA에서는 그 Account가 만든 Contract 수에 1을 더한 값이다([Ethereum Accounts](https://ethereum.org/developers/docs/accounts/)). |
| Balance(잔액) | 보유한 Ether(이더)의 양이다. Ether는 Ethereum의 암호화폐이며 단위는 ETH다. |
| StorageRoot | Smart Contract가 변수 값을 저장하는 공간인 Storage(스토리지)를 Trie(State Trie and Merkle Patricia Trie 참고)로 만든 뒤, 그 Root의 Hash를 담는다. |
| CodeHash | Smart Contract Code의 Hash다. Database(데이터베이스)에서 Code를 찾는 데 쓴다. |

논문은 EOA의 StorageRoot와 CodeHash를 Null이라고 적는다. 실제 값은 빈 Trie의 Root Hash와 빈 Code의 Hash다([Ethereum Accounts](https://ethereum.org/developers/docs/accounts/)). 단, 2025년 5월 Pectra Upgrade(펙트라 업그레이드) 이후에는 Ethereum Improvement Proposal(이더리움 개선 제안, 이하 EIP) 가운데 EIP-7702로 Code를 위임한 EOA가 있을 수 있고, 이 경우 CodeHash는 빈 Code의 Hash가 아니다.

### Transaction and State Transition

Transaction은 Sender(송신 계정)에서 Receiver(수신 계정)로 값을 옮긴다. 실행되면 두 Account의 Balance가 바뀌고 Sender의 Nonce가 1 늘어난다. Transaction이 유효하려면 두 조건을 만족해야 한다.

1. Sender의 Balance가 충분해야 한다.
2. Transaction에 적힌 Nonce가 Sender의 현재 Nonce와 같아야 한다.

Transaction에는 Sender의 서명과 Fee(수수료)가 들어 있다. 논문 시점에는 Fee가 Block을 만든 Miner에게 지급되었고, Miner는 Block을 만든 보상인 Block Reward(블록 보상)도 받았다. 이후 Fee 구조가 바뀐 내용은 Changes Since Publication에 있다.

Block i의 State를 σ_i, Block i에 든 Transaction 목록을 Tx_i라고 하자. State Transition(상태 전이)은 다음과 같다.

```
σ_i = Π(σ_(i-1), Tx_i)
```

Π는 Tx_i의 Transaction을 순서대로 σ_(i-1)에 적용하는 함수다. 따라서 최초 Block인 Genesis Block(제네시스 블록)의 State σ_0에 Transaction 목록을 차례로 적용하면 어느 Block의 State든 다시 만들 수 있다.

**예시 (논문 Figure 1).** Block i의 State에 Account 다섯 개가 있다. 논문은 Address를 6자로 줄여 쓰고, 모든 Account를 EOA로 가정한다.

| Account | Address |
|---|---|
| a1 | 0xa7d391 |
| a2 | 0xa7d397 |
| a3 | 0xa7f936 |
| a4 | 0xd81355 |
| a5 | 0xd815fc |

Block i+1에는 a2가 a4에게 5 ETH를 보내는 Transaction 하나가 있다. Fee는 0.01 ETH이고, 이 Block의 Miner는 a5다.

| Account | 변화 |
|---|---|
| a2 (Sender) | Balance 45.01 → 40.00, Nonce 10 → 11 |
| a4 (Receiver) | Balance 0.12 → 5.12, Nonce 2 그대로 |
| a5 (Miner) | Balance 32.01 → 34.02 (Fee 0.01 + Block Reward 2) |

Block i+2에서는 a4가 새 Address 0xd813a8(a6)에게 1 ETH를 보내고, Miner는 a1이다. Ethereum에서는 존재하지 않는 Address로 값을 보내면 그 Address의 Account가 새로 만들어진다. 그래서 a6가 생기고, a4와 a1이 갱신된다.

### State Trie and Merkle Patricia Trie

State Trie(상태 트라이)는 모든 Account의 State를 저장하는 자료구조다. 이 절은 State Trie가 어떻게 생겼는지 설명한다.

Trie(트라이)는 Key(키)를 앞에서부터 한 글자씩 따라 내려가며 값을 찾는 Tree(트리)다. Trie를 이루는 각 마디를 이 글에서는 Trie Node(트라이 노드)라고 부른다. Network 참여자인 Node와 구분하기 위해서다. 맨 위 Trie Node를 Root Node(루트 노드), 값이 달린 맨 아래 Trie Node를 Leaf Node(잎 노드)라고 한다.

Ethereum은 State Trie를 Merkle Patricia Trie(머클 패트리샤 트라이, 이하 MPT)로 구현한다. MPT는 두 구조를 합친 것이다.

- **Patricia Trie(패트리샤 트라이)**: Key 문자열이 그대로 경로가 되는 Trie다. 데이터는 Leaf Node에 있고, 앞부분이 같은 Key들은 경로를 공유한다. 그래서 검색이 효율적이다.
- **Merkle Tree(머클 트리)**: Leaf Node에는 데이터의 Hash를, 중간 Trie Node에는 자식들의 Hash를 다시 Hash한 값을 붙인다. 이를 Root Node까지 반복한다. Root Node의 Hash를 Root Hash(루트 해시)라고 한다. 데이터가 하나라도 바뀌면 Root Hash가 달라지므로, 큰 Tree 전체를 Root Hash 하나로 검증할 수 있다.

State Trie의 Root Hash를 State Root(상태 루트)라고 한다. State Root는 Block Header(블록 헤더)에 기록된다. Block Header는 Block의 요약 정보를 담은 부분으로, 이전 Block의 Hash, Transaction 목록의 Root Hash, State Root 등이 들어 있다. Transaction 목록 자체는 Block Body(블록 본문)에 있다.

**경로.** 논문은 Address 문자열이 그대로 State Trie의 경로가 된다고 설명한다. 실제 Ethereum은 Address의 Keccak-256 Hash를 경로로 쓰고, Leaf Node에는 Account의 네 값을 담는다([Merkle Patricia Trie](https://ethereum.org/developers/docs/data-structures-and-encoding/patricia-merkle-trie/)). 이 글의 예시는 설명을 쉽게 하려는 논문의 단순화를 따른다. 뒤에 설명할 Merkle Proof와 Void Proof의 원리는 어느 쪽이든 같다.

**중간 Trie Node의 종류.** 논문 표기로는 두 종류다.

| 종류 | 형태 (논문 표기) | 역할 |
|---|---|---|
| Branch Node(분기 노드) | 17개 항목 [v0, v1, ..., vf, Value] | 다음 한 글자(0부터 f)에 따라 갈라진다. v_i는 해당 자식 Trie Node의 Hash이고, 자식이 없으면 Null이다. |
| Extension Node(확장 노드) | 2개 항목 [Key, Path] | Path는 후손들이 공유하는 공통 Prefix(접두사)이고, Key는 유일한 자식 Trie Node의 Hash다. |

실제 Ethereum MPT의 Extension Node는 [Path, Key] 순서다. 또 남은 경로와 Account 값을 함께 담는 Leaf Node가 따로 있다([Merkle Patricia Trie](https://ethereum.org/developers/docs/data-structures-and-encoding/patricia-merkle-trie/)). 논문의 예시에서는 Leaf Node가 Account 데이터만 담고, 남은 경로는 바로 위 Extension Node가 담는다(Merkle Proof and Void Proof 참고).

**저장 방식.** 각 Trie Node는 자기 데이터로 계산한 Hash로 식별된다. 즉 Hash가 Key이고 데이터가 Value(값)다. 그래서 MPT는 LevelDB 같은 Key-Value Database로 구현할 수 있다. LevelDB는 Key로 Value를 저장하고 찾는 저장 Library(라이브러리)다. 논문은 Database에서 Hash가 hashX인 Trie Node의 데이터를 B(hashX)로 표기한다.

**갱신 방식.** Account가 갱신되면 Ethereum은 기존 Trie Node를 고치지 않는다. 새 Hash와 새 데이터를 가진 Trie Node를 만들어 Database에 덧붙인다. 부모 Trie Node도 같은 방식으로 새로 만들어지고, 새 Root Node가 생길 때까지 이어진다. 이전 Block의 Root Node와 그 후손은 그대로 남는다. 그래서 구조상 과거 Block의 State Root에서 출발하면 그 시점의 State Trie를 다시 찾아갈 수 있다. 대신 저장 공간이 많이 든다. 이 과거 Trie Node를 모두 보관하는 Node가 Archive Node(아카이브 노드)다(Full Node and Bootstrapping 참고).

### Merkle Proof and Void Proof

State Root만 있으면, State Trie 전체가 없어도 "어떤 Account가 그 Block에 있었는가"와 "없었는가"를 검증할 수 있다. 이 두 검증 수단을 Proof(증명)라고 한다. Ethanos는 이 두 Proof를 써서 지워진 Account를 되살린다(Dormant Account Restoration 참고).

**Merkle Proof(머클 증명, 존재 증명).** 어떤 Account의 Merkle Proof는 Root Node부터 그 Account까지 경로에 있는 모든 Trie Node 데이터의 목록이다. Verifier는 다음 순서로 확인한다.

1. 아래쪽 Trie Node부터 데이터의 Hash를 다시 계산한다.
2. 계산한 Hash가 부모 Trie Node에 적힌 Hash와 같은지 Root Node까지 확인한다.
3. 마지막에 다시 계산한 Root Hash가 Block Header의 State Root와 같은지 확인한다.

모두 같으면, 그 Account가 그 Block에 그 데이터로 존재했다는 것이 증명된다. 중간 데이터를 하나라도 조작하면 같은 Root Hash를 만들 수 없기 때문이다.

Figure 1에서 a5(Address 0xd815fc)의 Merkle Proof는 다음 다섯 개의 Trie Node 데이터다. 경로는 d → 81 → 5 → fc다. `{a: hashB, d: hashC}`는 Branch Node에서 Null이 아닌 항목만 적은 것이다.

```
B(hashA)     = {a: hashB, d: hashC}        Branch Node
B(hashC)     = [hashE, 81]                 Extension Node
B(hashE)     = {3: hashH, 5: hashI}        Branch Node
B(hashI)     = [hash(a5), fc]              Extension Node
B(hash(a5))  = {balance: 32.01, nonce: 30} Leaf Node (Account 데이터)
```

**Void Proof(부재 증명).** 같은 방식으로 어떤 Account가 없다는 것도 증명할 수 있다. Address 0xa7ec6b인 Account가 σ_i에 없다는 것을 보이려면 다음 세 개를 제시한다.

```
B(hashA) = {a: hashB, d: hashC}
B(hashB) = [hashD, 7]
B(hashD) = {d: hashF, f: hashG}
```

Verifier는 세 Trie Node의 Hash를 다시 계산해 Proof가 State Root와 이어지는지 확인한다. 그다음 B(hashD)에 Key e가 없다는 것을 본다. 0xa7e로 시작하는 Account가 σ_i에 없다는 뜻이다.

## Problem

앞에서 설명한 구조에서 Transaction을 검증하려면 현재 State가 있어야 한다. 이 장은 새로 참여하는 Node가 현재 State를 갖추는 비용이 너무 커졌다는 문제를 설명한다.

### Full Node and Bootstrapping

Node는 검증 능력과 보관 범위에 따라 나뉜다.

| 용어 | 의미 |
|---|---|
| Full Node(풀 노드) | Transaction을 스스로 완전히 검증할 수 있는 Node |
| Light Node(라이트 노드) | 스스로 완전히 검증하지 못하고, Transaction 전송과 검증을 다른 Full Node에 맡기는 Node |
| Archive Node(아카이브 노드) | 과거 모든 시점의 State Trie까지 보관하는 Node |

Bootstrapping(부트스트래핑)은 새 Node가 Network에 처음 참여해 현재 State까지 따라잡는 과정이다. Full Node가 되려면 Bootstrapping에서 현재 State를 갖춰야 한다.

### Synchronization: Full Sync and Fast Sync

Synchronization(동기화)은 Node가 현재 State에 도달하는 방법이다. 논문은 Go Ethereum(이하 Geth) Client(클라이언트)의 두 방식을 설명한다. Geth는 Ethereum Protocol(프로토콜)을 Go 언어로 구현한 Software(소프트웨어)이며, 논문 시점에 많이 쓰이던 Client다.

**Full Sync(전체 동기화)**

1. 모든 Block을 내려받는다.
2. Genesis Block부터 현재 Block까지 모든 Transaction을 다시 실행한다. 이를 Replay(재실행)라고 한다.
3. 그 과정에서 현재 State Trie와 과거 갱신 기록을 다시 만들고, Block Header를 검증한다.

**Fast Sync(빠른 동기화)**

1. 모든 Block을 내려받는다.
2. Pivot Block(기준 블록)의 State Trie Snapshot(스냅샷)을 내려받는다. Snapshot은 그 시점 State Trie의 사본이다. Pivot Block은 현재 Block보다 64 Block 이전의 Block이다(논문 시점 Geth 기준).
3. Pivot Block부터 현재 Block까지의 Transaction만 Replay해서 현재 State Trie를 만든다.

Fast Sync는 오래된 Block일수록 위조하기 어려우므로 검증 필요성이 낮다는 생각에 기반한다. Pivot Block 이전 Transaction은 내려받지만 Replay하지 않는다.

### Cost of Becoming a Full Node

논문이 제시하는 2020년 1월 기준 수치는 다음과 같다.

- Ethereum 전체 데이터는 3.6TB를 넘었다. Block 탐색 서비스인 Etherscan이 집계한 Archive Node 크기 기준이다.
- Full Sync는 큰 저장 공간과 수 주의 시간이 든다.
- Fast Sync도 약 235GB가 필요하고 약 하루가 걸린다.

저장 공간과 Network 대역폭이 제한된 개인 기기는 Full Node가 되기 어렵다. 논문은 그 결과 두 가지 보안 문제가 생긴다고 설명한다.

1. 사용자가 Light Node로 남아, Miner 같은 다른 Full Node나 Infura 같은 중앙 서비스에 검증을 맡기게 된다. Infura는 다른 사용자의 요청을 대신 처리해 주는 Ethereum Node 서비스다. 이렇게 맡기면 금융 사기나 Transaction 검열에 취약해진다.
2. Full Node와 Miner의 수가 적으면 Network 자체가 조작에 취약해진다.

따라서 논문의 목표는 **Full Node가 되는 데 꼭 필요한 데이터를 줄이는 것**이다.

### State Trie as the Bottleneck

Fast Sync의 235GB 가운데 State Trie는 70GB 이상으로 추정된다. 이 값은 논문 저자들의 추정치다. 2020년 1월 State Trie의 Trie Node 수(약 4억 7,500만 개)에, 저자들이 측정한 평균 Trie Node 크기(약 150 Byte)를 곱해 약 71GB로 계산했다. 나머지는 대부분 Transaction 데이터다.

크기만 보면 Transaction 데이터가 더 크다. 그런데 동기화 시간을 잡아먹는 것은 State Trie다. 동기화는 State Trie를 내려받는 단계와 Transaction을 내려받는 단계로 이루어지고, 두 단계는 병렬로 진행할 수 있다. 논문은 둘 가운데 State Trie를 내려받는 단계가 더 큰 병목이라고 설명한다.

- **State Trie**: Trie Node를 Hash로 찾아야 하므로, Database 접근 위치가 무작위로 흩어진다. 그래서 순회, 전송, 재구축이 모두 Disk Input/Output(디스크 입출력, 이하 I/O)에 묶인다. 논문은 이 때문에 Solid State Drive(반도체 저장장치, 이하 SSD)만 쓸 수 있고 Hard Disk Drive(하드 디스크, 이하 HDD)로는 어렵다는 자료를 인용한다.
- **Transaction 데이터**: Block의 Transaction Index(트랜잭션 색인)를 써서 묶음으로 빠르게 내려받을 수 있다.

이 차이는 뒤의 Synchronization Time 실험에서 수치로 확인된다. 1GB를 내려받는 데 걸리는 시간(sec/GB)으로 보면, State Trie는 약 475초, 나머지 데이터는 234에서 257초로, State Trie가 약 2배 느리다.

State Trie는 시간이 지날수록 계속 커진다는 점도 문제다. 2020년 1월 Account 수는 8,500만 개를 넘었고, 하루 5만에서 15만 개씩 늘고 있었다.

### Observation: Most Accounts Are Dormant

논문은 Genesis Block부터 800만 번째 Block까지 Account 활동을 추적했다. 이를 위해 두 용어를 정의한다.

- **Active Account(활성 계정)**: 해당 기간에 Transaction을 보내거나, 받거나, Block을 채굴한 Account
- **Dormant Account(휴면 계정)**: 해당 기간에 쓰이지 않은 Account

**관찰 1. Active Account는 소수다.** 최근 1주 기준 Active Account는 전체의 약 3%, 최근 1달 기준은 약 5%다. 즉 어느 기준으로 보아도 95% 이상이 Dormant Account다.

**관찰 2. 한번 쓰인 Account는 곧 다시 쓰인다.** 논문은 Account마다 연속한 두 갱신 사이의 평균 간격을 구하고, 그 간격별로 Account를 분류했다(논문 Table 1). 논문은 이를 "갱신된 Account가 1주 안에 다시 갱신될 확률이 76%"라는 식으로 해석한다. 1주는 약 40,320 Block, 1달은 약 172,800 Block으로 환산했다. Block 간격 15초로 계산하면 나오는 값이다.

| 평균 갱신 간격 | 1일 이내 | 1주 이내 | 2주 이내 | 1달 이내 | 6개월 이내 |
|---|---|---|---|---|---|
| Account 비율(%) | 62.3 | 76.0 | 82.4 | 89.0 | 98.4 |

### Problems to Solve

두 관찰에서 방향이 나온다.

- Dormant Account를 State Trie에서 빼면 크기가 크게 줄어든다.
- 최근 쓰인 Account는 곧 다시 쓰이므로, 이번 주기의 Transaction 대부분은 직전 주기의 State만으로 처리할 수 있다.
- Block 하나에 담을 수 있는 Transaction 양에는 한도가 있으므로, 한 주기에 들어가는 Transaction 수에도 상한이 있다. 따라서 한 주기의 Active Account 수와, 그 Account만 담은 State Trie의 크기도 시간이 지나도 계속 커지지 않는다.

여기서 지켜야 할 조건이 하나 있다. **State를 줄여도, Bootstrapping 이후의 모든 Transaction은 여전히 완전히 검증할 수 있어야 한다.** 이 조건 아래 논문이 풀어야 할 질문은 세 가지다.

1. **어떻게 걸러 낼까.** MPT를 순회하며 Dormant Account를 찾아 지우는 것은 비용이 매우 크다.
2. **다시 필요해지면 어떻게 복원할까.** 빠진 Account의 State를 State Trie 없이 믿을 수 있게 되살려야 한다. 더 유리한 과거 State로 되돌리거나 지난 Transaction을 다시 실행하는 공격도 막아야 한다.
3. **줄어든 State로 어떻게 동기화할까.**

## Solution: Ethanos

### Key Idea and Terminology

Ethanos는 Dormant Account를 찾아 지우지 않는다. 대신 **주기마다 빈 State Trie에서 시작해, 그 주기에 쓰인 Account만 다시 채운다.** 채워지지 않은 Account는 자연스럽게 빠진다. 빠진 Account는 과거 State Root에 대한 Merkle Proof와 Void Proof로 복원한다. 동기화할 때는 전체 State 대신 최근 주기의 작은 State Trie만 받는다.

| 질문(Problems to Solve) | 해결 방법 | 해당 소제목 |
|---|---|---|
| 어떻게 걸러 낼까 | 빈 State Trie에서 다시 채우기 | Sweep |
| 어떻게 복원할까 | Restore Transaction과 Crumb Account | Dormant Account Restoration |
| 어떻게 동기화할까 | 최근 State Trie 두 개만 받기 | Compact Sync |

Ethanos가 새로 쓰는 용어는 다음과 같다.

| 용어 | 의미 |
|---|---|
| Epoch(에폭) λ | Sweep 주기를 이루는 Block 수. 1주 주기라면 약 40,320 Block |
| Checkpoint(체크포인트) | Epoch의 마지막 Block |
| Sweep(스윕) | Dormant Account를 State Trie에서 걸러 내는 동작 |
| Current Trie(현재 트라이) | 현재 Epoch에서 빈 상태로 시작해 채워 가는 State Trie |
| Cached Trie(캐시 트라이) | 직전 Checkpoint의 State Trie |
| Last Active Checkpoint(마지막 활성 체크포인트) | Account가 Crumb Account가 아닌 원래 Account로서 마지막으로 State Trie에 들어 있던 Checkpoint |
| Restore Transaction(복원 트랜잭션) | 두 Trie 모두에 없는 Account를 Current Trie에 다시 만드는 Transaction |
| Crumb Account(크럼 계정) | Dormant Account가 Receiver일 때, 복원 없이 새로 만들어지는 Account |

### Sweep

**동작.**

1. 새 Epoch가 시작되면 빈 State Trie를 만든다. 이것이 Current Trie다.
2. 직전 Checkpoint의 State Trie를 보관한다. 이것이 Cached Trie다.
3. Transaction에 필요한 Account를 Current Trie에서 먼저 찾는다.
4. 없으면 Cached Trie에서 찾는다. 있으면 Current Trie로 복사한 뒤 갱신한다.
5. 두 Trie 모두에 없는데 그 Account가 Sender가 되려 하면, 먼저 복원해야 한다(Dormant Account Restoration 참고).
6. Epoch가 끝나면 Current Trie가 새 Cached Trie가 되고, 이전 Cached Trie는 버린다.

이렇게 하면 한 Epoch 동안 실제로 쓰인 Account만 Current Trie에 남는다. 지우는 작업 없이 Sweep이 이루어진다.

**Cached Trie를 하나만 두는 이유.** 논문은 세 가지를 든다.

- Full Node가 Trie 하나로 Bootstrapping할 수 있어 내려받는 크기가 줄어든다.
- 모든 Full Node가 같은 방식으로 동작한다.
- 연속한 Checkpoint의 State Trie에는 겹치는 Active Account가 많아, 여러 개를 두는 것이 비효율적이다.

**예시 (논문 Figure 3).** Transaction and State Transition의 예시를 Ethanos에 그대로 옮긴다. n번째 Epoch가 Block i에서 끝난다고 하자(i = n × λ). Block i가 Checkpoint이고, Cached Trie에는 a1부터 a5가 있다. n+1번째 Epoch는 빈 Current Trie로 시작한다.

Block i+1에서는 a2가 a4에게 보내고 Miner는 a5다. 세 Account 모두 Current Trie에 없으므로 Cached Trie에서 찾아 복사하고 갱신한다.

Block i+2에서는 a4가 새 Address a6에게 1 ETH를 보내고 Miner는 a1이다.

| Account | 찾은 위치 | 처리 |
|---|---|---|
| a4 (Sender) | Current Trie | 바로 갱신 |
| a1 (Miner) | Cached Trie | 복사 후 갱신 |
| a6 (Receiver) | 두 Trie 모두에 없음 | 새 Account로 생성 |

이 시점의 Current Trie에는 a1, a2, a4, a5, a6만 있다. 이번 Epoch에 쓰이지 않은 a3는 들어 있지 않다.

### Dormant Account Restoration

#### Sender and Receiver Handling

두 Trie 모두에 없는 Account가 Transaction에 등장하면, 그 역할에 따라 처리가 다르다.

- **Sender인 경우.** 먼저 Restore Transaction을 보내야 한다. Restore Transaction은 그 Account를 마지막 State 그대로 Current Trie에 다시 만든다.
- **Receiver인 경우.** 복원하지 않는다. Transaction and State Transition에서 보았듯 Ethereum에서는 존재하지 않는 Address로 값을 보내면 새 Account가 만들어진다. 이때 Ethanos는 Receiver가 정말 새 Address인지, 사실은 Dormant Account인지 구별하지 않고 똑같이 새 Account를 만든다. Dormant Account 자리에 새로 만들어진 Account가 Crumb Account다.

Crumb Account는 Balance가 충분하면 그대로 Sender가 될 수 있다. Balance가 부족하면 Restore Transaction을 보내야 하고, 이때 Crumb Account들이 원래 Account와 합쳐진다. Crumb Account는 여러 Epoch에 걸쳐 여러 개 생길 수 있다.

논문은 이렇게 나누어 Restore Transaction의 빈도를 줄인다고 설명한다. 값을 받기만 하는 Account까지 복원을 요구하지 않기 때문이다.

#### Restore Transaction: Roles and Proofs

**세 역할.**

| 역할 | 하는 일 |
|---|---|
| Owner(소유자) | 자신의 Account가 Dormant 상태인지 판단하고 복원을 요청한다. |
| Archive Node | 과거 Checkpoint들의 State Trie에서 Proof를 모아 Restore Transaction을 만들어 보낸다. |
| Miner와 Verifier | Proof를 검증하고 Current Trie에 Account를 만든다. |

Owner는 두 방법 중 하나로 Dormant 여부를 판단한다. 마지막 Transaction 이후 두 Epoch가 지났는지 확인하거나, 현재 Epoch에서 자신의 Account에 접근할 수 있는지 조회한다. 논문은 Ethanos에서는 Owner도 쉽게 Full Node가 될 수 있으므로 이 판단을 스스로 할 수 있다고 설명한다. 가끔만 쓰는 Account라면, 정기적으로 소액을 보내는 Smart Contract로 Dormant 상태를 피할 수 있다고도 적는다.

Archive Node가 Restore Transaction을 만드는 이유가 있다. 일반 Ethanos Full Node는 자신이 Bootstrapping한 Checkpoint 이전의 State Trie를 갖고 있지 않다. Last Active Checkpoint가 그보다 오래되었다면 Proof를 만들 수 없다. 그렇지 않은 경우에는 Full Node가 직접 만든다.

**담기는 Proof.** Last Active Checkpoint를 k, 최신 Checkpoint를 n이라고 하자(k < n).

| Proof | 대상 Checkpoint | 증명하는 것 |
|---|---|---|
| Merkle Proof | k | Account가 Checkpoint k에 그 State로 존재했다. |
| Void Proof | k+1부터 n-1까지 각각 | 그 이후로는 없었다. 즉 k가 정말 마지막이었다. |

Checkpoint n에 대한 Void Proof는 필요 없다. Cached Trie로 직접 확인할 수 있기 때문이다. 검증에는 각 Checkpoint Block Header의 State Root만 쓰인다(Merkle Proof and Void Proof 참고).

**어떤 공격을 막는가.** 누군가 Balance가 더 많았던 과거 Checkpoint j(j < k)의 State로 복원하려 한다고 하자. 그러면 j가 마지막이었음을 보이기 위해 Checkpoint k에 대한 Void Proof를 내야 한다. k에는 Account가 실제로 존재하므로 이 Proof는 통과하지 못한다.

#### Reducing Void Proofs with Bloom Filter

**문제.** n과 k의 차이가 커지면 Void Proof가 많아져 Restore Transaction이 커진다.

**해결.** 각 Checkpoint의 Block Header에 Bloom Filter(블룸 필터)를 저장한다. Bloom Filter는 어떤 원소가 집합에 들어 있는지를 적은 공간으로 판정하는 확률적 자료구조다.

- 들어 있는 원소에 대해서는 항상 "있다"고 답한다.
- 들어 있지 않은 원소에 대해서도 낮은 확률로 "있다"고 답할 수 있다. 이것이 False Positive(거짓 양성)다.
- 따라서 "없다"는 답은 항상 맞다.

어떤 Checkpoint의 Bloom Filter가 "없다"고 답하면, 그 Checkpoint의 Void Proof를 생략할 수 있다. 대신 Verifier는 Restore Transaction을 실행할 때 Bloom Filter로 부재를 직접 확인해야 한다. 논문은 False Positive 확률을 약 10%로 설정해 Void Proof의 90%를 생략한다.

#### Crumb Account Nonce and Replay Attack

**문제.** 일반 Ethanos Full Node는 모든 Checkpoint의 State Trie를 갖고 있지 않다. 그래서 새로 만들어지는 Account가 정말 새 Account인지 Crumb Account인지 구별할 수 없다. Crumb Account의 Nonce를 0으로 두면 문제가 생긴다. 공격자가 원래 Account가 과거에 보냈던 Transaction을 다시 보내면, Nonce가 맞아 다시 실행될 수 있다. 이것이 Replay Attack(재전송 공격)이다.

**해결.** 논문은 모든 새 Account의 초기 Nonce를 다음과 같이 정한다.

```
초기 Nonce = 현재 Block 번호 × (Account당 Block당 평균 Transaction 수)
```

논문은 이 값이 과거에 등장한 어떤 Nonce보다 항상 크다고 설명하며, [EIP-169](https://github.com/ethereum/EIPs/issues/169)를 근거로 든다.

**주의.** 인용된 EIP-169(Variant C)는 평균이 아니라 Account당 Block당 최대 Transaction 수(`MAX_TXS_PER_ACCT_PER_BLOCK`, 예시 값 64)를 곱한다. 또 Nonce가 Block 번호에 비례한 상한을 넘지 못하게 하는 검증 규칙을 함께 둔다. 평균을 쓰면, 평균보다 Transaction을 많이 보낸 Account의 기존 Nonce가 이 초기값보다 클 수 있다. 따라서 논문 표기를 글자 그대로 따르면 "항상 크다"는 보장이 성립하지 않는다(Errors in the Paper 참고). 이 판단은 논문에 없고, 이 글에서 EIP-169와 비교해 내린 것이다.

#### Crumb Account Merging and Restored Flag

**병합 방법.** Crumb Account가 있는 Account를 복원할 때는 Last Active Checkpoint의 Account와 Crumb Account들을 합친다. 그래서 Restore Transaction에는 Crumb Account가 있는 Checkpoint마다 Merkle Proof가 추가된다. 연속한 여러 Checkpoint에 Crumb Account가 있으면 마지막 Checkpoint의 Balance만 합친다. 그 Balance에 앞선 Checkpoint들의 활동이 이미 반영되어 있기 때문이다.

**문제.** Merkle Proof가 두 개(P1, P2) 있는 Restore Transaction은 "P1은 Last Active Checkpoint의 Account, P2는 Crumb Account"로 해석된다. 그런데 P2가 사실은 P1을 이미 복원한 Account라면, P1의 Balance가 한 번 더 더해진다.

**해결.** Account State에 1 Bit(비트)짜리 Restored Flag(복원 표시)를 추가한다. 기본값은 0이고, 복원될 때 Verifier가 1로 바꾼다. P2의 Flag가 1이면, 이미 복원된 Account를 Crumb Account로 속이는 시도로 보고 거부한다.

**보안 속성.** 유효한 Proof만 담긴 Restore Transaction에서, 각 Checkpoint의 Account는 네 상태 중 하나다.

| 기호 | 상태 | 판정 기준 |
|---|---|---|
| a | Active | Merkle Proof가 있고 Restored Flag가 0 |
| r | Restored | Merkle Proof가 있고 Restored Flag가 1 |
| c | Crumb | Merkle Proof가 있고 Restored Flag가 0이며, 앞쪽에 Active나 Restored 상태가 있음 |
| v | Void | Account가 없음 |

a와 c는 Restored Flag만으로는 구별되지 않고, 상태 열에서의 위치로 구별된다.

논문은 "Restore Transaction은 유효하지 않은 State를 만들 수 없다"는 속성을 제시한다. 유효한 상태 열은 다음 Regular Expression(정규 표현식)으로 표현된다. 시간 순서대로 왼쪽에서 오른쪽으로 읽는다. `+`는 1번 이상, `*`는 0번 이상, `|`는 둘 중 하나를 뜻한다.

```
(a+|r+)v+(c+v)*v*
```

이 형태에 맞지 않는 Restore Transaction은 거부된다. 마지막 Proof가 c이면 그 뒤에 v가 하나 더 있다고 가정한다.

- `avvvcccvv`는 유효하다. Active 뒤에 Void가 이어지고, Crumb 구간이 나온 뒤 다시 Void다.
- `avvvvvrvv`는 유효하지 않다. Void 뒤에 Restored가 나온다.
- `aav`처럼 a가 연속하는 경우도 유효하다. 논문은 이때 마지막 a에서 복원한다고 설명한다.

### Compact Sync

Ethanos는 두 가지 동기화 방식을 둔다.

| 방식 | 대응하는 Geth 방식 | 동작 |
|---|---|---|
| Archive Sync(아카이브 동기화) | Full Sync | 모든 Block을 내려받고 Genesis Block부터 모든 Transaction을 Replay한다. |
| Compact Sync(압축 동기화) | Fast Sync | Pivot Block의 State Trie를 내려받고 Pivot Block부터 현재까지만 Replay한다. |

Compact Sync는 Fast Sync와 두 가지가 다르다.

1. **최신 Checkpoint의 State Trie도 내려받는다.** Cached Trie로 쓰기 위해서다.
2. **Genesis Block부터 Pivot Block까지의 Transaction을 내려받지 않는다.** 어차피 Replay하지 않기 때문이다. 필요하면 Archive Node에 요청한다.

State Trie를 두 개 받지만, 둘 다 한 Epoch의 Active Account만 담고 있어 작다(실험에서 약 220MB 수준). 그 결과 새 Node는 전체 State 없이 최근 Epoch의 State Trie만으로 Bootstrapping하고, 그 이후의 모든 Transaction을 완전히 검증할 수 있다.

### Restore Transaction Fee

논문은 Restore Transaction의 Fee에 대해 구체적 규칙 대신 방향만 제시하며, 이 부분은 실험하지 않았다.

- 사용자는 Account의 가치가 Fee보다 크면 Fee를 내고 복원한다.
- 과거 State Trie를 보관하며 Restore Transaction을 만들어 주는 Archive Node도 Fee를 받아야 한다.
- Archive Node와 Miner의 수가 늘면 Fee가 내려가고, 줄면 올라간다. 수요와 공급이 수와 Fee를 결정한다.

## Evaluation

### Experimental Setup

| 항목 | 값 |
|---|---|
| 대상 구간 | Ethereum 700만 번째 Block부터 730만 번째 Block (300,000 Block, 2019년 초 약 2개월) |
| Transaction 수 | 30,575,237 |
| 갱신된 Account 수 | 4,588,065 |
| 구현 기반 | Geth v1.9 |
| Epoch | 40,320 Block (약 1주) |
| Checkpoint 수 | 7 |
| 추가된 Restore Transaction | 198,121 |
| Bloom Filter 크기 | Checkpoint Block당 512KB |
| 동기화 실험 연결 | 데이터를 내주는 컴퓨터와 Bootstrapping하는 컴퓨터를 Ethernet(이더넷)으로 직접 연결 |

이 실험은 700만 번째 Block을 Genesis Block으로 삼아 Ethanos Blockchain을 새로 시작한 것이다. 비교 대상인 Geth도 같은 지점에서 시작했다. 300,000번째 Block 시점에 1주 Active Account는 약 100만 개이고, 비율은 23.5%다.

실험은 두 단계였다.

1. **Pre-simulation(사전 시뮬레이션).** Transaction을 먼저 모의 실행해 Checkpoint마다 어떤 Account가 남는지 분류하고, Restore Transaction이 들어갈 위치를 표시했다. 이 단계에서는 Block이 아직 없어 Proof를 계산할 수 없으므로 위치만 정한다.
2. **실제 실행.** 수정한 Geth로 Transaction을 실행하고, Restore Transaction을 만들고, Block을 채굴하고, 동기화를 수행했다.

논문이 밝힌 제약은 다음과 같다.

- 모든 Transaction의 전송 값을 0으로 두었다. 빈 State에서 시작하므로 Balance 부족 오류를 피하기 위해서다. 논문은 Pre-simulation이 Restore Transaction 위치를 정확히 찾으므로, 저장 크기와 동기화 시간은 실제 값을 보냈을 때와 거의 같을 것이라고 본다.
- 모든 Transaction을 Delegated Transaction(대리 트랜잭션)으로 만들었다. 실제 Sender의 Private Key를 알 수 없어 서명을 만들 수 없기 때문이다. Transaction당 20 Byte가 늘어난다.
- CA를 EOA처럼 취급했다. Smart Contract가 실행 중에 일으키는 Internal Transaction(내부 트랜잭션)은 제외했다.

### Storage Size

**Archive Sync (300,000번째 Block까지, 논문 Table 2)**

| 구분 | Geth (MB) | Ethanos (MB) | 차이 (MB) |
|---|---|---|---|
| Trie Nodes | 46,333.43 | 40,342.62 | -5,990.81 |
| Headers | 110.26 | 119.98 | +9.72 |
| Bodies | 3,220.84 | 3,852.75 | +631.91 |
| 전체 | 52,031.68 | 46,676.61 | -5,355.07 |

표에는 주요 항목만 옮겼다. Trie Nodes는 Trie Node 전체, Headers는 Block Header, Bodies는 Block Body다. 전체는 Receipts(영수증, Transaction 실행 결과 기록), Transaction Index 같은 나머지 항목까지 더한 값이다.

전체가 약 5.3GB(10.3%) 줄었고, 대부분 Trie Nodes 감소에서 온다. 두 시스템의 Account 수와 Account별 갱신 횟수는 같다. 차이는 Trie의 크기다. Geth는 모든 Account(약 450만 개)를 담은 큰 Trie 하나를 유지하고, Ethanos는 Epoch마다 Active Account(약 100만 개)만 담은 작은 Trie를 유지한다. Trie가 작으면 Account까지의 깊이가 얕아져, 갱신할 때 새로 덧붙는 Trie Node 수가 적다(State Trie and Merkle Patricia Trie의 갱신 방식 참고). Headers는 Bloom Filter 때문에, Bodies는 Restore Transaction 때문에 늘었다.

**Fast Sync와 Compact Sync (7번째 Checkpoint, 논문 Table 3)**

이 비교에서 Geth의 Compact Sync는 Geth에도 같은 방식, 즉 Pivot Block 이전 Transaction을 받지 않는 방식을 적용한 값이다. 동기화는 Checkpoint 다음 64번째 Block에서 수행해 Checkpoint가 Pivot Block이 되게 했다. 논문은 이렇게 맞추면 두 시스템의 차이가 Pivot Block의 State Trie에 있다고 설명한다. Geth의 State Trie는 모든 Account를, Ethanos의 State Trie는 그 Epoch의 Active Account만 담는다. 다만 Ethanos는 Restore Transaction과 Bloom Filter 때문에 Block Body와 Block Header가 조금 더 크다.

| 구분 | Geth (MB) | Ethanos (MB) |
|---|---|---|
| Fast Sync 전체 | 6,020.87 | 5,966.79 |
| Compact Sync 전체 | 977.67 | 374.23 |
| Trie Nodes | 약 832 | 220.03 |

Fast Sync에서는 전체 크기 차이가 거의 없다. 300,000 Block만 지난 시점이라 Transaction 데이터가 Trie보다 훨씬 크기 때문이다. Transaction 내려받기를 생략하는 Compact Sync에서는 Ethanos가 Geth의 38% 크기다.

논문이 가장 중요하게 보는 결과는 Ethanos의 State Trie가 Checkpoint가 늘어나도 약 220MB 수준에서 유지된다는 점이다. 이것은 1주 Active Account 수가 약 100만 개 수준으로 유지된다는 조건 아래의 결론이다. 논문은 2020년 1월에도 이 조건이 맞는다고 적는다.

Epoch 끝 무렵에 Compact Sync를 하면 두 State Trie를 받아야 한다. 직전 Checkpoint의 State Trie 220MB와, 현재 Pivot Block 기준 Compact Sync 저장량 374MB를 합쳐 594MB다.

### Synchronization Time

각 경우를 15회씩 측정해 평균을 냈다. 7번째 Checkpoint 결과는 다음과 같다.

- Ethanos Fast Sync는 Geth Fast Sync보다 17% 짧다. 데이터 크기는 거의 같은데도 그렇다.
- Ethanos Compact Sync는 Geth Compact Sync보다 75% 짧다.

두 경우 모두 Geth와 Ethanos의 시간 차이는 약 290초이고, State Trie 크기 차이는 약 610MB다. 따라서 State Trie 내려받기는 약 475 sec/GB다.

나머지 데이터의 속도는 같은 시스템 안에서 Fast Sync와 Compact Sync를 비교해 구한다. 두 방식의 시간 차이를, State Trie를 뺀 데이터 크기 차이로 나누면 234에서 257 sec/GB다. State Trie as the Bottleneck에서 말한 병목이 이 수치로 확인된다.

### Account Types per Checkpoint

한 Epoch에서 Account가 처음 쓰일 때의 유형은 네 가지다.

| 유형 | 조건 |
|---|---|
| New | 이 실험의 Genesis Block부터 지금까지 한 번도 쓰인 적이 없다. |
| Cached | 직전 Checkpoint의 State Trie에 있다. |
| Crumb | Cached가 아니고 Receiver로 쓰인다. |
| Restored | Cached가 아니고, Balance가 부족한 Sender로 쓰인다. Restore Transaction이 먼저 실행된다. |

Checkpoint 1의 Account 약 120만 개는 모두 New다. 그중 약 35만 개가 Checkpoint 2에서 Cached다. Checkpoint 2까지는 Crumb과 Restored가 없다. 첫 Epoch에 쓰인 Account가 모두 Checkpoint 1의 Cached Trie에 있기 때문이다. Crumb과 Restored는 Checkpoint 3부터 나타난다.

Restored Account는 전체의 5% 미만으로, Crumb Account보다 훨씬 적다. 많은 Dormant Account가 복원 없이 Crumb Account로 다시 쓰였다는 뜻이다.

### Restore Transaction Overhead

Restore Transaction이 일반 Transaction에 비해 만드는 Overhead(추가 비용)를 수, 크기, 실행 시간으로 측정했다. 크기와 실행 시간은 Epoch마다 일반 Transaction 200개와 Restore Transaction 200개를 무작위로 뽑아 측정했다.

| 항목 | 일반 Transaction | Restore Transaction |
|---|---|---|
| 수 | Epoch별 전체의 98.5% 이상 | Epoch별 전체의 1.5% 미만 |
| 크기 | 0.12KB로 일정 | 3KB 이상, 편차가 큼 |
| 실행 시간 | 평균 1ms 미만 | 더 길다 |

Restore Transaction이 큰 이유는 Merkle Proof 하나가 약 3KB이고 Void Proof가 여러 개 붙기 때문이다. Bloom Filter가 크기를 절반 이상 줄였다. 실행 시간이 긴 이유는 Last Active Checkpoint에 닿을 때까지 Checkpoint를 차례로 확인해야 하기 때문이다. 각 Checkpoint에서 Bloom Filter를 조회하고 Proof를 검증한다.

논문은 7번째 Epoch 기준으로 Block 하나의 영향을 추정했다. 한 Block은 평균 일반 Transaction 248개와 Restore Transaction 2.7개를 실행한다. 측정한 실행 시간으로 계산하면 각각 99.2ms와 10.5ms이며, 실행 시간이 약 10% 늘어난다. 논문은 Block 간격이 15초이므로 이 증가는 채굴 시간에 비해 작다고 평가한다.

### Epoch Length

Epoch가 길면 State Trie가 커져 Bootstrapping 부담이 늘고, 대신 Restore Transaction은 줄어든다. 논문은 대상 구간을 864,000 Block으로 늘려 네 가지 Epoch 길이를 Pre-simulation으로 비교했다. 늘린 구간에는 가격 상승으로 Ethereum 사용이 많았던 2019년 5월이 포함된다.

| Epoch 길이 | Epoch 수 | Active Account가 가장 많았던 마지막 Epoch의 State Trie |
|---|---|---|
| 3일 | 50 | 138MB |
| 1주 | 20 | 278MB |
| 2주 | 10 | 454MB |
| 1달 | 5 | 817MB |

Epoch 수는 논문 값이다. 1주를 40,320 Block으로 계산하면 864,000 Block에는 Epoch가 21개(864,000 / 40,320 = 21.4) 들어간다. 논문은 20개로 적는다. 20개는 806,400 Block으로, 2주 Epoch 10개와 같은 구간이다. 논문은 이 차이를 설명하지 않는다(Errors in the Paper 참고).

State Trie 크기는 Epoch 길이에 비례하지 않고 더 완만하게 늘어난다. 3일에서 1달로 길이가 10배가 되어도 크기는 5.9배다. 논문은 Transaction이 최근에 쓰인 Account에 쏠려 있기 때문이라고 설명한다. Restore Transaction 수도 비례해서 줄지 않는다. 1달 Epoch의 Restore Transaction 수는 3일 Epoch의 약 1/5이다.

논문의 판단은 다음과 같다.

- 1달 Epoch가 비용 대비 효과가 좋아 보인다. 하지만 모바일 기기에는 817MB가 무거우므로, 당분간은 1주 Epoch가 적절하다.
- 2주 Epoch는 Restore Transaction을 줄이는 효과가 작다.
- 고정 길이 대신, Trie 크기가 기준값에 도달하면 Checkpoint를 만드는 가변 Epoch도 대안이다.

## Discussion and Limitations

### Contract Account Restoration

논문 6.1절의 내용이다. 실험에서는 CA를 다루지 않았다. 논문은 CA 복원도 원리는 같다고 설명한다. 차이는 Restore Transaction에 Last Active Checkpoint 시점의 Contract State Snapshot이 들어가야 해서 커질 수 있다는 점이다. 예를 들어 Ethereum Request for Comments 20(이하 ERC-20) Token(토큰)을 생각해 보자. ERC-20은 Ethereum 위에서 발행하는 Token의 표준 규격이다. 소유 기록 하나가 52 Byte(Address 20 + Balance 32)라면, 사용자 100만 명은 52MB가 된다.

논문이 드는 고려 사항은 세 가지다.

1. 서비스 중인 Smart Contract는 계속 갱신되므로 Dormant 상태가 되기 어렵다. 반대로 서비스가 끝난 Contract는 다시 복원될 가능성이 낮다. Ethanos는 이런 무거운 Dormant Contract를 걸러 낼 수 있다.
2. CA의 Address는 배포한 Account의 Address와 Nonce로 정해진다. Nonce는 계속 커지므로 같은 Address에 새 Contract를 배포할 수 없다. 따라서 Crumb CA는 값을 받아 생긴 Account일 뿐이고, Contract State 없이 Balance만 가진다는 것이 논문의 주장이다. 이 전제는 일반 배포 방식에만 맞는다(Errors in the Paper 참고).
3. Snapshot 크기를 줄이기 위해, Ethanos의 발상을 Storage를 담은 Trie인 Storage Trie(스토리지 트라이)에 재귀적으로 적용하는 방법을 제안한다. 필요한 기록만 복원하는 방식이다. 구체적 Protocol은 다른 곳에서 다루겠다고 적는다.

### Reducing Block Header Download

논문 6.2절의 내용이다. State Trie와 Transaction을 줄이고 나면 Block Header가 병목이 될 수 있다. 2020년 1월 기준 Block Header는 약 3GB다.

논문은 Non-Interactive Proofs of Proof-of-Work(비대화형 작업 증명의 증명, 이하 NIPoPoW)를 활용하자고 제안한다. NIPoPoW는 Super Block(슈퍼 블록)의 Block Header만 표본으로 내려받아 검증하는 방식이다. Super Block은 같은 Target(목표값) 아래에서 Block Hash가 Target의 1/2^μ 이하로 나와, 요구량보다 많은 작업을 증명한 Block이다([Kiayias et al.](https://eprint.iacr.org/2017/963)). 논문의 "채굴 난이도가 더 높은 Block"이라는 표현은 이 뜻이다(Errors in the Paper 참고).

Ethanos는 Checkpoint의 Block Header가 필요하다. 그래서 논문은 Checkpoint를 정확한 Epoch 경계 대신 경계 근처의 Super Block으로 정하자고 제안한다. 이 경우 2020년 1월(910만 Block)에 동기화하면 Block Header 226개(9.1M / 40,320), 약 84KB(226 × 370 Byte)만 받으면 된다고 계산한다. Block이 1억 개까지 늘어도 0.92MB라고 본다(약 2,480개 × 370 Byte).

다만 이 계산에는 Checkpoint Block Header에 저장되는 Bloom Filter(실험에서 Checkpoint당 512KB)가 빠져 있다. 같은 크기라면 Bloom Filter는 Checkpoint 226개에서 약 113MB(226 × 512KB), 1억 Block에 해당하는 약 2,480개에서 약 1.2GB(2,480 × 512KB)다. 이 절은 제안이며 실험으로 검증되지 않았다.

### Experimental Limitations

- **실험 규모.** 실험은 빈 State에서 시작한 300,000 Block이다. 이 구간의 1주 Active Account 비율은 23.5%로, 원래 Ethereum의 700만 번째 Block 시점 비율(3% 미만)과 다르다. 논문은 실제 효과가 더 클 것이라고 예상하지만, 측정값은 아니다.
- **Smart Contract.** 전송 값을 0으로 두고 CA를 EOA처럼 취급했다. 따라서 Contract가 많은 환경에서의 복원 비용은 측정되지 않았다. Contract Account Restoration의 내용은 설계 방향 수준이다.
- **Archive Node 의존.** 오래된 Account를 복원하려면 과거 Checkpoint의 State Trie를 가진 Archive Node가 있어야 한다. Archive Node가 충분히 유지되는지는 Restore Transaction Fee의 논의에 달려 있고, 실험되지 않았다.
- **"1GB 미만" 결론.** 논문 결론의 1GB 미만 Bootstrapping은 Compact Sync 크기(측정값을 합친 약 600MB)에 NIPoPoW 추정치(1억 Block 기준 0.92MB)를 더한 값이다. NIPoPoW 부분은 실험되지 않았다. 또 그 추정치에는 Checkpoint Bloom Filter 크기가 들어 있지 않다(Reducing Block Header Download 참고). 실험과 같은 크기(512KB)의 Bloom Filter를 더하면, 2020년 1월(Checkpoint 226개) 기준 합계는 약 700MB로 1GB 미만이다. 그러나 논문이 가정한 1억 Block 기준으로는 Bloom Filter만 약 1.2GB여서 1GB를 넘는다. Bloom Filter를 더한 계산은 논문에 없고, 이 글에서 한 것이다.

|---|---|---|

CREATE2는 2019년 2월 [Constantinople](https://ethereum.org/ethereum-forks/)(Block 7,280,000)에서 활성화되어 실험 구간 안에 있다. 따라서 "Crumb CA는 Contract State를 가질 수 없다"는 결론은 CREATE2를 고려해 추가 검토가 필요하다. |

## Changes Since Publication

아래 내용은 2026년 11월 기준이다.

- **합의 방식.** Ethereum은 2022년 9월 15일 [The Merge(병합)](https://ethereum.org/roadmap/merge/)로 Proof of Stake(지분 증명)로 전환했다. Miner는 Validator(밸리데이터)로 대체되었고, PoW Block Reward는 없다. Block 간격은 PoW 시기 약 13에서 15초였고, 현재는 12초 Slot(슬롯) 단위다.
- **Fee.** 2021년 8월 London Hard Fork의 [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559) 이후 Fee 가운데 Base Fee(기본 수수료)는 소각되고, Priority Fee(우선 수수료)만 Block 생성자에게 간다. Transaction and State Transition에서 설명한 Fee 지급 방식은 그 이전 기준이다.
- **Fast Sync.** Geth는 v1.10.0에서 Snap Sync(스냅 동기화)를 도입했고, v1.10.4부터 기본값으로 쓴다. Fast Sync는 v1.10.14에서 제거되었다([Geth FAQ(Frequently Asked Questions)](https://geth.ethereum.org/docs/faq)). 논문의 Fast Sync 비교는 Geth v1.9 기준이다.
- **Database.** Geth는 [v1.12.0](https://github.com/ethereum/go-ethereum/releases/tag/v1.12.0)부터 새로 만드는 Database의 기본 저장 엔진으로 LevelDB 대신 Pebble을 쓴다.
- **Client.** Geth 외의 Client였던 Parity Ethereum은 OpenEthereum으로 이름이 바뀌었다. 이전 [Parity Ethereum 저장소](https://github.com/openethereum/parity-ethereum)는 2020년 11월에, [OpenEthereum 저장소](https://github.com/openethereum/openethereum)는 2022년 5월에 보관(Archived) 처리되었다. OpenEthereum 저장소에는 Deprecated(지원 중단)로 표시되어 있다.
- **State Expiry(상태 만료).** Ethanos처럼 Dormant Account를 State에서 내보내는 Protocol 수준의 State Expiry는 Ethereum Mainnet(메인넷)에 도입되지 않았다. [ethereum.org의 Roadmap 문서](https://ethereum.org/roadmap/statelessness/)는 State Expiry를 연구 단계로 설명한다.
- **History Expiry(이력 만료).** State Expiry와는 다른 개념으로, 오래된 Block 이력을 내려놓는 EIP-4444가 부분 적용되었다. [2025년 7월 Ethereum Foundation 공지](https://blog.ethereum.org/2025/07/08/partial-history-exp) 기준으로, Client가 The Merge 이전 이력을 보관하지 않아도 되게 되었다. 이후 [Geth v1.17.2](https://github.com/ethereum/go-ethereum/releases/tag/v1.17.2)(2026년 3월)는 Prague Fork(프라하 포크, 2025년 5월 Pectra Upgrade 가운데 Execution Layer(실행 계층)에 해당하는 부분) 이전 이력까지 지울 수 있게 했다(`geth prune-history --history.chain postprague`). 일정 기간이 지난 이력을 계속 지우는 Rolling History Expiry(이력의 연속 만료)는 공지 시점에 진행 중인 작업으로 소개되었고, 도입되었다는 공식 발표는 찾지 못했다.
- **수치의 시점.** 3.6TB, 235GB, 70GB, Account 8,500만 개는 모두 2020년 1월 기준이다.
