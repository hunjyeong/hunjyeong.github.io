### TL;DR

Ethereum 같은 Account-based Blockchain에서 새 Node가 Full Node가 되려면 모든 Account의 현재 값을 담은 State Trie를 갖춰야 한다. 2020년 1월 기준으로는 과거 Transaction 재실행을 줄인 Fast Sync 방식으로도 약 235GB와 하루가 들었다. 병목은 그중 70GB 이상을 차지하는 State Trie다. Trie Node를 Hash로 하나씩 찾아야 해서, 다른 데이터보다 내려받는 데 약 2배 오래 걸린다. 그런데 Account의 95% 이상은 최근 1달 동안 쓰이지 않았고, 한번 쓰인 Account는 대개 곧 다시 쓰였다.

Ethanos는 Epoch마다 빈 State Trie에서 시작해, 그 Epoch에 쓰인 Account만 채운다. 직전 Epoch의 State Trie도 보관해 두고, 거기 있는 Account는 가져와 쓴다. 쓰이지 않는 Account를 찾아 지우지 않아도 State Trie가 작게 유지된다. 두 State Trie 모두에 없는 Account가 Transaction을 보내려면, 먼저 Restore Transaction으로 그 Account를 되살린다. Restore Transaction에는 과거 Checkpoint(Epoch의 마지막 Block)의 State Root를 기준으로 한 Proof 두 가지가 담긴다. 하나는 그 Account가 그때 있었다는 Merkle Proof이고, 다른 하나는 그 이후로는 없었다는 Void Proof다. 새 Node는 전체 State 대신 이 작은 State Trie 두 개를 받아 동기화한다(Compact Sync).

1주 Epoch로 300,000 Block을 처리한 실험에서 State Trie는 약 220MB로 유지되었다. Compact Sync 시간은 같은 조건의 Go Ethereum(Geth)보다 75% 짧았다. 대가는 Restore Transaction의 크기와 검증 시간, 그리고 과거 State Trie를 보관하는 Archive Node에 대한 의존이다. 2026년 11월 현재 Ethereum에는 이렇게 쓰이지 않는 Account를 State에서 내보내는 기능인 State Expiry(상태 만료)가 도입되지 않았다.

## Account-based Blockchain

### State를 기록하는 방식

Blockchain은 Transaction을 Block 단위로 묶어 순서대로 이어 붙인 기록이다. Transaction은 값을 옮기거나 프로그램을 호출하는 요청이다. Network에 참여하는 컴퓨터를 Node, Block을 만드는 Node를 Miner(채굴자), 받은 Block의 Transaction을 다시 실행해 결과를 확인하는 Node를 Verifier(검증자)라고 한다.

Blockchain이 "누가 얼마를 가졌는가"를 기록하는 방식은 크게 두 가지다.

- **Bitcoin**: Unspent Transaction Output(미사용 트랜잭션 출력, 이하 UTXO) 방식을 쓴다. 전체 상태를 따로 기록하지 않고, 아직 쓰이지 않은 Transaction 출력들로 암묵적으로 표현한다.

- **Ethereum**: Account-based 방식을 쓴다. 각 Account(계정)가 얼마를 가졌는지를 Transaction과 별도로 명시적으로 기록한다. 모든 Account의 현재 값을 묶은 것을 State(상태)라고 한다.

Account-based 방식은 Smart Contract 개발에 더 단순하고 직관적이다. Smart Contract는 Transaction이 호출하면 Account의 State를 사용해 정해진 작업을 수행하는 프로그램이다. 대신 Block마다 Transaction뿐 아니라 State까지 관리해야 하므로 데이터가 빠르게 늘어난다.

**⇒ State를 따로 기록하는 비용이 이 논문이 다루는 문제의 출발점이다.**

### Account

Account는 Address(주소)로 찾는다. Address는 20 Byte이며 16진수 40자로 쓴다. Account는 두 종류다.

- **Externally Owned Account(외부 소유 계정, 이하 EOA)**: 사용자의 Account다. 사용자는 Private Key(개인 키)로 Transaction에 서명해 EOA를 사용한다.

- **Contract Account(컨트랙트 계정, 이하 CA)**: Smart Contract의 Account다. 프로그램 Code와 그 프로그램의 데이터를 함께 가진다.

Account의 값을 설명하려면 Hash를 알아야 한다. Hash는 임의 길이의 데이터를 고정 길이 값으로 바꾼 결과다. 데이터가 조금만 바뀌어도 Hash가 달라지고, 같은 Hash를 갖는 다른 데이터를 찾기는 사실상 불가능하다.

| 필드 | 의미 |
|---|---|
| Nonce | 같은 Transaction이 두 번 실행되지 않게 하는 순번이다. EOA에서는 보낸 Transaction 수다. |
| Balance | 보유한 Ether의 양이다. Ether는 Ethereum의 암호화폐이며 단위는 ETH다. |
| StorageRoot | Smart Contract가 변수 값을 저장하는 공간인 Storage를 Trie(아래 State Trie에서 설명)로 만든 뒤, 그 Root의 Hash를 담는다. |
| CodeHash | Smart Contract Code의 Hash다. |

### Transaction과 State Transition

Transaction은 Sender(송신 계정)에서 Receiver(수신 계정)로 값을 옮긴다. 실행되면 두 Account의 Balance가 바뀌고 Sender의 Nonce가 1 늘어난다. Transaction이 유효하려면 두 조건을 만족해야 한다.

1. Sender의 Balance가 충분해야 한다.

2. Transaction에 적힌 Nonce가 Sender의 현재 Nonce와 같아야 한다.

Transaction에는 Sender의 서명과 Fee(수수료)가 들어 있다. Fee는 Block을 만든 Miner에게 지급되고, Miner는 Block을 만든 보상인 Block Reward(블록 보상)도 받는다.

Block i의 State를 σ_i, Block i에 든 Transaction 목록을 Tx_i라고 하자. State Transition(상태 전이)은 다음과 같다.

```
σ_i = Π(σ_(i-1), Tx_i)
```

Π는 Tx_i의 Transaction을 순서대로 σ_(i-1)에 적용하는 함수다. 따라서 최초 Block인 Genesis Block(제네시스 블록)의 State σ_0에 Transaction 목록을 차례로 적용하면 어느 Block의 State든 다시 만들 수 있다.

**예시.** Block i의 State에 Account 다섯 개가 있다. Address는 6자로 줄여 쓰고, 모든 Account를 EOA로 가정한다.

| Account | Address |
|---|---|
| a1 | 0xa7d391 |
| a2 | 0xa7d397 |
| a3 | 0xa7f936 |
| a4 | 0xd81355 |
| a5 | 0xd815fc |

Block i+1에는 a2가 a4에게 5 ETH를 보내는 Transaction 하나가 있다. Fee는 0.01 ETH이고, 이 Block의 Miner는 a5다.

| Account | 변화 |
|---|---|
| a2 (Sender) | Balance 45.01 → 40.00, Nonce 1 증가 |
| a4 (Receiver) | Balance 0.12 → 5.12, Nonce 그대로 |
| a5 (Miner) | Balance 32.01 → 34.02 (Fee 0.01 + Block Reward 2) |

Block i+2에서는 a4가 새 Address 0xd813a8(a6)에게 1 ETH를 보내고, Miner는 a1이다. Ethereum에서는 존재하지 않는 Address로 값을 보내면 그 Address의 Account가 새로 만들어진다. 그래서 a6가 생기고, a4와 a1이 갱신된다.

### State Trie

State Trie(상태 트라이)는 모든 Account의 State를 저장하는 자료구조다.

- **Trie(트라이)**: Key(키)를 앞에서부터 한 글자씩 따라 내려가며 값을 찾는 Tree(트리)다. Trie를 이루는 각 마디를 이 글에서는 Trie Node(트라이 노드)라고 부른다. Network 참여자인 Node와 구분하기 위해서다. 맨 위 Trie Node를 Root Node(루트 노드), 값이 달린 맨 아래 Trie Node를 Leaf Node(잎 노드)라고 한다.

Ethereum은 State Trie를 Merkle Patricia Trie(머클 패트리샤 트라이, 이하 MPT)로 구현한다. MPT는 두 구조를 합친 것이다.

- **Patricia Trie**: Address 문자열이 그대로 경로가 되는 Trie다. 데이터는 Leaf Node에 있고, 앞부분이 같은 Address들은 경로를 공유한다.

- **Merkle Tree**: Leaf Node에는 데이터의 Hash를, 중간 Trie Node에는 자식들의 Hash를 다시 Hash한 값을 붙인다. 이를 Root Node까지 반복한다. Root Node의 Hash를 Root Hash(루트 해시)라고 한다. 데이터가 하나라도 바뀌면 Root Hash가 달라지므로, 큰 Tree 전체를 Root Hash 하나로 검증할 수 있다.

State Trie의 Root Hash를 State Root(상태 루트)라고 한다. State Root는 Block Header(블록 헤더)에 기록된다. Block Header는 Block의 요약 정보를 담은 부분으로, 이전 Block의 Hash, Transaction 목록의 Root Hash, State Root 등이 들어 있다. Transaction 목록 자체는 Block Body(블록 본문)에 있다.

중간 Trie Node는 두 종류이고, 번갈아 나온다.

| 종류 | 형태 | 역할 |
|---|---|---|
| Branch Node | 17개 항목 [v0, v1, ..., vf, Value] | 다음 한 글자(0부터 f)에 따라 갈라진다. v_i는 해당 자식 Trie Node의 Hash이고, 자식이 없으면 Null이다. |
| Extension Node | 2개 항목 [Key, Path] | Path는 후손들이 공유하는 공통 Prefix(접두사)이고, Key는 유일한 자식 Trie Node의 Hash다. |

**저장 방식.** 각 Trie Node는 자기 데이터로 계산한 Hash로 식별된다. 즉 Hash가 Key이고 데이터가 Value(값)다. 그래서 MPT는 Key로 Value를 저장하고 찾는 Key-Value Database(DB)로 구현할 수 있다. 이 글에서는 Hash가 hashX인 Trie Node의 데이터를 B(hashX)로 쓴다.

**갱신 방식.** Account가 갱신되면 기존 Trie Node를 고치지 않는다. 새 Hash와 새 데이터를 가진 Trie Node를 만들어 DB에 덧붙인다. 부모 Trie Node도 같은 방식으로 새로 만들어지고, 새 Root Node가 생길 때까지 이어진다. 이전 Block의 Root Node와 그 후손은 그대로 남는다.

**⇒ 과거 Block의 State Root에서 출발하면 그 시점의 State Trie를 다시 찾아갈 수 있다. 대신 저장 공간이 많이 든다.**

위 설명은 논문의 단순화를 따른 것이다. 실제 Ethereum은 다음이 다르지만, 뒤에 나올 Proof의 원리는 같다.

- 경로는 Address 문자열이 아니라 Address의 Hash다. 남은 경로와 Account 값을 함께 담는 Leaf Node가 따로 있다([Merkle Patricia Trie](https://ethereum.org/developers/docs/data-structures-and-encoding/patricia-merkle-trie/)).

- 논문은 EOA의 StorageRoot와 CodeHash를 Null이라고 적지만, 실제 값은 빈 Trie의 Root Hash와 빈 Code의 Hash다([Ethereum Accounts](https://ethereum.org/developers/docs/accounts/)).

### Merkle Proof와 Void Proof

State Root만 있으면, State Trie 전체가 없어도 "어떤 Account가 그 Block에 있었는가"와 "없었는가"를 검증할 수 있다. 이 두 검증 수단을 Proof(증명)라고 한다. Ethanos는 이 두 Proof로 지워진 Account를 되살린다.

**Merkle Proof(머클 증명, 존재 증명).** 어떤 Account의 Merkle Proof는 Root Node부터 그 Account까지 경로에 있는 모든 Trie Node 데이터의 목록이다. Verifier는 다음 순서로 확인한다.

1. 아래쪽 Trie Node부터 데이터의 Hash를 다시 계산한다.

2. 계산한 Hash가 부모 Trie Node에 적힌 Hash와 같은지 Root Node까지 확인한다.

3. 마지막에 다시 계산한 Root Hash가 Block Header의 State Root와 같은지 확인한다.

모두 같으면, 그 Account가 그 Block에 그 데이터로 존재했다는 것이 증명된다. 중간 데이터를 하나라도 조작하면 같은 Root Hash를 만들 수 없기 때문이다.

앞 예시에서 a5(Address 0xd815fc)의 Merkle Proof는 다음 다섯 개의 Trie Node 데이터다. 경로는 d → 81 → 5 → fc다. `{a: hashB, d: hashC}`는 Branch Node에서 Null이 아닌 항목만 적은 것이다.

```
B(hashA)     = {a: hashB, d: hashC}        Branch Node
B(hashC)     = [hashE, 81]                 Extension Node
B(hashE)     = {3: hashH, 5: hashI}        Branch Node
B(hashI)     = [hash(a5), fc]              Extension Node
B(hash(a5))  = {balance: 32.01, nonce: 30} Leaf Node (Account 데이터)
```

**Void Proof(부재 증명).** 같은 방식으로 어떤 Account가 없다는 것도 증명할 수 있다. Address 0xa7ec6b인 Account가 σ_i에 없다는 것을 보이려면 다음 세 개를 제시한다.

```
B(hashA) = {a: hashB, d: hashC}
B(hashB) = [hashD, 7]
B(hashD) = {d: hashF, f: hashG}
```

Verifier는 세 Trie Node의 Hash를 다시 계산해 Proof가 State Root와 이어지는지 확인한다. 그다음 B(hashD)에 Key e가 없다는 것을 본다. 0xa7e로 시작하는 Account가 σ_i에 없다는 뜻이다.

## Problem

### Full Node가 되는 방법

| 용어 | 의미 |
|---|---|
| Full Node | Transaction을 스스로 완전히 검증할 수 있는 Node |
| Light Node | 스스로 완전히 검증하지 못하고, Transaction 전송과 검증을 다른 Full Node에 맡기는 Node |
| Archive Node | 과거 모든 시점의 State Trie까지 보관하는 Node |

Transaction을 검증하려면 현재 State가 있어야 한다. 새 Node가 Network에 처음 참여해 현재 State까지 따라잡는 과정을 Bootstrapping이라고 하고, 현재 State에 도달하는 방법을 Synchronization(동기화)이라고 한다. 논문은 Go Ethereum(이하 Geth)의 두 방식을 설명한다. Geth는 Ethereum Protocol을 Go 언어로 구현한 Software다.

- **Full Sync**: 모든 Block을 내려받고, Genesis Block부터 현재 Block까지 모든 Transaction을 다시 실행한다. 이를 Replay(재실행)라고 한다.

- **Fast Sync**: 모든 Block을 내려받되, Pivot Block(기준 블록)의 State Trie Snapshot(스냅샷, 그 시점 State Trie의 사본)을 내려받고 Pivot Block부터 현재 Block까지의 Transaction만 Replay한다. Pivot Block은 현재 Block보다 64 Block 이전의 Block이다. 오래된 Block일수록 위조하기 어려우므로 검증 필요성이 낮다는 생각에 기반한다.

### Full Node가 되는 비용

2020년 1월 기준 수치는 다음과 같다.

- Ethereum 전체 데이터는 3.6TB를 넘었다.

- Full Sync는 큰 저장 공간과 수 주의 시간이 든다.

- Fast Sync도 약 235GB가 필요하고 약 하루가 걸린다.

저장 공간과 Network 대역폭이 제한된 개인 기기는 Full Node가 되기 어렵다. 그 결과 두 가지 보안 문제가 생긴다.

1. 사용자가 Light Node로 남아, Miner 같은 다른 Full Node나 중앙 서비스에 검증을 맡기게 된다. 이렇게 맡기면 금융 사기나 Transaction 검열에 취약해진다.

2. Full Node와 Miner의 수가 적으면 Network 자체가 조작에 취약해진다.

**⇒ 목표는 Full Node가 되는 데 꼭 필요한 데이터를 줄이는 것이다.**

### 병목은 State Trie

Fast Sync의 235GB 가운데 State Trie는 70GB 이상으로 추정된다. 저자들이 Trie Node 수(약 4억 7,500만 개)에 평균 Trie Node 크기(약 150 Byte)를 곱해 약 71GB로 계산한 값이다. 나머지는 대부분 Transaction Data다.

크기만 보면 Transaction Data가 더 크다. 그런데 동기화 시간을 잡아먹는 것은 State Trie다.

- **State Trie**: Trie Node를 Hash로 찾아야 하므로, DB 접근 위치가 무작위로 흩어진다. 그래서 순회, 전송, 재구축이 모두 Disk Input/Output(디스크 입출력)에 묶인다.

- **Transaction Data**: Block의 Transaction Index(트랜잭션 색인)를 써서 묶음으로 빠르게 내려받을 수 있다.

논문의 실험에서 1GB를 내려받는 데 걸리는 시간은 State Trie가 약 475초, 나머지 데이터가 234에서 257초다. State Trie가 약 2배 느리다.

State Trie는 계속 커진다는 점도 문제다. 2020년 1월 Account 수는 8,500만 개를 넘었고, 하루 5만에서 15만 개씩 늘고 있었다.

### 관찰: 대부분의 Account는 쓰이지 않는다

논문은 Genesis Block부터 800만 번째 Block까지 Account 활동을 추적했다.

- **Active Account(활성 계정)**: 해당 기간에 Transaction을 보내거나, 받거나, Block을 채굴한 Account

- **Dormant Account(휴면 계정)**: 해당 기간에 쓰이지 않은 Account

**관찰 1. Active Account는 소수다.** 최근 1주 기준 Active Account는 전체의 약 3%, 최근 1달 기준은 약 5%다. 어느 기준으로 보아도 95% 이상이 Dormant Account다.

**관찰 2. 한번 쓰인 Account는 곧 다시 쓰인다.** Account마다 연속한 두 갱신 사이의 평균 간격을 구해 분류하면 다음과 같다. 논문은 이를 "갱신된 Account가 1주 안에 다시 갱신될 확률이 76%"라는 식으로 해석한다.

| 평균 갱신 간격 | 1일 이내 | 1주 이내 | 2주 이내 | 1달 이내 | 6개월 이내 |
|---|---|---|---|---|---|
| Account 비율(%) | 62.3 | 76.0 | 82.4 | 89.0 | 98.4 |

두 관찰에서 방향이 나온다.

- Dormant Account를 State Trie에서 빼면 크기가 크게 줄어든다.

- 최근 쓰인 Account는 곧 다시 쓰이므로, 이번 주기의 Transaction 대부분은 직전 주기의 State만으로 처리할 수 있다.

- 한 주기에 들어가는 Transaction 수에는 상한이 있으므로, 한 주기의 Active Account 수와 그 Account만 담은 State Trie의 크기도 시간이 지나도 계속 커지지 않는다.

**⇒ 조건은 하나다. State를 줄여도, Bootstrapping 이후의 모든 Transaction은 여전히 완전히 검증할 수 있어야 한다.** 이 조건 아래 풀어야 할 질문은 세 가지다.

1. **어떻게 걸러 낼까.** MPT를 순회하며 Dormant Account를 찾아 지우는 것은 비용이 매우 크다.

2. **다시 필요해지면 어떻게 복원할까.** 빠진 Account의 State를 State Trie 없이 믿을 수 있게 되살려야 한다.

3. **줄어든 State로 어떻게 동기화할까.**

## 기존 접근

State Trie를 줄이려는 시도는 있었다.

| 접근 | 내용 | Ethanos와의 차이 |
|---|---|---|
| [EIP-158](https://eips.ethereum.org/EIPS/eip-158), [EIP-161](https://eips.ethereum.org/EIPS/eip-161) | Nonce와 Balance가 0이고 Code가 없는 Empty Account(빈 계정)를 삭제한다. EIP는 Ethereum Improvement Proposal(이더리움 개선 제안)이다. | 빈 Account만 대상이다. |
| [EIP-168](https://github.com/ethereum/EIPs/issues/168) | Balance가 Transaction Fee보다 적은 Dust Account(먼지 계정)를 제거한다. | 채택되지 않았다. |
| Vault | Algorand(알고랜드) Blockchain용이다. Transaction에 만료 기한을 두어, Balance가 0이고 마지막 Transaction이 만료된 Account를 안전하게 제거한다. | 논문은 Vault가 Algorand에만 적용 가능하다고 본다. |
| Utreexo | Bitcoin의 UTXO 집합을 Hash 기반 Accumulator(누산기)로 요약한다. Proof가 있으면 전체 UTXO 집합 없이 검증한다. | 발상이 유사하다. 최근 UTXO만 보관하는 것이 Active Account만 보관하는 것에 대응한다. |

**⇒ EIP와 Vault는 Dormant Account를 대상으로 하지 않는다. Ethanos는 Account의 95% 이상을 차지하는 Dormant Account를 걸러 내고, 필요하면 복원한다.**

## Ethanos

### 핵심 아이디어

Ethanos는 Dormant Account를 찾아 지우지 않는다. 대신 **주기마다 빈 State Trie에서 시작해, 그 주기에 쓰인 Account만 다시 채운다.** 채워지지 않은 Account는 자연스럽게 빠진다.

| 질문 | 해결 방법 | 해당 절 |
|---|---|---|
| 어떻게 걸러 낼까 | 빈 State Trie에서 다시 채우기 | Sweep |
| 어떻게 복원할까 | 과거 State Root에 대한 Merkle Proof와 Void Proof를 담은 Restore Transaction | Dormant Account Restoration |
| 어떻게 동기화할까 | 최근의 작은 State Trie 두 개만 받기 | Compact Sync |

용어는 다음과 같다.

| 용어 | 의미 |
|---|---|
| Epoch(에폭) λ | Sweep 주기를 이루는 Block 수. 1주 주기라면 약 40,320 Block (Block 간격 15초 기준) |
| Checkpoint(체크포인트) | Epoch의 마지막 Block |
| Sweep(스윕) | Dormant Account를 State Trie에서 걸러 내는 동작 |
| Current Trie(현재 트라이) | 현재 Epoch에서 빈 상태로 시작해 채워 가는 State Trie |
| Cached Trie(캐시 트라이) | 직전 Checkpoint의 State Trie |
| Last Active Checkpoint(마지막 활성 체크포인트) | Account가 원래 Account로서 마지막으로 State Trie에 들어 있던 Checkpoint |
| Restore Transaction(복원 트랜잭션) | 두 Trie 모두에 없는 Account를 Current Trie에 다시 만드는 Transaction |
| Crumb Account(크럼 계정) | Dormant Account가 Receiver일 때, 복원 없이 새로 만들어지는 Account |

### Sweep

**문제 상황: Dormant Account를 찾아 지우는 것은 비용이 매우 큼**

**해결 방법: 지우지 않고, Epoch마다 빈 State Trie에서 다시 채움**

1. 새 Epoch가 시작되면 빈 State Trie를 만듦 → Current Trie

2. 직전 Checkpoint의 State Trie를 보관함 → Cached Trie

3. Transaction에 필요한 Account를 Current Trie에서 먼저 찾음

4. 없으면 Cached Trie에서 찾음. 있으면 Current Trie로 복사한 뒤 갱신함

5. 두 Trie 모두에 없는데 그 Account가 Sender가 되려 하면, 먼저 복원해야 함 (Dormant Account Restoration)

6. Epoch가 끝나면 Current Trie가 새 Cached Trie가 되고, 이전 Cached Trie는 버림

→ 한 Epoch 동안 실제로 쓰인 Account만 Current Trie에 남음. 지우는 작업 없이 Sweep이 이루어짐

예시: 앞의 State Transition 예시를 Ethanos로 옮김. n번째 Epoch가 Block i에서 끝남 (Block i가 Checkpoint). Cached Trie에는 a1부터 a5가 있고, n+1번째 Epoch는 빈 Current Trie로 시작함

- Block i+1: a2가 a4에게 보내고 Miner는 a5 → 세 Account 모두 Current Trie에 없으므로 Cached Trie에서 찾아 복사하고 갱신

- Block i+2: a4가 새 Address a6에게 1 ETH를 보내고 Miner는 a1

    | Account | 찾은 위치 | 처리 |
    |---|---|---|
    | a4 (Sender) | Current Trie | 바로 갱신 |
    | a1 (Miner) | Cached Trie | 복사 후 갱신 |
    | a6 (Receiver) | 두 Trie 모두에 없음 | 새 Account로 생성 |

- 이 시점의 Current Trie에는 a1, a2, a4, a5, a6만 있음. 이번 Epoch에 쓰이지 않은 a3는 들어 있지 않음

왜 Cached Trie를 하나만 두는가?

- Full Node가 Trie 하나로 Bootstrapping할 수 있어 내려받는 크기가 줄어듦

- 모든 Full Node가 같은 방식으로 동작함

- 연속한 Checkpoint의 State Trie에는 겹치는 Active Account가 많아, 여러 개를 두는 것이 비효율적임

### Dormant Account Restoration

두 Trie 모두에 없는 Account가 Transaction에 등장하면, 그 역할에 따라 처리가 다름

- **Sender인 경우**: 먼저 Restore Transaction을 보내야 함. Restore Transaction은 그 Account를 마지막 State 그대로 Current Trie에 다시 만듦

- **Receiver인 경우**: 복원하지 않음. 존재하지 않는 Address로 값을 보내면 새 Account가 만들어지는 Ethereum의 규칙을 그대로 씀

    - Receiver가 정말 새 Address인지, 사실은 Dormant Account인지 구별하지 않고 똑같이 새 Account를 만듦

    - Dormant Account 자리에 새로 만들어진 Account가 Crumb Account

    - Crumb Account는 Balance가 충분하면 그대로 Sender가 될 수 있음. 부족하면 Restore Transaction을 보내야 하고, 이때 Crumb Account들이 원래 Account와 합쳐짐

    - Crumb Account는 여러 Epoch에 걸쳐 여러 개 생길 수 있음

→ 값을 받기만 하는 Account까지 복원을 요구하지 않으므로 Restore Transaction의 빈도가 줄어듦

#### Restore Transaction

**문제 상황: 빠진 Account의 과거 State를, State Trie 없이 믿을 수 있게 되살려야 함**

**해결 방법: 과거 Checkpoint의 State Root에 대한 Proof를 Transaction에 담음**

세 역할

| 역할 | 하는 일 |
|---|---|
| Owner(소유자) | 자신의 Account가 Dormant 상태인지 판단하고 복원을 요청함. 마지막 Transaction 이후 두 Epoch가 지났는지 확인하거나, 현재 Epoch에서 자신의 Account에 접근할 수 있는지 조회함 |
| Archive Node | 과거 Checkpoint들의 State Trie에서 Proof를 모아 Restore Transaction을 만들어 보냄 |
| Miner와 Verifier | Proof를 검증하고 Current Trie에 Account를 만듦 |

- Archive Node가 만드는 이유: 일반 Ethanos Full Node는 자신이 Bootstrapping한 Checkpoint 이전의 State Trie를 갖고 있지 않음. Last Active Checkpoint가 그보다 오래되었다면 Proof를 만들 수 없음. 그렇지 않은 경우에는 Full Node가 직접 만듦

담기는 Proof (Last Active Checkpoint를 k, 최신 Checkpoint를 n이라고 함. k < n)

| Proof | 대상 Checkpoint | 증명하는 것 |
|---|---|---|
| Merkle Proof | k | Account가 Checkpoint k에 그 State로 존재했음 |
| Void Proof | k+1부터 n-1까지 각각 | 그 이후로는 없었음. 즉 k가 정말 마지막이었음 |

- Checkpoint n에 대한 Void Proof는 필요 없음. Cached Trie로 직접 확인할 수 있음

- 검증에는 각 Checkpoint Block Header의 State Root만 쓰임

왜 더 유리한 과거 State로 되돌릴 수 없는가?

- Balance가 더 많았던 과거 Checkpoint j(j < k)의 State로 복원하려 한다고 하자

- j가 마지막이었음을 보이려면 Checkpoint k에 대한 Void Proof를 내야 함

- k에는 Account가 실제로 존재하므로 이 Proof는 통과하지 못함

#### Bloom Filter

**문제 상황: n과 k의 차이가 커지면 Void Proof가 많아져 Restore Transaction이 커짐**

**해결 방법: 각 Checkpoint의 Block Header에 Bloom Filter(블룸 필터)를 저장함**

- Bloom Filter: 어떤 원소가 집합에 들어 있는지를 적은 공간으로 판정하는 확률적 자료구조

    - 들어 있는 원소에 대해서는 항상 "있다"고 답함

    - 들어 있지 않은 원소에 대해서도 낮은 확률로 "있다"고 답할 수 있음. 이것이 False Positive(거짓 양성)

    - → "없다"는 답은 항상 맞음

- 어떤 Checkpoint의 Bloom Filter가 "없다"고 답하면, 그 Checkpoint의 Void Proof를 생략함

- 대신 Verifier는 Restore Transaction을 실행할 때 Bloom Filter로 부재를 직접 확인해야 함

- 논문은 False Positive 확률을 약 10%로 설정해 Void Proof의 90%를 생략함

#### Crumb Account의 Nonce

**문제 상황: Crumb Account의 Nonce를 0으로 두면 Replay Attack(재전송 공격)이 가능함**

- 일반 Ethanos Full Node는 모든 Checkpoint의 State Trie를 갖고 있지 않음 → 새로 만들어지는 Account가 정말 새 Account인지 Crumb Account인지 구별할 수 없음

- Nonce가 0이면, 공격자가 원래 Account가 과거에 보냈던 Transaction을 다시 보냈을 때 Nonce가 맞아 다시 실행될 수 있음

**해결 방법: 모든 새 Account의 초기 Nonce를 Block 번호에 비례하게 정함**

```
초기 Nonce = 현재 Block 번호 × (Account당 Block당 평균 Transaction 수)
```

- 논문은 이 값이 과거에 등장한 어떤 Nonce보다 항상 크다고 설명하며 [EIP-169](https://github.com/ethereum/EIPs/issues/169)를 근거로 듦

- 주의: 논문 표기를 그대로 따르면 "항상 크다"는 보장이 성립하지 않음 (논문에 없는 판단)

    - EIP-169는 평균이 아니라 Account당 Block당 최대 Transaction 수(`MAX_TXS_PER_ACCT_PER_BLOCK`, 예시 값 64)를 곱하고, Nonce가 Block 번호에 비례한 상한을 넘지 못하게 하는 규칙을 함께 둠

    - 평균을 쓰면, 평균보다 Transaction을 많이 보낸 Account의 기존 Nonce가 초기값보다 클 수 있음

#### Crumb Account 병합과 Restored Flag

- Crumb Account가 있는 Account를 복원할 때는 Last Active Checkpoint의 Account와 Crumb Account들을 합침

- 그래서 Restore Transaction에는 Crumb Account가 있는 Checkpoint마다 Merkle Proof가 추가됨

- 연속한 여러 Checkpoint에 Crumb Account가 있으면 마지막 Checkpoint의 Balance만 합침. 그 Balance에 앞선 Checkpoint들의 활동이 이미 반영되어 있기 때문

**문제 상황: 이미 복원된 Account를 Crumb Account로 속이면 Balance가 두 번 더해짐**

- Merkle Proof가 두 개(P1, P2) 있는 Restore Transaction은 "P1은 Last Active Checkpoint의 Account, P2는 Crumb Account"로 해석됨

- 그런데 P2가 사실은 P1을 이미 복원한 Account라면, P1의 Balance가 한 번 더 더해짐

**해결 방법: Account State에 1 Bit(비트)짜리 Restored Flag(복원 표시)를 추가함**

- 기본값은 0이고, 복원될 때 Verifier가 1로 바꿈

- P2의 Flag가 1이면, 이미 복원된 Account를 Crumb Account로 속이는 시도로 보고 거부함

유효한 Restore Transaction의 형태: 각 Checkpoint에서 Account는 네 상태 중 하나임

| 기호 | 상태 | 판정 기준 |
|---|---|---|
| a | Active | Merkle Proof가 있고 Restored Flag가 0 |
| r | Restored | Merkle Proof가 있고 Restored Flag가 1 |
| c | Crumb | Merkle Proof가 있고 Restored Flag가 0이며, 앞쪽에 Active나 Restored 상태가 있음 |
| v | Void | Account가 없음 |

- a와 c는 Restored Flag만으로는 구별되지 않고, 상태 열에서의 위치로 구별됨

- 유효한 상태 열은 다음 Regular Expression(정규 표현식)으로 표현됨. 시간 순서대로 왼쪽에서 오른쪽으로 읽음. `+`는 1번 이상, `*`는 0번 이상, `|`는 둘 중 하나

```
(a+|r+)v+(c+v)*v*
```

- 이 형태에 맞지 않는 Restore Transaction은 거부됨 → "Restore Transaction은 유효하지 않은 State를 만들 수 없다"

- `avvvcccvv`: 유효함. Active 뒤에 Void가 이어지고, Crumb 구간이 나온 뒤 다시 Void

- `avvvvvrvv`: 유효하지 않음. Void 뒤에 Restored가 나옴

- `aav`: 유효함. a가 연속하면 마지막 a에서 복원함

#### 복원 예시

Account X의 이력 (현재는 Epoch 8, 최신 Checkpoint는 7)

1. Epoch 2까지 X는 일반 Account로 쓰임 → Checkpoint 2의 State Trie에 있음 (Last Active Checkpoint k = 2)

2. Epoch 3, 4 동안 쓰이지 않음 → Checkpoint 3, 4의 State Trie에 없음

    - Epoch 3 동안은 Cached Trie(Checkpoint 2)에 있어 바로 쓸 수 있음

    - Epoch 4부터는 두 Trie 모두에 없음 → Dormant 상태

3. Epoch 5에 누군가 X에게 값을 보냄 → 복원 없이 Crumb Account가 만들어짐 → Checkpoint 5의 State Trie에 Crumb Account가 있음

4. Epoch 6, 7 동안 쓰이지 않음 → Checkpoint 6, 7의 State Trie에 없음

5. Epoch 8에 X의 Owner가 Transaction을 보내려 함 → X는 Current Trie에도 Cached Trie(Checkpoint 7)에도 없음 → Restore Transaction이 필요함

Restore Transaction에 담기는 것 (k = 2, n = 7)

| Checkpoint | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|
| 상태 | a | v | v | c | v | v |
| Proof | Merkle Proof | Void Proof | Void Proof | Merkle Proof | Void Proof | 없음 (Cached Trie로 확인) |

- Checkpoint 3, 4, 6의 Void Proof는 그 Checkpoint의 Bloom Filter가 "없다"고 답하면 생략함

- 상태 열 `avvcvv`는 `(a+|r+)v+(c+v)*v*`에 맞음 → 유효함

- 결과: Current Trie에 X가 다시 만들어짐. Balance는 Checkpoint 2의 Balance와 Checkpoint 5 Crumb Account의 Balance를 합친 값이고, Restored Flag는 1

### Compact Sync

**문제 상황: 줄어든 State로 어떻게 동기화할 것인가**

**해결 방법: 최근 State Trie 두 개만 받고, 오래된 Transaction은 받지 않음**

| 방식 | 대응하는 Geth 방식 | 동작 |
|---|---|---|
| Archive Sync | Full Sync | 모든 Block을 내려받고 Genesis Block부터 모든 Transaction을 Replay함 |
| Compact Sync | Fast Sync | Pivot Block의 State Trie를 내려받고 Pivot Block부터 현재까지만 Replay함 |

Compact Sync가 Fast Sync와 다른 점

1. 최신 Checkpoint의 State Trie도 내려받음 → Cached Trie로 쓰기 위해서

2. Genesis Block부터 Pivot Block까지의 Transaction을 내려받지 않음 → 어차피 Replay하지 않기 때문. 필요하면 Archive Node에 요청함

왜 이것으로 충분한가?

- State Trie를 두 개 받지만, 둘 다 한 Epoch의 Active Account만 담고 있어 작음 (실험에서 약 220MB)

- 이후의 Transaction에 필요한 Account는 Current Trie나 Cached Trie에 있거나, Restore Transaction의 Proof로 복원됨. Proof 검증에는 Checkpoint Block Header의 State Root만 있으면 됨

- → 새 Node는 전체 State 없이 Bootstrapping하고, 그 이후의 모든 Transaction을 완전히 검증할 수 있음

### Restore Transaction Fee

논문은 구체적 규칙 대신 방향만 제시하며, 이 부분은 실험하지 않았다.

- 사용자는 Account의 가치가 Fee보다 크면 Fee를 내고 복원함

- 과거 State Trie를 보관하며 Restore Transaction을 만들어 주는 Archive Node도 Fee를 받아야 함

- Archive Node와 Miner의 수가 늘면 Fee가 내려가고, 줄면 올라감

## 평가

### 실험 설정

| 항목 | 값 |
|---|---|
| 대상 구간 | Ethereum 700만 번째 Block부터 730만 번째 Block (300,000 Block, 2019년 초 약 2개월) |
| Transaction 수 | 30,575,237 |
| 갱신된 Account 수 | 4,588,065 |
| 구현 기반 | Geth v1.9 |
| Epoch | 40,320 Block (약 1주), Checkpoint 7개 |
| 추가된 Restore Transaction | 198,121 |
| Bloom Filter 크기 | Checkpoint Block당 512KB |

- 700만 번째 Block을 Genesis Block으로 삼아 Ethanos Blockchain을 새로 시작한 실험임. 비교 대상인 Geth도 같은 지점에서 시작함

- 300,000번째 Block 시점에 1주 Active Account는 약 100만 개이고, 비율은 23.5%

- 제약

    - 모든 Transaction의 전송 값을 0으로 둠 (빈 State에서 시작하므로 Balance 부족 오류를 피하기 위해)

    - Sender의 Private Key를 알 수 없어, 모든 Transaction을 대신 보내는 Delegated Transaction(대리 트랜잭션)으로 만듦

    - CA를 EOA처럼 취급하고, Smart Contract가 실행 중에 일으키는 Internal Transaction(내부 트랜잭션)은 제외함

### 저장 크기

- **Archive Sync** (300,000번째 Block까지): 전체 52,031.68MB → 46,676.61MB. 약 5.3GB(10.3%) 줄었고, 대부분 Trie Node 감소(46,333.43MB → 40,342.62MB)에서 옴

    - 이유: Geth는 모든 Account(약 450만 개)를 담은 큰 Trie 하나를, Ethanos는 Epoch마다 Active Account(약 100만 개)만 담은 작은 Trie를 유지함. Trie가 작으면 Account까지의 깊이가 얕아져, 갱신할 때 새로 덧붙는 Trie Node 수가 적음

- **Fast Sync와 Compact Sync** (7번째 Checkpoint). Geth의 Compact Sync는 Geth에도 Pivot Block 이전 Transaction을 받지 않는 방식을 적용한 값임

    | 구분 | Geth (MB) | Ethanos (MB) |
    |---|---|---|
    | Fast Sync 전체 | 6,020.87 | 5,966.79 |
    | Compact Sync 전체 | 977.67 | 374.23 |
    | State Trie | 약 832 | 220.03 |

    - Fast Sync에서는 차이가 거의 없음. 300,000 Block만 지난 시점이라 Transaction Data가 Trie보다 훨씬 크기 때문

    - Compact Sync에서는 Ethanos가 Geth의 38% 크기

- **가장 중요한 결과**: Ethanos의 State Trie는 Checkpoint가 늘어나도 약 220MB 수준에서 유지됨. 1주 Active Account 수가 약 100만 개 수준으로 유지된다는 조건 아래의 결론임

- Epoch 끝 무렵에 Compact Sync를 하면 직전 Checkpoint의 State Trie 220MB와 Compact Sync 저장량 374MB를 합쳐 594MB

### 동기화 시간

7번째 Checkpoint 기준 (각 15회 측정 평균)

- Ethanos Fast Sync는 Geth Fast Sync보다 17% 짧음. 데이터 크기는 거의 같은데도 그러함

- Ethanos Compact Sync는 Geth Compact Sync보다 75% 짧음

- 두 경우 모두 시간 차이는 약 290초, State Trie 크기 차이는 약 610MB → State Trie 내려받기는 약 475 sec/GB

- 같은 시스템 안에서 Fast Sync와 Compact Sync를 비교하면, 나머지 데이터는 234에서 257 sec/GB

- → State Trie가 병목이라는 것이 수치로 확인됨

### Restore Transaction의 부담

- **빈도**: Restored Account는 전체의 5% 미만이고 Crumb Account보다 훨씬 적음. 많은 Dormant Account가 복원 없이 Crumb Account로 다시 쓰였다는 뜻

- **Overhead(추가 비용)**

    | 항목 | 일반 Transaction | Restore Transaction |
    |---|---|---|
    | 수 | Epoch별 전체의 98.5% 이상 | Epoch별 전체의 1.5% 미만 |
    | 크기 | 0.12KB로 일정 | 3KB 이상, 편차가 큼 |
    | 실행 시간 | 평균 1ms 미만 | 더 긺 |

    - 크기: Merkle Proof 하나가 약 3KB이고 Void Proof가 여러 개 붙음. Bloom Filter가 크기를 절반 이상 줄임

    - 실행 시간: Last Active Checkpoint에 닿을 때까지 Checkpoint마다 Bloom Filter를 조회하고 Proof를 검증해야 함

    - 7번째 Epoch 기준으로 한 Block은 평균 일반 Transaction 248개(99.2ms)와 Restore Transaction 2.7개(10.5ms)를 실행함 → 실행 시간이 약 10% 늘어남. Block 간격 15초에 비하면 작음

### Epoch 길이

Epoch가 길면 State Trie가 커져 Bootstrapping 부담이 늘고, 대신 Restore Transaction은 줄어듦. 대상 구간을 864,000 Block으로 늘려 비교한 결과는 다음과 같음

| Epoch 길이 | Active Account가 가장 많았던 마지막 Epoch의 State Trie |
|---|---|
| 3일 | 138MB |
| 1주 | 278MB |
| 2주 | 454MB |
| 1달 | 817MB |

- State Trie 크기는 Epoch 길이에 비례하지 않고 더 완만하게 늘어남. 3일에서 1달로 길이가 10배가 되어도 크기는 5.9배. Transaction이 최근에 쓰인 Account에 쏠려 있기 때문

- Restore Transaction 수도 비례해서 줄지 않음. 1달 Epoch의 Restore Transaction 수는 3일 Epoch의 약 1/5

- 논문의 판단: 1달 Epoch가 비용 대비 효과가 좋아 보이지만 모바일 기기에는 817MB가 무거우므로, 당분간은 1주 Epoch가 적절함. Trie 크기가 기준값에 도달하면 Checkpoint를 만드는 가변 Epoch도 대안임

## 한계와 주의

- **Contract Account**: 실험에서 다루지 않았고, 설계 방향만 제시함

    - 원리는 같지만 Restore Transaction에 Last Active Checkpoint 시점의 Contract State Snapshot이 들어가야 해서 커질 수 있음. 소유 기록 하나가 52 Byte(Address 20 + Balance 32)인 Token(토큰) Contract라면 사용자 100만 명은 52MB

    - 논문은 서비스 중인 Contract는 계속 갱신되어 Dormant 상태가 되기 어렵고, 서비스가 끝난 Contract는 다시 복원될 가능성이 낮다고 봄

    - Snapshot을 줄이기 위해 Ethanos의 발상을 Storage에도 재귀적으로 적용해, 필요한 기록만 복원하는 방법을 제안함. 구체적 Protocol은 없음

    - 주의: 논문은 "CA의 Address는 배포한 Account의 Address와 Nonce로 정해지므로 같은 Address에 새 Contract를 배포할 수 없고, 따라서 Crumb CA는 Contract State 없이 Balance만 가진다"고 주장함. 이 전제는 일반 배포 방식에만 맞음. [EIP-1014](https://eips.ethereum.org/EIPS/eip-1014)의 CREATE2는 배포자, Salt(임의 값), 초기화 Code의 Hash로 Address를 정하므로 Nonce와 무관함. CREATE2는 2019년 2월(Block 7,280,000)에 활성화되어 실험 구간 안에 있음 (논문에 없는 판단)

- **Block Header**: State Trie와 Transaction을 줄이고 나면 Block Header(2020년 1월 기준 약 3GB)가 병목이 될 수 있음

    - 논문의 제안: Non-Interactive Proofs of Proof-of-Work(비대화형 작업 증명의 증명, 이하 NIPoPoW)를 활용해 일부 Block Header만 받음. Checkpoint를 정확한 Epoch 경계 대신 경계 근처의 Super Block(슈퍼 블록)으로 정함. Super Block은 Block Hash가 Target(목표값)의 1/2^μ 이하로 나와, 요구량보다 많은 작업을 증명한 Block임([Kiayias et al.](https://eprint.iacr.org/2017/963))

    - 논문의 계산: 2020년 1월(910만 Block)에는 Block Header 226개, 약 84KB(226 × 370 Byte). Block이 1억 개여도 0.92MB

    - 이 제안은 실험으로 검증되지 않음

- **"1GB 미만" 결론**: 논문은 Compact Sync 크기(약 600MB)에 위 NIPoPoW 추정치를 더해 1GB 미만으로 Bootstrapping할 수 있다고 결론지음

    - 주의: 이 계산에는 Checkpoint Block Header에 저장되는 Bloom Filter가 빠져 있음 (논문에 없는 계산)

    - 실험과 같은 크기(Checkpoint당 512KB)라면, Checkpoint 226개에서 약 113MB(226 × 512KB) → 합계 약 700MB로 1GB 미만

    - 1억 Block에 해당하는 약 2,480개에서는 약 1.2GB(2,480 × 512KB) → Bloom Filter만으로 1GB를 넘음

- **초기 Nonce**: 논문 표기(평균)를 그대로 따르면 Replay Attack 방지가 보장되지 않음 (Crumb Account의 Nonce 참고)

- **실험 규모**: 빈 State에서 시작한 300,000 Block임. 이 구간의 1주 Active Account 비율은 23.5%로, 원래 Ethereum의 700만 번째 Block 시점 비율(3% 미만)과 다름. 논문은 실제 효과가 더 클 것이라고 예상하지만 측정값은 아님

- **Archive Node 의존**: 오래된 Account를 복원하려면 과거 Checkpoint의 State Trie를 가진 Archive Node가 있어야 함. Archive Node가 충분히 유지되는지는 Fee 논의에 달려 있고, 실험되지 않음

## 논문 이후

2026년 11월 기준이다.

- **합의 방식**: Ethereum은 2022년 9월 [The Merge(병합)](https://ethereum.org/roadmap/merge/)로 Proof of Stake로 전환했다. Miner는 Validator(밸리데이터)로 대체되었고, PoW Block Reward는 없다. Block은 12초 단위로 만들어진다.

- **Fee**: 2021년 8월 [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559) 이후 Fee 가운데 Base Fee(기본 수수료)는 소각되고, Priority Fee(우선 수수료)만 Block 생성자에게 간다.

- **동기화**: Geth는 v1.10.0에서 Snap Sync를 도입했고, v1.10.4부터 기본값으로 쓴다. Fast Sync는 v1.10.14에서 제거되었다([Geth FAQ(Frequently Asked Questions)](https://geth.ethereum.org/docs/faq)).

- **State Expiry(상태 만료)**: Ethanos처럼 Dormant Account를 State에서 내보내는 Protocol 수준의 기능은 Ethereum에 도입되지 않았다. [ethereum.org의 Roadmap 문서](https://ethereum.org/roadmap/statelessness/)는 State Expiry를 연구 단계로 설명한다. 오래된 Block 이력을 내려놓는 History Expiry(이력 만료)는 이와 다른 개념이며, 2025년 7월에 [일부가 적용되었다](https://blog.ethereum.org/2025/07/08/partial-history-exp).

## 결론

Ethanos는 Account-based Blockchain에서 새 Node가 Full Node가 되는 비용을 줄인다. 출발점은 두 관찰이다. Account의 95% 이상은 쓰이지 않고, 한번 쓰인 Account는 곧 다시 쓰인다. 그래서 Dormant Account를 찾아 지우는 대신, Epoch마다 빈 State Trie에서 시작해 그 Epoch에 쓰인 Account만 채운다. 빠진 Account는 과거 State Root에 대한 Merkle Proof와 Void Proof를 담은 Restore Transaction으로 되살리고, 값을 받기만 할 때는 복원 없이 Crumb Account를 만든다. Bloom Filter는 Void Proof를 줄이고, Block 번호 기반 초기 Nonce와 Restored Flag는 Replay Attack과 이중 복원을 막는다. 새 Node는 최근 State Trie 두 개만 받는 Compact Sync로 동기화한다.

1주 Epoch 실험에서 State Trie는 약 220MB로 유지되었고, Compact Sync 시간은 같은 조건의 Geth보다 75% 짧았다. 대가는 Restore Transaction의 비용과 Archive Node에 대한 의존이다. Contract Account의 복원과 Block Header 축소는 제안 단계이고 실험으로 검증되지 않았다.
