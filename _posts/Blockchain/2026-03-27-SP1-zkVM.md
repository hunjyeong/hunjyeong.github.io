## What is SP1?

SP1(Succinct Processor 1)은 Succinct Labs가 만든 RISC-V 기반 zkVM이다. RISC Zero처럼 **범용 CPU의 실행 자체를 증명**하므로, 개발자는 Circuit을 설계하지 않고 Rust 같은 일반 언어로 프로그램을 작성한다. SP1이 증명하는 것은 다음 사실이다.

> 주어진 프로그램이 특정 입력에 대해 RISC-V 명령어 규칙에 따라 정상적으로 실행되었고, 그 결과로 이 Public Values(공개 값)를 내놓았다.

이 글은 SP1 v6(SP1 Hypercube)를 기준으로 설명한다. SP1은 버전에 따라 내부 증명 시스템이 크게 바뀌었다.

| 버전 | ISA | 증명 시스템 | Field |
|------|-----|-------------|-------|
| SP1 ~ SP1 Turbo (v4, v5) | RV32IM | Plonky3 기반 단변수 STARK + FRI | BabyBear ($$2^{31} - 2^{27} + 1$$) |
| SP1 Hypercube (v6) | RV64IM | 자체 스택 SLOP(Succinct Library of Polynomials) 기반 Multilinear(다변수 선형) 증명 시스템 (Field와 해시 구현은 Plonky3 사용) | KoalaBear ($$2^{31} - 2^{24} + 1$$) |

SP1 Hypercube는 2025년 5월 공개되었고, 2026년 2월 Succinct Prover Network에 통합되어 프로덕션 사용이 시작되었다. Succinct Prover Network는 증명 요청을 올리면 외부 Prover들이 경쟁으로 받아 증명을 생성해 주는 분산 증명 네트워크다. Succinct는 2025년 11월 RTX 5090 GPU 16장으로 Ethereum 블록의 99.7%를 12초 안에, 95.4%를 10초 안에 증명했다고 발표했다. 자세한 내용은 [SP1 문서](https://docs.succinct.xyz/docs/sp1/introduction)에서 확인할 수 있다. Prover Network에서 v5 지원은 2026년 5월 19일에 종료되었으므로, 네트워크 증명을 쓰려면 v6 이상이어야 한다.

### Program과 Script

SP1도 증명 대상과 실행 관리자를 분리한다. RISC Zero의 Guest/Host에 해당하며, SP1 문서에서는 주로 Program과 Script라고 부른다.

- **Program (Guest):** 증명 대상 프로그램이다. Rust로 작성해 RISC-V ELF 바이너리로 컴파일한다.
- **Script (Host):** `ProverClient`로 Program에 입력을 넣고 실행하며, 증명 생성과 검증을 요청한다. 증명은 로컬 CPU/GPU나 Succinct Prover Network에서 생성한다.

## End-to-End Proving Process

1. **Program 작성**

    증명할 로직을 Rust로 작성한다. RISC Zero 글의 예제와 같은 로직을 SP1 API로 옮기면 다음과 같다.

    - **입력:** `sp1_zkvm::io::read()`로 Script에서 데이터를 받는다. 읽은 값은 기본적으로 비공개다.
    - **출력:** `sp1_zkvm::io::commit()`으로 Public Values에 기록한다. RISC Zero의 Journal에 해당한다.

    ```rust
    #![no_main]
    sp1_zkvm::entrypoint!(main);

    pub fn main() {
        // Script에서 입력 받기 (비공개)
        let a = sp1_zkvm::io::read::<u64>();
        let b = sp1_zkvm::io::read::<u64>();

        // 자명하지 않은 인수인지 확인 (0과 1 제외)
        if a < 2 || b < 2 {
            panic!("Trivial factors");
        }

        // 계산 (오버플로우 체크)
        let product = a.checked_mul(b).expect("Overflow");

        // 결과 공개 (Public Values)
        sp1_zkvm::io::commit(&product);
    }
    ```

    Script 쪽 코드는 다음과 같다. v6 SDK는 실행, 설정, 증명 생성이 async(비동기) API이고, `verify`는 동기 함수다.

    ```rust
    use sp1_sdk::prelude::*;
    use sp1_sdk::ProverClient;

    const ELF: Elf = include_elf!("factors-program");

    #[tokio::main]
    async fn main() {
        let mut stdin = SP1Stdin::new();
        stdin.write(&17u64);
        stdin.write(&23u64);

        let client = ProverClient::from_env().await;

        // 증명 없이 실행만 해서 사이클 수 확인
        let (_, report) = client.execute(ELF, stdin.clone()).await.unwrap();
        println!("cycles: {}", report.total_instruction_count());

        // Proving Key/Verifying Key 생성 후 증명
        let pk = client.setup(ELF).await.unwrap();
        let mut proof = client.prove(&pk, stdin).groth16().await.unwrap();

        // Public Values 읽기와 검증
        let product = proof.public_values.read::<u64>();
        client.verify(&proof, pk.verifying_key(), None).expect("verification failed");
    }
    ```

    `verify`의 세 번째 인자는 기대하는 종료 코드(`StatusCode`)다. `None`이면 정상 종료(`StatusCode::SUCCESS`)를 기대한다.

2. **Program 컴파일과 Verifying Key 생성**

    Program은 SP1 전용 Rust Toolchain(`sp1up`으로 설치)으로 RISC-V ELF 바이너리로 컴파일된다. v6의 `sp1up`은 64bit Toolchain을 설치하며, v5 이하의 32bit Toolchain과 호환되지 않는다. `cargo prove build`를 직접 실행하거나, Script 크레이트의 빌드 스크립트에서 `sp1-build`로 컴파일한다. Script는 `include_elf!`로 ELF를 가져온다.

    ```text
    Rust
    ↓
    cargo prove build (또는 sp1-build)
    ↓
    RISC-V RV64IM ELF 바이너리
    ↓
    client.setup(ELF): Program 테이블 등 Preprocessed Trace에 커밋
    ↓
    Proving Key(pk) (Verifying Key(vk)는 pk.verifying_key()로 꺼냄)
    ↓
    vk.bytes32() = On-chain에서 쓰는 Program Verification Key (32byte)
    ```

    v6의 `setup`은 pk 하나만 반환하므로, v5 코드처럼 `let (pk, vk) = ...`로 받지 않는다.

    **Verifying Key(vkey)**는 RISC Zero의 Image ID 역할을 한다. Verifier는 이 값으로 어떤 프로그램이 실행되었는지 식별하며, Program 코드가 바뀌면 vkey도 바뀐다.

3. **실행과 Shard 분할**

    Script의 Executor가 RISC-V 바이너리를 실행하며 명령어마다 Event(이벤트)를 기록한다. 예를 들어 `add` 명령은 ADD 이벤트를, 메모리 접근은 메모리 이벤트를, SHA-256 같은 Precompile 호출은 해당 Precompile 이벤트를 남긴다. 이렇게 모은 Execution Record(실행 기록)가 이후 Trace 테이블의 재료가 된다.

    실행이 길면 한 번에 증명할 수 없으므로, SP1은 실행을 **Shard** 단위로 나눈다. RISC Zero의 Segment에 해당한다. Hypercube에서 Shard의 경계는 고정된 명령어 수가 아니라 Trace 테이블의 면적(원소 수)과 높이 임계값으로 정해지며, 기본 설정의 높이 임계값(`HEIGHT_THRESHOLD`)은 $$2^{22}$$행이다. [SP1 Hypercube 문서](https://docs.succinct.xyz/docs/sp1/hypercube/)는 이를 "대략 $$2^{22}$$개의 RISC-V 명령어로 구성된 Shard"로 설명한다. 각 Shard는 독립적으로 증명된 뒤 Recursion으로 합쳐진다.

4. **Chip 기반 Arithmetization**

    RISC Zero가 하나의 큰 CPU Trace를 중심으로 제약을 거는 것과 달리, SP1은 **명령어 그룹마다 별도의 Chip(테이블)**을 둔다.

    - **명령어 Chip:** ADD, JALR, DivRem처럼 명령어 그룹별 Chip이 있다. 테이블의 한 행은 해당 명령어 한 번의 실행이고, 각 셀은 KoalaBear Field 원소다. 예를 들어 ADD Chip은 34열, JALR Chip은 39열, DivRem Chip은 247열이다. 테이블은 2의 거듭제곱 크기로 Padding되며, Padding 행은 `is_real = 0`으로 표시된다.
    - **메모리 Chip:** 메모리 읽기/쓰기와 초기화, 종료 상태를 다룬다.
    - **Program Chip:** 실행할 프로그램의 명령어 목록이다. Preprocessed Trace로 미리 커밋되어 vkey에 반영된다.
    - **Precompile Chip:** SHA-256, Keccak, 타원곡선 연산 같은 무거운 연산 전용 테이블이다. 호출 방식과 지원 연산은 뒤의 [Precompile](#precompile) 절에서 다룬다.
    - **Lookup 테이블:** Byte 연산, Range Check(범위 검사) 같은 반복적인 검사를 위한 테이블이다.

    각 Chip의 행은 자기 명령어의 의미만 제약한다. RV64IM의 정수 레지스터는 x0~x31의 64bit 레지스터 32개이며 x0은 항상 0이다. 그래서 ADD Chip의 제약은 64bit Wrap-around(넘침)를 반영한 $$\text{rd} = (\text{rs1} + \text{rs2}) \bmod 2^{64}$$이다. ADD Chip이 검사하는 것은 이 등식뿐이고, rs1과 rs2의 값이 어디서 왔는지, 이 ADD가 Program에 실제로 있는 명령어인지는 검사하지 않는다. 이런 Chip 사이의 연결, 즉 "Program에 있는 명령어가 실제로 실행되었다", "읽은 레지스터 값이 메모리 상태와 일치한다" 같은 사실은 **Bus**로 묶는다.

    Bus는 각 Chip이 값을 보내고(Send) 받는(Receive) Interaction(상호작용)으로 구성된다. 보낸 값들의 Multiset과 받은 값들의 Multiset이 같아야 하며, 이를 **LogUp** 논증으로 확인한다. 무작위 값 $$\alpha$$에 대해 다음 등식을 검사한다.

    $$
    \sum_{\text{send}} \frac{m_i}{\alpha - f_i} = \sum_{\text{receive}} \frac{m_j}{\alpha - f_j}
    $$

    $$f_i$$는 보낸 값(튜플)을 하나의 Field 원소로 압축한 Fingerprint이고, $$m_i$$는 Multiplicity(횟수)다. 보낸 값과 받은 값이 하나라도 다르면 무작위 $$\alpha$$에서 등식이 성립할 확률은 무시할 수 있을 만큼 작다.

    Bus가 확인하는 것은 **Shard 안**의 일관성이다. Shard를 넘어가는 메모리 상태는 Blum 등의 Offline Memory Checking 방식에 따라 **Multiset Hash**로 요약한다. 이 해시는 Poseidon2로 각 원소를 KoalaBear의 7차 확장체 위 타원곡선의 점으로 해싱하고, 그 점들을 곡선 위의 덧셈으로 합친다. 곡선 덧셈은 교환법칙이 성립하므로 원소를 어떤 순서로 더해도 같은 값이 나오고, 그래서 메모리 접근 순서와 무관한 Multiset의 해시로 쓸 수 있다. 또 집합의 해시를 원소 해시의 합으로 정의하므로, 부분 집합의 해시를 더하면 전체 집합의 해시가 된다(Additive, 가법성). 이 곡선에서 이산대수 문제가 어렵다는 가정이 해시의 충돌 저항성을 보장한다. Additive 성질 덕분에 Shard별 다이제스트를 Recursion 단계(5단계)에서 합산하고, 최종 합이 일관된지 확인할 수 있다. 자세한 내용은 [Global Memory Argument 문서](https://docs.succinct.xyz/docs/sp1/hypercube/global)를 참고한다.

5. **증명: Hypercube, Recursion, Wrapping**

    - **Multilinear 다항식:** 단변수 STARK는 Trace 열을 $$x$$ 하나의 다항식으로 보간한다. Hypercube는 $$2^n$$행의 열을 변수 $$n$$개짜리 Multilinear(다변수 선형) 다항식으로 본다. 이 다항식은 Boolean Hypercube $$\{0,1\}^n$$의 각 점에서 해당 행의 값을 가진다. "Hypercube"라는 이름이 여기서 나왔다. 단변수 STARK에서 Trace 보간과 제약 계산에 쓰던 FFT 연산(유한체 위의 FFT를 NTT, Number Theoretic Transform이라 한다)이 크게 줄어 증명 속도와 메모리 사용에서 유리하다. 다만 아래 Basefold 커밋의 Reed-Solomon 인코딩에는 여전히 NTT가 쓰인다.
    - **Zerocheck:** 모든 행에서 제약 다항식 $$C$$가 0인지는 무작위 점 $$r$$에 대한 Sumcheck로 확인한다.

        $$
        \sum_{x \in \{0,1\}^n} \mathrm{eq}(r, x) \cdot C(x) = 0
        $$

        $$\mathrm{eq}(r, x) = \prod_{i=1}^{n} \big(r_i x_i + (1 - r_i)(1 - x_i)\big)$$는 Boolean 입력에서 $$r = x$$이면 1, 아니면 0인 함수의 Multilinear 확장이다. 따라서 좌변은 각 행의 $$C$$ 값을 Multilinear 다항식으로 확장해 점 $$r$$에서 평가한 값이다. 어느 한 행이라도 $$C(x) \neq 0$$이면 이 다항식은 0이 아니므로, 무작위 $$r$$에서 0이 될 확률은 Schwartz-Zippel 보조정리에 따라 무시할 수 있을 만큼 작다. 즉 이 합이 0이면 높은 확률로 모든 행에서 $$C = 0$$이다.

    - **LogUp-GKR:** 위의 LogUp 분수 합을 GKR 프로토콜(Sumcheck를 층마다 반복하는 방식)로 계산해, 보조 열을 따로 커밋하지 않고 Bus 논증을 증명한다.
    - **Jagged PCS:** Chip마다 테이블 높이가 다르다. 실행에 ADD가 많고 DivRem이 적으면 ADD 테이블만 길다. 모든 테이블을 가장 긴 높이에 맞춰 Padding하면 낭비가 크다. Jagged PCS(Polynomial Commitment Scheme)는 높이가 제각각인 열들을 하나의 Dense 다항식으로 이어 붙여 커밋하고, 원래 열에 대한 평가 주장을 Sumcheck로 Dense 다항식에 대한 주장으로 바꾼다. Succinct는 이를 "쓴 만큼만 비용을 내는(Pay only for what you use)" 구조라고 설명한다. Dense 다항식 커밋에는 해시 기반 PCS인 Basefold(FRI의 Multilinear 버전)를 쓴다.
    - **보안 가정:** Hypercube의 Core 증명과 Recursion 증명은 Proximity Gap Conjecture(추측)가 아니라 증명된 Proximity Gaps 정리에 의존한다. 자세한 내용은 [Dense PCS 문서](https://docs.succinct.xyz/docs/sp1/hypercube/pcs)를 참고한다.
    - **Recursion:** Shard 증명들을 검증하는 Recursion 프로그램을 증명하는 과정을 반복해 하나의 Compressed Proof(상수 크기 증명)로 합친다. Recursion은 증명 검증에 특화된 별도의 Recursion VM에서 돈다.
    - **Wrapping:** Compressed Proof를 한 번 더 줄인(Shrink) 뒤, BN254 위에서 검증하기 쉬운 형태로 감싸(Wrap) Groth16 또는 PLONK 증명으로 바꾼다. 이 마지막 SNARK 단계는 gnark로 구현되어 있다.

    SP1이 제공하는 증명 종류는 다음과 같다. 크기와 Gas는 [SP1 문서](https://docs.succinct.xyz/docs/sp1/generating-proofs/proof-types)의 수치다.

    | 종류 | 호출 | 크기 | On-chain 검증 비용 | 비고 |
    |------|------|------|--------------------|------|
    | Core | 기본값 (`.core()`) | 실행 길이에 비례 | - | Shard 증명 모음. RISC Zero의 Composite Receipt |
    | Compressed | `.compressed()` | 상수 | - | Recursion으로 합친 증명. SP1 안에서 재귀 검증하기 좋음 |
    | Groth16 | `.groth16()` | 약 260byte (문서 수치, v5 기준. v6 `proofBytes`는 356byte) | 약 27만 Gas | Circuit별 Trusted Setup 필요 (Aztec Ignition 세레모니에 Succinct 팀의 엔트로피 기여를 더함) |
    | PLONK | `.plonk()` | 약 868byte (문서 수치, v5 기준. v6 `proofBytes`는 964byte) | 약 30만 Gas | Circuit별 Trusted Setup 불필요. Aztec Ignition의 Universal(범용) Setup 재사용. Compressed 이후 약 1분 30초 추가, 증명 비용은 Groth16의 3~4배 |

    v6에서 On-chain에 보내는 `proofBytes`의 레이아웃은 v5와 다르다. Verifier 선택용 4byte 접두어 뒤에 종료 코드(exit code), Recursion Verifying Key Root(vk_root), proof nonce가 각각 32byte씩 들어가고, 그 뒤에 증명 본문이 붙는다. Groth16은 본문이 256byte(A, B, C)이므로 총 356byte, PLONK는 본문이 864byte이므로 총 964byte다. v5는 4byte 접두어 + 본문이라 각각 260byte, 868byte였다. 따라서 v6의 실제 전송 크기는 표의 문서 수치보다 96byte 크다. sp1-contracts의 `v6.1.0/SP1VerifierGroth16.sol`과 `SP1VerifierPlonk.sol`에서 확인할 수 있다.

6. **Verification**

    Verifier는 **기대하는 vkey, Public Values, 증명**을 대조한다.

    - **Off-chain 검증:** SP1 SDK의 `client.verify(&proof, vk, ...)`를 호출한다. 증명이 해당 vkey의 Program 실행에서 나왔는지, Public Values가 증명된 출력과 일치하는지 확인한다.

    - **On-chain 검증:** `SP1VerifierGateway` 컨트랙트의 `ISP1Verifier` 인터페이스를 호출한다.

        ```solidity
        interface ISP1Verifier {
            function verifyProof(
                bytes32 programVKey,
                bytes calldata publicValues,
                bytes calldata proofBytes
            ) external view;
        }
        ```

        1. Gateway는 `proofBytes`의 앞 4byte(Verifier Hash 접두어)를 보고 해당 SP1 버전의 Verifier 컨트랙트로 라우팅한다.
        2. Verifier는 `programVKey`, `publicValues`의 해시(SHA-256의 상위 3bit를 지운 값), 종료 코드, Recursion Verifying Key Root, proof nonce 다섯 개를 Groth16/PLONK 증명의 공개 입력으로 넣어 검증한다. v5에서는 공개 입력이 `programVKey`와 `publicValues` 해시 두 개였고, v6에서 종료 코드, vk_root, nonce가 추가되었다. 접두어가 다르면 `WrongVerifierSelector`, 종료 코드가 0이 아니면 `InvalidExitCode`, vk_root가 컨트랙트에 고정된 값과 다르면 `InvalidVkRoot`로 Revert하고, 그다음 증명 자체를 검증한다. Off-chain `verify`는 `StatusCode`를 골라 기대할 수 있지만, On-chain Verifier는 종료 코드 0(정상 종료)만 받아들인다.
        3. 애플리케이션이 `publicValues`를 디코딩해 기대값(이전 State Root, 블록 번호 등)과 비교한다.

    RISC Zero는 `journalDigest`(해시)를 넘기지만, SP1은 `publicValues` 원본 바이트를 넘기고 해시는 Verifier가 계산한다. 어느 쪽이든 **검증 비용은 원래 계산의 크기와 관계없이 일정하다.**

    SP1 문서는 컨트랙트에 저장한 vkey를 업그레이드할 수 있게 만들라고 권장한다. Program을 고치거나 SP1 버전을 올리면 vkey가 바뀌기 때문이다. 보안 문제가 발견되면 Succinct가 Gateway에서 특정 버전의 Verifier를 Freeze(동결)할 수 있다. 실제로 2026년 10월 9일 Succinct는 Mainnet Gateway에서 v5.0.0과 v6.0.0의 Groth16 라우트를 동결했고, 이후 활성 라우트는 v6.1.0뿐이다. v6.0.0은 뒤의 [버전 의존성](#장점과-한계)에서 다루는 Recursion 회로 Soundness 결함(GHSA-63x8-x938-vx33)의 영향 버전이다. 동결된 버전으로 만든 증명은 Gateway에서 `RouteIsFrozen`으로 Revert되므로, vkey뿐 아니라 사용하는 SP1 버전도 바꿀 수 있는 업그레이드 경로가 필요하다.

### Precompile

zkVM에서 해시나 타원곡선 연산을 RISC-V 명령어로 그대로 실행하면 사이클이 매우 많이 든다. SP1은 이런 연산을 **Precompile**이라는 전용 Chip으로 처리한다. Program이 `ecall` 시스템 콜로 Precompile을 호출하면, 해당 연산은 수천 사이클의 일반 명령어 대신 전용 테이블의 몇 행으로 증명된다.

- **해시:** SHA-256, Keccak-256
- **타원곡선:** secp256k1, secp256r1, ed25519, BN254, BLS12-381
- **기타:** 256bit 정수 곱셈 등

개발자가 Precompile을 직접 호출할 일은 많지 않다. Succinct가 `sha2`, `k256`, `tiny-keccak` 같은 인기 크레이트를 Precompile을 쓰도록 패치한 버전을 제공하므로, `Cargo.toml`에서 패치 크레이트로 바꾸기만 하면 된다. Ethereum 블록 증명 비용의 상당 부분이 Keccak과 secp256k1이므로 Precompile 사용 여부가 성능에 큰 영향을 준다.

## RISC Zero와 비교

| 항목 | RISC Zero | SP1 (v6, Hypercube) |
|------|-----------|---------------------|
| ISA | RV32IM | RV64IM |
| 증명 시스템 | 단변수 STARK + FRI | Multilinear (Zerocheck, LogUp-GKR, Jagged PCS, Basefold) |
| Field | BabyBear | KoalaBear |
| Trace 구성 | CPU 중심 Trace | 명령어 그룹별 Chip + Bus |
| 실행 분할 단위 | Segment | Shard |
| 프로그램 식별자 | Image ID | Verifying Key (vkey) |
| 공개 출력 | Journal (`env::commit`) | Public Values (`io::commit`) |
| 최종 SNARK | Groth16 | Groth16 또는 PLONK |
| On-chain 검증 | `verify(seal, imageId, journalDigest)` | `verifyProof(programVKey, publicValues, proofBytes)` |
| 분산 증명 | Boundless | Succinct Prover Network |

두 zkVM은 개발 경험이 거의 같다. Rust로 Guest를 작성하고, 입력을 읽고, 결과를 커밋하고, Receipt/Proof를 검증한다. 차이는 주로 내부 증명 시스템과 성능 특성에 있다.

### 장점과 한계

**장점**

- **기존 언어 사용:** RISC Zero와 마찬가지로 Rust로 작성하므로 Reth 같은 기존 Ethereum Execution Client 코드를 재사용할 수 있다. 다만 zkVM 환경의 제약(파일 시스템, 네트워크, 스레드 없음 등)이 있다.
- **Pay only for what you use:** Chip 구조와 Jagged PCS 덕분에 실제로 많이 실행된 명령어의 테이블만 커진다. 쓰지 않은 Precompile이나 드물게 쓴 명령어 때문에 비용이 늘지 않는다.
- **Real-Time Proving:** Succinct의 발표에 따르면 GPU 16장 규모 클러스터로 Ethereum L1 블록 대부분을 12초 안에 증명한다. SP1 Turbo 대비 연산 위주 작업에서 약 4배, Precompile 위주 Ethereum 증명에서 약 2배 빠르다.
- **증명 종류 선택:** Groth16과 PLONK 중 고를 수 있다. PLONK는 증명이 조금 크고 비싸지만 Circuit별 Trusted Setup이 필요 없다.
- **형식 검증:** Succinct는 2025년 10월 Nethermind Security와 함께 Lean 4로 RISC-V 핵심 Chip의 62개 Opcode(ALU 41개, 제어 흐름 10개, 메모리 11개)를 공식 RISC-V Sail 명세에 대해 형식 검증했다고 발표했다. Nethermind가 ALU, Succinct가 제어 흐름과 메모리 Opcode를 맡았다. Ethereum Foundation zkEVM 팀의 2026년 5월 검토에 따르면 완전한 증명은 그중 51개였고(ALU 41개 중 40개, 제어 흐름 10개 중 7개, 메모리 11개 중 4개), Bus 논증과 메모리 일관성, Lookup 테이블은 검증 범위 밖이다. 검증 방향도 "제약이 성립하면 명세와 같은 상태 전이가 일어난다"는 Soundness 방향만 다루고, 그 역은 다루지 않는다. 이 검토에서 EF 팀은 v6.0.2에 RISC-V ACT 테스트를 돌려 JALR이 `rs1 + imm`의 최하위 비트를 지우지 않아 유효한 입력에서 Prover가 멈추는 것을 확인해 Succinct에 보고했고, 2026년 4월 11일 배포된 v6.1.0에서 고쳐졌다. 이 문제 자체는 Succinct가 2025년 9월 Code4rena 감사 때 알려진 이슈로 이미 공개한 것이었다. 잘못된 증명을 만드는 Soundness 문제가 아니라, 실질적으로 서비스 거부(DoS) 벡터가 될 수 있는 Completeness 문제였다. Lean 증명은 이 수정에 맞춰 갱신되지 않았다. 자세한 내용은 [Ethereum Foundation의 글](https://zkevm.ethereum.foundation/blog/sp1-fv)을 참고한다.

**한계**

- **명령어 단위 오버헤드:** 전용 Circuit보다 증명 오버헤드가 크다. Precompile이 없는 무거운 연산은 비용이 크게 늘어난다.
- **높은 증명 비용:** Real-Time Proving이 가능하다는 것은 RTX 5090 16장 규모 클러스터 기준이며, 개인 PC 한 대로는 불가능한 수준이다. 그래서 개인 장비에서는 Prover Network에 증명을 맡기는 경우가 많다.
- **작은 연산에서의 고정 비용:** 단순한 연산이라도 Recursion과 Wrapping 비용이 붙어, 해당 연산에 특화된 작은 Circuit보다 비쌀 수 있다.
- **버전 의존성:** 메이저 버전마다 증명 시스템이 크게 바뀌어 왔다. 버전을 올리면 vkey와 On-chain Verifier가 바뀌므로 컨트랙트 업그레이드 경로를 미리 마련해야 한다. 마이너 버전 갱신도 미룰 수 없는 경우가 있다. v6 출시 후 고심각도 Soundness 결함이 두 번 공개되었다.
    - [GHSA-63x8-x938-vx33](https://github.com/succinctlabs/sp1/security/advisories/GHSA-63x8-x938-vx33) (CVE-2026-40323, 2026년 4월 11일 공개): Recursion 회로의 Jagged PCS Verifier에서 커밋 쪽 행 수 벡터와 평가 쪽 Prefix Sum 증인이 따로 존재하는데, 둘이 같은 Trace 모양을 가리키는지 확인하는 제약이 빠져 있었다. 악의적 Prover가 커밋에는 한 모양을, 다항식 평가에는 다른 모양을 넣을 수 있었고, Preprocessed Trace(회로 구조)에도 적용되므로 회로 자체를 왜곡할 여지가 있었다. 네이티브 Verifier는 하나의 Jagged PCS 객체에서 두 값을 같이 유도하므로 영향이 없었고, 6.0.0~6.0.2가 영향 버전이며 같은 날 배포된 6.1.0에서 고쳐졌다. Code4rena 버그 바운티로 발견되었다. 즉 v6.1.0은 JALR Completeness 수정과 이 Soundness 수정을 함께 담은 버전이다.
    - [GHSA-p7v2-jjv3-8p8f](https://github.com/succinctlabs/sp1/security/advisories/GHSA-p7v2-jjv3-8p8f) (2026년 10월 11일 공개): SP1 네이티브 Rust Verifier(`sp1_hypercube`, `sp1_prover`, `sp1_sdk`) 6.0.0부터 6.8.0까지에 있던 결함이다. Verifier가 증명 데이터를 역직렬화할 때 Tensor가 선언한 Shape(차원)만 믿고, 실제로 저장된 원소 수가 차원들의 곱과 일치하는지는 확인하지 않았다. 그래서 악의적 Prover가 Core 또는 Compressed 증명을 네이티브 Verifier에 직접 제출하면 잘못된 실행의 증명도 수락될 수 있었다. 공지 시점에 알려진 영향 대상은 외부 Prover의 증명을 받는 Succinct의 Mainnet Prover Network뿐이었고, 네트워크 요청자는 별도 조치가 필요 없었다. 결함이 공개되기 17일 전인 9월 24일에 이미 6.8.1로 수정되어 있었다. 패치를 먼저 배포하고 나중에 공개하는 Responsible Disclosure(책임 있는 공개) 순서다. Groth16과 PLONK 검증은 Shape가 고정된 Wrap Proof를 쓰므로 영향을 받지 않았다. Immunefi 버그 바운티로 발견되었다.

    JALR 버그가 Prover만 멈추게 하는 Completeness 문제였던 것과 달리, 두 결함은 모두 Verifier가 잘못된 증명을 받아들일 수 있는 Soundness 문제였다.
