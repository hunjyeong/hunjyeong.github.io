## SP1 zkVM

### What is SP1?

SP1(Succinct Processor 1)은 Succinct Labs가 만든 RISC-V 기반 zkVM이다. RISC Zero처럼 **범용 CPU의 실행 자체를 증명**하므로, 개발자는 Circuit을 설계하지 않고 Rust 같은 일반 언어로 프로그램을 작성한다. SP1이 증명하는 것은 다음 사실이다.

> 주어진 프로그램이 특정 입력에 대해 RISC-V 명령어 규칙에 따라 정상적으로 실행되었고, 그 결과로 이 공개 값(Public Values)을 내놓았다.

이 글은 SP1 v6(SP1 Hypercube)를 기준으로 설명한다. SP1은 버전에 따라 내부 증명 시스템이 크게 바뀌었다.

| 버전 | ISA | 증명 시스템 | Field |
|------|-----|-------------|-------|
| SP1 ~ SP1 Turbo (v4, v5) | RV32IM | Plonky3 기반 단변수 STARK + FRI | BabyBear ($$2^{31} - 2^{27} + 1$$) |
| SP1 Hypercube (v6) | RV64IM | 다변수 선형(Multilinear) 다항식 기반 증명 시스템 | KoalaBear ($$2^{31} - 2^{24} + 1$$) |

SP1 Hypercube는 2025년 5월 공개되었고 2026년 2월 메인넷에 적용되었다. Succinct는 2025년 11월 RTX 5090 GPU 16장으로 Ethereum 블록의 99.7%를 12초 안에 증명했다고 발표했다. 자세한 내용은 [SP1 문서](https://docs.succinct.xyz/docs/sp1/introduction)에서 확인할 수 있다. Prover Network에서 v5 지원은 2026년 5월 19일에 종료되었으므로, 네트워크 증명을 쓰려면 v6 이상이어야 한다.

### Program과 Script

SP1도 증명 대상과 실행 관리자를 분리한다. RISC Zero의 Guest/Host에 해당하며, SP1 문서에서는 주로 Program과 Script라고 부른다.

- **Program (Guest):** 증명 대상 프로그램이다. Rust로 작성해 RISC-V ELF 바이너리로 컴파일한다.
- **Script (Host):** `ProverClient`로 Program에 입력을 넣고 실행하며, 증명 생성과 검증을 요청한다. 증명은 로컬 CPU/GPU나 Succinct Prover Network에서 생성한다.

### End-to-End Proving Process

1. **Program 작성**

    증명할 로직을 Rust로 작성한다. RISC Zero 글의 예제와 같은 로직을 SP1 API로 옮기면 다음과 같다.

    - **입력:** `sp1_zkvm::io::read()`로 Script에서 데이터를 받는다. 읽은 값은 기본적으로 비공개다.
    - **출력:** `sp1_zkvm::io::commit()`으로 Public Values에 기록한다. RISC Zero의 Journal에 해당한다.

    ```rust
    #![no_main]
    sp1_zkvm::entrypoint!(main);

    pub fn main() {
        // Script에서 입력 받기 (비공개)
        let a = sp1_zkvm::io::read::<u64>();
        let b = sp1_zkvm::io::read::<u64>();

        // 자명하지 않은 인수인지 확인 (0과 1 제외)
        if a < 2 || b < 2 {
            panic!("Trivial factors");
        }

        // 계산 (오버플로우 체크)
        let product = a.checked_mul(b).expect("Overflow");

        // 결과 공개 (Public Values)
        sp1_zkvm::io::commit(&product);
    }
    ```

    Script 쪽 코드는 다음과 같다. v6 SDK는 실행, 설정, 증명 생성이 비동기(async) API이고, `verify`는 동기 함수다.

    ```rust
    use sp1_sdk::prelude::*;
    use sp1_sdk::ProverClient;

    const ELF: Elf = include_elf!("factors-program");

    #[tokio::main]
    async fn main() {
        let mut stdin = SP1Stdin::new();
        stdin.write(&17u64);
        stdin.write(&23u64);

        let client = ProverClient::from_env().await;

        // 증명 없이 실행만 해서 사이클 수 확인
        let (_, report) = client.execute(ELF, stdin.clone()).await.unwrap();
        println!("cycles: {}", report.total_instruction_count());

        // Proving Key/Verifying Key 생성 후 증명
        let pk = client.setup(ELF).await.unwrap();
        let mut proof = client.prove(&pk, stdin).groth16().await.unwrap();

        // Public Values 읽기와 검증
        let product = proof.public_values.read::<u64>();
        client.verify(&proof, pk.verifying_key(), None).expect("verification failed");
    }
    ```

    `verify`의 세 번째 인자는 기대하는 종료 코드(`StatusCode`)다. `None`이면 정상 종료(`StatusCode::SUCCESS`)를 기대한다.

2. **Program 컴파일과 Verifying Key 생성**

    Program은 SP1 전용 Rust Toolchain(`sp1up`으로 설치)으로 RISC-V ELF 바이너리로 컴파일된다. v6의 `sp1up`은 64bit Toolchain을 설치하며, v5 이하의 32bit Toolchain과 호환되지 않는다. `cargo prove build`를 직접 실행하거나, Script 크레이트의 빌드 스크립트에서 `sp1-build`로 컴파일한다. Script는 `include_elf!`로 ELF를 가져온다.

    ```text
    Rust
    ↓
    cargo prove build (또는 sp1-build)
    ↓
    RISC-V RV64IM ELF 바이너리
    ↓
    client.setup(ELF): Program 테이블 등 Preprocessed Trace에 커밋
    ↓
    Proving Key(pk) + Verifying Key(vk)
    ↓
    vk.bytes32() = On-chain에서 쓰는 Program Verification Key (32byte)
    ```

    **Verifying Key(vkey)**는 RISC Zero의 Image ID 역할을 한다. Verifier는 이 값으로 어떤 프로그램이 실행되었는지 식별하며, Program 코드가 바뀌면 vkey도 바뀐다.

3. **실행과 Shard 분할**

    Script의 Executor가 RISC-V 바이너리를 실행하며 명령어마다 이벤트(Event)를 기록한다. 예를 들어 `add` 명령은 ADD 이벤트를, 메모리 접근은 메모리 이벤트를, SHA-256 같은 Precompile 호출은 해당 Precompile 이벤트를 남긴다. 이렇게 모은 실행 기록(Execution Record)이 이후 Trace 테이블의 재료가 된다.

    실행이 길면 한 번에 증명할 수 없으므로, SP1은 실행을 **Shard** 단위로 나눈다. RISC Zero의 Segment에 해당한다. Hypercube에서 Shard의 경계는 고정된 명령어 수가 아니라 Trace 테이블의 면적과 높이 임계값으로 정해지며, 기본 설정의 높이 임계값은 $$2^{22}$$행이다. [L2BEAT](https://l2beat.com/zk-catalog/sp1hypercube)는 Shard 크기를 약 $$2^{22}$$로 설명한다. 각 Shard는 독립적으로 증명된 뒤 Recursion으로 합쳐진다.

    RV64IM이므로 정수 레지스터는 x0~x31의 64bit 레지스터 32개이며 x0은 항상 0이다.

4. **Chip 기반 Arithmetization**

    RISC Zero가 하나의 큰 CPU Trace를 중심으로 제약을 거는 것과 달리, SP1은 **명령어 그룹마다 별도의 테이블(Chip)**을 둔다.

    - **명령어 Chip:** ADD, JALR, DivRem처럼 명령어 그룹별 Chip이 있다. 테이블의 한 행은 해당 명령어 한 번의 실행이고, 각 셀은 KoalaBear Field 원소다. 예를 들어 ADD Chip은 34열, JALR Chip은 39열, DivRem Chip은 247열이다. 테이블은 2의 거듭제곱 크기로 Padding되며, Padding 행은 `is_real = 0`으로 표시된다.
    - **메모리 Chip:** 메모리 읽기/쓰기와 초기화, 종료 상태를 다룬다.
    - **Program Chip:** 실행할 프로그램의 명령어 목록이다. Preprocessed Trace로 미리 커밋되어 vkey에 반영된다.
    - **Precompile Chip:** SHA-256, Keccak, 타원곡선 연산 같은 무거운 연산 전용 테이블이다.
    - **Lookup 테이블:** Byte 연산, 범위 검사(Range Check) 같은 반복적인 검사를 위한 테이블이다.

    각 Chip의 행은 자기 명령어의 의미만 제약한다. 예를 들어 ADD Chip은 $$\text{rd} = (\text{rs1} + \text{rs2}) \bmod 2^{64}$$만 검사한다. Chip 사이의 연결, 즉 "Program에 있는 명령어가 실제로 실행되었다", "읽은 레지스터 값이 메모리 상태와 일치한다" 같은 사실은 **Bus**로 묶는다.

    Bus는 각 Chip이 값을 보내고(Send) 받는(Receive) 상호작용(Interaction)으로 구성된다. 보낸 값들의 Multiset과 받은 값들의 Multiset이 같아야 하며, 이를 **LogUp** 논증으로 확인한다. 무작위 값 $$\alpha$$에 대해 다음 등식을 검사한다.

    $$
    \sum_{\text{send}} \frac{m_i}{\alpha - f_i} = \sum_{\text{receive}} \frac{m_j}{\alpha - f_j}
    $$

    $$f_i$$는 보낸 값(튜플)을 하나의 Field 원소로 압축한 Fingerprint이고, $$m_i$$는 횟수(Multiplicity)다. 보낸 값과 받은 값이 하나라도 다르면 무작위 $$\alpha$$에서 등식이 성립할 확률은 무시할 수 있을 만큼 작다.

5. **증명: Hypercube, Recursion, Wrapping**

    - **Multilinear 다항식:** 단변수 STARK는 Trace 열을 $$x$$ 하나의 다항식으로 보간한다. Hypercube는 $$2^n$$행의 열을 변수 $$n$$개짜리 다변수 선형(Multilinear) 다항식으로 본다. 이 다항식은 Boolean Hypercube $$\{0,1\}^n$$의 각 점에서 해당 행의 값을 가진다. "Hypercube"라는 이름이 여기서 나왔다. NTT 기반 보간이 필요 없어 증명 속도와 메모리 사용에서 유리하다.
    - **Zerocheck:** 모든 행에서 제약 다항식 $$C$$가 0인지는 무작위 점 $$r$$에 대한 Sumcheck로 확인한다.

        $$
        \sum_{x \in \{0,1\}^n} \mathrm{eq}(r, x) \cdot C(x) = 0
        $$

    - **LogUp-GKR:** 위의 LogUp 분수 합을 GKR 프로토콜(Sumcheck를 층마다 반복하는 방식)로 계산해, 보조 열을 따로 커밋하지 않고 Bus 논증을 증명한다.
    - **Jagged PCS:** Chip마다 테이블 높이가 다르다. 실행에 ADD가 많고 DivRem이 적으면 ADD 테이블만 길다. 모든 테이블을 가장 긴 높이에 맞춰 Padding하면 낭비가 크다. Jagged PCS(Polynomial Commitment Scheme)는 높이가 제각각인 열들을 하나의 Dense 다항식으로 이어 붙여 커밋하고, 원래 열에 대한 평가 주장을 Sumcheck로 Dense 다항식에 대한 주장으로 바꾼다. Succinct는 이를 "쓴 만큼만 비용을 내는(Pay only for what you use)" 구조라고 설명한다. Dense 다항식 커밋에는 해시 기반 PCS인 Basefold를 쓴다. Hypercube의 Core 증명과 Recursion 증명은 Proximity Gap 추측(Conjecture)이 아니라 증명된 Proximity Gaps 정리에 의존한다. 자세한 내용은 [Dense PCS 문서](https://docs.succinct.xyz/docs/sp1/hypercube/pcs)를 참고한다.
    - **Shard 간 메모리 일관성:** Shard 안의 메모리 일관성은 Bus로 확인한다. Shard를 넘어가는 메모리 상태는 Blum 등의 Offline Memory Checking 방식에 따라 Multiset Hash로 요약한다. 이 해시는 Poseidon2로 각 원소를 타원곡선 위의 점으로 해싱하고 곡선 위의 덧셈으로 합치므로 더할 수 있는(Additive) 성질이 있다. 그래서 Shard별 다이제스트를 Recursion 단계에서 합산하고, 최종 합이 일관된지 확인할 수 있다. 자세한 내용은 [Global Memory Argument 문서](https://docs.succinct.xyz/docs/sp1/hypercube/global)를 참고한다.
    - **Recursion:** Shard 증명들을 검증하는 Recursion 프로그램을 증명하는 과정을 반복해 하나의 상수 크기 증명(Compressed Proof)으로 합친다. Recursion은 증명 검증에 특화된 별도의 Recursion VM에서 돈다.
    - **Wrapping:** Compressed Proof를 한 번 더 줄인(Shrink) 뒤, BN254 위에서 검증하기 쉬운 형태로 감싸(Wrap) Groth16 또는 PLONK 증명으로 바꾼다. 이 마지막 SNARK 단계는 gnark로 구현되어 있다.

    SP1이 제공하는 증명 종류는 다음과 같다. 크기와 Gas는 [SP1 문서](https://docs.succinct.xyz/docs/sp1/generating-proofs/proof-types)의 수치다.

    | 종류 | 호출 | 크기 | On-chain 검증 비용 | 비고 |
    |------|------|------|--------------------|------|
    | Core | 기본값 (`.core()`) | 실행 길이에 비례 | - | Shard 증명 모음. RISC Zero의 Composite Receipt |
    | Compressed | `.compressed()` | 상수 | - | Recursion으로 합친 증명. SP1 안에서 재귀 검증하기 좋음 |
    | Groth16 | `.groth16()` | 약 260byte | 약 27만 Gas | Circuit별 Trusted Setup 필요 (Phase 1은 Aztec Ignition, Phase 2는 Succinct 팀 기여) |
    | PLONK | `.plonk()` | 약 868byte | 약 30만 Gas | Circuit별 Trusted Setup 불필요. Aztec Ignition의 범용(Universal) Setup 재사용. Compressed 이후 약 1분 30초 추가, 증명 비용은 Groth16의 3~4배 |

    On-chain에 보내는 `proofBytes`에는 증명 본문 외에 Verifier 선택용 4byte 접두어와 종료 코드 등 추가 데이터가 붙으므로, 실제 전송 크기는 표의 증명 크기보다 크다.

6. **Verification**

    Verifier는 **기대하는 vkey, Public Values, 증명**을 대조한다.

    - **Off-chain 검증:** SP1 SDK의 `client.verify(&proof, vk, ...)`를 호출한다. 증명이 해당 vkey의 Program 실행에서 나왔는지, Public Values가 증명된 출력과 일치하는지 확인한다.

    - **On-chain 검증:** `SP1VerifierGateway` 컨트랙트의 `ISP1Verifier` 인터페이스를 호출한다.

        ```solidity
        interface ISP1Verifier {
            function verifyProof(
                bytes32 programVKey,
                bytes calldata publicValues,
                bytes calldata proofBytes
            ) external view;
        }
        ```

        1. Gateway는 `proofBytes`의 앞 4byte(Verifier Hash 접두어)를 보고 해당 SP1 버전의 Verifier 컨트랙트로 라우팅한다.
        2. Verifier는 `programVKey`, `publicValues`의 해시, 종료 코드, Recursion Verifying Key Root가 서로 일치하는지 공개 입력으로 확인하며 Groth16/PLONK 증명을 검증한다. 실패하면 Revert한다.
        3. 애플리케이션이 `publicValues`를 디코딩해 기대값(이전 State Root, 블록 번호 등)과 비교한다.

    RISC Zero는 `journalDigest`(해시)를 넘기지만, SP1은 `publicValues` 원본 바이트를 넘기고 해시는 Verifier가 계산한다. 어느 쪽이든 **검증 비용은 원래 계산의 크기와 관계없이 일정하다.**

    SP1 문서는 컨트랙트에 저장한 vkey를 업그레이드할 수 있게 만들라고 권장한다. Program을 고치거나 SP1 버전을 올리면 vkey가 바뀌기 때문이다. 보안 문제가 발견되면 Succinct가 Gateway에서 특정 버전의 Verifier를 동결(Freeze)할 수 있다.

### Precompile

zkVM에서 해시나 타원곡선 연산을 RISC-V 명령어로 그대로 실행하면 사이클이 매우 많이 든다. SP1은 이런 연산을 **Precompile**이라는 전용 Chip으로 처리한다. Program이 `ecall` 시스템 콜로 Precompile을 호출하면, 해당 연산은 수천 사이클의 일반 명령어 대신 전용 테이블의 몇 행으로 증명된다.

- **해시:** SHA-256, Keccak-256
- **타원곡선:** secp256k1, secp256r1, ed25519, BN254, BLS12-381
- **기타:** 256bit 정수 곱셈 등

개발자가 Precompile을 직접 호출할 일은 많지 않다. Succinct가 `sha2`, `k256`, `tiny-keccak` 같은 인기 크레이트를 Precompile을 쓰도록 패치한 버전을 제공하므로, `Cargo.toml`에서 패치 크레이트로 바꾸기만 하면 된다. Ethereum 블록 증명 비용의 상당 부분이 Keccak과 secp256k1이므로 Precompile 사용 여부가 성능에 큰 영향을 준다.

### RISC Zero와 비교

| 항목 | RISC Zero | SP1 (v6, Hypercube) |
|------|-----------|---------------------|
| ISA | RV32IM | RV64IM |
| 증명 시스템 | 단변수 STARK + FRI | Multilinear (Zerocheck, LogUp-GKR, Jagged PCS, Basefold) |
| Field | BabyBear | KoalaBear |
| Trace 구성 | CPU 중심 Trace | 명령어 그룹별 Chip + Bus |
| 실행 분할 단위 | Segment | Shard |
| 프로그램 식별자 | Image ID | Verifying Key (vkey) |
| 공개 출력 | Journal (`env::commit`) | Public Values (`io::commit`) |
| 최종 SNARK | Groth16 | Groth16 또는 PLONK |
| On-chain 검증 | `verify(seal, imageId, journalDigest)` | `verifyProof(programVKey, publicValues, proofBytes)` |
| 분산 증명 | Boundless | Succinct Prover Network |

두 zkVM은 개발 경험이 거의 같다. Rust로 Guest를 작성하고, 입력을 읽고, 결과를 커밋하고, Receipt/Proof를 검증한다. 차이는 주로 내부 증명 시스템과 성능 특성에 있다.

### 장점과 한계

**장점**

- **기존 언어 사용:** RISC Zero와 마찬가지로 Rust로 작성하므로 Reth 같은 기존 Ethereum Execution Client 코드를 재사용할 수 있다. 다만 zkVM 환경의 제약(파일 시스템, 네트워크, 스레드 없음 등)이 있다.
- **Pay only for what you use:** Chip 구조와 Jagged PCS 덕분에 실제로 많이 실행된 명령어의 테이블만 커진다. 쓰지 않은 Precompile이나 드물게 쓴 명령어 때문에 비용이 늘지 않는다.
- **Real-Time Proving:** Succinct의 발표에 따르면 GPU 16장 규모 클러스터로 Ethereum L1 블록 대부분을 12초 안에 증명한다. SP1 Turbo 대비 연산 위주 작업에서 약 4배, Precompile 위주 Ethereum 증명에서 약 2배 빠르다.
- **증명 종류 선택:** Groth16과 PLONK 중 고를 수 있다. PLONK는 증명이 조금 크고 비싸지만 Circuit별 Trusted Setup이 필요 없다.
- **형식 검증:** Succinct는 Nethermind Security, Ethereum Foundation과 함께 Lean 4로 RISC-V 핵심 제약 62개 Opcode를 공식 RISC-V Sail 명세에 대해 형식 검증했다고 발표했다. 다만 Ethereum Foundation zkEVM 팀의 2026년 5월 검토에 따르면 완전한 증명은 그중 51개였고(ALU 41개 중 40개, 제어 흐름 10개 중 7개, 메모리 11개 중 4개), Bus 논증과 메모리 일관성, Lookup 테이블은 검증 범위 밖이다. 검증 방향도 "제약이 성립하면 명세와 같은 상태 전이가 일어난다"는 Soundness 방향만 다루고, 그 역은 다루지 않는다. 이 검토 과정에서 JALR이 `rs1 + imm`의 최하위 비트를 지우지 않는 버그가 v6.0.2에서 발견되어 v6.1.0에서 고쳐졌다. 이 버그는 잘못된 증명을 만드는 Soundness 문제가 아니라 유효한 입력에서 Prover가 멈추는 Completeness 문제였다. 자세한 내용은 [Ethereum Foundation의 글](https://zkevm.ethereum.foundation/blog/sp1-fv)을 참고한다.

**한계**

- **명령어 단위 오버헤드:** 전용 Circuit보다 증명 오버헤드가 크다. Precompile이 없는 무거운 연산은 비용이 크게 늘어난다.
- **높은 증명 비용:** Real-Time Proving에도 고성능 GPU 클러스터가 필요하다. 개인 장비에서는 Prover Network에 증명을 맡기는 경우가 많다.
- **작은 연산에서의 고정 비용:** 단순한 연산이라도 Recursion과 Wrapping 비용이 붙어, 해당 연산에 특화된 작은 Circuit보다 비쌀 수 있다.
- **버전 의존성:** 메이저 버전마다 증명 시스템이 크게 바뀌어 왔다. 버전을 올리면 vkey와 On-chain Verifier가 바뀌므로 컨트랙트 업그레이드 경로를 미리 마련해야 한다.
