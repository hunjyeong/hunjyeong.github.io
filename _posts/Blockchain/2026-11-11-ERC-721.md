# ERC-721: Ethereum의 Non-Fungible Token(대체 불가능 토큰) 표준

## 1. 배경과 필요성

Ethereum(이더리움)에서 Token(토큰)은 Smart Contract(스마트 컨트랙트)가 관리하는 장부 위의 기록이다. Smart Contract는 Blockchain(블록체인)에 배포되어 정해진 코드대로 실행되는 프로그램이다. 누가 어떤 Token을 가졌는지는 이 프로그램의 저장 공간에 기록된다.

Token은 성질에 따라 두 종류로 나뉜다.

- Fungible Token(대체 가능 토큰): 같은 종류의 Token은 서로 구분되지 않는다. ERC-20 표준이 이 방식이며, 주소별 잔액만 기록한다.
- Non-Fungible Token(대체 불가능 토큰, 이하 NFT): Token 하나하나가 고유하다. 같은 Contract에서 발행된 Token이라도 서로 다른 Token으로 취급한다.

잔액만 기록하는 방식으로는 "어느 Token인가"를 표현할 수 없다. 수집품, 게임 아이템, 증명서처럼 개별 식별이 필요한 자산을 다루려면 Token마다 식별자를 붙이고, 식별자 단위로 소유자를 기록해야 한다. ERC-721은 이 방식을 정한 표준이다.

ERC는 Ethereum Request for Comments의 줄임말이다. Ethereum의 변경 제안 문서인 EIP(Ethereum Improvement Proposal, 이더리움 개선 제안) 가운데 Application 수준의 표준을 다루는 분류다. ERC-721의 사양 문서는 EIP-721이다.

표준은 구현 코드가 아니라 Interface(인터페이스)를 정한다. Interface는 Contract가 외부에 제공해야 하는 함수와 Event(이벤트)의 목록이다. 모든 ERC-721 Contract가 같은 Interface를 따르므로, Wallet(지갑)이나 Marketplace(거래소)는 Contract마다 내부 구현을 알지 못해도 같은 방법으로 소유자를 조회하고 전송을 요청할 수 있다.

NFT는 ERC-1155 표준으로도 발행할 수 있다. 이 문서는 ERC-721만 다룬다.

## 2. 핵심 개념

### 2.1 TokenID와 고유성

ERC-721 Contract 안의 NFT는 각각 `uint256` 타입의 식별자를 가진다. 이 문서에서는 이 식별자를 TokenID(Token Identifier)라고 부른다.

- TokenID는 하나의 Contract 안에서 고유하다.
- (Contract 주소, TokenID) 쌍은 하나의 Ethereum Chain 안에서 고유하다.
- TokenID는 Contract가 존재하는 동안 바뀌면 안 된다.
- 호출자는 TokenID에 특정 규칙이 있다고 가정하면 안 된다. 예를 들어 0부터 순서대로 증가한다고 가정할 수 없다.

따라서 NFT의 Non-Fungibility(대체 불가능성)는 (Contract 주소, TokenID) 쌍에서 나온다. 예를 들어 PudgyPenguins Contract(Name: `PudgyPenguins`, Symbol: `PPG`)의 TokenID 777은 같은 Contract의 다른 TokenID와도, 다른 Contract의 TokenID 777과도 다른 NFT다.

### 2.2 Owner, Approved Address, Operator

NFT 하나를 전송할 수 있는 주체는 세 종류다.

- Owner(소유자): 해당 TokenID를 소유한 주소다.
- Approved Address(승인된 주소): Owner가 특정 TokenID 하나에 대해 전송 권한을 준 주소다. TokenID 하나에 주소 하나만 지정된다.
- Operator(운영자): Owner가 자신의 모든 NFT에 대해 전송 권한을 준 주소다. Owner 한 명이 여러 Operator를 둘 수 있다.

Approved Address와 Operator는 Owner가 직접 Transaction(트랜잭션)을 보내지 않아도 제3자 Contract가 NFT를 옮길 수 있게 한다. Marketplace가 판매자의 NFT를 구매자에게 넘기는 동작이 이 권한 위에서 이루어진다.

### 2.3 표준의 구성

EIP-721은 필수 Interface 하나와 선택 확장 두 개, 그리고 NFT를 받는 Contract가 구현하는 Interface 하나를 정의한다.

| Interface | 구현 의무 | Interface Identifier | 역할 |
| --- | --- | --- | --- |
| ERC721 | 필수 | `0x80ac58cd` | 소유권 조회, 전송, 승인 |
| ERC165 | 필수 | `0x01ffc9a7` | 지원하는 Interface 조회 |
| ERC721Metadata | 선택 | `0x5b5e139f` | Name, Symbol, TokenURI 조회 |
| ERC721Enumerable | 선택 | `0x780e9d63` | 전체 NFT 목록 열거 |
| ERC721TokenReceiver | Safe Transfer를 받는 Contract에 필요 | `0x150b7a02` | NFT 수신 가능 여부 응답 |

Interface Identifier는 EIP-165가 정한 4바이트 값이다. Interface에 속한 모든 함수의 Function Selector(함수 선택자)를 XOR(Exclusive OR, 배타적 논리합)한 결과다. Function Selector는 함수 시그니처를 Keccak-256으로 해시한 값의 앞 4바이트다. 외부에서는 `supportsInterface(bytes4 interfaceID)`를 호출해 Contract가 특정 Interface를 구현하는지 확인한다.

ERC165의 `0x01ffc9a7`은 EIP-721 문서에 적힌 값이 아니다. `supportsInterface(bytes4)` 함수 하나의 Function Selector이며, 이 문서의 예시 Contract를 컴파일해 확인한 값이다.

## 3. 필수 Interface

아래는 EIP-721이 정의한 ERC721 Interface에서 주석을 뺀 것이다. 사양 문서의 코드는 Solidity `^0.4.20` 문법으로 작성되어 있다.

```solidity
interface ERC721 /* is ERC165 */ {
    event Transfer(address indexed _from, address indexed _to, uint256 indexed _tokenId);
    event Approval(address indexed _owner, address indexed _approved, uint256 indexed _tokenId);
    event ApprovalForAll(address indexed _owner, address indexed _operator, bool _approved);

    function balanceOf(address _owner) external view returns (uint256);
    function ownerOf(uint256 _tokenId) external view returns (address);

    function safeTransferFrom(address _from, address _to, uint256 _tokenId, bytes data) external payable;
    function safeTransferFrom(address _from, address _to, uint256 _tokenId) external payable;
    function transferFrom(address _from, address _to, uint256 _tokenId) external payable;

    function approve(address _approved, uint256 _tokenId) external payable;
    function setApprovalForAll(address _operator, bool _approved) external;
    function getApproved(uint256 _tokenId) external view returns (address);
    function isApprovedForAll(address _owner, address _operator) external view returns (bool);
}
```

함수는 역할에 따라 세 묶음으로 나뉜다.

| 묶음 | 함수 | 동작 |
| --- | --- | --- |
| 조회 | `balanceOf` | 주소가 소유한 NFT 개수를 반환한다. Zero Address(영 주소, `0x0000...0000`)를 조회하면 실패한다. |
| 조회 | `ownerOf` | TokenID의 Owner를 반환한다. 유효하지 않은 TokenID면 실패한다. |
| 전송 | `transferFrom` | NFT를 `_from`에서 `_to`로 옮긴다. 수신자가 NFT를 다룰 수 있는지 확인하지 않는다. |
| 전송 | `safeTransferFrom` | `transferFrom`과 같되, 수신자가 Contract이면 수신 가능 여부를 확인한다. |
| 승인 | `approve` | TokenID 하나의 Approved Address를 지정한다. |
| 승인 | `setApprovalForAll` | 호출자의 모든 NFT에 대한 Operator를 지정하거나 해제한다. |
| 승인 | `getApproved` | TokenID의 Approved Address를 반환한다. 없으면 Zero Address를 반환한다. |
| 승인 | `isApprovedForAll` | 특정 주소가 Owner의 Operator인지 반환한다. |

Interface에 대해 알아둘 조건은 다음과 같다.

- Mint(발행)와 Burn(소각) 함수는 표준에 없다. 구현마다 방식이 다르다. 다만 NFT가 생성될 때는 `_from`이 Zero Address인 `Transfer` Event를, 소각될 때는 `_to`가 Zero Address인 `Transfer` Event를 발생시킨다.
- Contract 생성 중에는 `Transfer` Event 없이 NFT를 생성하고 할당할 수 있다. 따라서 Event만으로 소유 현황을 복원하면 누락이 생길 수 있다.
- 전송 함수와 `approve`는 사양에서 `payable`로 선언되어 있다. EIP-721은 구현이 Interface보다 엄격한 Mutability(상태 변경 가능성)를 가져도 된다고 명시한다. 그래서 `payable` 함수를 Non-Payable로 구현할 수 있다. OpenZeppelin 5.6.1은 이 함수들을 Non-Payable로 구현한다.
- 표에 적은 실패 조건 외에도 구현은 추가 조건에서 실패할 수 있다.

## 4. 동작 원리

이 절은 EIP-721의 요구사항과, 그것을 구현한 OpenZeppelin Contracts 5.6.1의 `ERC721.sol`을 함께 설명한다. OpenZeppelin은 널리 쓰이는 Smart Contract Library(라이브러리)다. 어느 쪽 내용인지는 문장마다 구분해 적는다.

### 4.1 저장 상태

OpenZeppelin의 `ERC721`은 네 개의 Mapping(매핑)으로 소유권과 승인 상태를 저장한다.

```solidity
mapping(uint256 tokenId => address) private _owners;
mapping(address owner => uint256) private _balances;
mapping(uint256 tokenId => address) private _tokenApprovals;
mapping(address owner => mapping(address operator => bool)) private _operatorApprovals;
```

| Mapping | 의미 | 조회 함수 |
| --- | --- | --- |
| `_owners` | TokenID의 Owner | `ownerOf` |
| `_balances` | 주소가 가진 NFT 개수 | `balanceOf` |
| `_tokenApprovals` | TokenID의 Approved Address | `getApproved` |
| `_operatorApprovals` | Owner별 Operator 지정 여부 | `isApprovedForAll` |

`_owners[tokenId]`가 Zero Address이면 그 TokenID는 존재하지 않는 것으로 취급한다.

### 4.2 Mint

Mint는 존재하지 않던 TokenID에 Owner를 처음 지정하는 동작이다. OpenZeppelin의 `_mint(to, tokenId)`는 다음 순서로 동작한다.

1. `to`가 Zero Address이면 `ERC721InvalidReceiver`로 Revert(되돌림)한다.
2. `_balances[to]`를 1 늘리고 `_owners[tokenId]`에 `to`를 기록한다.
3. `Transfer(address(0), to, tokenId)` Event를 발생시킨다.
4. 이전 Owner가 Zero Address가 아니었다면, 즉 이미 존재하는 TokenID였다면 `ERC721InvalidSender`로 Revert한다. Revert되면 2번과 3번의 변경도 모두 취소된다.

`_safeMint`는 `_mint`를 실행한 뒤 4.5의 수신자 확인을 추가로 수행한다.

### 4.3 승인

`approve(to, tokenId)`는 호출자가 TokenID의 Owner이거나 Owner의 Operator일 때만 성공한다. Approved Address는 자신이 받은 권한을 다른 주소에 다시 `approve`할 수 없다. 성공하면 `_tokenApprovals[tokenId]`가 바뀌고 `Approval` Event가 발생한다.

`setApprovalForAll(operator, approved)`는 호출자 자신의 모든 NFT에 대해 `operator`의 권한을 켜거나 끈다. 이후에 호출자가 새로 얻는 NFT에도 적용된다. `ApprovalForAll` Event가 발생한다.

두 승인의 차이는 범위와 유지 기간이다.

| 구분 | `approve` | `setApprovalForAll` |
| --- | --- | --- |
| 범위 | TokenID 1개 | Owner의 모든 NFT |
| 지정 가능한 주소 수 | TokenID당 1개 | 제한 없음 |
| 전송 후 | 초기화된다 | 유지된다 |

### 4.4 전송

EIP-721은 `transferFrom`이 다음 조건 중 하나라도 어기면 실패해야 한다고 정한다.

- 호출자가 Owner, Approved Address, Operator 중 하나여야 한다.
- `_from`이 현재 Owner여야 한다.
- `_to`가 Zero Address가 아니어야 한다.
- `_tokenId`가 유효한 NFT여야 한다.

OpenZeppelin의 `transferFrom(from, to, tokenId)`는 다음 순서로 동작한다.

1. `to`가 Zero Address이면 `ERC721InvalidReceiver`로 Revert한다.
2. 현재 Owner를 읽고, 호출자가 Owner, Operator, Approved Address 중 하나인지 확인한다. 아니면 TokenID가 존재하지 않을 때는 `ERC721NonexistentToken`으로, 존재할 때는 `ERC721InsufficientApproval`로 Revert한다.
3. `_tokenApprovals[tokenId]`를 Zero Address로 초기화한다.
4. 이전 Owner의 `_balances`를 1 줄이고 `to`의 `_balances`를 1 늘린다.
5. `_owners[tokenId]`에 `to`를 기록한다.
6. `Transfer(이전 Owner, to, tokenId)` Event를 발생시킨다.
7. 이전 Owner가 인자 `from`과 다르면 `ERC721IncorrectOwner`로 Revert한다.

3번의 초기화에서는 `Approval` Event가 발생하지 않는다. EIP-721은 `Transfer` Event가 발생하면 해당 NFT의 Approved Address도 초기화된 것으로 본다고 정하고 있다.

2번부터 6번까지는 내부 함수 `_update(to, tokenId, auth)`가 수행한다. Mint와 Burn도 같은 `_update`를 거친다. 이 구조는 7절에서 다시 설명한다.

### 4.5 Safe Transfer

`transferFrom`은 수신자가 NFT를 다룰 수 있는지 확인하지 않는다. NFT를 다시 내보내는 기능이 없는 Contract로 전송하면 그 NFT는 영구히 꺼낼 수 없게 될 수 있다. EIP-721은 `transferFrom`을 쓸 때 수신 가능 여부를 확인할 책임이 호출자에게 있다고 명시한다.

`safeTransferFrom`은 이 확인을 Contract 수준에서 수행한다.

1. `transferFrom`과 같은 방식으로 전송한다.
2. `_to` 주소에 Code가 있는지 확인한다. Code 크기가 0보다 크면 Contract로 판단한다.
3. Contract이면 `_to`의 `onERC721Received`를 호출한다.
4. 반환값이 `0x150b7a02`가 아니면 전체 전송을 실패 처리한다.

`0x150b7a02`는 `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`의 값이다. 수신 Contract는 다음 Interface를 구현해야 한다.

```solidity
interface ERC721TokenReceiver {
    function onERC721Received(
        address _operator,
        address _from,
        uint256 _tokenId,
        bytes _data
    ) external returns (bytes4);
}
```

수신자가 EOA(Externally Owned Account, 개인 키로 제어하는 계정)처럼 Code가 없는 주소이면 3번과 4번은 건너뛴다. `bytes data` 인자가 있는 `safeTransferFrom`은 그 값을 `onERC721Received`에 그대로 전달한다.

`safeTransferFrom`은 수신 Contract가 "받을 수 있다"고 응답했는지만 확인한다. 수신 Contract가 실제로 NFT를 다시 내보낼 수 있는지는 보장하지 않는다.

### 4.6 Burn

Burn은 TokenID의 Owner 기록을 지우는 동작이다. OpenZeppelin의 `_burn(tokenId)`는 Approved Address를 초기화하고, Owner의 `_balances`를 1 줄이고, `_owners[tokenId]`를 Zero Address로 바꾼 뒤 `Transfer(이전 Owner, address(0), tokenId)` Event를 발생시킨다. 존재하지 않는 TokenID이면 `ERC721NonexistentToken`으로 Revert한다.

`_burn`은 호출자의 권한을 확인하지 않는 내부 함수다. 외부에 Burn 기능을 열 때는 권한 확인을 직접 추가하거나 `ERC721Burnable` 확장을 사용한다.

## 5. Metadata 확장

### 5.1 Interface

ERC721Metadata는 NFT의 이름과 설명 정보를 조회하는 선택 확장이다. EIP-721에서 구현 의무가 없다.

```solidity
interface ERC721Metadata /* is ERC721 */ {
    function name() external view returns (string _name);
    function symbol() external view returns (string _symbol);
    function tokenURI(uint256 _tokenId) external view returns (string);
}
```

- `name`: NFT Collection(컬렉션)의 이름이다. 예: `PudgyPenguins`
- `symbol`: NFT Collection의 약칭이다. 예: `PPG`
- `tokenURI`: TokenID에 해당하는 URI(Uniform Resource Identifier, 통합 자원 식별자)를 반환한다. 유효하지 않은 TokenID면 실패한다. 이 문서에서는 이 반환값을 TokenURI라고 부른다.

TokenURI는 Metadata(메타데이터) 파일의 위치를 가리킨다. Metadata는 NFT의 이름, 설명, 이미지 주소 같은 부가 정보다.

### 5.2 On-Chain과 Off-Chain의 경계

ERC-721 NFT의 구성 요소는 저장 위치에 따라 다음과 같이 나뉜다. On-Chain(온체인)은 Blockchain의 Contract 저장 공간 또는 Code에 있다는 뜻이고, Off-Chain(오프체인)은 Blockchain 밖에 있다는 뜻이다.

| 요소 | 위치 | 설명 |
| --- | --- | --- |
| TokenID, Owner, 승인 정보 | On-Chain | 필수 Interface가 다루는 상태 |
| Name, Symbol | On-Chain | Metadata 확장이 반환하는 값 |
| TokenURI 문자열 | On-Chain | Contract가 저장하거나 계산해서 반환하는 값 |
| Metadata 파일 | 일반적으로 Off-Chain | TokenURI가 가리키는 대상 |
| 이미지 등 실제 Content | 일반적으로 Off-Chain | Metadata 파일이 가리키는 대상 |

TokenURI 문자열 자체는 `tokenURI` 함수가 반환하는 On-Chain 값이다. Off-Chain에 있는 것은 그 URI가 가리키는 Metadata 파일이다. 둘을 구분해야 "무엇이 Blockchain에 의해 보장되는가"를 정확히 판단할 수 있다. Blockchain이 보장하는 것은 소유권 기록과 URI 문자열까지다. URI가 가리키는 내용은 저장 위치의 성질을 따른다.

### 5.3 TokenURI를 만드는 두 가지 방식

**Base URI와 TokenID를 이어 붙이는 방식**

TokenID마다 URI 전체를 저장하지 않는다. 공통 접두사인 Base URI 하나만 두고, 조회 시점에 TokenID를 문자열로 바꿔 이어 붙인다.

- Base URI: `https://mycollection.com/metadata/`
- TokenID: `100`
- TokenURI: `https://mycollection.com/metadata/100`

OpenZeppelin 5.6.1의 `ERC721.tokenURI`가 이 방식이다.

```solidity
function tokenURI(uint256 tokenId) public view virtual returns (string memory) {
    _requireOwned(tokenId);

    string memory baseURI = _baseURI();
    return bytes(baseURI).length > 0 ? string.concat(baseURI, tokenId.toString()) : "";
}
```

- `_requireOwned(tokenId)`는 존재하지 않는 TokenID이면 Revert한다.
- `_baseURI()`는 기본값으로 빈 문자열을 반환한다. 상속한 Contract에서 Override(재정의)해 Base URI를 지정한다.
- Base URI가 빈 문자열이면 `tokenURI`도 빈 문자열을 반환한다.
- 구분자를 자동으로 넣지 않는다. Base URI가 `/`로 끝나지 않으면 `.../metadata100`처럼 붙는다.

같은 동작을 직접 구현하면 다음과 같다. `baseTokenURI()`는 Base URI를 반환하도록 따로 정의한 함수라고 가정한다.

```solidity
function tokenURI(uint256 tokenId) public view override returns (string memory) {
    _requireOwned(tokenId);
    return string.concat(baseTokenURI(), Strings.toString(tokenId));
}
```

- `string.concat`은 Solidity 0.8.12 이상에서 사용할 수 있다.
- Solidity 0.5.0 이상에서는 `string` 반환 타입에 Data Location(데이터 위치)을 명시해야 한다. 함수 안에서 만든 문자열을 반환하므로 `memory`를 쓴다.
- 숫자를 문자열로 바꾸는 함수는 OpenZeppelin `Strings` Library의 `toString`이다.

**TokenID별로 URI를 저장하는 방식**

TokenID마다 다른 URI를 Contract 저장 공간에 기록한다. OpenZeppelin의 `ERC721URIStorage` 확장이 이 방식이다. `_setTokenURI(tokenId, uri)`로 값을 저장하고, 저장할 때 ERC-4906의 `MetadataUpdate` Event를 발생시킨다.

`ERC721URIStorage.tokenURI`의 반환 규칙은 다음과 같다.

| Base URI | 저장된 URI | 반환값 |
| --- | --- | --- |
| 없음 | 있음 또는 없음 | 저장된 URI |
| 있음 | 있음 | Base URI + 저장된 URI |
| 있음 | 없음 | Base URI + TokenID |

두 방식의 차이는 비용과 유연성이다. 이어 붙이는 방식은 TokenID마다 저장할 값이 없으므로 Mint 비용이 작지만 URI 형태가 규칙에 묶인다. 저장하는 방식은 TokenID마다 임의의 URI를 줄 수 있지만 문자열 저장 비용이 든다. OpenZeppelin 문서도 `ERC721URIStorage`를 더 유연하지만 더 비싼 방식으로 설명한다.

### 5.4 Metadata 파일

EIP-721은 TokenURI가 "ERC721 Metadata JSON Schema"를 따르는 JSON(JavaScript Object Notation) 파일을 가리킬 수 있다고 정한다. 이 Schema가 정의하는 속성은 세 개다.

| 속성 | 타입 | 의미 |
| --- | --- | --- |
| `name` | string | 자산의 이름 |
| `description` | string | 자산의 설명 |
| `image` | string | 이미지 자원을 가리키는 URI |

실제 NFT Metadata에는 이 세 속성 외의 값이 자주 들어간다. 아래 예시에서 `external_url`과 `attributes`는 EIP-721 Schema에 없는 속성이다. Marketplace가 화면 표시에 사용하는 관례적인 확장이다.

```json
{
  "description": "Friendly OpenSea Creature that enjoys long swims in the ocean.",
  "external_url": "https://openseacreatures.io/3",
  "image": "https://storage.googleapis.com/opensea-prod.appspot.com/puffs/3.png",
  "name": "Dave Starbelly",
  "attributes": [
    { "trait_type": "Mouth", "value": "Surprised" },
    { "trait_type": "Level", "value": 5 }
  ]
}
```

NFT를 보여주는 서비스는 다음 순서로 동작한다.

1. Contract의 `tokenURI(tokenId)`를 호출해 TokenURI를 얻는다.
2. TokenURI가 가리키는 위치에서 Metadata 파일을 가져온다.
3. Metadata 파일을 해석해 이름, 설명, 이미지를 표시한다.

### 5.5 Metadata의 저장 위치와 변경 가능성

Metadata 파일은 일반적으로 IPFS(InterPlanetary File System) 또는 중앙화된 서버에 저장한다. 중앙화된 서버에 둔 파일은 서버 운영자가 내용을 바꿀 수 있고, 서버가 중단되면 조회할 수 없다.

EIP-721은 URI가 변할 수 있다고 명시한다. 사양은 집을 나타내는 NFT의 Metadata가 시간이 지나며 바뀌는 경우를 예로 든다. 반면 TokenID는 바뀌면 안 된다. 그래서 NFT의 정체성은 TokenURI나 Metadata가 아니라 (Contract 주소, TokenID) 쌍에 있다. TokenURI와 Metadata는 그 NFT에 연결된 설명 정보이며 구현에 따라 바뀔 수 있다.

## 6. Enumerable 확장

ERC721Enumerable은 Contract가 가진 NFT 목록을 On-Chain에서 열거할 수 있게 하는 선택 확장이다.

```solidity
interface ERC721Enumerable /* is ERC721 */ {
    function totalSupply() external view returns (uint256);
    function tokenByIndex(uint256 _index) external view returns (uint256);
    function tokenOfOwnerByIndex(address _owner, uint256 _index) external view returns (uint256);
}
```

- `totalSupply`: Contract가 추적하는 유효한 NFT의 개수
- `tokenByIndex`: 전체 NFT 중 `_index`번째 TokenID
- `tokenOfOwnerByIndex`: 특정 Owner의 NFT 중 `_index`번째 TokenID

필수 Interface만으로는 "이 주소가 가진 TokenID 전체"를 조회할 수 없다. `balanceOf`는 개수만 반환하기 때문이다. Enumerable 확장은 이 조회를 가능하게 한다. EIP-721은 열거 순서를 정하지 않는다.

OpenZeppelin의 `ERC721Enumerable`은 전송, Mint, Burn마다 목록을 갱신하는 저장 공간 쓰기가 추가된다. OpenZeppelin 문서는 이 확장에 상당한 Gas(가스) 비용이 든다고 설명한다. Gas는 Ethereum에서 연산과 저장에 매기는 비용 단위다. 기본 `ERC721` Contract는 Metadata 확장은 포함하지만 Enumerable 확장은 포함하지 않는다.

## 7. OpenZeppelin 구현에서 확인할 점

이 절의 내용은 OpenZeppelin Contracts 5.6.1 기준이다. 버전에 따라 달라지는 부분은 따로 표시한다.

### 7.1 `_update`: 소유권 변경의 단일 지점

```solidity
function _update(address to, uint256 tokenId, address auth) internal virtual returns (address)
```

Mint, 전송, Burn은 모두 `_update`를 거친다. 현재 Owner와 `to`의 값에 따라 동작이 결정된다.

| 현재 Owner | `to` | 동작 |
| --- | --- | --- |
| Zero Address | 일반 주소 | Mint |
| 일반 주소 | 일반 주소 | 전송 |
| 일반 주소 | Zero Address | Burn |

- `auth`가 Zero Address가 아니면 `auth`가 Owner이거나 승인을 받았는지 확인한다. `transferFrom`은 호출자 주소를 `auth`로 넘긴다. `_mint`와 `_burn`은 Zero Address를 넘겨 확인을 생략한다.
- 반환값은 변경 전의 Owner다.

모든 소유권 변경이 한 함수를 거치므로, 전송 규칙을 바꾸는 확장은 `_update`를 Override한다. `ERC721Enumerable`과 `ERC721Pausable`이 이 방식으로 구현되어 있다.

버전 조건: OpenZeppelin 4.x의 `ERC721`에는 `_beforeTokenTransfer` Hook(훅)이 있었고, 확장은 이 Hook을 Override했다. 5.6.1의 `ERC721.sol`에는 이 Hook이 없다. 4.x 기준으로 작성된 코드는 5.x에서 그대로 컴파일되지 않는다.

### 7.2 Custom Error

5.6.1의 `ERC721`은 실패 시 Custom Error(사용자 정의 오류)로 Revert한다. 4.9 버전은 `require`와 문자열 메시지를 사용했다.

| Custom Error | 발생 조건 |
| --- | --- |
| `ERC721InvalidOwner(owner)` | `balanceOf`에 Zero Address를 넘김 |
| `ERC721NonexistentToken(tokenId)` | 존재하지 않는 TokenID를 조회, 전송, Burn함 |
| `ERC721IncorrectOwner(sender, tokenId, owner)` | `transferFrom`의 `from`이 실제 Owner와 다름 |
| `ERC721InvalidSender(sender)` | 이미 존재하는 TokenID를 Mint함 |
| `ERC721InvalidReceiver(receiver)` | 수신자가 Zero Address이거나, 수신 Contract가 NFT를 거부함 |
| `ERC721InsufficientApproval(operator, tokenId)` | 호출자에게 전송 권한이 없음 |
| `ERC721InvalidApprover(approver)` | 호출자에게 `approve` 권한이 없음 |
| `ERC721InvalidOperator(operator)` | Operator로 Zero Address를 지정함 |

### 7.3 확장 목록

| 확장 | 기능 |
| --- | --- |
| `ERC721Enumerable` | 전체 NFT와 Owner별 NFT 열거 |
| `ERC721URIStorage` | TokenID별 URI 저장 |
| `ERC721Burnable` | Token 보유자가 자신의 NFT를 Burn |
| `ERC721Pausable` | 전송, Mint, Burn 일시 정지 |
| `ERC721Consecutive` | Contract 생성 시 일괄 Mint (ERC-2309) |
| `ERC721Royalty` | Royalty(로열티) 정보 제공 (ERC-2981). 지급을 강제하지는 않는다. |
| `ERC721Votes` | NFT 1개당 1표의 투표와 위임 |
| `ERC721Wrapper` | 다른 ERC-721 NFT를 예치받아 감싸기 |

NFT를 받는 Contract를 위한 `ERC721Holder`도 제공된다. `onERC721Received`의 기본 구현을 담고 있다.

## 8. 예시

### 8.1 Contract

OpenZeppelin 5.6.1을 상속해 만든 최소 구성의 ERC-721 Contract다. Solidity 0.8.38로 컴파일을 확인했다. 5.6.1의 `ERC721.sol`은 `pragma solidity ^0.8.24`를 요구한다. 다른 OpenZeppelin 버전을 쓸 때는 해당 버전의 `pragma`를 따른다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {ERC721} from "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";

contract MyCollection is ERC721, Ownable {
    uint256 private _nextTokenId;

    constructor(address initialOwner)
        ERC721("MyCollection", "MYC")
        Ownable(initialOwner)
    {}

    function _baseURI() internal pure override returns (string memory) {
        return "https://mycollection.com/metadata/";
    }

    function safeMint(address to) external onlyOwner returns (uint256 tokenId) {
        tokenId = _nextTokenId++;
        _safeMint(to, tokenId);
    }
}
```

- `ERC721("MyCollection", "MYC")`: Name과 Symbol을 지정한다.
- `Ownable`: Contract 관리자를 한 명 두는 OpenZeppelin Contract다. `onlyOwner`가 붙은 함수는 관리자만 호출할 수 있다. 여기서의 관리자는 NFT의 Owner와 다른 개념이다.
- `_baseURI`: Base URI를 지정한다. `tokenURI`는 여기에 TokenID를 이어 붙인다.
- `safeMint`: TokenID를 0부터 1씩 늘려가며 Mint한다. Mint와 Burn은 표준에 없으므로 함수 이름과 권한은 이 Contract가 정한 것이다.

### 8.2 호출 흐름

Deployer(배포자), Alice, Bob, Carol 네 주소가 있고 모두 EOA라고 가정한다. Deployer가 `initialOwner`로 자신을 지정해 Contract를 배포했다. 아래 결과는 8.1의 Contract를 로컬 EVM(Ethereum Virtual Machine, 이더리움 가상 머신) 구현인 `@ethereumjs/vm`에서 Cancun Hardfork(하드포크) 설정으로 실행해 확인한 것이다.

| 순서 | 호출자 | 호출 | 결과 |
| --- | --- | --- | --- |
| 1 | Deployer | `safeMint(Alice)` | TokenID 0 생성. `Transfer(address(0), Alice, 0)` 발생 |
| 2 | 누구나 | `ownerOf(0)` | Alice |
| 3 | 누구나 | `tokenURI(0)` | `https://mycollection.com/metadata/0` |
| 4 | Alice | `approve(Bob, 0)` | `Approval(Alice, Bob, 0)` 발생. `getApproved(0)`은 Bob |
| 5 | Bob | `transferFrom(Alice, Carol, 0)` | `Transfer(Alice, Carol, 0)` 발생. `ownerOf(0)`은 Carol |
| 6 | 누구나 | `getApproved(0)` | Zero Address. 전송 시 초기화됨 |
| 7 | Bob | `transferFrom(Carol, Bob, 0)` | `ERC721InsufficientApproval(Bob, 0)`로 Revert |

5번에서 Bob은 Owner가 아니지만 Approved Address이므로 전송할 수 있다. 전송과 함께 승인이 초기화되므로 7번에서 Bob은 같은 NFT를 다시 옮길 수 없다. 4번에서 Alice가 `approve` 대신 `setApprovalForAll(Bob, true)`를 호출했더라도 7번은 실패한다. Operator 권한은 Alice의 NFT에 대한 것이고, 전송 후의 Owner는 Carol이기 때문이다.
