## 1. 배경과 필요성

### 1.1 디지털 데이터는 소유를 증명하기 어렵다

디지털 파일은 복사본과 원본이 비트 단위로 같고, 복사하는 데 드는 비용도 거의 없다. 그래서 파일만 보고는 어느 것이 원본인지, 누가 그 파일을 가졌는지 증명할 수 없다.

Blockchain(블록체인)은 네트워크에 참여하는 여러 Node(노드)가 같은 장부를 나눠 보관하고, 참여자들이 합의한 기록만 장부에 덧붙이는 시스템이다. 한번 확정된 기록은 위변조하기 어렵다. 따라서 "누가 무엇을 가졌는가"를 기록하는 장부로 쓸 수 있다.

### 1.2 기존 토큰은 개별 자산을 구분하지 못한다

블록체인 위에서 자산을 나타내는 단위를 Token(토큰)이라고 한다. 초기 토큰 표준은 주소마다 잔액이 얼마인지만 기록했다. 대표적인 예가 Ethereum(이더리움)의 ERC-20이다. ERC(Ethereum Request for Comments)는 Ethereum에서 토큰 같은 애플리케이션 수준의 표준을 정하는 문서이고, EIP(Ethereum Improvement Proposal, 이더리움 개선 제안)의 한 분류다.

Ethereum에서 ERC-20 토큰은 Smart Contract(스마트 컨트랙트)가 관리한다. 스마트 컨트랙트는 블록체인에 배포되어 정해진 규칙대로 실행되는 프로그램이다. 이 글에서는 이후 줄여서 컨트랙트라고 쓴다.

잔액만 기록하는 방식으로는 앨리스가 가진 그림 한 점과 밥이 가진 다른 그림 한 점을 구분할 수 없다. 장부에는 둘 다 "1개"로만 남기 때문이다. [EIP-721](https://eips.ethereum.org/EIPS/eip-721) 문서도 같은 이유를 든다. NFT(Non-Fungible Token, 대체 불가능 토큰)는 자산 하나하나가 서로 다르지만 ERC-20 토큰은 단위끼리 모두 같으므로, ERC-20으로는 NFT를 추적할 수 없다는 것이다.

### 1.3 등장 과정

- 2012년: Bitcoin(비트코인)의 특정 코인에 표시를 붙여 주식이나 증서 같은 다른 자산을 나타내는 [Colored Coins](https://en.wikipedia.org/wiki/Colored_Coins)(컬러드 코인) 개념이 나왔다. 3월에 Yoni Assia가 처음 제안했고, 12월에 Meni Rosenfeld가 백서를 발표했다.
- 2017년 6월: Larva Labs가 Ethereum에서 10,000개의 픽셀 캐릭터인 [CryptoPunks](https://en.wikipedia.org/wiki/CryptoPunks)를 공개했다. NFT 표준이 없던 때라 ERC-20 코드를 고쳐 만든 자체 컨트랙트를 썼다([David Gerard](https://davidgerard.co.uk/blockchain/2022/06/16/the-early-history-of-nfts-part-4-game-sprites-on-the-blockchain-cryptopunks/)).
- 2017년 9월: Axiom Zen의 Dieter Shirley가 GitHub [이슈 #721](https://github.com/ethereum/EIPs/issues/721)로 NFT 표준을 제안했다.
- 2017년 11월: 같은 회사가 만든 게임 [CryptoKitties](https://en.wikipedia.org/wiki/CryptoKitties)가 출시됐다. 12월에는 이용자가 몰려 Ethereum 네트워크가 크게 느려졌다.
- 2018년 1월: 제안이 [EIP-721](https://eips.ethereum.org/EIPS/eip-721) 문서로 정리됐다. 현재 상태는 Final(확정)이다.

## 2. 핵심 개념

### 2.1 Fungible과 Non-Fungible

Fungible(대체 가능)은 같은 종류의 단위끼리 바꿔도 가치와 의미가 달라지지 않는다는 뜻이다. 내 1만 원권과 친구의 1만 원권을 바꿔도 달라지는 것이 없다.

Non-Fungible(대체 불가능)은 단위마다 고유한 성질이 있어 서로 바꿀 수 없다는 뜻이다. 같은 공연의 티켓이라도 A열 1번 좌석과 R열 30번 좌석은 서로 다른 티켓이다.

정리하면 NFT는 토큰마다 고유한 식별자를 붙여, 블록체인 장부에서 토큰 하나하나를 구분하고 각각의 소유자를 기록하는 토큰이다.

| 구분 | 대체 가능 토큰 | NFT |
|---|---|---|
| 장부가 기록하는 것 | 주소별 잔액 | 토큰별 소유자 |
| 단위끼리 교환 | 가능 | 불가능 |
| 쪼개기 | 소수 단위로 나눌 수 있게 만드는 경우가 많음 | 나눌 수 없음 |
| 예 | 화폐, 포인트 | 미술품, 좌석 지정 티켓, 도메인 이름 |

[EIP-721](https://eips.ethereum.org/EIPS/eip-721) 문서는 NFT가 나타낼 수 있는 대상으로 집이나 미술품 같은 물리 자산, 고양이 그림이나 수집 카드 같은 가상 수집품, 대출이나 부채 같은 "음의 가치" 자산을 예로 든다. 같은 문서의 요약은 NFT를 Deed(증서)라고도 부른다.

### 2.2 NFT를 이루는 요소

체인마다 구현은 다르지만, 이 글에서는 NFT를 다음 네 요소로 나눠 본다.

- 식별자: 체인 안에서 토큰 하나만을 가리키는 고유한 값이다.
- 소유자: 토큰을 가진 계정의 주소다.
- Metadata(메타데이터): 데이터를 설명하는 데이터다. NFT에서는 이름, 설명, 이미지 위치처럼 토큰이 무엇을 나타내는지 적은 정보를 말한다.
- 전송 규칙: 누가 어떤 조건에서 소유권을 옮길 수 있는지 정한 규칙이다.

### 2.3 토큰과 콘텐츠는 분리되어 있다

NFT는 그림 파일 자체가 아니다. 블록체인에 기록되는 것은 대개 식별자, 소유자, 그리고 메타데이터가 있는 곳을 가리키는 URI다. URI(Uniform Resource Identifier, 통합 자원 식별자)는 `https://...`나 `ipfs://...`처럼 자원의 위치나 이름을 나타내는 문자열이다. 웹 주소인 URL(Uniform Resource Locator)도 URI의 한 종류다.

블록체인 안을 On-chain(온체인), 밖을 Off-chain(오프체인)이라고 부른다. 이미지나 영상 같은 실제 콘텐츠는 대부분 오프체인에 저장된다. 블록체인에 큰 데이터를 저장하는 비용이 높기 때문이다.

따라서 NFT를 가진다는 것은 "장부에 내 주소가 그 토큰의 소유자로 기록되어 있다"는 뜻이다. 콘텐츠가 계속 보관되는지, 콘텐츠에 대한 권리가 누구에게 있는지는 별개의 문제다. 이 내용은 5장에서 다룬다.

## 3. 동작 원리

### 3.1 생명주기: 발행, 전송, 소각

사용자가 쓰는 계정 주소는 공개키를 바탕으로 정해진다. 장부를 바꾸는 요청인 Transaction(트랜잭션)은 그 공개키와 짝이 되는 개인키로 서명해야 처리된다. 그래서 어떤 주소의 토큰을 움직이거나 그 주소의 주인임을 증명하려면, 그 주소의 개인키로 서명해야 한다.

NFT의 장부 기록은 세 가지 동작으로 바뀐다.

1. Mint(발행): 새 식별자를 만들고 첫 소유자를 기록한다. 누가 발행할 수 있는지는 구현마다 다르다.
2. Transfer(전송): 소유자 기록을 새 주소로 바꾼다. 일반적으로 소유자 본인이나 소유자가 권한을 위임한 주소만 전송할 수 있다.
3. Burn(소각): 토큰을 장부에서 없앤다. 이후에는 그 토큰의 소유자가 없다.

### 3.2 메타데이터 조회 흐름

Wallet(지갑)은 개인키를 보관하고 트랜잭션에 서명하는 프로그램이고, Marketplace(마켓플레이스)는 NFT를 사고파는 서비스다. 지갑이나 마켓플레이스는 다음 순서로 NFT를 화면에 보여준다.

1. 체인에서 토큰의 메타데이터 URI를 읽는다.
2. URI가 가리키는 JSON(JavaScript Object Notation) 파일을 가져온다.
3. JSON의 `image` 필드에 적힌 URI로 이미지를 가져와 표시한다.

```
토큰 (온체인)
  └─► 메타데이터 URI (온체인)
        └─► metadata.json (오프체인)
              └─► image 필드의 URI가 가리키는 이미지 파일 (오프체인)
```

ERC-721은 메타데이터 JSON의 기본 필드로 `name`, `description`, `image` 세 가지를 정의한다([EIP-721](https://eips.ethereum.org/EIPS/eip-721)). 마켓플레이스들은 속성 목록(`attributes`)처럼 표준에 없는 필드를 추가로 쓰기도 한다.

### 3.3 콘텐츠 저장 위치

메타데이터와 이미지를 어디에 두느냐에 따라 NFT가 가리키는 콘텐츠가 얼마나 오래 남는지, 나중에 바뀔 수 있는지가 달라진다.

IPFS(InterPlanetary File System)는 파일을 저장 위치가 아니라 내용의 해시값으로 찾는 분산 파일 시스템이다. 해시값은 데이터를 고정 길이 값으로 바꾼 결과로, 데이터가 조금만 달라져도 완전히 다른 값이 나온다. IPFS에서 이 해시 기반 식별자를 CID(Content Identifier, 콘텐츠 식별자)라고 한다. 다만 IPFS에 올렸다고 영구 보관되지는 않는다. 데이터를 계속 꺼낼 수 있으려면 최소 한 노드가 그 데이터를 Pinning(피닝)해야 한다. 피닝은 노드가 특정 데이터를 지우지 않고 계속 보관하도록 고정하는 것이다([IPFS 문서](https://docs.ipfs.tech/concepts/lifecycle)).

[Arweave](https://docs.ar.io/build/guides/storing-nfts/)는 한 번 비용을 내면 데이터를 영구 보관하는 것을 목표로 설계된 저장 네트워크다. 낸 비용 일부를 기금으로 적립해 장기 저장 비용을 대는 구조다.

| 저장 위치 | 콘텐츠를 찾는 기준 | 계속 남으려면 | 내용 변경 |
|---|---|---|---|
| 온체인 | 체인 안의 데이터(컨트랙트나 계정 저장소) | 체인이 유지되면 남음 | 컨트랙트나 프로그램 설계에 따름 |
| IPFS | 내용 해시(CID) | 최소 한 노드가 피닝해야 함 | 같은 CID로는 불가능 |
| Arweave | 트랜잭션 ID | 한 번 낸 비용으로 영구 보관을 목표로 함 | 불가능 |
| 일반 웹 서버 | 위치(URL) | 운영자가 서버를 계속 운영해야 함 | 운영자가 언제든 가능 |

## 4. 예시

### 4.1 공연 티켓 NFT 하나 따라가기

공연 주최자가 좌석마다 NFT 티켓을 발행한다고 가정한다. 컬렉션 이름은 "Concert 2026"이고, 토큰 #42는 A열 1번 좌석이다. 메타데이터는 IPFS에 저장했다고 가정한다.

```json
{
  "name": "Concert 2026 Ticket #42",
  "description": "A열 1번 좌석",
  "image": "ipfs://<이미지 폴더 CID>/42.png"
}
```

장부에서 토큰 #42의 기록은 다음처럼 바뀐다.

| 단계 | 동작 | 토큰 #42의 소유자 |
|---|---|---|
| 1 | 발행: 주최자가 #42를 발행해 앨리스에게 준다 | 앨리스 |
| 2 | 전송: 앨리스가 밥에게 티켓을 판다. 앨리스가 자기 개인키로 전송에 서명한다 | 밥 |
| 3 | 입장 확인: 공연장이 장부에서 #42의 소유자가 밥의 주소인지 확인하고, 밥에게 그 주소의 개인키로 서명하게 한다 | 밥 (변화 없음) |
| 4 | 소각: 입장한 밥이 티켓을 소각한다 | 없음 |

이 예시에서 다음을 확인할 수 있다.

- #42와 #43은 같은 컬렉션이지만 좌석이 다르므로 서로 바꿀 수 없다. 이것이 대체 불가능의 의미다.
- 2단계에서 바뀌는 것은 장부의 소유자 기록뿐이다. 메타데이터 JSON과 이미지는 그대로다.
- 3단계에서 공연장은 티켓 이미지를 보지 않는다. 장부의 소유자 기록과 서명만으로 소유를 확인한다. 이미지는 누구나 복사할 수 있지만, 서명은 개인키를 가진 사람만 만들 수 있다.

### 4.2 실제 활용 사례

- 디지털 아트와 수집품: 1.3의 CryptoPunks와 CryptoKitties가 여기에 속한다.
- 도메인 이름: ENS(Ethereum Name Service, 이더리움 네임 서비스)에서 `.eth` 바로 아래 이름(예: `ens.eth`)은 ENSv1 기준으로 ERC-721 토큰이다. Name Wrapper 컨트랙트로 감싸면 같은 이름을 ERC-1155 토큰으로 다룬다([ENS 문서](https://docs.ens.domains/namewrapper)). ERC-1155는 한 컨트랙트에서 여러 종류의 토큰을 함께 관리하는 Ethereum 표준이다.
- 유동성 포지션: Uniswap은 Ethereum에서 시작한 탈중앙화 거래소다. Uniswap v3에서 LP(Liquidity Provider, 유동성 공급자)는 유동성을 공급할 가격 범위를 직접 정한다. 범위가 포지션마다 다르므로 포지션끼리 대체할 수 없다. 그래서 `NonfungiblePositionManager` 컨트랙트가 각 포지션을 ERC-721 토큰으로 발행한다([Uniswap 문서](https://docs.uniswap.org/contracts/v3/reference/periphery/NonfungiblePositionManager)).
- 양도할 수 없는 토큰: SBT(Soulbound Token, 양도 불가 토큰)는 한 주소에 묶여 전송할 수 없는 NFT다. [ERC-5192](https://eips.ethereum.org/EIPS/eip-5192)는 ERC-721 토큰이 잠겨 있는지 알려주는 `locked(tokenId)` 함수와 잠금 상태가 바뀔 때 내는 이벤트만 정한 최소 표준이다.

## 5. 한계와 흔한 오해

### 5.1 NFT 소유와 저작권은 별개다

NFT 표준은 장부에 소유자를 기록하는 방법만 정한다. 콘텐츠의 저작권이 넘어가는지, 구매자가 콘텐츠를 어디까지 쓸 수 있는지는 토큰이 아니라 발행자가 정한 라이선스나 계약으로 정해진다.

### 5.2 콘텐츠가 사라지거나 바뀔 수 있다

- 메타데이터나 이미지가 일반 웹 서버에 있으면, 서버가 내려가는 순간 콘텐츠를 볼 수 없다. 토큰과 소유 기록은 체인에 그대로 남는다.
- IPFS에 둔 데이터도 피닝하는 노드가 하나도 없으면 사라질 수 있다.
- 체인에 기록된 메타데이터 URI를 나중에 바꿀 수 있는지는 컨트랙트나 프로그램 설계에 따른다. 바꿀 수 있게 만들었다면 발행자가 토큰이 다른 콘텐츠를 가리키게 할 수 있다.

### 5.3 로열티 강제 여부는 표준마다 다르다

Royalty(로열티)는 NFT가 다시 팔릴 때 원 창작자에게 돌아가는 수수료다.

- Ethereum의 [ERC-2981](https://eips.ethereum.org/EIPS/eip-2981)은 `royaltyInfo(tokenId, salePrice)`로 로열티를 받을 주소와 금액을 알려주는 방법만 정하고, 지급은 강제하지 않는다([OpenZeppelin 문서](https://docs.openzeppelin.com/contracts/api/token/common)). 실제로 지급할지는 마켓플레이스가 정한다.
- Solana(솔라나)에서 NFT 표준 프로그램을 제공하는 Metaplex는 2023년 Programmable NFT 표준을 내놓아, 전송 규칙으로 로열티를 강제할 수 있게 했다. 2024년에 공개한 Core도 로열티 강제를 지원한다([Metaplex Core 문서](https://www.metaplex.com/docs/core)).

## 6. 체인별 구현

NFT의 개념은 같지만, 식별자와 소유 기록을 어디에 어떻게 두는지는 체인마다 다르다.

| 구분 | Ethereum | Solana (Metaplex) |
|---|---|---|
| 주요 표준 | ERC-721, ERC-1155 | Token Metadata, Core |
| 식별자 | (컨트랙트 주소, tokenId) 쌍 | Token Metadata: Mint 계정 주소<br>Core: Asset 계정 주소 |
| 소유 기록 위치 | 컨트랙트 저장소 | Token Metadata: 토큰 계정<br>Core: Asset 계정 |

- Ethereum: ERC-721에서 각 NFT는 컨트랙트 안에서 `uint256` 숫자인 tokenId로 구분되고, (컨트랙트 주소, tokenId) 쌍이 체인 전체에서 고유한 식별자가 된다([EIP-721](https://eips.ethereum.org/EIPS/eip-721)). ERC-1155에서는 토큰 ID마다 메타데이터와 발행량을 따로 정할 수 있다([EIP-1155](https://eips.ethereum.org/EIPS/eip-1155)).
- Solana: Mint 계정은 토큰 한 종류의 공급량과 소수점 자리수를 기록하는 계정이다. Token Metadata 표준에서 NFT는 공급량이 1이고 소수점 자리수가 0인 Mint 계정이며, 여기에 메타데이터 계정과 Master Edition 계정이 붙는다. Master Edition 계정은 이 Mint가 NFT임을 증명하고 복제본 발행을 관리하는 계정이다([Metaplex 문서](https://developers.metaplex.com/token-metadata)). 소유자는 토큰 계정에 기록된다. 토큰 계정은 어떤 주소가 특정 Mint의 토큰을 몇 개 가졌는지 기록하는 계정이다. Core는 소유자와 메타데이터 URI를 Asset 계정 하나에 담는다([Metaplex Core 문서](https://www.metaplex.com/docs/core)).

Ethereum 구현은 [ERC-721]({% post_url Blockchain/2026-11-11-ERC-721 %}) 글에서, Solana 구현은 Solana NFT 글에서 자세히 다룬다.
