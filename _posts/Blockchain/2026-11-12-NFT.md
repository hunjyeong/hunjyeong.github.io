## 1. What is an NFT?

### 1.1 Blockchain과 Token

Blockchain은 네트워크에 참여하는 여러 Node가 같은 Ledger(장부)를 나눠 보관하고, 참여자들이 합의한 기록만 Ledger에 덧붙이는 시스템이다. 한번 확정된 기록은 위변조하기 어렵다. 대표적인 Blockchain으로 Bitcoin, Ethereum, Solana가 있다.

Blockchain Ledger에서 자산을 가진 주체는 Account(계정)이고, Account는 Address(주소)로 구분된다. 사용자가 쓰는 Account의 Address는 Public Key(공개키)를 바탕으로 정해진다. Ledger를 바꾸는 요청인 Transaction은 그 Public Key와 짝이 되는 Private Key(개인키)로 서명해야 처리된다. 그래서 어떤 Address의 자산을 움직이거나 그 Address의 주인임을 증명하려면, 그 Address의 Private Key로 서명해야 한다.

Blockchain 위에서 자산을 나타내는 단위를 Token(토큰)이라고 한다. 이 글에서 다루는 Ethereum의 Token은 Smart Contract가 관리한다. Smart Contract는 Blockchain에 배포되어 정해진 규칙대로 실행되는 프로그램이다. 이 글에서는 이후 줄여서 Contract라고 쓴다. Solana에서는 Contract에 해당하는 프로그램을 Program이라고 부른다.

### 1.2 Fungible과 Non-Fungible

Fungible(대체 가능)은 같은 종류의 단위끼리 바꿔도 가치와 의미가 달라지지 않는다는 뜻이다. 내 1만 원권과 친구의 1만 원권을 바꿔도 달라지는 것이 없다.

Non-Fungible(대체 불가능)은 단위마다 고유한 성질이 있어 서로 바꿀 수 없다는 뜻이다. 같은 공연의 티켓이라도 A열 1번 좌석과 R열 30번 좌석은 서로 다른 티켓이다.

### 1.3 NFT의 정의

NFT(Non-Fungible Token, 대체 불가능 토큰)는 Token마다 고유한 식별자를 붙여, Blockchain Ledger에서 Token 하나하나를 구분하고 각각의 Owner(소유자)를 기록하는 Token이다. Owner는 Token을 가진 Account의 Address다. 반대로 단위끼리 구분하지 않는 Token은 Fungible Token(대체 가능 토큰)이라고 부른다.

| 구분 | Fungible Token | NFT |
|---|---|---|
| Ledger가 기록하는 것 | Address별 Balance(잔액) | Token별 Owner (구현에 따라 수량 1인 Balance로 기록, 3.7) |
| 단위끼리 교환 | 가능 | 불가능 |
| 쪼개기 | 소수 단위로 나눌 수 있게 만드는 경우가 많음 | 나눌 수 없음 |
| 예 | 화폐, 포인트 | 미술품, 좌석 지정 티켓, 도메인 이름 |

Ethereum의 대표적인 NFT 표준은 ERC-721이다. ERC(Ethereum Request for Comments)는 Ethereum에서 Token 같은 애플리케이션 수준의 표준을 정하는 문서이고, EIP(Ethereum Improvement Proposal, 이더리움 개선 제안) 중 Standards Track(표준 트랙)의 한 분류다([EIP-1](https://eips.ethereum.org/EIPS/eip-1)). ERC-721의 사양 문서인 [EIP-721](https://eips.ethereum.org/EIPS/eip-721)은 NFT가 나타낼 수 있는 대상으로 집이나 미술품 같은 물리 자산, 고양이 그림이나 수집 카드 같은 가상 Collectible(수집품), 대출이나 부담(Burden), 그 밖의 책임 같은 "음의 가치" 자산을 예로 든다. 같은 문서의 Simple Summary(요약)는 NFT를 Deed(증서)라고도 부른다.

### 1.4 NFT가 증명하는 것

NFT가 증명하는 것은 "Ledger에 어떤 Address가 그 Token의 Owner로 기록되어 있다"는 사실이다. NFT는 그림 파일 자체가 아니며, 그림 같은 콘텐츠는 대부분 Blockchain 밖에 따로 저장된다(3.2). 따라서 다음 두 가지는 NFT를 가진 것과 별개의 문제다.

- 콘텐츠가 계속 보관되는지: 콘텐츠를 어디에 저장했는지에 따라 다르다(3.5).

- 콘텐츠에 대한 권리: NFT 표준은 Ledger에 Owner를 기록하는 방법만 정한다. 콘텐츠의 저작권이 넘어가는지, 구매자가 콘텐츠를 어디까지 쓸 수 있는지는 Token이 아니라 NFT를 만든 주체가 정한 라이선스나 계약으로 정해진다.

## 2. NFT는 왜 나왔는가

### 2.1 디지털 데이터는 소유를 증명하기 어렵다

디지털 파일은 복사본과 원본이 비트 단위로 같고, 복사하는 데 드는 비용도 거의 없다. 그래서 파일만 보고는 어느 것이 원본인지, 누가 그 파일을 가졌는지 증명할 수 없다.

Blockchain은 파일 대신 Ledger의 기록으로 소유를 나타낼 수 있다. 한번 확정된 기록은 위변조하기 어렵고, 기록을 바꾸려면 해당 Address의 Private Key로 서명해야 하기 때문이다(1.1). 따라서 "누가 무엇을 가졌는가"를 기록하는 Ledger로 쓸 수 있다.

### 2.2 Balance만 기록하는 Token은 개별 자산을 구분하지 못한다

Blockchain에 자산의 소유를 기록하려면 자산 하나하나를 구분할 수 있어야 한다. 그런데 초기 Token 표준은 Address마다 Balance가 얼마인지만 기록했다. 대표적인 예가 Ethereum의 [ERC-20](https://eips.ethereum.org/EIPS/eip-20)이다.

Balance만 기록하는 방식으로는 Alice가 가진 그림 한 점과 Bob이 가진 다른 그림 한 점을 구분할 수 없다. Ledger에는 둘 다 "1개"로만 남기 때문이다. [EIP-721](https://eips.ethereum.org/EIPS/eip-721) 문서의 Motivation(동기) 절도 같은 이유를 든다. NFT는 자산 하나하나가 서로 다르지만 ERC-20 Token은 단위끼리 모두 같으므로, ERC-20으로는 NFT를 추적할 수 없다는 것이다. 그래서 Token마다 식별자를 붙여 따로 기록하는 표준이 필요해졌다.

### 2.3 등장 과정

- 2012년: Bitcoin의 특정 코인에 표시를 붙여 주식이나 증서 같은 다른 자산을 나타내는 [Colored Coins](https://en.wikipedia.org/wiki/Colored_Coins)(컬러드 코인) 개념이 나왔다. 3월에 Yoni Assia가 처음 제안했고, 12월에 Meni Rosenfeld가 백서를 발표했다.

- 2017년 6월: Larva Labs가 Ethereum에서 10,000개의 픽셀 캐릭터인 [CryptoPunks](https://en.wikipedia.org/wiki/CryptoPunks)를 공개했다. NFT 표준이 없던 때라 ERC-20 코드를 고쳐 만든 자체 Contract를 썼다([David Gerard](https://davidgerard.co.uk/blockchain/2022/06/16/the-early-history-of-nfts-part-4-game-sprites-on-the-blockchain-cryptopunks/)).

- 2017년 9월: Axiom Zen의 Dieter Shirley가 GitHub [Issue #721](https://github.com/ethereum/EIPs/issues/721)로 NFT 표준을 제안했다.

- 2017년 11월: 같은 회사가 만든 게임 [CryptoKitties](https://en.wikipedia.org/wiki/CryptoKitties)가 출시됐다. 12월에는 이용자가 몰려 Ethereum 네트워크가 크게 느려졌다.

- 2018년 1월: 제안이 [EIP-721](https://eips.ethereum.org/EIPS/eip-721) 문서로 정리됐다. 현재 상태는 Final(확정)이다.

## 3. NFT는 어떤 구조인가

### 3.1 구성 요소

Blockchain마다 구현은 다르지만, 이 글에서는 NFT를 다음 네 요소로 나눠 본다.

- 식별자: 하나의 Blockchain 안에서 Token 하나만을 가리키는 고유한 값이다.

- Owner: Token을 가진 Account의 Address다.

- Metadata: 데이터를 설명하는 데이터다. NFT에서는 이름, 설명, 이미지 위치처럼 Token이 무엇을 나타내는지 적은 정보를 말한다.

- Transfer 규칙: 누가 어떤 조건에서 소유권을 옮길 수 있는지 정한 규칙이다.

3.2부터 3.6까지는 이 요소들이 어디에 기록되고 어떻게 쓰이는지 설명하고, 3.7에서 Blockchain별 구현 차이를 정리한다.

### 3.2 Token과 콘텐츠의 분리

Blockchain에 기록되는 것은 대개 식별자, Owner, 그리고 Metadata가 있는 곳을 가리키는 URI다. URI(Uniform Resource Identifier, 통합 자원 식별자)는 `https://...`나 `ipfs://...`처럼 자원의 위치나 이름을 나타내는 문자열이다. 웹 주소인 URL(Uniform Resource Locator)도 URI의 한 종류다.

Blockchain 안을 On-Chain(온체인), 밖을 Off-Chain(오프체인)이라고 부른다. 이미지나 영상 같은 실제 콘텐츠는 대부분 Off-Chain에 저장된다. Blockchain에 큰 데이터를 저장하는 비용이 높기 때문이다.

### 3.3 Lifecycle(생명주기): Mint, Transfer, Burn

NFT의 Ledger 기록은 세 가지 동작으로 바뀐다. 각 동작은 Transaction으로 요청한다(1.1).

1. Mint(발행): 새 식별자를 만들고 첫 Owner를 기록한다. 누가 Mint할 수 있는지는 구현마다 다르다.

2. Transfer(전송): Owner 기록을 새 Address로 바꾼다. 일반적으로 Owner 본인이나 Owner가 Approve(권한 위임)한 Address만 Transfer할 수 있다.

3. Burn(소각): Token을 Ledger에서 없앤다. 이후에는 그 Token의 Owner가 없다.

### 3.4 Metadata 조회 흐름

Wallet(지갑)은 Private Key를 보관하고 Transaction에 서명하는 프로그램이고, Marketplace(마켓플레이스)는 NFT를 사고파는 서비스다. Wallet이나 Marketplace는 다음 순서로 NFT를 화면에 보여준다.

1. Blockchain에서 Token의 Metadata URI를 읽는다. ERC-721에서는 선택 사항인 Metadata Extension(확장)의 `tokenURI(tokenId)` 함수가 이 값을 돌려준다.
2. URI가 가리키는 JSON(JavaScript Object Notation) 파일을 가져온다.
3. JSON의 `image` 필드에 적힌 URI로 이미지를 가져와 표시한다.

```
Token (On-Chain)
  └─► Metadata URI (On-Chain)
        └─► metadata.json (Off-Chain)
              └─► image 필드의 URI가 가리키는 이미지 파일 (Off-Chain)
```

ERC-721은 같은 Metadata Extension에서 Metadata JSON의 기본 필드로 `name`, `description`, `image` 세 가지를 정의한다([EIP-721](https://eips.ethereum.org/EIPS/eip-721)). Marketplace들은 속성 목록(`attributes`)처럼 표준에 없는 필드를 추가로 쓰기도 한다([OpenSea 문서](https://docs.opensea.io/docs/media-and-traits)).

### 3.5 콘텐츠 저장 위치

Metadata와 이미지를 어디에 두느냐에 따라 NFT가 가리키는 콘텐츠가 얼마나 오래 남는지, 나중에 바뀔 수 있는지가 달라진다.

IPFS(InterPlanetary File System)는 파일을 저장 위치가 아니라 내용의 Hash(해시)로 찾는 분산 파일 시스템이다. Hash는 데이터를 고정 길이 값으로 바꾼 결과로, 데이터가 조금만 달라져도 완전히 다른 값이 나온다. IPFS에서 이 Hash 기반 식별자를 CID(Content Identifier, 콘텐츠 식별자)라고 한다. 다만 IPFS에 올렸다고 영구 보관되지는 않는다. IPFS Node는 저장 공간을 비우려고 필요 없다고 판단한 데이터를 지운다. 데이터를 계속 꺼낼 수 있으려면 최소 한 Node가 그 데이터를 Pinning(피닝)해야 한다. Pinning은 Node가 특정 데이터를 지우지 않고 계속 보관하도록 고정하는 것이다([IPFS 문서](https://docs.ipfs.tech/concepts/persistence/)).

Arweave는 한 번 비용을 내면 데이터를 영구 보관하는 것을 목표로 설계된 저장 네트워크다([ar.io 문서](https://docs.ar.io/build/guides/storing-nfts/)). 업로드 비용의 일부는 그 Transaction을 Block에 넣은 채굴자에게 바로 지급되고, 나머지는 Endowment(기금)에 적립된다. Endowment는 데이터 복제 저장을 증명하는 채굴자들에게 오랜 기간에 걸쳐 지급된다([Arweave 문서](https://docs.arweave.org/developers/development/overview)).

| 저장 위치 | 콘텐츠를 찾는 기준 | 계속 남으려면 | 내용 변경 |
|---|---|---|---|
| On-Chain | Blockchain 안의 데이터(Contract나 Account의 Storage(저장소)) | Blockchain이 유지되면 남음 | Contract나 Program 설계에 따름 |
| IPFS | 내용의 Hash(CID) | 최소 한 Node가 Pinning해야 함 | 같은 CID로는 불가능 |
| Arweave | Transaction ID | 한 번 낸 비용으로 영구 보관을 목표로 함 | 불가능 |
| 일반 웹 서버 | 위치(URL) | 운영자가 서버를 계속 운영해야 함 | 운영자가 언제든 가능 |

이 차이 때문에 다음 상황이 생길 수 있다.

- Metadata나 이미지가 일반 웹 서버에 있으면, 서버가 내려가는 순간 콘텐츠를 볼 수 없다. Token과 소유 기록은 Blockchain에 그대로 남는다.
- IPFS에 둔 데이터도 Pinning하는 Node가 하나도 없으면 사라질 수 있다.
- Blockchain에 기록된 Metadata URI를 나중에 바꿀 수 있는지는 Contract나 Program 설계에 따른다. 바꿀 수 있게 만들었다면 URI를 바꿀 권한을 가진 주체가 Token이 다른 콘텐츠를 가리키게 할 수 있다.

### 3.6 Transfer 규칙과 Royalty

Royalty(로열티)는 NFT가 다시 팔릴 때 원 창작자에게 돌아가는 수수료다. Transfer 규칙으로 Royalty 지급을 강제할 수 있는지는 표준마다 다르다.

- Ethereum의 [ERC-2981](https://eips.ethereum.org/EIPS/eip-2981)은 `royaltyInfo(tokenId, salePrice)`로 Royalty를 받을 Address와 금액을 알려주는 방법만 정하고, 지급은 강제하지 않는다([OpenZeppelin 문서](https://docs.openzeppelin.com/contracts/api/token/common)). 실제로 지급할지는 Marketplace가 정한다.

- Solana에서 NFT 표준 Program을 제공하는 Metaplex는 Programmable NFT 표준에서 Transfer 규칙으로 Royalty를 강제할 수 있게 했다([Metaplex Programmable NFT 문서](https://www.metaplex.com/docs/smart-contracts/token-metadata/pnfts)). 2024년에 공개한 Core도 Royalty 강제를 지원한다([Metaplex Core 문서](https://www.metaplex.com/docs/smart-contracts/core)).

### 3.7 Blockchain별 구현

NFT의 개념은 같지만, 식별자와 소유 기록을 어디에 어떻게 두는지는 Blockchain마다 다르다. 표의 TokenID(Token Identifier)는 ERC-721이 Contract 안의 NFT마다 붙이는 번호다.

| 구분 | Ethereum | Solana (Metaplex) |
|---|---|---|
| 주요 표준 | ERC-721, ERC-1155 | Token Metadata, Core |
| 식별자 | (Contract Address, TokenID) 쌍 | Token Metadata: Mint Account Address<br>Core: Asset Account Address |
| 소유 기록 위치 | Contract Storage | Token Metadata: Token Account<br>Core: Asset Account |

- Ethereum
  - ERC-721에서 각 NFT는 Contract 안에서 `uint256` 숫자인 TokenID로 구분되고, (Contract Address, TokenID) 쌍이 하나의 Ethereum Blockchain 안에서 고유한 식별자가 된다([EIP-721](https://eips.ethereum.org/EIPS/eip-721)). 
  - ERC-721은 Token별 Owner를 기록하고 `ownerOf(tokenId)`로 조회한다. 
  - [ERC-1155](https://eips.ethereum.org/EIPS/eip-1155)에서는 Contract 하나가 Fungible Token과 NFT를 포함한 여러 종류의 Token을 ID로 구분해 함께 관리한다. 
  - ERC-1155는 Owner를 직접 기록하지 않고 ID와 Address별 Balance를 기록하므로, NFT의 Owner는 그 ID의 Balance가 1인 Address다.

- Solana
  - Solana는 데이터를 Account 단위로 저장한다. 
  - Mint Account는 Token 한 종류의 Supply(공급량)와 Decimals(소수점 자릿수)를 기록하는 Account다. 
  - Token Metadata 표준에서 NFT는 Supply가 1이고 Decimals가 0인 Mint Account이며, 여기에 Metadata Account와 Master Edition Account가 붙는다. Master Edition Account는 이 Mint Account가 NFT임을 증명하고 Print Edition(복제본) Mint를 관리하는 Account다([Metaplex 문서](https://www.metaplex.com/docs/smart-contracts/token-metadata)). 
  - Owner는 Token Account에 기록된다. Token Account는 어떤 Address가 특정 Mint Account의 Token을 몇 개 가졌는지 기록하는 Account이고, NFT의 Owner는 이 Balance가 1인 Address다. 
  - Core는 Owner와 Metadata URI를 Asset Account 하나에 담는다([Metaplex Core 문서](https://www.metaplex.com/docs/smart-contracts/core)). 
  - Metaplex는 현재 Token Metadata를 Legacy(구형) Program으로 분류하고, 새 프로젝트에는 Core를 권장한다([Metaplex 문서](https://www.metaplex.com/docs/smart-contracts/token-metadata)).

## 4. 예시

### 4.1 공연 티켓 NFT 하나 따라가기

공연 주최자가 좌석마다 NFT 티켓을 Mint한다고 가정한다. NFT 묶음인 Collection(컬렉션)의 이름은 "Concert 2026"이고, Token #42는 A열 1번 좌석이다. Metadata는 IPFS에 저장했다고 가정한다.

```json
{
  "name": "Concert 2026 Ticket #42",
  "description": "A열 1번 좌석",
  "image": "ipfs://<이미지 폴더 CID>/42.png"
}
```

Ledger에서 Token #42의 기록은 다음처럼 바뀐다.

| 단계 | 동작 | Token #42의 Owner |
|---|---|---|
| 1 | Mint: 주최자가 #42를 Mint해 Alice에게 준다 | Alice |
| 2 | Transfer: Alice가 Bob에게 티켓을 판다. Alice가 자기 Private Key로 Transfer Transaction에 서명한다 | Bob |
| 3 | 입장 확인: 공연장이 Ledger에서 #42의 Owner가 Bob의 Address인지 확인하고, Bob에게 그 Address의 Private Key로 서명하게 한다 | Bob (변화 없음) |
| 4 | Burn: 입장한 Bob이 티켓을 Burn한다 | 없음 |

이 예시에서 다음을 확인할 수 있다.

- #42와 #43은 같은 Collection이지만 좌석이 다르므로 서로 바꿀 수 없다. 이것이 Non-Fungible의 의미다(1.2).
- 2단계에서 바뀌는 것은 Ledger의 Owner 기록뿐이다. Metadata JSON과 이미지는 그대로다(3.2).
- 3단계에서 공연장은 티켓 이미지를 보지 않는다. Ledger의 Owner 기록과 서명만으로 소유를 확인한다. 이미지는 누구나 복사할 수 있지만, 서명은 Private Key를 가진 사람만 만들 수 있다(1.1, 1.4).

### 4.2 실제 활용 사례

- 디지털 아트와 Collectible: 2.3의 CryptoPunks와 CryptoKitties가 여기에 속한다.

- 도메인 이름: ENS(Ethereum Name Service, 이더리움 네임 서비스)의 이름도 NFT로 다룬다. ENSv1(ENS의 첫 번째 버전)에서 `.eth` 바로 아래 이름(예: `ens.eth`)은 ERC-721 Token이고, Name Wrapper Contract로 감싸면 같은 이름을 ERC-1155 Token으로 다룬다([ENS 문서](https://docs.ens.domains/wrapper/overview/)). 2026년 10월 Ethereum Mainnet에 출시된 ENSv2에서는 이름마다 Owner가 정확히 하나인 ERC-1155 변형 Token(ERC1155Singleton)을 쓰고, Role(권한)이 바뀌거나 이름이 재등록되면 Token ID가 바뀐다([ENS 문서](https://docs.ens.domains/ensv2/erc1155-singleton)). 기존 ENSv1 이름은 그대로 작동하며, ENSv2로 업그레이드할 수 있다. ERC-1155는 3.7에서 설명한, 한 Contract에서 여러 종류의 Token을 함께 관리하는 Ethereum 표준이다.

- Liquidity Position(유동성 포지션): Uniswap은 Ethereum에서 시작한 DEX(Decentralized Exchange, 탈중앙화 거래소)다. Uniswap v3에서 LP(Liquidity Provider, 유동성 공급자)는 Liquidity를 공급할 Price Range(가격 범위)를 직접 정한다. Price Range가 Position마다 다르므로 Position끼리 대체할 수 없다. 그래서 `NonfungiblePositionManager` Contract가 각 Position을 ERC-721 Token으로 Mint한다([Uniswap 문서](https://developers.uniswap.org/docs/get-started/concepts/how-uniswap-works)).

- 양도할 수 없는 Token: SBT(Soulbound Token, 양도 불가 토큰)는 한 Address에 묶여 Transfer할 수 없는 NFT다. [ERC-5192](https://eips.ethereum.org/EIPS/eip-5192)는 ERC-721 Token이 잠겨 있는지 알려주는 `locked(tokenId)` 함수와 잠금 상태가 바뀔 때 내는 Event(이벤트)만 정한 최소 표준이다. Event는 Contract가 실행 중에 남기는 기록이다.
